# 6.2 · Rc, RefCell y árboles

Con `Box`, cada nodo tiene un solo dueño. [6.1 Box y listas enlazadas]{.ref}
cerró con dos estructuras que ese supuesto no deja armar: dos listas que
comparten la misma cola, y un hijo que apunta de vuelta a su padre. A las dos
les falta lo mismo, un valor con varios dueños. Detrás viene un segundo
problema: modificar ese valor después de haberlo compartido.

El primero choca con la regla 2 del ownership: solo un dueño a la vez. El
segundo choca con la regla 1 del borrow checker: una `&mut` o varias `&`. Las
herramientas de este capítulo no agregan reglas ni suspenden esas dos. Cada
una toma una regla de la sección 3 y cambia dónde o cuándo se cumple.

## Definiciones y reglas

Conteo de referencias
:   *(reference counting)*: llevar, junto al valor, la cuenta de cuántos
    dueños tiene. El valor se libera cuando la cuenta llega a cero.

`Rc<T>`
:   un puntero a un valor del heap que lleva esa cuenta. Cada `Rc` que apunta
    al valor es uno de sus dueños.

Mutabilidad interior
:   *(interior mutability)*: modificar un valor a través de una referencia
    `&`. El permiso no lo da el binding: lo da el tipo que envuelve al valor.

`RefCell<T>`
:   una celda que guarda un valor y una bandera con sus préstamos vivos.
    Entrega préstamos con `borrow()` y `borrow_mut()`.

*Guard*
:   un valor que sostiene un permiso y lo devuelve al destruirse, en su
    `Drop`. Con el *guard* de un `match` ([2.4 Patrones]{.ref}) comparte el
    nombre y nada más.

`Weak<T>`
:   un puntero al valor de un `Rc` que no cuenta como dueño.

::: {.reglas titulo="Qué cambia cada herramienta"}
1. `Rc<T>` reparte la propiedad entre varios dueños. El valor se libera
   cuando el contador de dueños llega a cero.
2. `RefCell<T>` comprueba «una `&mut` o varias `&`» al ejecutar. Violarla
   es un panic, no un error de compilación.
3. Un préstamo de `RefCell` dura lo que vive su *guard*, no hasta su último
   uso.
:::

## De un vistazo

| Tipo | Dueños | ¿Se puede mutar? | Los préstamos se comprueban |
| :--- | :--- | :--- | :--- |
| `Box<T>` | uno | sí, con `mut` o `&mut` | al compilar |
| `Rc<T>` | varios | no | al compilar |
| `RefCell<T>` | uno | sí, también desde `&` | al ejecutar |
| `Rc<RefCell<T>>` | varios | sí | al ejecutar |

Criterio: se cuentan los dueños y se pregunta si hay que mutar después de
compartir. Un dueño pide `Box<T>`, o ninguna indirección. Varios dueños que
solo leen piden `Rc<T>`. Varios dueños que además modifican piden
`Rc<RefCell<T>>`.

## Las reglas, una por una

### Dos padres y una hoja

El caso mínimo: dos nodos como los de 6.1 quieren el mismo hijo.

```rust,compile_fail
struct Nodo { valor: i32, hijo: Option<Box<Nodo>> }

fn main() {
    let hoja = Box::new(Nodo { valor: 3, hijo: None });
    let padre_a = Nodo {
        valor: 1,
        hijo: Some(hoja),
    };
    let padre_b = Nodo {
        valor: 2,
        hijo: Some(hoja),
    };
}
```

```salida
error[E0382]: use of moved value: `hoja`
 4 |     let hoja = Box::new(Nodo { valor: 3, hijo: None });
   |         ---- move occurs because `hoja` has type
   |              `Box<Nodo>`, which does not implement the
   |              `Copy` trait
 7 |         hijo: Some(hoja),
   |                    ---- value moved here
11 |         hijo: Some(hoja),
   |                    ^^^^ value used here after move
```

Es la regla 2 de [3.2 Ownership]{.ref}: `padre_a` se quedó con la hoja.
Clonar, como propone la nota del compilador, daría dos hojas distintas.

Prestar tampoco alcanza. Un campo `hijo: Option<&Nodo>` no es dueño de nada:
la hoja necesita un dueño aparte que viva más que los dos padres, y la regla
2 de [3.3 Borrowing]{.ref} obliga a demostrarlo al compilar. Una función que
arma el árbol y lo devuelve ya no puede, y recibe *E0515: cannot return
value referencing local variable `hoja`*.

### [Regla 1:]{.prefijo} `Rc<T>` reparte la propiedad

`Rc<T>` (*reference counted*) guarda el valor en el heap, como `Box`, junto
con un contador de dueños. `Rc::new` lo deja en 1, `Rc::clone` suma 1 sin
copiar el valor, y cada `Rc` que se destruye resta 1. `Rc::strong_count` lo
lee. Con `Rc` en el campo del nodo, el árbol de dos padres compila:

```rust
use std::rc::Rc;

struct Nodo { valor: i32, hijo: Option<Rc<Nodo>> }

fn main() {
    let hoja = Rc::new(Nodo { valor: 3, hijo: None });
    let padre_a = Nodo {
        valor: 1,
        hijo: Some(Rc::clone(&hoja)),   // no copia: suma 1
    };
    {
        let padre_b = Nodo {
            valor: 2,
            hijo: Some(Rc::clone(&hoja)),
        };
        println!("{}", Rc::strong_count(&hoja));  // 3
    }   // padre_b sale de scope: resta 1
    println!("{}", Rc::strong_count(&hoja));      // 2
}
```

La hoja llega a tener tres dueños: la variable `hoja` y los dos padres. Al
cerrar el bloque se destruye `padre_b` con su campo `hijo`, y el contador
baja a 2. El contador es del valor, no de una variable: se lee igual desde
cualquiera de sus dueños.

::: {.figura src="figuras/6.2-conteo.html"}
:::

Ningún dueño es el principal. Con un `drop(hoja)` al final desaparece la
variable que creó el nodo, y el nodo sigue vivo en `padre_a.hijo` con el
contador en 1. Los campos se leen a través del puntero, `hoja.valor`, porque
`Rc<T>` implementa `Deref` ([4.5 Operadores y conversiones]{.ref}).

`hoja.clone()` hace lo mismo que `Rc::clone(&hoja)`. Por convención se
escribe la segunda forma. En [3.2 Ownership]{.ref}, `.clone()` marcaba el
punto donde se paga una copia completa; `Rc::clone` deja ver que aquí solo
se incrementa un entero.

Las reglas 1 y 3 del ownership siguen intactas. El valor tiene dueño en todo
momento, y se libera cuando sale de scope el último. Lo que cambió es la
regla 2, y la decisión de liberar ya no se toma al compilar: la toma el
contador al ejecutar.

### `Rc` comparte, pero no deja mutar

Con la hoja compartida, el paso siguiente es cambiarle el valor desde uno
de sus dueños:

```rust,compile_fail
use std::rc::Rc;

struct Nodo { valor: i32 }

fn main() {
    let hoja = Rc::new(Nodo { valor: 3 });
    let otro = Rc::clone(&hoja);

    otro.valor = 4;
    println!("{}", hoja.valor);
}
```

```salida
error[E0594]: cannot assign to data in an `Rc`
 9 |     otro.valor = 4;
   |     ^^^^^^^^^^^^^^ cannot assign
   = help: trait `DerefMut` is required to modify through a
           dereference, but it is not implemented for
           `Rc<Nodo>`
```

`Rc` atendió la regla 2 del ownership. La regla 1 del borrow checker sigue en
pie: mutar pide acceso exclusivo, y con dos dueños vivos nadie lo tiene. Por
eso `Rc<T>` implementa `Deref` y no `DerefMut`: solo entrega `&T`. Declarar
`let mut otro` no cambia nada, porque ese `mut` permitiría reapuntar a
`otro`, no modificar el nodo.

### [Regla 2:]{.prefijo} `RefCell<T>` comprueba al ejecutar

El borrow checker rechaza todo programa que no puede demostrar correcto, y
algunos de los que rechaza lo son. En el árbol de dos padres, nada impide
modificar la hoja mientras nadie más la lea. El compilador no puede saber si
alguien la lee en ese momento. El programa sí, al correr.

`RefCell<T>` hace esa comprobación en ejecución. Guarda el valor junto a una
bandera que registra los préstamos vivos. `borrow()` pide un préstamo
compartido y `borrow_mut()` uno exclusivo. Los dos reciben `&self`: la celda
no necesita un binding `mut`.

```rust
use std::cell::RefCell;

fn main() {
    let celda = RefCell::new(5);     // sin `mut`
    *celda.borrow_mut() += 1;        // préstamo exclusivo
    println!("{}", celda.borrow());  // préstamo compartido: 6
}
```

Cada llamada aplica la regla 1 de [3.3 Borrowing]{.ref}, sin cambios:

::: {.figura src="figuras/6.2-refcell.html"}
:::

El tercer caso es el programa que en 3.3 no compilaba con *E0502*. Aquí
compila, y la bandera lo detiene al correr:

```rust,should_panic
use std::cell::RefCell;

fn main() {
    let celda = RefCell::new(5);

    let lector = celda.borrow();
    let mut escritor = celda.borrow_mut();
    *escritor += 1;
    println!("{lector}");
}
```

```salida
thread 'main' panicked at src/main.rs:7:30:
RefCell already borrowed
```

El panic ocurre en la línea 7, al pedir el segundo préstamo, y antes de que
se escriba nada. En el orden contrario, con el escritor primero, el mensaje
es *RefCell already mutably borrowed*. Dos `borrow_mut()` vivos fallan igual
que un lector y un escritor.

El programa no llega a un estado inválido: se detiene antes. La garantía de
3.3 se conserva, y lo que se pierde es el aviso temprano. Un error que el
compilador habría señalado ahora aparece solo si la ejecución pasa por esa
línea. De ahí el criterio: `RefCell` se usa cuando el borrow checker no puede
demostrar algo que sí es correcto, y no para callar un error de préstamo.

### `Rc<RefCell<T>>`: compartir y mutar

Las dos herramientas se combinan. `Rc` por fuera reparte la propiedad, y
`RefCell` por dentro permite modificar lo compartido:

```rust
use std::cell::RefCell;
use std::rc::Rc;

struct Nodo { valor: i32 }

fn main() {
    let hoja = Rc::new(RefCell::new(Nodo { valor: 3 }));
    let otro = Rc::clone(&hoja);          // segundo dueño

    otro.borrow_mut().valor = 4;          // muta desde otro
    println!("{}", hoja.borrow().valor);  // 4: el mismo nodo
}
```

Es el programa que falló con *E0594*, con el nodo dentro de una celda. Ninguna
regla se rompió. La regla 2 del ownership la atiende `Rc` con su contador. La
regla 1 del borrow checker la atiende `RefCell`, que la verifica en cada
`borrow`. La regla es la misma; mover la comprobación es lo que cuesta.

El orden de los dos tipos importa. `Rc<RefCell<T>>` es un valor mutable con
varios dueños. `RefCell<Rc<T>>` sería una celda con un solo dueño que permite
cambiar a qué valor compartido apunta.

### Lo que cuesta mover la comprobación

`RefCell<T>` no es un envoltorio transparente. Comprobar al ejecutar deja
huella en cuatro frentes:

| Frente | Con referencias | Con `RefCell<T>` |
| :--- | :--- | :--- |
| Memoria | nada | la bandera: 8 bytes |
| Ejecución | nada | leer, comparar y escribir la bandera en cada préstamo |
| Tipo de falla | error de compilación | panic, o `Err` con `try_borrow_mut` |
| Hilos | según el tipo | no se comparte entre hilos |

La memoria se mide con `size_of` ([3.1 Stack y heap]{.ref}). En una máquina
de 64 bits, `size_of::<i32>()` da 4 y `size_of::<RefCell<i32>>()` da 16: 8
bytes de bandera, 4 del `i32` y 4 de relleno para alinear. `Rc<T>` también
cobra: guarda sus contadores en el heap, junto al valor, y cada `Rc::clone`
y cada destrucción escriben en ellos.

Las abstracciones de la sección 4 se resolvían al compilar y no dejaban
rastro en el programa final. Estas dos son la excepción: su trabajo ocurre al
ejecutar, y se paga ahí.

El cuarto frente es un límite, no un costo. Ni el contador de `Rc` ni la
bandera de `RefCell` están protegidos contra dos hilos que los toquen a la
vez, y el compilador rechaza el programa que intenta enviarlos a otro hilo
con *E0277: `Rc<RefCell<i32>>` cannot be sent between threads safely*
([8.2 Send y Sync]{.ref}). Sus equivalentes entre hilos son `Arc` y `Mutex`
([8.3 Estado compartido]{.ref}).

### [Regla 3:]{.prefijo} el préstamo dura lo que vive el guard

`borrow()` no devuelve un `&T`. Devuelve un `Ref<T>`, y `borrow_mut()` un
`RefMut<T>`. Los dos son guards: se usan como referencias, gracias a `Deref`,
y al destruirse avisan a la celda que el préstamo terminó. Ese aviso está en
su `Drop` ([4.4 Traits de la stdlib]{.ref}). La bandera no sabe nada de usos:
solo cuenta guards vivos.

```rust,should_panic
use std::cell::RefCell;

fn main() {
    let celda = RefCell::new(vec![1, 2, 3]);

    let lector = celda.borrow();   // el guard queda ligado
    celda.borrow_mut().push(4);    // panic: lector vive
    println!("{lector:?}");
}
```

```salida
thread 'main' panicked at src/main.rs:7:11:
RefCell already borrowed
```

Con referencias, un préstamo termina en su último uso
([3.6 Lifetimes]{.ref}). La intuición dice que borrar el `println!` final
arregla el programa, porque `lector` ya no se usaría después de la línea 6.
No lo arregla: el programa compila y hace panic en la misma línea. Un guard
es un valor con destructor, y un valor con destructor vive hasta que cierra
su scope, se use o no. El último uso decide cuánto dura una referencia, no
cuándo corre un `Drop`.

Hay tres formas de terminar el préstamo antes, y las tres consisten en
destruir el guard:

```rust
use std::cell::RefCell;

fn main() {
    let celda = RefCell::new(vec![1, 2, 3]);

    let n = celda.borrow().len();  // temporal: muere en `;`
    celda.borrow_mut().push(4);
    {
        let lector = celda.borrow();
        println!("{n} {lector:?}");  // 3 [1, 2, 3, 4]
    }                              // muere con el bloque
    celda.borrow_mut().push(5);

    let lector = celda.borrow();
    drop(lector);                  // muere aquí
    celda.borrow_mut().push(6);
}
```

La primera es la más común y explica por qué
`celda.borrow_mut().push(4)` no estorba a la línea siguiente. Un guard que
no se liga a una variable es un temporal, y se destruye al terminar el
enunciado que lo creó.

### Árboles: dos hijos y tres recorridos

Un árbol binario es la lista de 6.1 con dos enlaces por nodo. Recorrerlo es
visitar cada nodo una vez. Los tres recorridos clásicos hacen las mismas
tres cosas en cada nodo: visitarlo, bajar a la izquierda y bajar a la
derecha. Solo cambia el orden.

::: {.figura src="figuras/6.2-recorridos.html"}
:::

Las tres funciones reciben `&Nodo`. Recorrer es leer, y para leer basta un
préstamo compartido que baja de padre a hijo. El árbol del ejemplo es de
búsqueda: los menores a la izquierda y los mayores a la derecha. Por eso el
inorden entrega los valores ordenados.

En el programa no hay `Rc` ni `RefCell`. Cada nodo tiene un solo padre, así
que tiene un solo dueño, y `Box` lo expresa completo.

```rust
struct Nodo {
    valor: i32,
    izq: Option<Box<Nodo>>,
    der: Option<Box<Nodo>>,
}

fn hoja(valor: i32) -> Option<Box<Nodo>> {
    Some(Box::new(Nodo { valor, izq: None, der: None }))
}

fn preorden(n: &Nodo) {
    print!("{} ", n.valor);
    if let Some(i) = &n.izq { preorden(i); }
    if let Some(d) = &n.der { preorden(d); }
}

fn inorden(n: &Nodo) {
    if let Some(i) = &n.izq { inorden(i); }
    print!("{} ", n.valor);
    if let Some(d) = &n.der { inorden(d); }
}

fn postorden(n: &Nodo) {
    if let Some(i) = &n.izq { postorden(i); }
    if let Some(d) = &n.der { postorden(d); }
    print!("{} ", n.valor);
}

fn main() {
    let dos = Nodo { valor: 2, izq: hoja(1), der: hoja(3) };
    let izq = Some(Box::new(dos));
    let raiz = Nodo { valor: 4, izq, der: hoja(6) };
    preorden(&raiz);    // 4 2 1 3 6
    inorden(&raiz);     // 1 2 3 4 6
    postorden(&raiz);   // 1 3 2 6 4
}
```

### Qué indirección pide cada algoritmo

La mayoría de los algoritmos sobre árboles binarios tampoco los necesitan. La
indirección la decide la forma de la estructura, no la operación:

| Caso | Alcanza con |
| :--- | :--- |
| buscar, insertar y borrar en un árbol de búsqueda | `Option<Box<Nodo>>`, mutando por `&mut` desde la raíz |
| los tres recorridos | `&Nodo`: son de solo lectura |
| rotaciones de un árbol balanceado | `Box` y `take()`: una rotación mueve subárboles |
| un nodo que apunta a su padre | `Rc<RefCell<T>>` hacia abajo, `Weak<T>` hacia arriba |
| un nodo con varios padres | `Rc<T>`, o `Rc<RefCell<T>>` si además se muta |

Las tres primeras filas son árboles en sentido estricto: un dueño por nodo,
y toda modificación entra por la raíz con un `&mut` que baja. Las dos últimas
dejaron de serlo. Un nodo con varios padres es un grafo, y un enlace al padre
cierra un ciclo.

### `Weak<T>`: el enlace al padre

Si el padre es dueño del hijo y el hijo es dueño del padre, cada uno sostiene
el contador del otro y ninguno llega a cero. `Weak<T>` rompe el ciclo: apunta
al mismo valor que un `Rc`, pero no cuenta como dueño y no impide liberarlo.

Se obtiene con `Rc::downgrade`. Como el valor pudo liberarse ya, un `Weak` no
se usa directo. `.upgrade()` devuelve un `Option<Rc<T>>`: `Some` con un dueño
nuevo si el valor sigue vivo, y `None` si ya no existe. No hay forma de
saltarse esa pregunta.

```rust
use std::rc::Rc;

fn main() {
    let fuerte = Rc::new(5);
    let debil = Rc::downgrade(&fuerte);         // Weak<i32>

    println!("{}", Rc::strong_count(&fuerte));  // 1
    println!("{:?}", debil.upgrade());          // Some(5)
    drop(fuerte);                               // llega a 0
    println!("{:?}", debil.upgrade());          // None
}
```

En el árbol, cada nodo guarda a sus hijos como dueño y a su padre como
`Weak`: los campos son `hijos: Vec<Rc<RefCell<Nodo>>>` y
`padre: Weak<RefCell<Nodo>>`. Soltar la raíz libera el árbol completo,
porque ningún enlace hacia arriba sostiene un contador.

:::

## Aplicación

Dos jugadores pertenecen al mismo equipo, y el nombre del equipo no debe
copiarse. Nadie lo modifica después, así que basta `Rc<String>` (ejercicio del
curso *Aprende Rust*). Destruir a `luis` destruye su campo `equipo`, y el
contador baja de 3 a 2. El texto sigue en el heap mientras quede un dueño.

```rust
use std::rc::Rc;

struct Jugador {
    nombre: String,
    equipo: Rc<String>,
}

fn main() {
    let equipo = Rc::new(String::from("Los Cangrejos"));

    let ana = Jugador {
        nombre: String::from("Ana"),
        equipo: Rc::clone(&equipo),
    };
    let luis = Jugador {
        nombre: String::from("Luis"),
        equipo: Rc::clone(&equipo),
    };

    println!("{} juega en {}", ana.nombre, ana.equipo);
    println!("{} juega en {}", luis.nombre, luis.equipo);
    println!("Dueños: {}", Rc::strong_count(&equipo));    // 3

    drop(luis);
    println!("Sin Luis: {}", Rc::strong_count(&equipo));  // 2
}
```

Una lista de tareas que dos personas llenan sí cambia después de compartirse,
y pide `Rc<RefCell<...>>` (ejercicio del curso *Aprende Rust*). El tipo
completo es largo y se repetiría en cada firma. Un alias de tipo, `type`, le
pone nombre sin crear un tipo nuevo: `Tareas` y `Rc<RefCell<Vec<String>>>`
son intercambiables.

```rust
use std::cell::RefCell;
use std::rc::Rc;

type Tareas = Rc<RefCell<Vec<String>>>;

fn nueva_lista() -> Tareas {
    Rc::new(RefCell::new(Vec::new()))
}

fn anotar(tareas: &Tareas, tarea: &str) {
    tareas.borrow_mut().push(tarea.to_string());
}

fn cuantas(tareas: &Tareas) -> usize {
    tareas.borrow().len()
}

fn main() {
    let lista = nueva_lista();
    let ana = Rc::clone(&lista);
    let luis = Rc::clone(&lista);

    anotar(&ana, "Comprar pan");
    anotar(&luis, "Pasear a Ferris");
    anotar(&ana, "Estudiar Rust");

    println!("Tareas: {}", cuantas(&lista));   // Tareas: 3
    println!("{:?}", lista.borrow());          // las tres
}
```

`anotar` recibe `&Tareas`, una referencia compartida, y aun así agrega una
tarea: es la mutabilidad interior. Cada función pide su préstamo y lo suelta
en el mismo enunciado, con un guard temporal. Ningún guard sale de la función
que lo pidió, y con esa disciplina el panic de `RefCell` no tiene ocasión
de ocurrir.

## A fondo

**Un ciclo de `Rc` nunca llega a cero.** Es el panel izquierdo de la figura
anterior. Dos nodos que se sostienen entre sí con `Rc` quedan con el
contador en 1 cuando sus variables salen de scope. Ningún `drop` corre, y
los dos siguen en el heap hasta que el proceso termina. No es un agujero en
las reglas: es la consecuencia de contar dueños al ejecutar. El programa
sigue siendo seguro en el sentido de [3.2 Ownership]{.ref}, porque una fuga
no produce accesos inválidos.

**Lo que ninguna herramienta cambia.** La regla 1 del ownership: `Rc` no
quita el dueño, lo reparte. La regla 3 del ownership: el valor se libera
cuando sale de scope su último dueño. La regla 2 del borrow checker: toda
referencia es válida mientras viva, y eso se sigue verificando al compilar.
Un guard no puede sobrevivir a su celda, y un `&T` sacado de un guard no
puede sobrevivir al guard. Solo la regla 1 del borrow checker cambia de
momento, y solo dentro de un `RefCell`.

**El guard de un temporal puede vivir más que una línea.** Un temporal se
destruye al terminar su enunciado, y un `match`, un `if let` o un `for`
completos son un solo enunciado. El guard creado en la cabecera sigue vivo
dentro del cuerpo, y un `borrow_mut()` en una rama o en una vuelta hace
panic.

| Escrito | El guard muere |
| :--- | :--- |
| `let g = c.borrow();` | al cerrar el scope de `g`, o en `drop(g)` |
| `let n = c.borrow().len();` | en el `;` |
| `if c.borrow().len() == 3 { ... }` | antes de entrar al bloque |
| `match c.borrow().len() { ... }` | al cerrar el `match` |
| `if let Some(x) = c.borrow().first() { ... }` | al cerrar el bloque |
| `for x in c.borrow().iter() { ... }` | al terminar el `for` |

En los tres últimos casos el arreglo es el mismo: sacar el dato a una
variable con `let` en un enunciado propio, y ramificar o iterar después
sobre la variable.

**`try_borrow_mut` devuelve un `Result`.** Cuando un préstamo ocupado es una
situación esperada, `try_borrow()` y `try_borrow_mut()` hacen la misma
consulta sin panic ([5.2 Result]{.ref}). Con un lector vivo,
`celda.try_borrow_mut()` devuelve un `Err` que se imprime como
`RefCell already borrowed`, y el programa sigue corriendo.

**Un `Rc` mide lo que un puntero.** `size_of::<Rc<Nodo>>()` da 8 bytes en una
máquina de 64 bits, igual que `Box<Nodo>` y que un `Weak`. Los contadores
están en el heap, junto al valor, y son dos: `Rc::strong_count` lee el de
dueños y `Rc::weak_count` el de `Weak`. El valor se destruye cuando el
primero llega a cero. El bloque del heap se devuelve cuando además no queda
ningún `Weak`, y por eso `upgrade()` siempre tiene un contador que
consultar.
