# 6.3 · Despacho dinámico

Un programa de dibujo guarda sus figuras en una lista: círculos y
rectángulos, en el orden en que se crearon. Los dos tipos implementan el
trait `Figura` de [4.1 Traits]{.ref}, y una función genérica acepta
cualquiera de ellos. La lista no. Un `Vec<T>` guarda un solo tipo, y
[4.2 Generics]{.ref} mostró que cada uso fija `T` a uno.

Los genéricos resuelven el trait al compilar: una copia del código por
tipo. Este capítulo presenta la otra mitad. `dyn Trait` conserva una sola
copia y decide en ejecución, con una tabla, qué método llamar. Con eso la
lista se puede escribir.

## Definiciones y reglas

Despacho
:   la decisión de qué función ejecuta una llamada como `f.area()`.

Despacho estático
:   el compilador conoce el tipo concreto y deja escrita una llamada
    directa. Es lo que hacen los genéricos e `impl Trait`.

Despacho dinámico
:   la función se busca al ejecutar, en una tabla que acompaña al valor.

*Trait object*
:   un valor visto como `dyn Trait`: de él solo se sabe que implementa el
    trait. El tipo concreto no aparece en el código que lo usa.

Tabla de métodos
:   *(vtable)*: una tabla por cada par de tipo y trait, con la dirección
    de cada método. El compilador la genera y queda en el ejecutable.

::: {.reglas titulo="Las tres reglas de dyn"}
1. `dyn Trait` no tiene tamaño conocido al compilar. Siempre se usa detrás
   de un puntero.
2. Ese puntero es doble: una dirección al dato y otra a la tabla de
   métodos del tipo concreto. Cada llamada pasa por la tabla.
3. Un trait sirve como `dyn` solo si todos sus métodos se pueden llamar
   con el puntero y la tabla.
:::

## De un vistazo

| | Genérico o `impl Trait` | `dyn Trait` |
| :--- | :--- | :--- |
| Se resuelve | al compilar | al ejecutar |
| Mecanismo | monomorfización | tabla de métodos |
| Costo en ejecución | ninguno | una indirección por llamada |
| Costo en compilación | una copia del código por tipo | una sola copia |
| Tipos por colección | uno solo | varios distintos |
| Traits que admite | todos | los compatibles con `dyn` |

Criterio: genérico por default. `dyn` cuando el conjunto de tipos se
decide en ejecución, y el caso típico es una colección con tipos
mezclados.

## Las reglas, una por una

### Un `Vec<T>` guarda un solo tipo

El primer intento pone las dos figuras en el mismo `vec!`:

```rust,compile_fail
trait Figura { fn area(&self) -> f64; }
struct Circulo { radio: f64 }
struct Rectangulo { ancho: f64, alto: f64 }

impl Figura for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
}
impl Figura for Rectangulo {
    fn area(&self) -> f64 { self.ancho * self.alto }
}

fn main() {
    let figuras = vec![
        Circulo { radio: 1.0 },
        Rectangulo { ancho: 2.0, alto: 3.0 },
    ];
}
```

```salida
error[E0308]: mismatched types
15 |         Rectangulo { ancho: 2.0, alto: 3.0 },
   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |         expected `Circulo`, found `Rectangulo`
```

Con el primer elemento el compilador fija el tipo: `Vec<Circulo>`. El
segundo ya no encaja. Que los dos implementen `Figura` no cambia nada,
porque `T` es un tipo concreto y no un trait. Hay además una razón física.
Un `Vec` guarda sus elementos uno tras otro, todos del mismo tamaño
([5.3 Vec]{.ref}). Un `Circulo` mide 8 bytes y un `Rectangulo`, 16.

### El mismo trait, resuelto de dos maneras

El programa siguiente usa `Figura` por las dos vías. La función `imprimir`
es genérica, como en [4.1 Traits]{.ref}. La lista es un
`Vec<Box<dyn Figura>>`:

```rust
trait Figura { fn area(&self) -> f64; }
struct Circulo { radio: f64 }
struct Rectangulo { ancho: f64, alto: f64 }

impl Figura for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
}
impl Figura for Rectangulo {
    fn area(&self) -> f64 { self.ancho * self.alto }
}

fn imprimir(f: &impl Figura) { println!("{:.2}", f.area()); }

fn main() {
    let c = Circulo { radio: 1.0 };
    imprimir(&c);   // 3.14, llamada directa a Circulo::area
    let figuras: Vec<Box<dyn Figura>> = vec![
        Box::new(Circulo { radio: 1.0 }),
        Box::new(Rectangulo { ancho: 2.0, alto: 3.0 }),
    ];
    for f in &figuras {
        println!("{:.2}", f.area());   // 3.14 y 6.00
    }
}
```

En `imprimir(&c)` el despacho es estático. El compilador genera una
versión de `imprimir` para `Circulo`, y en ella la llamada a `area` va
directo a la función de ese tipo.

En el `for`, el despacho es dinámico. El cuerpo del ciclo existe una sola
vez y `f.area()` ejecuta una función distinta en cada vuelta. Todos los
elementos tienen el mismo tipo, `Box<dyn Figura>`, y eso satisface al
`Vec`. La anotación es necesaria: sin ella el compilador infiere
`Vec<Box<Circulo>>` y repite el `E0308`. Con ella, cada `Box<Circulo>` se
convierte en `Box<dyn Figura>` al entrar a la lista.

El trait se declaró una sola vez, y cada punto de uso elige cómo
resolverlo.

### [Regla 1:]{.prefijo} `dyn Trait` vive detrás de un puntero

Una variable de tipo `dyn Figura`, sin el `Box`, no compila:

```rust,compile_fail
trait Figura { fn area(&self) -> f64; }
struct Circulo { radio: f64 }
impl Figura for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
}
fn main() {
    let f: dyn Figura = Circulo { radio: 1.0 };
}
```

```salida
error[E0277]: the size for values of type `dyn Figura`
              cannot be known at compilation time
7 |     let f: dyn Figura = Circulo { radio: 1.0 };
  |         ^ doesn't have a size known at compile-time
  = help: the trait `Sized` is not implemented for
          `dyn Figura`
  = note: all local variables must have a statically
          known size
```

Una variable local va en el stack, y lo que va en el stack tiene tamaño
conocido al compilar ([3.1 Stack y heap]{.ref}). `dyn Figura` puede ser un
`Circulo` de 8 bytes o un `Rectangulo` de 16: no hay un número que
reservar. `Sized` es el trait que marca a los tipos con tamaño conocido, y
`dyn Figura` no lo tiene. Es la situación de `str` en
[3.4 Strings]{.ref}, que tampoco se usa suelto y aparece como `&str`. El
compilador emite además un `E0308` por la asignación, y su ayuda propone
la salida: *you could box the found value and coerce it to the trait
object `Box<dyn Figura>`*.

Un puntero sí tiene tamaño fijo, apunte a lo que apunte. Sirve cualquiera
de los tres ya presentados:

| Escrito | Qué es | Cuándo |
| :--- | :--- | :--- |
| `Box<dyn Figura>` | dueño, dato en el heap | guardar o devolver el valor |
| `&dyn Figura` | préstamo | solo usarlo, como parámetro |
| `Rc<dyn Figura>` | varios dueños | compartirlo ([6.2 Rc, RefCell y árboles]{.ref}) |

### Devolver un tipo u otro

[4.2 Generics]{.ref} dejó un caso abierto. Una función con retorno
`impl Figura` no puede devolver un `Circulo` en una rama y un `Rectangulo`
en la otra: `E0308`, *`if` and `else` have incompatible types*. Ese
retorno es un solo tipo, fijo al compilar.

En el programa siguiente, las dos ramas de `elegir` producen el mismo
tipo, `Box<dyn Figura>`, y cuál figura hay dentro depende de un dato de
ejecución. Esta `imprimir` recibe `&dyn Figura` y existe una sola vez en
el ejecutable. `&c` es un `&Circulo` y se convierte en `&dyn Figura` al
pasar como argumento. Las últimas líneas miden los punteros.

```rust
use std::rc::Rc;

trait Figura { fn area(&self) -> f64; }
struct Circulo { radio: f64 }
struct Rectangulo { ancho: f64, alto: f64 }

impl Figura for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
}
impl Figura for Rectangulo {
    fn area(&self) -> f64 { self.ancho * self.alto }
}

fn elegir(redonda: bool) -> Box<dyn Figura> {
    if redonda {
        Box::new(Circulo { radio: 1.0 })
    } else {
        Box::new(Rectangulo { ancho: 2.0, alto: 3.0 })
    }
}

fn imprimir(f: &dyn Figura) { println!("{:.2}", f.area()); }

fn main() {
    let c = Circulo { radio: 1.0 };
    let caja = elegir(false);
    imprimir(&c);             // 3.14
    imprimir(caja.as_ref());  // 6.00

    println!("{}", size_of::<Box<Circulo>>());      // 8
    println!("{}", size_of::<Box<dyn Figura>>());   // 16
    println!("{}", size_of::<&dyn Figura>());       // 16
    println!("{}", size_of::<Rc<dyn Figura>>());    // 16
}
```

### [Regla 2:]{.prefijo} el puntero lleva el dato y la tabla

El programa anterior midió cuatro punteros. Un `Box<Circulo>` ocupa 8
bytes: una dirección. Las tres formas de `dyn` ocupan 16. La segunda dirección apunta a la tabla de métodos del tipo
concreto. Al convertir un `Box<Circulo>` en `Box<dyn Figura>`, el
compilador sabe todavía que es un círculo y anota la dirección de la
tabla de `Circulo`. Después el tipo se pierde de vista y la tabla lo
sustituye.

La llamada `f.area()` sobre un `dyn Figura` hace tres pasos: lee la
segunda dirección, toma de la tabla la entrada de `area` y llama a esa
función con la primera dirección como `&self`. La figura siguiente es la
contraparte de la de [4.2 Generics]{.ref}. Allá había una función por
tipo y ninguna tabla. Aquí hay una sola función que llama y una tabla por
tipo.

El `&str` de [3.4 Strings]{.ref} tiene la misma forma: 16 bytes, la
dirección y un dato extra, que en su caso es la longitud. En los dos
casos el puntero carga lo que el tipo no dice.

### [Regla 3:]{.prefijo} no todo trait sirve como `dyn`

Todo trait sirve como bound genérico. Como `dyn Trait` sirven solo
algunos: los que la documentación llama *dyn compatible*. La condición
sale de la regla 2. Cada método debe poder llamarse teniendo nada más el
puntero y la tabla. Este trait no la cumple:

```rust,compile_fail
trait Dibujable {
    fn dibujar(&self);
    fn copia(&self) -> Self;
}
struct Punto;
impl Dibujable for Punto {
    fn dibujar(&self) { println!("."); }
    fn copia(&self) -> Self { Punto }
}
fn main() {
    let d: Box<dyn Dibujable> = Box::new(Punto);
}
```

```salida
error[E0038]: the trait `Dibujable` is not dyn compatible
11 |     let d: Box<dyn Dibujable> = Box::new(Punto);
   |                    ^^^^^^^^^ `Dibujable` is not dyn
   |                              compatible
note: for a trait to be dyn compatible it needs to allow
      building a vtable
 3 |     fn copia(&self) -> Self;
   |                        ^^^^ ...because method `copia`
   |            references the `Self` type in its return type
```

`copia` devuelve `Self`, el tipo concreto. Quien llama a través de
`dyn Dibujable` no conoce ese tipo ni su tamaño, así que no puede reservar
lugar para el resultado. El trait y su `impl` son correctos: el error
aparece donde se escribe `dyn Dibujable`. Cuatro cosas impiden usar un
trait como `dyn`:

| En el trait | Por qué rompe la tabla |
| :--- | :--- |
| un método genérico: `fn f<T>(&self, x: T)` | haría falta una entrada por cada `T` posible |
| un método que devuelve `Self` | el tamaño del retorno se desconoce |
| una función asociada sin `self` | no hay valor del cual sacar la tabla |
| `Self: Sized` como bound: `trait T: Sized` | declara que el tipo se conoce al compilar |

Cada una produce `E0038` con su propia nota. Para la función sin `self`,
por ejemplo: *associated function `nuevo` has no `self` parameter*.

Un método que estorba se puede dejar fuera de la tabla sin quitarlo del
trait. Se marca con `where Self: Sized`:

```rust
trait Dibujable {
    fn dibujar(&self);
    // fuera de la tabla:
    fn copia(&self) -> Self where Self: Sized;
}
struct Punto;
impl Dibujable for Punto {
    fn dibujar(&self) { println!("."); }
    fn copia(&self) -> Self { Punto }
}

fn main() {
    let q = Punto.copia();   // tipo concreto: se puede
    let d: Box<dyn Dibujable> = Box::new(q);
    d.dibujar();             // .
}
```

La marca dice que `copia` solo existe cuando el tipo tiene tamaño
conocido. `dyn Dibujable` no lo tiene, así que el método queda disponible
por tipo concreto o por genérico, y el resto del trait sirve como `dyn`.
Llamar `d.copia()` no compila: *the `copia` method cannot be invoked on a
trait object*.

Dos traits de la biblioteca estándar quedan uno de cada lado:

```rust
fn pares(tope: u64) -> Box<dyn Iterator<Item = u64>> {
    Box::new((0..tope).filter(|n| n % 2 == 0))
}

fn main() {
    let v: Vec<u64> = pares(9).collect();
    println!("{v:?}");   // [0, 2, 4, 6, 8]

    // let c: Box<dyn Clone> = Box::new(5);
    // E0038: the trait `Clone` is not dyn compatible
}
```

`Iterator` es compatible: `next` recibe `&mut self` y devuelve un
`Option<Item>`, y sus adaptadores, que son genéricos, llevan la marca
`Self: Sized`. El tipo asociado se fija en el propio `dyn`, con
`Item = u64`. `Clone` no es compatible, porque `clone` devuelve `Self` y
el trait entero exige `Self: Sized`.

### Closures distintas en una misma colección

[4.3 Closures]{.ref} dejó otro caso abierto. Cada closure tiene un tipo propio, sin
nombre, así que dos closures no caben en el mismo `Vec`. Con
`vec![|x: i32| x + n, |x: i32| x * n]` el compilador responde `E0308` y la
nota *no two closures, even if identical, have the same type*. Lo que sí
comparten es el trait: las dos son `Fn(i32) -> i32`.

```rust
fn main() {
    let n = 10;
    let pasos: Vec<Box<dyn Fn(i32) -> i32>> = vec![
        Box::new(|x| x + n),
        Box::new(|x| x * n),
        Box::new(|x| x - 1),
    ];

    let mut valor = 2;
    for paso in &pasos {
        valor = paso(valor);
    }
    println!("{valor}");   // 119
}
```

`Fn(i32) -> i32` es un trait como cualquier otro y su tabla tiene la
entrada de la llamada. Las closures capturan cosas distintas y miden
distinto: las dos primeras guardan una referencia a `n` y la tercera no
guarda nada. Detrás del `Box`, los tres elementos miden 16 bytes. Una
función que devuelve una closure u otra según una condición se escribe
igual, con retorno `Box<dyn Fn(i32) -> i32>`.

### Cuál usar

El genérico es el default. La llamada es directa, el compilador puede
copiar el cuerpo del método en el lugar de la llamada y todo se comprueba
con el tipo concreto a la vista.

`dyn` se elige cuando el conjunto de tipos se decide en ejecución: una
colección con tipos mezclados, o una función que devuelve un tipo u otro
según un dato. Su costo es una lectura de la tabla por llamada, y que el
compilador casi nunca puede copiar el cuerpo de un método que no conoce.
Ese costo pesa cuando el método es mínimo y se llama dentro de un ciclo
largo. Frente a un método que hace trabajo real, es pequeño.

La decisión se toma en cada punto de uso y no al declarar el trait:
`Figura` se usó de las dos maneras en un mismo programa.

### El mapa de la sección

Ninguna herramienta de la sección 6 agrega reglas a las de la sección 3.
Cada una toma algo que antes quedaba fijo al compilar y cambia dónde o
cuándo se cumple:

| Herramienta | Antes | Después |
| :--- | :--- | :--- |
| `Box<T>`, 6.1 | el dato vive donde vive su dueño | un dueño, el dato en el heap |
| `Rc<T>`, 6.2 | un dueño a la vez | varios dueños; se libera al irse el último |
| `RefCell<T>`, 6.2 | una `&mut` o varias `&`, al compilar | la misma regla, comprobada al ejecutar |
| `dyn Trait`, 6.3 | el tipo concreto se conoce al compilar | solo se conoce su tabla de métodos |

Lo demás queda como estaba. Todo valor tiene dueño y se libera cuando
sale de scope el último, y toda referencia es válida mientras vive, lo
que se sigue comprobando al compilar. Solo la regla 1 de
[3.3 Borrowing]{.ref} cambia de momento, y solo dentro de un `RefCell`:
violarla deja de ser un error de compilación y pasa a ser un panic.
[6.2 Rc, RefCell y árboles]{.ref} lo detalla, junto con los ciclos de
`Rc`.

## Aplicación

Ejercicio del curso *Aprende Rust*. El trait `Forma` declara dos métodos,
y el ejercicio pide una lista con un rectángulo y un círculo y una función
`area_total` que sume las áreas. Aquí se agrega un tercer tipo.

```rust
trait Forma {
    fn area(&self) -> f64;
    fn nombre(&self) -> String;
}
struct Rectangulo { ancho: f64, alto: f64 }
struct Circulo { radio: f64 }
struct Triangulo { base: f64, altura: f64 }
impl Forma for Rectangulo {
    fn area(&self) -> f64 { self.ancho * self.alto }
    fn nombre(&self) -> String { String::from("Rectángulo") }
}
impl Forma for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
    fn nombre(&self) -> String { String::from("Círculo") }
}
impl Forma for Triangulo {
    fn area(&self) -> f64 { self.base * self.altura / 2.0 }
    fn nombre(&self) -> String { String::from("Triángulo") }
}

fn area_total(formas: &[Box<dyn Forma>]) -> f64 {
    formas.iter().map(|forma| forma.area()).sum()
}

fn main() {
    let formas: Vec<Box<dyn Forma>> = vec![
        Box::new(Rectangulo { ancho: 2.0, alto: 3.0 }),
        Box::new(Circulo { radio: 1.0 }),
        Box::new(Triangulo { base: 4.0, altura: 1.5 }),
    ];
    for forma in &formas {
        println!("{}: {:.2}", forma.nombre(), forma.area());
    }
    println!("Total: {:.2}", area_total(&formas));
}
```

```salida
Rectángulo: 6.00
Círculo: 3.14
Triángulo: 3.00
Total: 12.14
```

`area_total` recibe `&[Box<dyn Forma>]`, un slice prestado, y no
`&Vec<Box<dyn Forma>>`. Así acepta la lista entera o una parte:
`area_total(&formas[..2])` devuelve 9.14. El ejercicio la escribe con un
`for` y un acumulador. Aquí usa `map` y `sum` ([5.6 Iteradores]{.ref}).

`Triangulo` no estaba en el ejercicio. Agregarlo pidió su `struct`, su
`impl` y una línea en el `vec!`. `area_total` y el `for` no cambiaron ni
se copiaron: el tipo nuevo solo aportó su tabla.

## A fondo

**`Box<dyn Error>` es este mismo mecanismo.** `Error` es un trait de la
biblioteca estándar que implementan los tipos de error. Una función que
puede fallar por causas de tipos distintos devuelve
`Result<T, Box<dyn Error>>`, y cada error viaja detrás del mismo puntero
doble. Se usa en [7.4 Manejo de errores idiomático]{.ref}.

**La tabla guarda más que los métodos del trait.** Lleva también el
tamaño del tipo concreto, su alineación y la dirección de su `drop`. Con
eso un `Box<dyn Figura>` que sale de scope libera lo correcto sin saber
qué tipo guardaba.

**Un `enum` también mezcla tipos, sin tabla.** Si el conjunto de figuras
es cerrado, un `enum` con una variante por figura cabe en un `Vec` y se
resuelve con `match` ([2.3 Enums]{.ref}). Agregar una variante obliga a
revisar cada `match`. Agregar un tipo a un `dyn` no toca el código que ya
existe.
