# 3.2 · Ownership

Todo programa pide memoria mientras corre, y alguien tiene que devolverla. Un
recolector de basura la devuelve solo, pero cobra CPU y pausas en ejecución. La
liberación manual de C no cobra nada, y a cambio permite fugas, dobles liberaciones
y usos de memoria ya liberada.

Rust toma un tercer camino: un conjunto de reglas que el compilador verifica. La
memoria se libera sola, en un punto fijo que se conoce al compilar.

## Definiciones y reglas

Dueño
:   *(owner)*: la variable responsable de liberar un valor.

Mover
:   *(move)*: transferir esa responsabilidad a otra variable. La original
    queda invalidada.

::: {.reglas titulo="Las tres reglas del ownership"}
1. Cada valor tiene un dueño.
2. Solo puede haber un dueño a la vez.
3. Cuando el dueño sale de scope, el valor se libera.
:::

Un programa que viola alguna de las tres no compila.

## De un vistazo

Lo que le pasa a una variable `a` depende de su tipo. Los tipos que viven enteros
en el stack se copian. Los que guardan datos en el heap se mueven
([3.1 Stack y heap]{.ref}).

| Operación | Tipo `Copy`: `i32`, `bool`, `char` | Tipo con heap: `String` |
| :--- | :--- | :--- |
| `let b = a;` | se copia; `a` sigue válida | se mueve; `a` queda invalidada |
| `funcion(a)` | se copia; `a` sigue válida | se mueve; `a` queda invalidada |
| `a.clone()` | igual que copiar | duplica el heap; `a` sigue válida |
| el dueño sale de scope | se descarta del stack | se libera el heap |

El resto del capítulo explica de dónde sale cada celda.

## Las reglas, una por una

El orden de lectura es 3, 2, 1: la regla 3 dice cuándo se libera la memoria, y la
regla 2 existe para que la 3 funcione.

### [Regla 3:]{.prefijo} el valor se libera al salir de scope

```rust
fn main() {
    {
        let s = String::from("hola"); // s es dueña desde aquí
        println!("{s}");
    } // sale de scope: se libera
    // aquí s ya no existe
}
```

Al cerrar la llave, Rust llama a `drop` sobre `s` y devuelve su memoria. No hay
recolector ni llamada escrita a mano. El punto de liberación se lee en el código: es
la llave que cierra el scope del dueño.

### [Regla 2:]{.prefijo} un solo dueño a la vez

Un `String` son dos piezas. En el stack hay tres datos de tamaño fijo: un puntero
al texto (`ptr`), cuántos bytes están en uso (`len`) y cuántos hay reservados
(`cap`). En el heap están los bytes del texto.

`let s2 = s1;` copia los tres datos del stack, 24 bytes en una máquina de 64 bits.
El heap no se toca, así que las dos variables apuntarían al mismo texto.

::: {.advertencia titulo="Lo que evita invalidar s1"}
Con dos dueñas, al salir de scope `s2` liberaría `"hola"` y después `s1`
liberaría la misma memoria.
:::

Con dos dueñas del mismo buffer, la regla 3 se aplicaría dos veces. Al salir de
scope, `s2` liberaría el texto y después `s1` liberaría la misma memoria. Es la
*doble liberación* de C, y corrompe el heap.

Rust lo evita en la asignación: `s1` queda invalidada y `s2` es la única dueña. El
texto no se duplica ni se destruye, solo cambia de dueño. Eso es mover.

Usar la variable movida es un error de compilación:

```rust,compile_fail
fn main() {
    let s1 = String::from("hola");
    let s2 = s1;
    println!("{s1} y {s2}");
}
```

```salida
error[E0382]: borrow of moved value: `s1`
2 |     let s1 = String::from("hola");
  |         -- move occurs because `s1` has type `String`,
  |            which does not implement the `Copy` trait
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{s1} y {s2}");
  |                ^^ value borrowed here after move
```

El mensaje señala tres líneas, y cada una responde una pregunta: por qué este valor
se mueve y no se copia, dónde lo perdió la variable, y dónde se intentó usar
después. Dice *borrowed* porque `println!` toma prestado lo que imprime
([3.3 Borrowing]{.ref}).

### Dónde ocurre un move

Una asignación no es el único lugar. Pasar un valor a una función lo mueve al
parámetro, y devolverlo lo mueve a quien llamó.

```rust
fn firmar(texto: String) -> String {  // texto: la nueva dueña
    let mut firmado = texto;          // se mueve otra vez
    firmado.push_str(" (firmado)");
    firmado                           // se mueve a quien llamó
}

fn main() {
    let carta = String::from("hola");
    let carta = firmar(carta);        // entra y regresa
    println!("{carta}");
}
```

El caso que más sorprende es el bucle. La primera vuelta mueve el valor, y la
segunda ya no tiene qué pasar:

```rust,compile_fail
fn imprimir(texto: String) {
    println!("{texto}");
}

fn main() {
    let saludo = String::from("hola");
    for _ in 0..2 {
        imprimir(saludo);  // E0382: value moved here,
    }                      //   in previous iteration of loop
}
```

El compilador propone dos arreglos: clonar el valor, o cambiar el parámetro para
que tome prestado.

### Copiar en vez de mover

Con un entero no pasa nada de esto:

```rust
fn main() {
    let x = 10;
    let y = x;
    println!("{x} y {y}");   // las dos siguen válidas
}
```

Un `i32` vive entero en el stack. Copiar sus bits produce dos valores
independientes, y ninguno tiene nada que liberar. No hay doble liberación posible,
así que no hace falta invalidar a `x`. Los tipos que se comportan así implementan
el trait `Copy`.

### `.clone()`: la copia se pide

Cuando hacen falta dos textos independientes, se pide de forma explícita:

```rust
fn main() {
    let s1 = String::from("hola");
    let s2 = s1.clone();      // otro buffer, mismos bytes
    println!("{s1} y {s2}");  // cada una con su texto
}
```

Rust nunca duplica el heap por su cuenta. Una asignación cuesta siempre lo mismo:
los datos del stack. `.clone()` marca en el código el punto donde se paga una copia
completa.

## Aplicación

Una función que mide un texto se lo queda. Para que quien llama pueda seguir
usándolo, la función tiene que devolverlo junto con su resultado.

```rust
fn longitud(s: String) -> (String, usize) {
    let n = s.len();
    (s, n)                        // devuelve el texto también
}

fn main() {
    let s1 = String::from("hola");
    let (s1, n) = longitud(s1);   // se mueve, y regresa
    println!("{s1} mide {n} bytes");
}
```

El programa es correcto y cumple las tres reglas, pero repetir ese ir y venir en
cada función no escala. La alternativa es prestar el valor sin entregarlo, y es el
tema de [3.3 Borrowing]{.ref}.

## A fondo

**La regla exacta de `Copy`.** Un tipo puede implementar `Copy` solo si todos sus
campos son `Copy` y no implementa `Drop`. Todo lo demás se mueve.

```rust
fn main() {
    let a = (1, true);           // (i32, bool) es Copy
    let b = a;                   // las dos viven
    println!("{a:?} {b:?}");

    let c = (1, String::new());  // String no es Copy:
    let d = c;                   // la tupla se mueve
    println!("{d:?}");
}
```

Las dos tuplas viven en el stack. Estar ahí es una consecuencia frecuente de ser
`Copy`, no la causa.

**Un struct se mueve entero.** Si alguno de sus campos no es `Copy`, el struct
tampoco lo es, y `let v = u;` invalida a `u` con todos sus campos.

```rust,compile_fail
struct Usuario {
    nombre: String,
    edad: u8,
}

fn main() {
    let u = Usuario {
        nombre: String::from("Gio"),
        edad: 25,
    };
    let v = u;
    println!("{}", u.edad);  // E0382: u se movió entera
}
```

**Reasignar también libera.** Declarar (`let y = x;`) y reasignar (`y = x;`) siguen
la misma semántica de copia o movimiento. La diferencia es que al reasignar, el
valor que la variable tenía antes se queda sin dueño y se libera en ese momento.

```rust
fn main() {
    let mut s = String::from("primero");
    s = String::from("segundo");  // "primero" se libera aquí
    println!("{s}");
}
```

**`drop` es un trait.** La liberación de la regla 3 es el método del trait `Drop`,
que el compilador invoca al terminar el scope del dueño. Cualquier tipo puede
implementarlo para correr código propio en ese punto.
