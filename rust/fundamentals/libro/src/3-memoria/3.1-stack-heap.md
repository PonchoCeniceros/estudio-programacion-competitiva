# 3.1 · Stack y heap

Las secciones 1 y 2 usaron valores sin preguntar dónde quedan guardados. Un
`i32`, una tupla o un struct existían desde su declaración y dejaban de existir
al cerrar la llave. Con esos tipos la pregunta no hacía falta.

Con un `String` sí hace falta. Su texto puede crecer mientras el programa
corre, así que su tamaño no se conoce al compilar. Un programa guarda sus
valores en dos regiones de memoria, el stack y el heap, y cada una cobra
distinto. Las reglas de toda la sección 3 salen de esa diferencia.

## Definiciones y reglas

Stack
:   *(pila)*: la región donde cada llamada a una función guarda sus
    variables locales. Lo último que entra es lo primero que sale.

Marco
:   *(stack frame)*: el bloque del stack que pertenece a una llamada.
    Contiene sus parámetros y sus variables locales.

Heap
:   *(montículo)*: la región donde se reservan bloques de cualquier tamaño
    mientras el programa corre. Se devuelven en cualquier orden.

Asignador
:   *(allocator)*: la parte del programa que reparte los bloques del heap.
    Busca un hueco libre, lo entrega y más tarde lo recibe de vuelta.

Puntero
:   un valor que guarda una dirección de memoria. Mide lo mismo sin importar
    a qué apunte: 8 bytes en una máquina de 64 bits.

::: {.reglas titulo="Las tres reglas de la memoria"}
1. Todo lo que va en el stack tiene un tamaño conocido al compilar.
2. Cada llamada apila un marco, y al terminar el marco se descarta entero.
3. Lo que puede crecer vive en el heap. En el stack queda una parte de tamaño
   fijo que apunta a él.
:::

## De un vistazo

| | Stack | Heap |
| :--- | :--- | :--- |
| Qué guarda | parámetros y variables locales | datos cuyo tamaño se decide al ejecutar |
| Tamaño de cada valor | fijo, conocido al compilar | variable |
| Reservar | mover la marca de la cima | pedir un bloque al asignador |
| Liberar | todo el marco, al terminar la función | bloque por bloque |
| Orden | último en entrar, primero en salir | cualquiera |
| Ejemplos | `i32`, `char`, tuplas, arreglos, structs | el texto de un `String` |

Rust pone un valor en el stack por default. El heap se usa cuando el tamaño no
se conoce al compilar, o cuando se pide de forma explícita
([6.1 Box y listas enlazadas]{.ref}).

## Las reglas, una por una

### [Regla 1:]{.prefijo} el tamaño se conoce al compilar

La función `std::mem::size_of` devuelve cuántos bytes ocupa un tipo. El tipo
se escribe entre `::<` y `>`; esa sintaxis se explica en [4.2 Generics]{.ref}.

```rust
fn main() {
    println!("{}", std::mem::size_of::<i32>());          // 4
    println!("{}", std::mem::size_of::<char>());         // 4
    println!("{}", std::mem::size_of::<(i32, bool)>());  // 8
    println!("{}", std::mem::size_of::<[i32; 4]>());     // 16
}
```

Ningún número depende de un valor concreto: el tamaño es parte del tipo. Un
`[i32; 4]` son cuatro `i32` seguidos, y por eso la longitud de un arreglo se
escribe en su tipo ([2.1 Tuplas y arreglos]{.ref}).

Una longitud que sale de una variable no compila:

```rust,compile_fail
fn main() {
    let n = 3;
    let ceros = [0; n];
    println!("{ceros:?}");
}
```

```salida
error[E0435]: attempt to use a non-constant value
              in a constant
3 |     let ceros = [0; n];
  |                     ^ non-constant value
```

`n` vale 3 y nunca cambia, pero es una variable: su valor existe al ejecutar.
El compilador necesita la longitud antes, para saber cuánto mide el marco de
`main`. Con `const N: usize = 3;` el programa compila, porque una constante se
conoce al compilar ([1.3 Variables]{.ref}).

### [Regla 2:]{.prefijo} un marco por llamada

```rust
fn cuadrado(n: u32) -> u32 {
    let r = n * n;
    r
}

fn main() {
    let lenguaje = String::from("Rust");
    let lado = 4;
    let area = cuadrado(lado);
    println!("{lenguaje}: {area}");
}
```

Al llamar a `cuadrado`, el programa apila un marco sobre el de `main`. En él
viven `n` y `r`. Al terminar, el resultado se copia al lugar de `area` y el
marco se descarta entero.

::: {.figura src="figuras/3.1-marcos.html"}
:::

Descartar un marco no borra nada: el programa solo mueve la marca que señala
la cima del stack. Reservarlo es mover la misma marca en sentido contrario. El
costo no depende de cuántas variables tenga el marco.

El marco de `main` tiene el lugar de `area` desde antes de la llamada. Es
posible por la regla 1: el compilador ya sabía cuánto mide cada variable.

El orden de pila alcanza porque las llamadas terminan en orden inverso al que
empezaron. `cuadrado` empieza después que `main` y termina antes.

### [Regla 3:]{.prefijo} lo que crece va al heap

Un `String` cambia de tamaño al ejecutar:

```rust
fn main() {
    let mut s = String::from("hola");
    println!("{}", s.len());                         // 4
    s.push_str(" mundo");
    println!("{}", s.len());                         // 10
    println!("{}", std::mem::size_of::<String>());   // 24
}
```

El texto pasa de 4 a 10 bytes, así que no puede estar en el marco de `main`:
la regla 1 exige un tamaño fijo. La solución es partir el valor en dos. El
texto va al heap, en un bloque que el asignador entrega al ejecutar. En el
stack queda una parte de 24 bytes que guarda dónde está ese bloque.

::: {.figura src="figuras/3.1-crecer.html"}
:::

Esos 24 bytes son los mismos para un texto vacío que para uno de un millón de
letras. Cuando el texto ya no cabe en su bloque, `push_str` pide al asignador
uno más grande. Si el nuevo queda en otra dirección, los bytes se copian ahí.
La parte del stack no cambia de tamaño: solo se actualiza. Su contenido se
detalla en [3.2 Ownership]{.ref}.

Decir que un `String` «vive en el heap» es una abreviatura. La variable está
en el stack, y su texto en el heap.

### Dos formas de vivir

Una variable local vive lo que vive su marco: desde que la función empieza
hasta que termina. Un bloque del heap no pertenece a ningún marco. Sigue
reservado hasta que alguien lo devuelve al asignador.

```rust
fn saludo() -> String {
    let s = String::from("hola");
    s
}   // el marco se descarta; el texto sigue en el heap

fn main() {
    let texto = saludo();
    println!("{texto}");
}
```

El marco de `saludo` desaparece al terminar, y el texto sobrevive. Los 24
bytes de `s` se copian al marco de `main` y apuntan al mismo bloque de antes.
El bloque nunca se movió.

## Aplicación

El programa declara tres valores. Para cada uno se puede decir qué queda en
el marco de `main` y qué queda en el heap.

```rust
struct Punto {
    x: f64,
    y: f64,
}

struct Usuario {
    nombre: String,
    edad: u8,
}

fn main() {
    let origen = Punto { x: 0.0, y: 0.0 };
    let notas = [90, 85, 100];
    let ana = Usuario {
        nombre: String::from("Ana"),
        edad: 30,
    };
    println!("{}", std::mem::size_of::<Punto>());     // 16
    println!("{}", std::mem::size_of::<[i32; 3]>());  // 12
    println!("{}", std::mem::size_of::<Usuario>());   // 32
    println!("{} {}", origen.x + origen.y, notas[0]);
    println!("{} tiene {} años", ana.nombre, ana.edad);
}
```

| Variable | En el marco de `main` | En el heap |
| :--- | :--- | :--- |
| `origen` | 16 bytes: dos `f64` | nada |
| `notas` | 12 bytes: tres `i32` | nada |
| `ana` | 32 bytes: la parte fija de `nombre`, y `edad` | 3 bytes: `Ana` |

Un struct está en el stack aunque uno de sus campos guarde datos en el heap.
`Usuario` mide 32 bytes con cualquier nombre, y por eso cumple la regla 1.

Queda una pregunta abierta. Con un entero, `let y = x;` copia 4 bytes y deja
dos valores independientes. Con `ana`, copiar los 32 bytes del stack dejaría
dos variables apuntando al mismo bloque del heap. El stack se libera solo, por
la regla 2. Para el heap falta decidir cuál de las dos variables devuelve el
bloque, y cuándo. Esa regla es el tema de [3.2 Ownership]{.ref}.

## A fondo

**El stack tiene un límite.** Su tamaño se fija al arrancar el hilo; en Linux
y macOS el hilo principal recibe por lo común 8 MiB. Una recursión que no
termina apila marcos hasta agotarlo, y el sistema detiene el programa.

```rust,should_panic
fn bajar(n: u64) -> u64 {
    1 + bajar(n + 1)
}

fn main() {
    println!("{}", bajar(0));
}
```

```salida
thread 'main' (1550330) has overflowed its stack
fatal runtime error: stack overflow, aborting
```

El número entre paréntesis identifica al hilo y cambia en cada ejecución.

**El heap cuesta más.** Reservar en el stack es mover una marca. Reservar en el
heap es una llamada al asignador, que busca un bloque libre del tamaño pedido
y lleva la cuenta de cuáles entregó. Leer el dato también cuesta un paso más:
primero se lee el puntero y después lo apuntado.

**El tamaño incluye relleno.** Cada tipo tiene una alineación: un `u32` empieza
en una dirección múltiplo de 4. El compilador inserta bytes de relleno para
cumplirla, y por eso un tipo puede medir más que la suma de sus campos. La
tupla `(u8, u32)` mide 8 bytes, no 5. En la tabla de la aplicación, `Usuario`
mide 32: 24 de `nombre`, 1 de `edad` y 7 de relleno.

**Un tipo que se contiene a sí mismo no tiene tamaño.** El compilador no puede
calcular cuánto mide `Lista`, porque dentro de cada `Lista` cabría otra.

```rust,compile_fail
enum Lista {
    Nodo(i32, Lista),
    Fin,
}

fn main() {
    let l = Lista::Fin;
}
```

```salida
error[E0072]: recursive type `Lista` has infinite size
1 | enum Lista {
  | ^^^^^^^^^^
2 |     Nodo(i32, Lista),
  |               ----- recursive without indirection
```

La solución es la misma de la regla 3: guardar la parte recursiva en el heap y
dejar un puntero de tamaño fijo en su lugar
([6.1 Box y listas enlazadas]{.ref}).

**Un literal de texto no está en ninguno de los dos.** Los bytes de `"hola"`
quedan grabados en el ejecutable y existen durante todo el programa.
`String::from("hola")` los copia a un bloque del heap ([3.4 Strings]{.ref}).
