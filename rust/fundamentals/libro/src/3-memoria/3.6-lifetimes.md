# 3.6 · Lifetimes

La regla 2 de [3.3 Borrowing]{.ref} quedó enunciada y sin explicar: toda
referencia debe ser siempre válida. La regla 1 se comprueba mirando qué
préstamos coexisten. La regla 2 pide otra cosa: saber hasta dónde vive cada
dato y hasta dónde se usa cada referencia.

El síntoma aparece sin escribir sintaxis nueva. Una referencia se guarda en
una variable, el dato al que apunta se libera, y la referencia se usa después.
El compilador lo rechaza con *does not live long enough*. Los *lifetimes* son
la medida con la que llega a ese veredicto, y la anotación `'a` es la forma de
darle el dato que a veces le falta.

## Definiciones y reglas

Lifetime
:   la región de código donde una referencia está viva: desde que se crea
    hasta su último uso. El compilador la calcula; no se escribe.

Parámetro de lifetime
:   `'a`: el nombre de una región que todavía no se conoce. Se declara entre
    `<` y `>`, y relaciona varias referencias de una firma o de un tipo.

Elisión
:   las tres reglas con las que el compilador completa los lifetimes que una
    firma no escribe.

`'static`
:   el lifetime que abarca toda la ejecución del programa.

::: {.reglas titulo="Las tres reglas de los lifetimes"}
1. Una referencia no se usa fuera de la región donde su dato existe.
2. Una función que devuelve una referencia dice en su firma de qué entrada
   sale.
3. Un tipo que guarda una referencia declara su lifetime, y ningún valor de
   ese tipo sobrevive al dato.
:::

## De un vistazo

Los lifetimes existen en todo programa que usa referencias. Lo que cambia es
quién los escribe.

| Situación | ¿Se escribe `'a`? | Por qué |
| :--- | :--- | :--- |
| referencia dentro de una función | no | el compilador ve las dos regiones |
| función con una entrada prestada | no | la elisión la completa |
| método con `&self` | no | la elisión ata la salida a `self` |
| función con dos entradas prestadas que devuelve una referencia | sí | la firma no dice de cuál sale |
| struct con un campo que es referencia | sí | el tipo debe declarar su límite |
| literal de texto | ya lo trae | es `&'static str` |

Criterio: `'a` se escribe cuando el compilador lo pide con `E0106`. Antes de
anotar una struct conviene preguntar si debería ser dueña de su dato.

## Las reglas, una por una

Primero el síntoma, sin anotaciones. Después las regiones que el compilador
compara, y al final la sintaxis.

### El síntoma: la referencia sobrevive a su dato

`let r;` declara la variable y deja su valor para después. El valor llega
dentro de un bloque interior:

```rust,compile_fail
fn main() {
    let r;
    {
        let x = 5;
        r = &x;
    }
    println!("{r}");
}
```

```salida
error[E0597]: `x` does not live long enough
4 |         let x = 5;
  |             - binding `x` declared here
5 |         r = &x;
  |             ^^ borrowed value does not live long enough
6 |     }
  |     - `x` dropped here while still borrowed
7 |     println!("{r}");
  |                - borrow later used here
```

El mensaje señala tres puntos: dónde se presta `x`, dónde se libera y dónde se
usa el préstamo después. `x` sale de scope en la llave del bloque interior. El
`println!` usaría `r` cuando ya no hay nada a donde apuntar.

:::

### [Regla 1:]{.prefijo} la referencia cabe en la región de su dato

El compilador mide dos regiones de código, y ninguna se escribe:

- La del dato va de su declaración a la llave que cierra su bloque, donde
  se libera ([3.2 Ownership]{.ref}).
- La de la referencia va de su creación a su último uso, no hasta la llave
  ([3.3 Borrowing]{.ref}).

La segunda región es el lifetime de la referencia. Con el último uso de `r`
dentro del bloque, cabe en la del dato y el programa compila:

```rust
fn main() {
    let r;
    {
        let x = 5;
        r = &x;
        println!("{r}");   // último uso de r
    }                      // aquí se libera x
}
```

`r` sigue declarada fuera del bloque y eso no estorba. Importa dónde se usa la
referencia, no dónde vive la variable que la guarda. El otro arreglo es
declarar `x` en el bloque exterior, para que viva más.

En este capítulo, `L(x)` nombra la región donde `x` está vivo, sea un dato o
una referencia. La regla 1 se escribe `L(r) ≤ L(x)`: la región de `r` cabe
dentro de la de `x`.

### [Regla 2:]{.prefijo} la firma dice de dónde sale la referencia

Dentro de una sola función, el compilador ve las dos regiones y compara.
Cuando la referencia sale de una llamada, le falta un dato:

```rust,compile_fail
fn mas_larga(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let s = String::from("hello");
    let t = String::from("hola");
    let r = mas_larga(&s, &t);
    println!("{r}");
}
```

```salida
error[E0106]: missing lifetime specifier
1 | fn mas_larga(a: &str, b: &str) -> &str {
  |                 ----     ----     ^ expected named
  |                                     lifetime parameter
  = help: this function's return type contains a borrowed
          value, but the signature does not say whether it
          is borrowed from `a` or `b`
```

El compilador revisa cada función por separado. Al revisar `main` no lee el
cuerpo de `mas_larga`: solo su firma. Y la firma no dice si `r` apunta al
texto de `s` o al de `t`, así que no hay región con la cual comparar `L(r)`.
Leer el cuerpo tampoco lo resolvería: cuál de las dos sale depende de las
longitudes, que se conocen al ejecutar.

La firma se completa con un parámetro de lifetime:

```rust
fn mas_larga<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let s = String::from("hello");   // ①
    let t = String::from("hola");    // ②
    let r = mas_larga(&s, &t);       // ③
    println!("{r}");                 // ④ hello
}
```

`<'a>` declara el nombre, entre `<` y `>` después del nombre de la función. El
apóstrofo lo distingue de una variable, y por convención es una letra
minúscula. Se usa justo después del `&`: `&'a str`, `&'a mut String`. El
cuerpo de la función no cambió. Los números de los comentarios marcan los
puntos del programa que se usan más adelante.

### `'a` es una incógnita, no una duración

La anotación no alarga ni acorta la vida de nada. No dice cuánto viven `a` y
`b`. Dice cómo se relacionan con la salida: la referencia devuelta no puede
usarse más allá de la entrada que termine primero.

`'a` es el nombre de una incógnita. La función se escribe una vez, y en cada
llamada el compilador le da a `'a` un valor distinto, calculado con las
regiones de esa llamada. Comparar lifetimes es comparar regiones de código, no
cantidades de tiempo.

| Notación | Se lee |
| :--- | :--- |
| `L(x)` | la región donde `x` está vivo |
| `min(L(s), L(t))` | de las dos regiones, la que termina primero |
| `max(L(r))` | el punto más tardío donde se usa `r` |

Con `s` y `t` como entradas y `r` como salida, el compilador da tres pasos:

1. Leer las regiones: `L(s)`, `L(t)` y `L(r)`.
2. Resolver la incógnita: `'a = min(L(s), L(t))`.
3. Verificar que el último uso de la salida cae dentro: `max(L(r)) ≤ 'a`.

Los pasos 2 y 3 juntos son la ecuación general de los lifetimes: `'a` vale lo
que dure la entrada más corta, y el último uso de la salida debe caer dentro
de esa región.

La notación `L`, `min` y `max` es de este libro. La documentación de Rust
habla de regiones y de que una sobrevive a otra (*outlives*). El modelo
predice los mismos veredictos; el mecanismo real está en «A fondo».

### Caso válido: los dos datos sobreviven al uso

::: {.figura src="figuras/3.6-caso-valido.html"}
:::

1. Leer. `L(s)` va de ① al final de `main`. `L(t)` va de ② al final. `L(r)`
   va de ③ a ④, su último uso.
2. Resolver. `'a = min(L(s), L(t))`. Las dos entradas llegan al final de
   `main`, así que `'a` también llega hasta ahí.
3. Verificar. `max(L(r))` es ④, y ④ cae dentro de `'a`. El programa compila.

### Caso inválido: un dato muere antes

El mismo `mas_larga`, con `t` declarada en un bloque interior:

```rust,compile_fail
fn mas_larga<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let s = String::from("hello world");   // ①
    let r;
    {
        let t = String::from("hola");      // ②
        r = mas_larga(&s, &t);             // ③
    }                                      // ④ muere t
    println!("{r}");                       // ⑤
}
```

```salida
error[E0597]: `t` does not live long enough
 9 |         let t = String::from("hola");      // ②
   |             - binding `t` declared here
10 |         r = mas_larga(&s, &t);             // ③
   |                           ^^ borrowed value does not
   |                              live long enough
11 |     }                                      // ④ muere t
   |     - `t` dropped here while still borrowed
12 |     println!("{r}");                       // ⑤
   |                - borrow later used here
```

::: {.figura src="figuras/3.6-caso-invalido.html"}
:::

1. Leer. `L(s)` va de ① al final de `main`. `L(t)` va de ② a ④, donde se
   libera. `L(r)` va de ③ a ⑤.
2. Resolver. `'a = min(L(s), L(t)) = L(t)`. `t` es la entrada que termina
   primero, y `'a` no puede pasar de ④.
3. Verificar. `max(L(r))` es ⑤, y ⑤ queda después de ④. No se cumple.

A simple vista el programa debería compilar. `s` mide 11 bytes y `t` mide 4:
al ejecutar, `mas_larga` devolvería `s`, que sigue viva en ⑤. El compilador no
ejecuta nada. Lee la firma, y la firma dice que la salida puede venir de
cualquiera de las dos entradas.

El error no es que `t` se haya liberado. Es que `r` quedó atada a `'a`, y `'a`
quedó atada a la entrada más corta. Por eso el arreglo casi nunca consiste en
alargar un lifetime. Consiste en acortar el uso de `r`, con el `println!`
dentro del bloque, o en dejar de prestar: que la función devuelva un `String`
propio.

### Dos formas distintas de no compilar

Los dos errores del capítulo salen de pasos distintos.

| | Falta información | Falla la verificación |
| :--- | :--- | :--- |
| Error típico | `E0106` *missing lifetime specifier* | `E0597` *does not live long enough* |
| Paso | 2: no hay con qué resolver `'a` | 3: la comprobación no se cumple |
| Qué dice | no se sabe de dónde sale la referencia | se comprobó, y la referencia sobrevive al dato |
| Se arregla | anotando `<'a>` en la firma o en la struct | cambiando el código: acortar el uso o dejar de prestar |

`E0106` no dice que el programa esté mal. Dice que al compilador le falta un
dato para juzgarlo. `E0597` sí es un veredicto. Anotar lifetimes no convierte
un programa inválido en válido: solo permite que se le evalúe.

### Las tres reglas de elisión

Las funciones de [3.4 Strings]{.ref} devolvían referencias sin anotar nada:
`fn sin_extension(nombre: &str) -> &str` compila. Los lifetimes están ahí. El
compilador los completa con tres reglas fijas, que solo leen la firma.

::: {.reglas titulo="Las tres reglas de elisión"}
1. Cada referencia de entrada sin anotar recibe un lifetime propio.
2. Si hay un solo lifetime de entrada, se asigna a todas las referencias de
   salida.
3. Si una de las entradas es `&self` o `&mut self`, su lifetime se asigna a
   todas las referencias de salida.
:::

Si después de aplicarlas queda una referencia de salida sin lifetime, el
compilador no adivina: emite `E0106`.

| Reglas | | Firma |
| :---- | :--------- | :------------------------------ |
| 1 y 2 | se escribe | `fn f(s: &str) -> &str` |
| | se entiende | `fn f<'a>(s: &'a str) -> &'a str` |
| 1 | se escribe | `fn f(a: &str, b: &str) -> usize` |
| | se entiende | `fn f<'a, 'b>(a: &'a str, b: &'b str) -> usize` |
| 1 y 3 | se escribe | `fn f(&self, t: &str) -> &str` |
| | se entiende | `fn f<'a, 'b>(&'a self, t: &'b str) -> &'a str` |
| 1 | se escribe | `fn f(a: &str, b: &str) -> &str` |
| | se entiende | `E0106`: quedan dos lifetimes de entrada y ninguno es de `self` |

El último par es `mas_larga`. La regla 1 le da un lifetime a cada entrada, la
regla 2 no aplica porque son dos, y la regla 3 tampoco porque no hay `self`.

### [Regla 3:]{.prefijo} una struct que guarda una referencia

Los campos de las structs de [2.2 Structs]{.ref} eran dueños de sus datos. Un
campo que es referencia no compila sin más:

```rust,compile_fail
struct Usuario {
    nombre: &str,
}

fn main() {
    let u = Usuario { nombre: "Ferris" };
    println!("{}", u.nombre);
}
```

```salida
error[E0106]: missing lifetime specifier
2 |     nombre: &str,
  |             ^ expected named lifetime parameter
help: consider introducing a named lifetime parameter
1 ~ struct Usuario<'a> {
2 ~     nombre: &'a str,
```

En los campos no hay elisión. El parámetro se declara después del nombre del
tipo y se usa en el campo. `Usuario<'a>` se lee así: un `Usuario` no puede
vivir más que el texto al que apunta su `nombre`.

```rust,compile_fail
struct Usuario<'a> {
    nombre: &'a str,
}

fn main() {
    let u;
    {
        let nombre = String::from("Ferris");
        u = Usuario { nombre: &nombre };
    }   // E0597: `nombre` does not live long enough
    println!("{}", u.nombre);
}
```

Es el síntoma del principio, ahora a través de un campo: `u` se usa cuando
`nombre` ya se liberó.

Hay una alternativa de diseño que evita el lifetime: declarar el campo como
`String` y que la struct sea dueña de su texto. Una struct con referencias
sirve como vista temporal de datos ajenos. Una que debe guardarse o
devolverse suele necesitar ser dueña.

### El lifetime `'static`

`'static` es el único lifetime con nombre fijo. Abarca toda la ejecución del
programa. Los literales de texto lo tienen porque viven en el binario
([3.4 Strings]{.ref}) y nunca se liberan:

```rust
fn saludo() -> &'static str {
    "hola"   // el literal está en el ejecutable
}

fn main() {
    println!("{}", saludo());
}
```

`saludo` no recibe ninguna referencia, así que su salida no puede venir de una
entrada. Solo puede apuntar a algo que no se libera nunca.

El compilador sugiere `'static` cuando una función sin entradas prestadas
devuelve una referencia. Seguir la sugerencia con un dato local no arregla
nada:

```rust,compile_fail
fn titulo() -> &'static str {
    let t = String::from("Lifetimes");
    // E0515: cannot return reference to local variable `t`
    &t
}

fn main() {
    println!("{}", titulo());
}
```

::: {.advertencia titulo="Cuando el compilador sugiere 'static"}
Casi nunca es la solución. La propia ayuda lo avisa: *this is uncommon unless
you're returning a borrowed value from a `const` or a `static`*. Escribir
`'static` no hace que un dato viva más: promete que ya vive todo el programa.
Si el dato es local, lo correcto es devolver un valor con dueño.
:::

## Aplicación

Dos ejercicios del curso *Aprende Rust*. El primero busca la primera línea de
un texto que contiene una palabra. `.lines()` recorre el texto línea por línea
y `.contains()` dice si un texto incluye a otro. La línea devuelta es un slice
de `texto`, nunca de `palabra`, y la firma lo dice anotando solo `texto`:

```rust
fn buscar_linea<'a>(
    texto: &'a str,
    palabra: &str,
) -> &'a str {
    for linea in texto.lines() {
        if linea.contains(palabra) {
            return linea;
        }
    }
    ""   // un literal: &'static str, sirve como &'a str
}

fn main() {
    let poema = String::from(
        "Caminante, no hay camino,\nse hace camino al andar.",
    );
    let resultado;
    {
        let palabra = String::from("andar");
        resultado = buscar_linea(&poema, &palabra);
    }   // palabra se libera; resultado apunta a poema
    println!("{resultado}");   // se hace camino al andar.
}
```

`palabra` muere antes del `println!` y el programa compila, porque
`resultado` no quedó atado a ella. Con `palabra: &'a str` la firma seguiría
siendo aceptada, pero `main` fallaría con `E0597`: `'a` quedaría limitada por
la entrada más corta, igual que en el caso inválido. Anotar de más rechaza
programas correctos.

El segundo ejercicio guarda una referencia en una struct y le agrega un
método. El lifetime se declara tres veces: en la struct, después de `impl` y
en el tipo al que pertenece el bloque.

```rust
struct Resaltado<'a> {
    texto: &'a str,
}

impl<'a> Resaltado<'a> {
    fn primera_palabra(&self) -> &str {
        for (i, c) in self.texto.char_indices() {
            if c == ' ' {
                return &self.texto[..i];
            }
        }
        self.texto
    }
}

fn main() {
    let nota = String::from("Rust es rápido");
    let r = Resaltado { texto: &nota };
    println!("{}", r.primera_palabra());       // Rust

    let vacio = Resaltado { texto: "" };
    println!("[{}]", vacio.primera_palabra()); // []
}
```

`primera_palabra` devuelve `&str` sin anotar: la regla 3 de elisión ata la
salida a `&self`. El recorrido es el de `primera_palabra` en
[3.4 Strings]{.ref}, y con un texto vacío devuelve un texto vacío.

## A fondo

**La regla 3 de elisión ata la salida a `&self`, no a `'a`.** La firma
completa de `primera_palabra` es
`fn primera_palabra<'s>(&'s self) -> &'s str`. El slice devuelto apunta al
texto original, que vive `'a`, pero la firma solo promete que dura lo que dure
el préstamo de la struct. La diferencia se nota cuando la struct muere antes
que el texto. Basta un método que devuelve el campo entero:

```rust,compile_fail
struct Resaltado<'a> {
    texto: &'a str,
}

impl<'a> Resaltado<'a> {
    fn completo(&self) -> &str {
        self.texto
    }
}

fn main() {
    let nota = String::from("Rust es rápido");
    let copia;
    {
        let r = Resaltado { texto: &nota };
        copia = r.completo();
    }   // E0597: `r` does not live long enough
    println!("{copia}");
}
```

`nota` sigue viva en el `println!`, pero la firma ató `copia` a `r`. Con
`fn completo(&self) -> &'a str` el mismo `main` compila e imprime el texto:
la salida queda atada al dato y no a la struct. Lo mismo vale para
`primera_palabra`: cuando un método devuelve una parte del dato prestado,
`&'a` es la firma más permisiva.

**Mientras la salida vive, todas las entradas con `'a` siguen prestadas.**
El compilador no sabe de cuál salió la referencia, así que protege a las dos.
Aquí `r` apunta al texto de `t`, y aun así `s` no se puede modificar:

```rust,compile_fail
fn mas_larga<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let mut s = String::from("hola");
    let t = String::from("hello world");
    let r = mas_larga(&s, &t);
    s.push('!');       // E0502: cannot borrow `s` as mutable
    println!("{r}");
}
```

**El compilador no calcula un mínimo.** Reúne restricciones y busca una
región que las cumpla. `'a` debe cubrir cada punto donde se usa la salida, y
ningún dato prestado con `'a` puede liberarse, moverse ni modificarse dentro
de ella. Dos entradas con regiones distintas caben en la misma `'a` porque
una referencia que vive más se acepta donde se pide una que vive menos. La
ecuación con `min` y `max` llega al mismo veredicto.

**Lo que garantizan juntas las reglas de la sección.** Ownership, el borrow
checker y los lifetimes rechazan al compilar las referencias colgantes, la
doble liberación y las carreras de datos, sin recolector de basura. Las fugas
de memoria quedan fuera de la garantía ([6.2 Rc, RefCell y árboles]{.ref}).
