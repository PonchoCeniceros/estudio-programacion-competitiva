# 9.7 · Una API con serde y axum

El servidor de [9.6 Un servidor mínimo]{.ref} respondía JSON armado a mano con
`json!`, y nunca recibió datos: sus rutas solo leían la URL. Una API recibe
datos en el cuerpo de la petición, y esos datos tienen forma: dos números, un
pedido con sus renglones. En el programa, esa forma es un struct.

Entre el texto que llega y el struct hay trabajo. Hay que comprobar que el
texto sea JSON, que cada campo exista y que cada valor tenga su tipo, y
responder algo útil cuando no. A mano son varias líneas por campo, y otras
tantas para armar el texto de la respuesta. El crate `serde` genera ese código
al compilar, a partir de la definición del struct, y `axum` lo llama.

## Definiciones y reglas

Serializar
:   convertir un valor de Rust en el texto o los bytes de un formato.

Deserializar
:   el camino inverso: construir un valor a partir de ese texto. Puede fallar.

Formato
:   la convención con que se escriben los datos: JSON, TOML, CSV.

Cuerpo
:   *(body)*: los datos que una petición o una respuesta HTTP lleva después de
    sus cabeceras.

::: {.reglas titulo="Las tres reglas de serde en una API"}
1. `serde` define dos traits, `Serialize` y `Deserialize`, y `derive` escribe
   sus `impl`. El formato lo pone otro crate.
2. Deserializar devuelve un `Result`. Si es `Ok`, el struct está completo y
   cada campo tiene su tipo.
3. En `axum`, `Json<T>` como parámetro deserializa el cuerpo y como retorno
   serializa la respuesta. Lo que no encaja se responde con un código 4xx sin
   llamar al manejador.
:::

## De un vistazo

| Pieza | Qué hace | De qué crate |
| :--- | :--- | :--- |
| `derive(Serialize)` | genera el `impl` que lleva el tipo a un formato | `serde` |
| `derive(Deserialize)` | genera el `impl` que lo construye desde un formato | `serde` |
| `to_string(&valor)` | valor a texto JSON | `serde_json` |
| `from_str::<T>(texto)` | texto JSON a `Result<T, Error>` | `serde_json` |
| `Json<T>` como parámetro | cuerpo de la petición a `T`, o un 4xx | `axum` |
| `Json<T>` como retorno | `T` a cuerpo de la respuesta | `axum` |

Las cuatro primeras filas son la primera mitad del capítulo: `serde` en un
programa sin servidor. Las dos últimas son la segunda: una API de dos rutas,
donde `axum` hace esas mismas llamadas por su cuenta.

## Primero, serde sin servidor

### [Regla 1:]{.prefijo} dos traits, y el formato aparte

El proyecto de prueba declara dos dependencias en su manifiesto:
`serde = { version = "1", features = ["derive"] }` y `serde_json = "1"`. El
programa convierte un struct en texto JSON, y un texto JSON en un struct:

```rust,ignore
// src/main.rs
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Suma {
    a: i64,
    b: i64,
}

fn main() -> Result<(), serde_json::Error> {
    let suma = Suma { a: 2, b: 40 };
    let texto = serde_json::to_string(&suma)?;
    println!("{texto}");

    let entrada = r#"{ "b": 5, "a": -3 }"#;
    let otra = serde_json::from_str::<Suma>(entrada)?;
    println!("{otra:?}");
    Ok(())
}
```

```salida
$ cargo run
{"a":2,"b":40}
Suma { a: -3, b: 5 }
```

`r#"..."#` es un literal de texto crudo: las comillas de adentro no se escapan.
`to_string` recibe una referencia a un tipo que implemente `Serialize` y
devuelve el texto. `from_str` va en sentido contrario, y el turbofish dice qué
tipo construir ([4.2 Generics]{.ref}). Los campos se buscan por nombre: en la
entrada, `b` viene antes que `a`.

El programa no dice cómo se escribe una llave ni dónde va una coma, y no tiene
un `impl` a la vista. `#[derive(Serialize, Deserialize)]` los escribe: es una
macro procedural, compilada en un crate aparte
([7.6 Macros y atributos]{.ref}). Por eso el manifiesto pide la feature
`derive` ([7.2 Crates y Cargo]{.ref}). Sin ella, el error es *cannot find derive
macro `Serialize` in this scope*: el trait existe, la macro no.

`serde` no sabe nada de JSON. Define los dos traits y un modelo de datos
pequeño: enteros, textos, listas, mapas. El `impl` derivado describe el struct
con ese modelo, y un crate de formato traduce entre el modelo y un texto. La
prueba es cambiar de formato sin tocar el struct: con el crate `toml` en el
manifiesto, `toml::to_string(&suma)` devuelve las dos líneas de la figura.

### [Regla 2:]{.prefijo} si es `Ok`, el struct está completo

`from_str` devuelve un `Result` ([5.2 Result]{.ref}). El programa siguiente le
da cuatro textos y abre cada resultado con `match`:

```rust,ignore
// src/main.rs
use serde::Deserialize;

#[derive(Debug, Deserialize)]
struct Suma { a: i64, b: i64 }

fn main() {
    let casos = [
        r#"{ "a": 2 }"#,
        r#"{ "a": 2, "b": "tres" }"#,
        r#"{ "a": 2, "b": "#,
        r#"{ "a": 2, "b": 3, "c": 4 }"#,
    ];
    for texto in casos {
        match serde_json::from_str::<Suma>(texto) {
            Ok(suma) => println!("{suma:?}"),
            Err(e) => println!("{e}"),
        }
    }
}
```

```salida
$ cargo run
missing field `b` at line 1 column 10
invalid type: string "tres", expected i64 at line 1 column 21
EOF while parsing a value at line 1 column 15
Suma { a: 2, b: 3 }
```

Los tres primeros fallan, cada uno con su causa y su posición en el texto. Al
primero le falta un campo. El segundo trae `b` con otro tipo. El tercero se
corta antes de cerrar: no es JSON. El cuarto trae un campo de más, `c`, y se
acepta: lo que el struct no tiene se ignora.

Los mensajes salen del `impl` derivado, que conoce los nombres y los tipos de
los campos. El programa no escribió una sola comparación. Después del `Ok`,
`suma.a` y `suma.b` existen y son `i64`, y nada vuelve a revisarlo.

### Tres ajustes de uso diario

Un JSON real trae campos que pueden faltar, nombres con otra convención y
datos dentro de datos. El struct declara las tres cosas:

```rust,ignore
// src/main.rs
use serde::Deserialize;

#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
struct Pedido {
    id_cliente: u32,
    nota: Option<String>,
    #[serde(rename = "items")]
    renglones: Vec<Renglon>,
}

#[derive(Deserialize)]
struct Renglon { producto: String, cantidad: u32 }

fn main() -> Result<(), serde_json::Error> {
    let entrada = r#"{ "idCliente": 7, "items": [
        { "producto": "tuerca", "cantidad": 50 } ] }"#;
    let pedido: Pedido = serde_json::from_str(entrada)?;
    println!("{}", pedido.id_cliente);            // 7
    println!("{:?}", pedido.nota);                // None
    let primero = &pedido.renglones[0];
    println!("{} {}", primero.producto, primero.cantidad);
    Ok(())                                        // tuerca 50
}
```

- Un campo `Option<T>` es opcional. La entrada no trae `nota`, y el campo
  queda en `None` ([5.1 Option]{.ref}). Al serializar, un `None` sale como
  `null`.
- Los nombres se traducen con un atributo que la macro lee. `rename_all`
  convierte `id_cliente` en `idCliente` para todo el struct. `rename` cambia un
  solo campo: `renglones` viaja como `items`.
- Los tipos se componen. `Vec<Renglon>` funciona porque `Renglon` también
  deriva el trait ([5.3 Vec]{.ref}). Sin ese `derive`, el error es el E0277 de
  [7.6 Macros y atributos]{.ref}: *the trait bound
  `Renglon: serde::Deserialize<'de>` is not satisfied*.

## El programa, línea por línea

La API tiene dos rutas. `GET /saludo/{nombre}` es la de 9.6. `POST /suma`
recibe dos números en el cuerpo y responde su suma. El manifiesto declara tres
dependencias:

```toml
# Cargo.toml
[dependencies]
axum = "0.8.9"
serde = { version = "1.0.229", features = ["derive"] }
tokio = { version = "1.54.1", features = ["full"] }
```

`serde_json` no aparece: `axum` lo trae como dependencia suya, y el programa
nunca lo nombra. `features = ["full"]` es la forma corta que 9.6 mencionó: todo
`tokio`, sin elegir piezas. El programa completo es este:

```rust,ignore
// src/main.rs
use axum::{
    Json, Router, extract::Path, routing::get, routing::post,
};
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct Suma { a: i64, b: i64 }

#[derive(Serialize)]
struct Resultado {
    resultado: i64,
}

async fn saludo(Path(nombre): Path<String>) -> String {
    format!("hola, {nombre}")
}

async fn suma(Json(datos): Json<Suma>) -> Json<Resultado> {
    Json(Resultado {
        resultado: datos.a + datos.b,
    })
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let api = Router::new()
        .route("/saludo/{nombre}", get(saludo))
        .route("/suma", post(suma));
    let listener =
        tokio::net::TcpListener::bind("127.0.0.1:3000")
            .await?;
    println!("escuchando en http://127.0.0.1:3000");
    axum::serve(listener, api).await?;
    Ok(())
}
```

| En el código | Qué es | Explicado en |
| :--- | :--- | :--- |
| `derive(Deserialize)` | macro de un crate | [7.6 Macros y atributos]{.ref} |
| `Suma`, `Resultado` | entrada y salida | [2.2 Structs]{.ref} |
| `Json(datos)` en la firma | patrón en un parámetro | [2.4 Patrones]{.ref} |
| `Json(Resultado { .. })` | un tuple struct | [2.2 Structs]{.ref} |
| `post(suma)` | función como valor | [4.3 Closures]{.ref} |
| `Path`, `Router`, `serve` | lo mismo que en 9.6 | [9.6 Un servidor mínimo]{.ref} |

El `main`, el enrutador y `saludo` son los de 9.6, con otros nombres de
variable. Lo nuevo son dos structs, un manejador y `post`. `Suma` es lo que la
ruta acepta y `Resultado` es lo que entrega: el contrato de la ruta, escrito
en el lenguaje. Cada uno deriva solo el trait que usa.

### [Regla 3:]{.prefijo} `Json<T>`, de entrada y de salida

`Json` es un tuple struct de `axum` con un solo campo. Aquí está en los dos
lados de la firma, y cada lado pide un trait distinto.

Como parámetro, `Json<Suma>` es un extractor: pide el cuerpo de la petición,
convertido a `Suma`. `axum` lee los bytes y llama a `serde_json`, como el
`from_str` de la primera mitad. Si el resultado es `Ok`, llama al manejador. El
patrón `Json(datos)` desarma el envoltorio, como `Path(nombre)`
([2.4 Patrones]{.ref}), y `datos` es un `Suma` ya validado. Este lado exige
`Suma: Deserialize`.

Como retorno, `Json<Resultado>` es el camino inverso: `axum` serializa el
struct y agrega la cabecera `content-type`. Este lado exige
`Resultado: Serialize`. El cuerpo del manejador es una suma: no revisa nada,
porque no le llega nada sin revisar.

`post` viene del mismo módulo que `get` y se usa igual: asocia el manejador al
método POST, el que por convención manda un cuerpo. Una ruta puede atender los
dos métodos: `get(ver).post(crear)`.

### La prueba con `curl`

`cargo run` imprime `escuchando en http://127.0.0.1:3000` y espera.
`/saludo/Ferris` responde `hola, Ferris`, como en 9.6. Para `/suma`, `-H`
agrega una cabecera, y `-d` manda un cuerpo y cambia el método a POST:

```salida
$ URL=http://127.0.0.1:3000/suma
$ CT='Content-Type: application/json'
$ curl -i $URL -H "$CT" -d '{"a": 2, "b": 40}'
HTTP/1.1 200 OK
content-type: application/json
content-length: 16
date: Thu, 26 Nov 2026 22:48:17 GMT

{"resultado":42}
```

### Cuatro peticiones que no encajan

Las peticiones mal hechas enseñan más. De cada respuesta se copian la línea
de estado y el cuerpo. El cuerpo llega en una sola línea, partida aquí para
caber en la página:

```salida
$ curl -i $URL -H "$CT" -d '{"a": 2}'
HTTP/1.1 422 Unprocessable Entity
Failed to deserialize the JSON body into the target type:
missing field `b` at line 1 column 8

$ curl -i $URL -H "$CT" -d '{"a": 2, "b": "tres"}'
HTTP/1.1 422 Unprocessable Entity
Failed to deserialize the JSON body into the target type:
b: invalid type: string "tres", expected i64 at line 1
column 20
```

En las dos el texto es JSON válido, pero no tiene la forma de `Suma`. Después
de los dos puntos está el mensaje de `serde` de la regla 2. `axum` le antepone
el campo, `b:`, cuando lo conoce. Las otras dos fallan antes:

```salida
$ curl -i $URL -H "$CT" -d '{"a": 2, "b": '
HTTP/1.1 400 Bad Request
Failed to parse the request body as JSON: b: EOF while
parsing a value at line 1 column 14

$ curl -i $URL -d '{"a": 2, "b": 40}'
HTTP/1.1 415 Unsupported Media Type
Expected request with `Content-Type: application/json`
```

En la primera el texto no es JSON: `axum` responde 400 a los errores de
sintaxis de `serde_json` y 422 a los de datos. En la segunda, sin `-H`, `curl`
declara otro tipo de contenido, y el extractor la rechaza sin leer el cuerpo.

Son tres códigos distintos, con su mensaje en texto plano, y el archivo no
tiene una línea que los mencione. La figura ubica cada uno, junto al 405 de 9.6.

### El error de compilación: falta un `derive`

El descuido usual es escribir el struct y olvidar el atributo. Aquí `Suma`
quedó sin su `#[derive(Deserialize)]`:

```rust,ignore,compile_fail
// src/main.rs
struct Suma { a: i64, b: i64 }
```

```salida
warning: unused import: `Deserialize`
5 | use serde::{Deserialize, Serialize};
  |             ^^^^^^^^^^^
error[E0277]: the trait bound `fn(Json<Suma>) -> impl
              Future<Output = Json<Resultado>> {suma}:
              Handler<_, _>` is not satisfied
28 |         .route("/suma", post(suma));
   |                         ---- ^^^^ the trait
   |                         |    `Handler<_, _>` is not
   |                         |    implemented for fn item
   |                         |    `fn(Json<Suma>) -> impl
   |                         |    Future<Output =
   |                         |    Json<Resultado>> {suma}`
   |                         required by a bound
   |                         introduced by this call
   = note: Consider using `#[axum::debug_handler]` to
           improve the error message
```

Es el error de `Handler` de 9.6: señala el `route` y no dice qué condición
falló. `Json<Suma>` solo es un extractor si `Suma` implementa `Deserialize`. Sin
el `impl`, la función deja de ser un manejador. La línea que orienta es el
aviso de arriba: un `Deserialize` importado que nadie usa.

La nota final lleva al mensaje preciso. Con `#[axum::debug_handler]` sobre
`suma`, como en 9.6, el error señala `Json<Suma>` en la firma y dice *the trait
bound `Suma: serde::Deserialize<'de>` is not satisfied*. Quitarle el `derive` a
`Resultado` da el mismo par de errores, con `Resultado: serde::Serialize` y el
tipo de retorno señalado.

## Aplicación

Una ruta más, `POST /promedio`, junta las dos mitades. Recibe una lista de
números y un nombre opcional, y responde cuántos son y su promedio. Al archivo
se le agregan dos structs, una función, un manejador y una línea en el
enrutador: `.route("/promedio", post(promediar))`.

```rust,ignore
// src/main.rs
#[derive(Deserialize)]
struct Muestra {
    nombre: Option<String>,
    valores: Vec<f64>,
}

#[derive(Serialize)]
struct Promedio {
    nombre: String,
    cuenta: usize,
    promedio: Option<f64>,
}

fn promedio(valores: &[f64]) -> Option<f64> {
    if valores.is_empty() {
        return None;
    }
    let total: f64 = valores.iter().sum();
    Some(total / valores.len() as f64)
}

async fn promediar(Json(m): Json<Muestra>) -> Json<Promedio> {
    Json(Promedio {
        nombre: m.nombre.unwrap_or("sin nombre".to_string()),
        cuenta: m.valores.len(),
        promedio: promedio(&m.valores),
    })
}
```

```salida
$ URL=http://127.0.0.1:3000/promedio
$ curl $URL -H "$CT" \
    -d '{"nombre": "lluvia", "valores": [12.5, 0, 31]}'
{"nombre":"lluvia","cuenta":3,"promedio":14.5}
$ curl $URL -H "$CT" -d '{"valores": [8, 9, 10]}'
{"nombre":"sin nombre","cuenta":3,"promedio":9.0}
$ curl $URL -H "$CT" -d '{"valores": []}'
{"nombre":"sin nombre","cuenta":0,"promedio":null}
$ curl $URL -H "$CT" -d '{"valores": [8, "nueve", 10]}'
Failed to deserialize the JSON body into the target type:
valores[1]: invalid type: string "nueve", expected f64 at
line 1 column 23
```

Las dos `Option` hacen trabajos distintos. La de `Muestra` acepta una entrada
sin `nombre`, y `unwrap_or` pone el default ([5.1 Option]{.ref}). La de
`Promedio` responde `null` cuando la lista está vacía: ese promedio no existe,
y el tipo lo dice. Los enteros `8, 9, 10` se aceptan como `f64`.

El último caso responde 422, y el mensaje trae el camino hasta el dato malo:
`valores[1]`. `promedio` recibe un slice y no sabe de JSON ni de HTTP: se
prueba con un `#[test]` normal ([7.3 Tests]{.ref}).

## A fondo

**`Json` va al final de los parámetros.** Un manejador puede llevar varios
extractores, pero el cuerpo de una petición se lee una sola vez. `Path` y
`State` no lo tocan. `Json` lo consume, y `axum` exige que sea el último. Con
`Json<Suma>` antes de un `Path<i64>`, `debug_handler` reporta *`Json<_>`
consumes the request body and thus must be the last argument to the handler
function*. Sin el atributo, es el E0277 de `Handler`.

**`Value` y `json!` siguen teniendo su lugar.** `serde_json::Value` es un enum
que representa cualquier JSON ([2.3 Enums]{.ref}). Sirve cuando la forma no se
conoce al compilar, o para una respuesta de un solo campo, como en 9.6. A
cambio, cada lectura se revisa en ejecución: `v["nada"]` no falla, da `null`.

**`Deserialize` lleva un lifetime.** El trait completo es `Deserialize<'de>`,
y así aparece en los errores. `'de` es el lifetime del texto de entrada
([3.6 Lifetimes]{.ref}): permite que un campo `&'de str` apunte a ese texto en
lugar de copiarlo. En un struct dueño de sus datos no cambia nada.

**No hay reflexión en ejecución.** El `impl` derivado es código normal, que el
compilador especializa para cada formato ([4.2 Generics]{.ref}). El costo
está en la compilación.

**Tipos correctos no son valores correctos.** El 422 revisa la forma, no el
contenido. `{"a": 9223372036854775807, "b": 1}` pasa la validación, y la suma
se desborda ([1.2 Tipos escalares]{.ref}). En modo debug la tarea hace panic:
`curl` reporta *Empty reply from server* y el servidor sigue atendiendo. Un
rango permitido o un `checked_add` son reglas del programa, y van en el
manejador. [9.8 Un servidor MCP]{.ref} recibe sus parámetros con estas mismas
piezas, y los crates de formato están en [10.1 El ecosistema]{.ref}.
