# 9.6 · Un servidor mínimo

Las secciones 8 y 9 presentaron sus piezas una por una, cada una en un programa
de quince líneas hecho para mostrarla. Un programa real las usa todas a la vez,
mezcladas con tipos de crates que ningún capítulo describió. La duda razonable
es si lo aprendido alcanza para leerlo.

Este capítulo arma un servidor HTTP de treinta y seis líneas con tres crates
externos y lo recorre línea por línea. Cada línea se explica con un capítulo
anterior. Lo único nuevo son los nombres que traen los crates.

## Definiciones y reglas

Ruta
:   el camino de una URL, como `/visitas`, junto con el método HTTP que acepta.

Manejador
:   *(handler)*: la función que el servidor llama cuando llega una petición a
    una ruta.

Enrutador
:   *(router)*: la tabla que asocia cada ruta con su manejador.

Extractor
:   un tipo que, puesto como parámetro de un manejador, dice qué parte de la
    petición recibe.

Estado
:   un valor que vive mientras el servidor corre y que todos los manejadores
    pueden usar.

Las reglas son las que el crate `axum` impone a un manejador, dichas con el
vocabulario del libro:

::: {.reglas titulo="Las tres reglas del manejador"}
1. Un manejador es una función o una closure `async`. Sus parámetros dicen qué
   toma de la petición, y su tipo de retorno, qué responde.
2. El estado entra al enrutador una vez y cada petición recibe un clon. Lo que
   cambia va en `Arc<Mutex<T>>`.
3. El futuro de un manejador tiene que ser `Send`: ningún valor que no lo sea
   puede seguir vivo en un `.await`.
:::

## De un vistazo

El servidor tiene tres rutas. `/` responde un texto fijo. `/saludo/{nombre}` lee
un parámetro de la ruta. `/visitas` cuenta cuántas veces se ha pedido y responde
JSON: su contador lo comparten todas las peticiones.

El proyecto son dos archivos. `cargo new api` crea el paquete
([7.2 Crates y Cargo]{.ref}), y a su manifiesto se le agregan tres
dependencias:

```toml
# Cargo.toml
[dependencies]
axum = "0.8"
serde_json = "1"

[dependencies.tokio]
version = "1"
default-features = false
features = ["rt-multi-thread", "macros", "net"]
```

El otro archivo es el programa completo:

```rust,ignore
// src/main.rs
use std::error::Error;
use std::sync::{Arc, Mutex};

use axum::extract::{Path, State};
use axum::{Json, Router, routing::get};
use serde_json::{Value, json};
use tokio::net::TcpListener;

type Contador = Arc<Mutex<u64>>;

async fn saludo(Path(nombre): Path<String>) -> String {
    format!("hola, {nombre}\n")
}

async fn visitas(State(c): State<Contador>) -> Json<Value> {
    let n = {
        let mut cuenta = c.lock().unwrap();
        *cuenta += 1;
        *cuenta
    };
    Json(json!({ "visitas": n }))
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn Error>> {
    let contador: Contador = Arc::new(Mutex::new(0));
    let app = Router::new()
        .route("/", get(|| async { "servidor en pie\n" }))
        .route("/saludo/{nombre}", get(saludo))
        .route("/visitas", get(visitas))
        .with_state(contador);
    let escucha = TcpListener::bind("127.0.0.1:3000").await?;
    axum::serve(escucha, app).await?;
    Ok(())
}
```

Y esta es la tabla de dónde sale cada línea:

| En el código | Qué es | Explicado en |
| :--- | :--- | :--- |
| `use axum::extract::...` | rutas de módulos de un crate | [7.1 Módulos]{.ref} |
| `type Contador` | alias de un tipo largo | [6.2 Rc, RefCell y árboles]{.ref} |
| `Arc<Mutex<u64>>` | varios dueños y un candado | [8.3 Estado compartido]{.ref} |
| `async fn` | función que devuelve un futuro | [9.2 async, await y Future]{.ref} |
| `Path(nombre): Path<String>` | patrón en un parámetro | [2.4 Patrones]{.ref} |
| `get(saludo)` | una función pasada como valor | [4.3 Closures]{.ref} |
| el `lock()` en su bloque | el *guard* muere antes de responder | [9.4 Send en las tareas]{.ref} |
| `json!({ ... })` | macro de un crate | [7.6 Macros y atributos]{.ref} |
| `#[tokio::main]` | atributo que reescribe `main` | [9.3 El runtime]{.ref} |
| `Result<(), Box<dyn Error>>` | errores desde `main` | [7.4 Manejo de errores idiomático]{.ref} |
| `.await?` | esperar, y propagar el error | [9.2 async, await y Future]{.ref}, [5.2 Result]{.ref} |

Ninguna fila remite a un concepto que el libro no tenga. `Router`, `Path`,
`State`, `Json` y `get` son nombres de `axum`: se aprenden en su documentación.

## El programa, línea por línea

### Las dependencias y sus features

La tabla `[dependencies.tokio]` es otra manera de escribir una dependencia que
lleva más de un dato: equivale a `tokio = { version = "1", ... }` en una línea.

`tokio` es el runtime: ejecuta los futuros ([9.3 El runtime]{.ref}). `axum`
recibe las peticiones y llama al manejador de cada ruta. `serde_json` escribe el
JSON de la respuesta. En esta compilación Cargo resolvió `axum` 0.8.9,
`serde_json` 1.0.154 y `tokio` 1.54.1, y el `Cargo.lock` quedó con 52 paquetes:
las tres dependencias traen las suyas.

Las features son partes opcionales de un crate. `default-features = false`
apaga las que `tokio` trae activas, y la lista enciende las tres que el programa
usa: `rt-multi-thread` es el planificador de varios hilos, `macros` es
`#[tokio::main]` y `net` son los sockets. Los tutoriales suelen pedir
`features = ["full"]`, que compila todo el crate.

### El `main`: un atributo y un `Result`

`#[tokio::main]` es un atributo que reescribe la función que lo sigue
([7.6 Macros y atributos]{.ref}). El `main` que queda es síncrono: crea el
runtime y le entrega el cuerpo original como un futuro
([9.3 El runtime]{.ref}). Por eso el cuerpo puede usar `.await`.

El tipo de retorno es el de [7.4 Manejo de errores idiomático]{.ref}:
`Box<dyn Error>` acepta cualquier error, y cada `?` propaga el suyo. Hay dos.
`bind` falla con un `io::Error` si no consigue la dirección. Con el puerto ya
ocupado por otro proceso, el programa termina con código 1 y este mensaje:

```salida
$ cargo run
Error: Os { code: 48, kind: AddrInUse,
            message: "Address already in use" }
```

`axum::serve` atiende conexiones hasta que el proceso se detiene con Ctrl+C. Su
futuro no termina por sí solo, así que el `Ok(())` final existe para que los
tipos cuadren.

### [Regla 1:]{.prefijo} funciones `async` con extractores

`Router::new()` crea un enrutador vacío y cada `route` le agrega una fila: una
ruta y, con `get`, el manejador de las peticiones GET. `get` recibe una función
como valor ([4.3 Closures]{.ref}). Las tres rutas muestran dos
formas: una closure y dos funciones con nombre.

La de `/` es una closure sin parámetros que devuelve un bloque `async`. No
captura nada. El bloque es un futuro que produce un `&'static str`
([3.6 Lifetimes]{.ref}).

`saludo` es una `async fn`: al llamarla no ejecuta nada, devuelve un futuro
([9.2 async, await y Future]{.ref}). Su parámetro es un patrón. `Path` es un
struct de tupla de `axum`, y `Path(nombre)` lo desarma en la firma, como
`(a, b): (i32, i32)` desarma una tupla ([2.4 Patrones]{.ref}). El tipo
`Path<String>` es el extractor: pide el segmento `{nombre}` de la ruta,
convertido a `String`.

El tipo de retorno también es un contrato. `axum` define un trait para lo que
puede convertirse en respuesta y lo implementa para `&'static str`, `String` y
`Json<T>`, entre otros ([4.1 Traits]{.ref}). Los dos primeros salen como texto.
`Json` serializa su contenido y pone la cabecera `content-type`.

### [Regla 2:]{.prefijo} el estado va en `Arc<Mutex<T>>`

El contador tiene que sobrevivir a cada petición y ser el mismo para todas.
Son los dos problemas de [8.3 Estado compartido]{.ref}: `Arc` da varios dueños
a un valor entre hilos, y `Mutex` deja que uno a la vez lo modifique. El alias
`Contador` evita repetir el tipo ([6.2 Rc, RefCell y árboles]{.ref}).

`with_state(contador)` mueve el `Arc` al enrutador. En cada petición, el
extractor `State<Contador>` entrega un clon: otro puntero al mismo `Mutex`, con
la cuenta de referencias aumentada en uno.

El manejador toma el candado dentro de un bloque. `lock()` devuelve un `Result`
porque el mutex queda envenenado si un hilo hace panic con el candado tomado; el
`unwrap` lo descarta. El *guard* se usa como un `&mut u64`. El bloque es una
expresión ([1.4 Todo es una expresión]{.ref}): su valor es la copia `*cuenta`, y
al cerrar la llave el *guard* muere y el candado se suelta. La respuesta se
construye con `n`, ya sin candado. `json!` es una macro de `serde_json` que
recibe sintaxis de JSON y devuelve un `Value` ([7.6 Macros y atributos]{.ref}).

### Arrancar y esperar

`TcpListener::bind` reserva la dirección. Es el `TcpListener` de `tokio`, no el
de `std`: `bind` devuelve un futuro, y `.await` lo espera sin bloquear el hilo.
`127.0.0.1` solo acepta conexiones de la misma máquina.

`axum::serve(escucha, app)` recibe las conexiones y entrega cada una al
runtime como una tarea ([9.3 El runtime]{.ref}). La figura sigue una petición a
`/visitas` desde que llega hasta que sale la respuesta:

### La prueba con `curl`

`cargo run` compila y deja el servidor esperando. Desde otra terminal:

```salida
$ curl http://127.0.0.1:3000/
servidor en pie
$ curl http://127.0.0.1:3000/saludo/Ferris
hola, Ferris
$ curl http://127.0.0.1:3000/saludo/Mar%C3%ADa
hola, María
```

`%C3%AD` son los dos bytes de la `í` en UTF-8 ([3.4 Strings]{.ref}), en la
forma en que una URL los admite. `Path` los decodifica antes de entregar el
`String`. La tercera ruta cuenta, y con `-i` se ven las cabeceras de la
respuesta:

```salida
$ curl http://127.0.0.1:3000/visitas
{"visitas":1}
$ curl http://127.0.0.1:3000/visitas
{"visitas":2}
$ curl -i http://127.0.0.1:3000/visitas
HTTP/1.1 200 OK
content-type: application/json
content-length: 13
date: Wed, 25 Nov 2026 10:46:06 GMT

{"visitas":3}
```

El enrutador responde solo lo que el programa no previó: `/nada` da
`404 Not Found`, y un POST a `/visitas` da `405 Method Not Allowed`.

El contador pasó de 1 a 3 con peticiones en fila. La prueba que importa es con
peticiones simultáneas. `xargs -P 20` mantiene veinte `curl` corriendo a la vez
hasta completar doscientos:

```salida
$ seq 200 | xargs -P 20 -I{} \
    curl -s -o /dev/null http://127.0.0.1:3000/visitas
$ curl http://127.0.0.1:3000/visitas
{"visitas":204}
```

Tres de antes, doscientas simultáneas y la que pregunta: 204. `*cuenta += 1`
lee, suma y escribe. El runtime reparte las tareas entre varios hilos, y sin
candado dos de ellas podrían leer el mismo valor y perder una suma. El `Mutex`
hace que cada tarea complete los tres pasos sola. Es el programa de los ocho
hilos de [8.3 Estado compartido]{.ref}, con tareas en lugar de hilos.

### [Regla 3:]{.prefijo} el futuro del manejador debe ser `Send`

Un cambio pequeño rompe la compilación. El manejador ahora deja un registro de
cada visita. `registrar` es otra `async fn`, que recibe el número y lo
imprime. El manejador la espera con el candado tomado:

```rust,ignore,compile_fail
// src/main.rs
async fn visitas(State(c): State<Contador>) -> Json<Value> {
    let mut cuenta = c.lock().unwrap();
    *cuenta += 1;
    registrar(*cuenta).await;
    Json(json!({ "visitas": *cuenta }))
}
```

```salida
error[E0277]: the trait bound `fn(State<Arc<Mutex<u64>>>)
              -> ... {visitas}: Handler<_, _>` is not
              satisfied
33 |         .route("/visitas", get(visitas))
   |                            --- ^^^^^^^ the trait
   |                            |  `Handler<_, _>` is not
   |                            |  implemented for fn item
   |                            |  `fn(State<Arc<Mutex<u64>>>)
   |                            |  -> impl Future<Output =
   |                            |  ...> {visitas}`
   |                            required by a bound
   |                            introduced by this call
   = note: Consider using `#[axum::debug_handler]` to
           improve the error message
```

El mensaje señala la línea 33 del archivo, la del `route`, que no cambió. No
menciona `Send`, ni el `MutexGuard`, ni el `.await`. Dice que `visitas` no
implementa `Handler`, el trait que `get` exige a su argumento con un límite
`H: Handler<T, S>` ([4.2 Generics]{.ref}). `axum` implementa ese trait para las funciones que
cumplen todas sus condiciones, y una de ellas es que el futuro sea `Send`. Al
fallar una, el compilador solo puede decir que el trait no está.

La línea que importa es la nota: usar `#[axum::debug_handler]`. Es un atributo
que revisa el manejador y reporta la condición que falla. Vive detrás de una
feature, así que el manifiesto cambia a
`axum = { version = "0.8", features = ["macros"] }`. Sin ella el error es
E0433, *could not find `debug_handler` in `axum`*, con la nota *the item is
gated behind the `macros` feature*. Con el atributo sobre `visitas`, que ahora
empieza en la línea 21, aparece un error nuevo antes del anterior:

```salida
error: future cannot be sent between threads safely
20 | #[axum::debug_handler]
   | ^^^^^^^^^^^^^^^^^^^^^^ future returned by `visitas`
   |                        is not `Send`
   = help: within `impl Future<Output = Json<Value>>`, the
           trait `Send` is not implemented for
           `std::sync::MutexGuard<'_, u64>`
note: future is not `Send` as this value is used across an
      await
22 |     let mut cuenta = c.lock().unwrap();
   |         ---------- has type
   |                    `std::sync::MutexGuard<'_, u64>`
   |                    which is not `Send`
23 |     *cuenta += 1;
24 |     registrar(*cuenta).await;
   |                        ^^^^^ await occurs here, with
   |                              `mut cuenta` maybe used
   |                              later
```

Es el error de [9.4 Send en las tareas]{.ref}, con las mismas tres piezas: el
valor, su tipo y el `.await` que cruza. `MutexGuard` no es `Send`
([8.2 Send y Sync]{.ref}). Cada conexión corre en una tarea que puede
reanudarse en otro hilo, y un futuro que guarda un *guard* a través de la pausa
no puede cambiar de hilo.

El arreglo es el del programa original. El bloque `let n = { ... };` suelta el
*guard* al cerrar la llave, y `registrar(n).await` va después, con la copia.
Un `Rc` vivo en un `.await` da el mismo E0277 sobre `Handler`, y se lee igual.

## Aplicación

Una ruta nueva que devuelve las iniciales de un nombre. La función `iniciales`
es la de [5.7 Iteradores a fondo]{.ref}, copiada sin cambiar una letra: recibe
un `&str` y devuelve un `String`. No es `async` y no sabe que existe un
servidor. Al archivo se le agregan la función, el manejador `siglas` que la
llama y una ruta en el enrutador: `/iniciales/{nombre}`, con `get(siglas)`.

```rust,ignore
// src/main.rs
fn iniciales(nombre: &str) -> String {
    nombre
        .split_whitespace()
        .filter_map(|palabra| palabra.chars().next())
        .flat_map(|c| c.to_uppercase())
        .collect()
}

async fn siglas(Path(nombre): Path<String>) -> Json<Value> {
    let letras = iniciales(&nombre);
    Json(json!({ "nombre": nombre, "iniciales": letras }))
}
```

```salida
$ curl http://127.0.0.1:3000/iniciales/ada%20lovelace
{"iniciales":"AL","nombre":"ada lovelace"}
$ curl http://127.0.0.1:3000/iniciales/%C3%A1ngela%20ruiz
{"iniciales":"ÁR","nombre":"ángela ruiz"}
```

El manejador tiene dos líneas y las dos son de frontera: sacar el dato de la
petición y envolver el resultado. `iniciales(&nombre)` presta el `String`, y
después `json!` todavía puede usarlo ([3.3 Borrowing]{.ref}). El manejador no
tiene ningún `.await`, y aun así es una `async fn`: la regla 1 lo pide. La
función de dominio se prueba con un `#[test]` normal, sin levantar el servidor
([7.3 Tests]{.ref}).

## A fondo

**Una tarea por conexión.** `axum::serve` es un bucle: acepta una conexión, la
entrega al runtime con `tokio::spawn` y vuelve a aceptar
([9.3 El runtime]{.ref}). Doscientas conexiones son doscientas tareas sobre
unos pocos hilos. De ahí sale la regla 3: `spawn` exige un futuro `Send` y
`'static`, y el futuro del manejador forma parte de esa tarea.

**El estado va en `Arc` porque cada tarea necesita su dueño.** Una tarea
`'static` no puede guardar una referencia a una variable de `main`. `with_state`
exige que el estado implemente `Clone`, y cada petición recibe su clon. Clonar
un `Arc` cuesta un incremento atómico ([8.3 Estado compartido]{.ref}). El
`Mutex` de `std` basta mientras el *guard* no cruce un `.await`. El de `tokio`,
con `lock().await`, solo hace falta cuando el candado debe seguir tomado
durante la espera ([9.4 Send en las tareas]{.ref}).

**Los extractores y las respuestas son traits.** `Path` y `State` implementan
un trait de `axum` que sabe construirlos a partir de una petición, y los tipos
de retorno implementan otro que sabe convertirlos en respuesta. `Handler` está
implementado con genéricos para las funciones `async` cuyos parámetros cumplen
el primero y cuyo resultado cumple el segundo ([4.1 Traits]{.ref}). Por eso un
manejador mal escrito aparece como un trait que falta.

**Cargo une las features de todo el árbol.** Sin `rt-multi-thread`, el error
es *The default runtime flavor is `multi_thread`, but the `rt-multi-thread`
feature is disabled*. En cambio, quitar `macros` y `net` del manifiesto no
rompe nada: `axum` ya se las pide a `tokio`, y Cargo compila cada crate una
vez con la unión de lo que le piden. El manifiesto las declara porque
`src/main.rs` las usa directamente.

**La versión de un crate es parte del programa.** La sintaxis `{nombre}` en las
rutas es de `axum` 0.8; la 0.7 escribía `:nombre`. Un requisito `"0.8"` no
acepta `0.9` ([7.2 Crates y Cargo]{.ref}), y el `Cargo.lock` fija lo demás.

**Lo que este servidor no tiene.** No valida lo que recibe, no guarda nada
fuera de la memoria, no responde errores con su código HTTP y no tiene
pruebas. Tampoco calcula nada pesado: un cálculo largo dentro de un manejador
ocupa un hilo del runtime ([9.5 async o hilos]{.ref}). Cada uno de esos
faltantes es un crate o una técnica de los proyectos aplicados: una base de
datos, un enum de error que se convierte en respuesta
([7.4 Manejo de errores idiomático]{.ref}), tests de integración
([7.3 Tests]{.ref}). Ninguno pide sintaxis que el libro no haya presentado.
