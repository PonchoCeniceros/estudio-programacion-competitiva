# 9.8 · Un servidor MCP

Un asistente de IA no puede sumar dos números con un programa ajeno si nadie
le dice que ese programa existe, qué datos pide y cómo llamarlo. El *Model
Context Protocol* (MCP) fija esa conversación: un programa anuncia las
operaciones que ofrece, y el asistente las descubre y las pide con mensajes de
forma conocida.

Este capítulo recorre un servidor MCP de 137 líneas repartidas en seis
archivos. Ofrece dos operaciones, saludar y sumar, por dos caminos: HTTP y la
entrada y salida estándar. Como en [9.6 Un servidor mínimo]{.ref}, no queda
sintaxis por aprender: solo un crate por conocer, `rmcp`. Lo que el programa
enseña es su orden: cuatro capas, y cada una ignora a las de fuera.

## Definiciones y reglas

Herramienta
:   *(tool)*: una operación que un servidor MCP ofrece a un cliente, que es
    el programa del asistente. Tiene nombre, descripción y esquema de entrada.

Esquema de entrada
:   un documento *JSON Schema* que dice qué campos recibe la herramienta, de
    qué tipo y cuáles son obligatorios. El modelo lo lee para armar la llamada.

Transporte
:   el canal por el que viajan los mensajes. Este programa tiene dos: *stdio*
    y HTTP.

::: {.reglas titulo="Las tres reglas de las capas"}
1. La lógica vive en funciones de Rust puro. Cada capa depende de la de dentro
   y nunca al revés.
2. Cada herramienta declara su entrada en un struct. `Deserialize` la lee y
   `JsonSchema` la describe.
3. En stdio, la salida estándar es del protocolo. Los mensajes propios salen
   por `eprintln!`.
:::

El programa tiene cuatro capas. Una operación nueva se escribe de dentro
hacia fuera, y ningún archivo de transporte cambia. Esta es la tabla de dónde
sale cada pieza:

| En el código | Qué es | Explicado en |
| :--- | :--- | :--- |
| `src/lib.rs`, dos binarios | paquete con librería | [7.2 Crates y Cargo]{.ref} |
| `pub mod`, `pub use` | la API de la librería | [7.1 Módulos]{.ref} |
| `derive(Deserialize)` | `derive` de un crate | [9.7 Una API con serde y axum]{.ref} |
| `ToolRouter<Self>` | un tipo genérico | [4.2 Generics]{.ref} |
| `#[tool_router]` | atributo que reescribe | [7.6 Macros y atributos]{.ref} |
| `Parameters(...)` | patrón en un parámetro | [2.4 Patrones]{.ref} |
| `async fn suma` | método que da un futuro | [9.2 async, await y Future]{.ref} |
| `impl ServerHandler` | trait de otro crate | [4.1 Traits]{.ref} |
| la fábrica de `main` | closure sin capturas | [4.3 Closures]{.ref} |
| `nest_service` | una ruta de `axum` | [9.6 Un servidor mínimo]{.ref} |
| `eprintln!` | la salida de error | [7.5 Entrada y salida]{.ref} |

Ninguna fila remite a un concepto que el libro no tenga. Lo demás son nombres
de `rmcp`.

## El programa, archivo por archivo

### El protocolo, lo justo

Los mensajes son objetos JSON con el formato JSON-RPC: llevan `method` y
`params`, y un `id` que la respuesta repite. El cliente abre con
`initialize`, donde dice qué versión del protocolo habla, y el servidor
responde con lo que ofrece. El cliente confirma con
`notifications/initialized`, que no lleva `id` ni espera respuesta. Después
pregunta qué herramientas hay con `tools/list` y ejecuta una con
`tools/call`, que lleva el nombre y un objeto `arguments`.

El transporte decide cómo viajan esos objetos. En stdio, el cliente lanza el
servidor como proceso hijo: le escribe un mensaje por línea en la entrada
estándar y lee las respuestas de su salida. En HTTP, el servidor ya está
corriendo y cada mensaje es una petición POST a una URL.

El paquete `mcp` tiene una librería y dos binarios
([7.2 Crates y Cargo]{.ref}). A los crates de
[9.7 Una API con serde y axum]{.ref} suma dos: `schemars` 1.2.3 y `rmcp`
3.12.0, el SDK de MCP para Rust, con una feature por transporte.

### [Regla 1:]{.prefijo} `dominio.rs`, la lógica en Rust puro

Dos funciones de [1.5 Funciones]{.ref}, sin un solo `use`. El comentario que
abre el archivo en el proyecto lo dice: no sabe nada de MCP, JSON, HTTP ni
stdio.

```rust,ignore
// src/dominio.rs
pub fn saludar(nombre: &str) -> String {
    format!("hola, {nombre}")
}

pub fn sumar(a: i64, b: i64) -> i64 {
    a + b
}
```

Por eso se puede probar y reutilizar sin esas capas. Es la regla 1: la capa
de fuera llama a la de dentro, nunca al revés. Los comentarios del proyecto
pasaron aquí a la prosa.

### [Regla 2:]{.prefijo} `params.rs`, el contrato de entrada

Un struct por herramienta, con dos `derive` de crates distintos
([7.6 Macros y atributos]{.ref}). `Deserialize` convierte el JSON que manda
el modelo en el struct ([9.7 Una API con serde y axum]{.ref}). `JsonSchema`,
de `schemars`, genera el esquema que el modelo lee antes de llamar.

```rust,ignore
// src/params.rs
use schemars::JsonSchema;
use serde::Deserialize;

#[derive(Deserialize, JsonSchema)]
pub struct SaludoParams {
    #[schemars(
        description = "nombre de la persona a saludar"
    )]
    pub nombre: String,
}

#[derive(Deserialize, JsonSchema)]
pub struct SumaParams {
    #[schemars(description = "primer numero")]
    pub a: i64,
    #[schemars(description = "segundo numero")]
    pub b: i64,
}
```

Este es el esquema de `SumaParams`,
como llega en la respuesta a `tools/list`:

```json
"inputSchema": {
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "properties": {
    "a": { "description": "primer numero",
           "format": "int64", "type": "integer" },
    "b": { "description": "segundo numero",
           "format": "int64", "type": "integer" }
  },
  "required": ["a", "b"], "type": "object"
}
```

Todo sale del struct: los nombres, el `i64` vuelto `integer`, y los dos
campos obligatorios porque ninguno es un `Option`. El modelo no ve el código.
Ve este documento, y los textos de `#[schemars(description = ...)]` le dicen
para qué sirve cada dato.

### `servidor.rs`, la capa MCP

`Servidor` tiene un campo: la tabla que asocia cada nombre de herramienta con
su método. `ToolRouter<Self>` es un tipo genérico de `rmcp`, y `Self` es
`Servidor` ([4.2 Generics]{.ref}). Por dentro es un `HashMap`
([5.4 HashMap y HashSet]{.ref}). `impl Default` no lo pide nadie: es la
convención para un tipo cuyo `new` no recibe argumentos
([4.4 Traits de la stdlib]{.ref}).

```rust,ignore
// src/servidor.rs
use rmcp::handler::server::router::tool::ToolRouter;
use rmcp::handler::server::wrapper::Parameters;
use rmcp::model::{ServerCapabilities, ServerConfig};
use rmcp::{ServerHandler, tool, tool_handler, tool_router};

use crate::dominio;
use crate::params::{SaludoParams, SumaParams};

#[derive(Clone)]
pub struct Servidor {
    tool_router: ToolRouter<Self>,
}

impl Default for Servidor {
    fn default() -> Self {
        Self::new()
    }
}
```

Cada método es una herramienta y solo traduce: parámetros, dominio,
respuesta. El parámetro es un patrón anidado ([2.4 Patrones]{.ref}).
`Parameters` es un struct de tupla de `rmcp`, como el `Path` de `axum`:
`Parameters(SumaParams { a, b })` lo desarma, desarma el struct de dentro y
deja `a` y `b` como variables. El tipo `Parameters<SumaParams>` dice de dónde
salen: del objeto `arguments` de la llamada, pasado por `Deserialize`.

```rust,ignore
#[tool_router]
impl Servidor {
    pub fn new() -> Self {
        Self {
            tool_router: Self::tool_router(),
        }
    }

    #[tool(
        description = "Saluda a una persona por su nombre"
    )]
    async fn saludo(
        &self,
        Parameters(SaludoParams { nombre }):
            Parameters<SaludoParams>,
    ) -> String {
        dominio::saludar(&nombre)
    }

    #[tool(description = "Suma dos numeros enteros")]
    async fn suma(
        &self,
        Parameters(SumaParams { a, b }):
            Parameters<SumaParams>,
    ) -> String {
        dominio::sumar(a, b).to_string()
    }
}
```

Hay una llamada que no se ve de dónde sale: `Self::tool_router()`. Nadie
escribió esa función. Los tres atributos de `rmcp` son macros que reescriben
lo que decoran ([7.6 Macros y atributos]{.ref}), y el código de `rmcp-macros`
dice qué hace cada una:

- `#[tool]` agrega junto al método una función, `suma_tool_attr`, que devuelve
  la ficha de la herramienta: el nombre, que es el del método; la descripción,
  y el esquema del tipo que va dentro de `Parameters`. Además reescribe el
  método: le quita el `async` y lo deja devolviendo un futuro en un `Box`.
- `#[tool_router]` recorre el `impl`, junta los métodos marcados con `#[tool]`
  y agrega la función `tool_router`, que arma la tabla.
- `#[tool_handler]` agrega al `impl ServerHandler` los métodos que no están
  escritos: `list_tools` y `call_tool`, que consultan la tabla que se le
  indicó con `router = self.tool_router`.

El método reescrito ya no es una `async fn`. Devuelve
`Pin<Box<dyn Future<Output = String> + Send + '_>>`: un futuro en el heap,
con su tipo concreto borrado para que la tabla guarde métodos distintos bajo
un mismo tipo ([6.3 Despacho dinámico]{.ref}). El `+ Send` es la exigencia de
[9.4 Send en las tareas]{.ref}, escrita por la macro.

Y termina con el trait:

```rust,ignore
#[tool_handler(router = self.tool_router)]
impl ServerHandler for Servidor {
    fn get_info(&self) -> ServerConfig {
        let capacidades = ServerCapabilities::builder()
            .enable_tools()
            .build();
        ServerConfig::new(capacidades).with_instructions(
            "Servidor MCP de prueba: saluda y suma numeros",
        )
    }
}
```

`ServerHandler` es el trait con el que `rmcp` habla con un servidor
([4.1 Traits]{.ref}). Casi todos sus métodos tienen un cuerpo default. Aquí
se escribe uno, `get_info`: declara que el servidor ofrece herramientas y
deja unas instrucciones para el modelo.

### `lib.rs`, lo que comparten los dos binarios

```rust,ignore
// src/lib.rs
pub mod dominio;
pub mod params;
pub mod servidor;

pub use servidor::Servidor;
```

Tres módulos públicos y un `pub use` que deja `Servidor` en la raíz
([7.1 Módulos]{.ref}). Los binarios lo nombran `mcp::Servidor`, sin saber en
qué archivo vive. El paquete tiene librería porque tiene dos programas que
usan lo mismo: sin ella, el segundo tendría que copiar las tres capas.

### `main.rs`, el transporte HTTP

El `main` termina como el de [9.6 Un servidor mínimo]{.ref}: reservar la
dirección, servir y esperar. Lo nuevo es `mcp`, que se construye con tres
argumentos.

El primero es una closure sin parámetros y sin capturas
([4.3 Closures]{.ref}). Es una fábrica: `rmcp` la guarda y la llama cada vez
que un cliente abre una sesión, así que cada cliente recibe su `Servidor`.
Un campo de `Servidor` sería un dato de esa sesión; lo que deban ver todas
va en un `Arc` que la closure captura ([8.3 Estado compartido]{.ref}). El
segundo argumento lleva la cuenta de las sesiones: `default()` lo crea e
`.into()` lo envuelve en el `Arc` que el parámetro pide
([4.5 Operadores y conversiones]{.ref}). El tercero es la configuración, con
sus valores default.

```rust,ignore
// src/main.rs
use mcp::Servidor;
use rmcp::transport::streamable_http_server::{
    StreamableHttpService,
    session::local::LocalSessionManager,
};
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // el SDK crea un `Servidor` nuevo por cada sesion
    let mcp = StreamableHttpService::new(
        || Ok(Servidor::new()),
        LocalSessionManager::default().into(),
        Default::default(),
    );

    // el MCP es una ruta mas dentro de axum
    let api = axum::Router::new().nest_service("/mcp", mcp);

    let listener = TcpListener::bind("127.0.0.1:8000").await?;
    println!("MCP escuchando en http://127.0.0.1:8000/mcp");
    axum::serve(listener, api).await?;
    Ok(())
}
```

`route` asocia una ruta con un manejador. `nest_service` entrega a un
*servicio* todo lo que llegue bajo un prefijo: un valor que recibe la
petición entera y produce la respuesta. El enrutador puede tener además las
rutas de una API normal: el servidor MCP es una más.

### [Regla 3:]{.prefijo} `examples/stdio.rs`, el mismo servidor por stdio

Cargo trata cada archivo de la carpeta `examples/` como un binario más del
paquete, que puede usar la librería. No se compila con `cargo run`: se pide
por nombre, con `cargo run --example stdio`.

```rust,ignore
// examples/stdio.rs
use mcp::Servidor;
use rmcp::{ServiceExt, transport::stdio};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // OJO: stdout es el canal del protocolo. Un println! lo
    // corromperia; para mensajes propios usa eprintln!
    eprintln!(
        "MCP stdio listo, esperando mensajes por stdin"
    );

    // un solo cliente, una sola sesion: un solo Servidor
    let servicio = Servidor::new().serve(stdio()).await?;

    // se queda atendiendo hasta que el cliente cierre stdin
    servicio.waiting().await?;
    Ok(())
}
```

No hay `axum`, ni puerto, ni fábrica. Un proceso atiende a un cliente, así
que basta un `Servidor`. `stdio()` devuelve la entrada y la salida estándar
en su versión de `tokio`. `serve` es un método que el trait `ServiceExt`
agrega a todo servidor: por eso el `use` lo trae ([4.1 Traits]{.ref}). Espera
el `initialize` del cliente y devuelve el servicio ya en marcha. `waiting`
termina cuando el cliente cierra la entrada.

::: {.advertencia titulo="La salida estándar ya tiene dueño"}
En stdio, cada línea que el servidor escribe en la salida estándar es un
mensaje del protocolo. Un `println!` mete ahí una línea que no es JSON. El
aviso de arranque sale por `eprintln!`, que escribe en la salida de error.
:::

### La prueba por stdio

El archivo `sesion.jsonl` guarda los cuatro mensajes de una conversación. En
el archivo cada uno ocupa una línea; aquí dos se parten para caber:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "protocolVersion":"2025-11-25","capabilities":{},
  "clientInfo":{"name":"a-mano","version":"0.1.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{
  "name":"suma","arguments":{"a":2,"b":40}}}
```

El servidor los recibe por la entrada estándar. `jq`, una herramienta de
terminal que lee JSON, imprime el `id` de cada respuesta y después el
resultado de la tercera:

```salida
$ cargo run -q --example stdio < sesion.jsonl | jq -c .id
MCP stdio listo, esperando mensajes por stdin
1
3
2
$ cargo run -q --example stdio < sesion.jsonl 2>/dev/null \
    | jq -c 'select(.id == 3) | .result'
{"content":[{"type":"text","text":"42"}],"isError":false}
```

Tres respuestas para cuatro mensajes: la notificación no lleva `id` y no
recibe ninguna. La de `suma` es el `String` del método, envuelto en una lista
`content` con un bloque de tipo `text`. La respuesta 1 trae lo que `get_info`
declaró, y la 2 es la lista con el esquema de cada herramienta.

La respuesta 3 salió antes que la 2. `rmcp` atiende cada petición en su
propia tarea ([9.3 El runtime]{.ref}) y escribe cada respuesta cuando está
lista. El `id` es lo que deja al cliente emparejarlas.

El aviso de arranque llegó a la pantalla sin pasar por `jq`: es la separación
de [7.5 Entrada y salida]{.ref}. Con `println!` en su lugar, el aviso entra a
la tubería y el primer comando termina con *jq: parse error: Invalid numeric
literal at line 1, column 4*. Qué hace un cliente con esa línea depende del
cliente: el transporte de `rmcp` descarta las líneas que no son JSON.

### La prueba por HTTP

`cargo run` levanta el otro binario, que imprime
`MCP escuchando en http://127.0.0.1:8000/mcp`. Desde otra terminal, `curl`
manda el mismo `initialize` con un POST a esa URL. El transporte exige dos
cabeceras: `Content-Type: application/json` y
`Accept: application/json, text/event-stream`. Sin la segunda responde un
406: *Client must accept both application/json and text/event-stream*.

Con las dos, la respuesta es un 200 de tipo `text/event-stream`: el mismo
objeto JSON de stdio, en una línea que empieza con `data:`. Trae además una
cabecera `mcp-session-id` con la sesión que la fábrica acaba de abrir. Las
peticiones siguientes la devuelven; sin ella reciben un 400, *Session ID is
required*.

### Conectarlo a un cliente

A mano se ve el protocolo. Un cliente real hace esos pasos solo. En Claude
Code un servidor se registra con `claude mcp add`, que recibe un nombre y,
según el transporte, un comando o una URL:

```salida
$ cargo build --example stdio
$ claude mcp add pruebas -- \
    /ruta/al/paquete/target/debug/examples/stdio
$ claude mcp add --transport http pruebas-http \
    http://127.0.0.1:8000/mcp
```

Con el primero, el cliente lanza el binario cada vez que arranca. Con el
segundo, se conecta a un servidor que ya está corriendo.

### El error: un struct sin `JsonSchema`

La regla 2 pide los dos `derive`. Si el de `SumaParams` queda en
`#[derive(Deserialize)]`, y se quitan los atributos `#[schemars]` que
dependen del otro, `cargo build` responde:

```salida
error[E0277]: the trait bound `SumaParams: JsonSchema` is not
              satisfied
  --> src/servidor.rs:44:13
44 |             Parameters<SumaParams>,
   |             ^^^^^^^^^^^^^^^^^^^^^^ unsatisfied trait
   |                                    bound
note: required by a bound in `schema_for_input`
```

El error aparece en `servidor.rs`, el archivo que no cambió. La nota nombra
la función que `#[tool]` puso en
la ficha de la herramienta: `schema_for_input` tiene un límite
`T: JsonSchema` ([4.2 Generics]{.ref}). Sin esquema no hay qué anunciar, y el
programa no compila.

Quitar `Deserialize` da un error menos claro, de la familia del `Handler` de
[9.6 Un servidor mínimo]{.ref}: un E0277 sobre la línea de `#[tool_router]`,
*the trait `IntoToolRoute<Servidor, _>` is not implemented*, que no menciona
`Deserialize`.

## Aplicación

Una tercera herramienta que cuenta las vocales de un texto. La función es
`contar_vocales` de [3.4 Strings]{.ref}, copiada tal cual. Cada pieza va a su
capa. La función entra a `dominio.rs` con un `pub` delante. El contrato va
en `params.rs`: un struct `VocalesParams` con un campo `texto: String`, sus
dos `derive` y su descripción. El método va dentro del `impl Servidor`:

```rust,ignore
// src/servidor.rs
    #[tool(description = "Cuenta las vocales de un texto")]
    async fn vocales(
        &self,
        Parameters(VocalesParams { texto }):
            Parameters<VocalesParams>,
    ) -> String {
        dominio::contar_vocales(&texto).to_string()
    }
```

Nadie registra la herramienta en ninguna lista: `#[tool_router]` la encuentra
al recorrer el `impl`. A `sesion.jsonl` se le agrega una quinta línea, un
`tools/call` con `id` 4, nombre `vocales` y argumento
`{"texto":"Murciélago"}`. `jq` filtra las respuestas 2 y 4:

```salida
$ cargo run -q --example stdio < sesion.jsonl 2>/dev/null \
    | jq -c 'select(.id == 2) | [.result.tools[].name]'
["saludo","suma","vocales"]
$ cargo run -q --example stdio < sesion.jsonl 2>/dev/null \
    | jq -c 'select(.id == 4) | .result'
{"content":[{"type":"text","text":"5"}],"isError":false}
```

Cambiaron tres archivos, y ninguno de transporte: la herramienta nueva
existe en HTTP y en stdio. Un test de `contar_vocales` no necesita servidor,
ni `tokio`, ni JSON ([7.3 Tests]{.ref}).

## A fondo

**Lo que `rmcp` exige de `Servidor`.** El trait está declarado
`ServerHandler: Sized + Send + Sync + 'static`. Con un campo `Rc<u64>` en el
struct, el error es E0277 sobre `impl ServerHandler for Servidor`: *`Rc<u64>`
cannot be shared between threads safely* ([8.2 Send y Sync]{.ref}). El
servidor se usa desde tareas que cambian de hilo
([9.4 Send en las tareas]{.ref}). `Clone`, en cambio, no es una exigencia
aquí: el programa compila igual sin `#[derive(Clone)]`.

**Una herramienta que hace panic no responde.** `sumar` usa `+`, y en modo
debug un desbordamiento es un panic ([1.2 Tipos escalares]{.ref}). Una
llamada con `a` igual a `i64::MAX` y `b` igual a 1 deja en la salida de
error *attempt to add with overflow*. El servidor sigue atendiendo, porque el
panic termina solo la tarea de esa petición ([9.3 El runtime]{.ref}), pero la
petición se queda sin respuesta. El arreglo va de dentro hacia fuera: `sumar`
devuelve un `Option<i64>` con `a.checked_add(b)`, y el método, un
`Result<String, String>`. La misma llamada recibe entonces el texto del
`Err` con `"isError":true`, y el modelo puede leerlo y corregirse.
