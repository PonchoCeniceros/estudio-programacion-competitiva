# 9.4 · Send en las tareas

[9.3 El runtime]{.ref} dejó `tokio::spawn` como la forma de lanzar una tarea
independiente. Basta que esa tarea tenga un `Rc` mientras espera para que el
compilador la rechace. El mensaje pasa de veinte líneas, no trae código de
error y señala la llamada a `spawn`, donde no hay ningún `Rc` a la vista. La
misma función, esperada con `.await` en vez de lanzada, compila y corre.

La causa sale de juntar dos capítulos. [9.2 async, await y Future]{.ref}: una
`async fn` se compila a un struct que guarda las variables vivas en cada
`.await`. [8.2 Send y Sync]{.ref}: un struct es `Send` si todos sus campos lo
son. Un `Rc` vivo en un `.await` es un campo que no es `Send`, dentro de un
valor que el runtime necesita pasar de un hilo a otro.

## Definiciones y reglas

Punto de suspensión
:   cada `.await`. Es el único lugar donde una tarea puede ceder su hilo, y
    el lugar donde otro hilo puede retomarla.

Cruzar un `.await`
:   estar vivo antes y después de él. Un valor que cruza queda guardado en
    el futuro mientras la tarea está suspendida.

Robo de trabajo
:   *(work stealing)*: la política del runtime de varios hilos. Un hilo que
    se queda sin tareas toma las que otro tiene pendientes.

::: {.reglas titulo="Qué exige una tarea"}
1. `tokio::spawn` exige un futuro `Send + 'static`: la tarea puede
   reanudarse en otro hilo y vivir más que quien la lanzó.
2. Un futuro es `Send` si todo lo que cruza un `.await` lo es.
3. Un valor cruza un `.await` si su scope lo contiene, se use después o
   no.
:::

## De un vistazo

| Vivo en el `.await` | ¿Futuro `Send`? | Arreglo |
| :------------------ | :---------- | :-------------- |
| `i32`, `String`, `Arc<Mutex<T>>` | sí | ninguno |
| `Rc<T>`, `Rc<RefCell<T>>` | no | un bloque, o `Arc` y `Mutex` |
| *guard* de `std::sync::Mutex` | no | un bloque que lo suelte |
| guard de `tokio::sync::Mutex` | sí | ninguno |
| `&T` a una local de quien lanza | no es `'static` | `async move` y `Arc` |

Criterio: primero se intenta que el valor muera antes del `.await`. El tipo
se cambia solo cuando el valor tiene que seguir vivo durante la espera.

## Las reglas, una por una

### El error y su mapa de lectura

Los ejemplos del capítulo son el `src/main.rs` de un proyecto con `tokio`,
como los de 9.3. `pausa` cede el hilo una vez con `yield_now`, sin esperar
nada: es el `.await` más corto que suspende de verdad.

```rust,ignore,compile_fail
// src/main.rs
use std::rc::Rc;

async fn pausa() {
    tokio::task::yield_now().await;
}

async fn tarea() {
    let n = Rc::new(5);
    pausa().await;
    println!("{n}");
}

#[tokio::main]
async fn main() {
    tokio::spawn(tarea()).await.unwrap();
}
```

```salida
error: future cannot be sent between threads safely
 16 |     tokio::spawn(tarea()).await.unwrap();
    |                  ^^^^^^^ future returned by `tarea` is
    |                          not `Send`
    = help: within `impl Future<Output = ()>`, the trait
            `Send` is not implemented for `Rc<i32>`
```

El mensaje tiene cuatro partes fijas, y esa es la primera mitad. La línea
`error` no trae código `E...`, y su flecha apunta al argumento de `spawn`.
Ahí es donde el futuro tendría que cruzar de hilo, no donde está la causa.
El `help` nombra al culpable: `Send` no está implementado para `Rc<i32>`.
El «within» dice que ese tipo está dentro del futuro, como campo. Con un
bloque `async` en lugar de una `async fn`, el futuro aparece como
`{async block@src/main.rs:10:18: 10:23}`. La salida sigue con dos notas:

```salida
note: future is not `Send` as this value is used across an
      await
  9 |     let n = Rc::new(5);
    |         - has type `Rc<i32>` which is not `Send`
 10 |     pausa().await;
    |             ^^^^^ await occurs here, with `n` maybe
    |                   used later
note: required by a bound in `tokio::spawn`
176 |         F: Future + Send + 'static,
    |                     ^^^^ required by this bound in
    |                          `spawn`
```

La primera `note` es la parte útil, y trae dos flechas. La de guiones
marca la línea donde nace el valor. La de acentos marca el `.await` que
ese valor cruza. La segunda `note` dice quién lo exige: el bound de `spawn`.

Lo que el mensaje no marca es dónde muere el valor: `n` muere en la llave
que cierra `tarea`, después del `.await`. La función sola compila. El
error aparece donde alguien exige `Send`, que puede estar en otro módulo o
dentro de un framework, y la primera `note` devuelve a la línea correcta.

### [Regla 1:]{.prefijo} `spawn` exige `Send` y `'static`

Las dos firmas, la de [8.1 Hilos]{.ref} y la de 9.3, lado a lado:

```rust,ignore
// std::thread::spawn
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,

// tokio::spawn
pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
where
    F: Future + Send + 'static,
    F::Output: Send + 'static,
```

Es la misma exigencia. Un hilo recibe una closure y una tarea recibe un
futuro; los dos son valores que salen del hilo que los creó. La diferencia
está en cuándo cruzan. La closure cruza una vez, al lanzar el hilo. El
futuro puede cruzar en cada `.await`: el runtime de varios hilos reparte
las tareas por robo de trabajo, y la que cedió en el hilo A puede
continuar en el B.

::: {.figura src="figuras/9.4-cambio-de-hilo.html"}
:::

Nada garantiza que el cambio ocurra, y nada lo impide. El compilador no
conoce la carga del runtime, así que exige `Send` siempre.

### [Regla 2:]{.prefijo} `Send` se propaga por lo que cruza el `.await`

El futuro de `tarea()` es un struct que el compilador genera. Mientras la
tarea está suspendida en `pausa().await`, ese struct guarda lo que hará
falta al continuar: en qué punto va, y `n`. Lo mismo ocurre con una closure
y lo que captura ([4.3 Closures]{.ref}): las variables viven dentro del
valor generado. Y `Send` se decide campo por campo. El futuro tiene un
campo `Rc<i32>`, así que no es `Send`.

El problema no es usar un `Rc` dentro de una tarea. Es tenerlo vivo a
través de un `.await`. El mismo `Rc`, creado y destruido antes de la
espera, nunca llega a ser campo del futuro:

```rust,ignore
// src/main.rs (solo cambia `tarea`)
async fn tarea() {
    let doble = {
        let n = Rc::new(5);
        *n * 2
    };                      // n muere aquí
    pausa().await;          // solo cruza `doble`, un i32
    println!("{doble}");    // 10
}
```

La regla también explica por qué `tarea().await` compilaba con el `Rc`
vivo. Un futuro que no es `Send` se puede crear y ejecutar. Lo único
prohibido es entregarlo a algo que exige `Send`.

### [Regla 3:]{.prefijo} cruzar es cuestión de scope

Con referencias, un préstamo termina en su último uso
([3.3 Borrowing]{.ref}). Aquí esa intuición falla dos veces. Si `tarea`
imprime `n` antes de `pausa().await` y no lo vuelve a tocar, el error es
el mismo: `n` sigue vivo hasta la llave de cierre. Y destruirlo a mano
tampoco alcanza:

```rust,ignore,compile_fail
// src/main.rs (solo cambia `tarea`)
async fn tarea() {
    let n = Rc::new(5);
    let doble = *n * 2;
    drop(n);                // n ya no existe
    pausa().await;          // y aun así cuenta como vivo
    println!("{doble}");
}
```

`rustc` 1.94 responde con el mismo mensaje y las mismas dos flechas:
*await occurs here, with `n` maybe used later*. El programa sería correcto
al ejecutarse, porque `n` se destruye antes de la espera. El análisis que
decide qué guarda el futuro es más conservador que eso, y «A fondo» precisa
cuándo. La forma que siempre funciona es la del apartado anterior: un
bloque `{ }` que encierre al valor y deje salir solo el dato.

### Los dos arreglos

El primero es acortar la vida del valor con un bloque, como en `doble`. No
cuesta nada al ejecutar y no cambia ningún tipo.

El segundo es cambiar el tipo por su equivalente entre hilos, con la tabla
de [8.3 Estado compartido]{.ref}: `Rc<T>` por `Arc<T>`, `RefCell<T>` por
`Mutex<T>`, `Rc<RefCell<T>>` por `Arc<Mutex<T>>`. El primer programa del
capítulo compila con solo cambiar `Rc::new(5)` por `Arc::new(5)`, e
imprime 5.

El segundo corresponde cuando el valor tiene que cruzar: se necesita
después de la espera, o se comparte con otras tareas. Se paga con un
contador atómico o con un candado.

### El guard de un `Mutex`

Con `Arc<Mutex<T>>` el estado ya es `Send`, y el error vuelve por otro
lado. `lock()` devuelve un `MutexGuard`, que no es `Send` (8.3), y la
regla 3 de [6.2 Rc, RefCell y árboles]{.ref} vale igual aquí: el candado
dura lo que vive el guard.

```rust,ignore,compile_fail
// src/main.rs
use std::sync::{Arc, Mutex};

async fn pausa() { tokio::task::yield_now().await }

async fn sumar(m: Arc<Mutex<i32>>) {
    let mut guard = m.lock().unwrap();
    *guard += 1;
    pausa().await;
    println!("{}", *guard);
}

#[tokio::main]
async fn main() {
    let m = Arc::new(Mutex::new(0));
    tokio::spawn(sumar(m)).await.unwrap();
}
```

```salida
error: future cannot be sent between threads safely
   = help: within `impl Future<Output = ()>`, the trait
           `Send` is not implemented for
           `std::sync::MutexGuard<'_, i32>`
note: future is not `Send` as this value is used across an
      await
 7 |     let mut guard = m.lock().unwrap();
   |         --------- has type `std::sync::MutexGuard<'_,
   |                   i32>` which is not `Send`
 8 |     *guard += 1;
 9 |     pausa().await;
   |             ^^^^^ await occurs here, with `mut guard`
   |                   maybe used later
```

El mapa es el mismo: el culpable en el `help`, y en la `note` la línea
donde nace y el `.await` que cruza. La flecha de la línea `error`, que el
recorte omite, apunta otra vez al argumento de `spawn`. El arreglo normal
es el primero. Se toma el candado, se actualiza, se copia o se clona lo
que haga falta después, y el guard muere antes de esperar:

```rust,ignore
// src/main.rs (solo cambia `sumar`)
async fn sumar(m: Arc<Mutex<i32>>) {
    let valor = {
        let mut guard = m.lock().unwrap();
        *guard += 1;
        *guard              // copia el i32 hacia afuera
    };                      // el candado se suelta aquí
    pausa().await;
    println!("{valor}");    // 1
}
```

Un guard temporal también sirve. `let valor = *m.lock().unwrap();` lo
destruye en el `;`, antes de cualquier espera.

Para el caso en que el candado sí debe seguir tomado durante la espera,
`tokio` trae su propio mutex. `tokio::sync::Mutex` tiene un `lock()`
asíncrono, sin `Result` que desempacar, y su guard sí puede cruzar un
`.await`:

```rust,ignore
// src/main.rs (solo cambian los `use` y `sumar`)
use std::sync::Arc;
use tokio::sync::Mutex;

async fn sumar(m: Arc<Mutex<i32>>) {
    let mut guard = m.lock().await;   // sin unwrap
    *guard += 1;
    pausa().await;                    // el guard cruza
    println!("{}", *guard);           // 1
}
```

El mutex de `std` es la opción por default para secciones cortas: tomar,
modificar y soltar, sin ningún `.await` en medio. El de `tokio` cuesta más
en cada toma. Se justifica cuando la operación protegida incluye la
espera, como una conexión compartida donde una petición y su respuesta no
pueden mezclarse con las de otra tarea.

### `'static`: la tarea no toma prestado de quien la lanza

El otro bound tiene la misma razón que en un hilo (8.1): la tarea puede
seguir corriendo cuando la función que la lanzó ya terminó. Un bloque
`async` captura como una closure, por referencia si el cuerpo solo lee:

```rust,ignore,compile_fail
// src/main.rs
async fn pausa() { tokio::task::yield_now().await }

#[tokio::main]
async fn main() {
    let nombre = String::from("Ferris");
    let tarea = tokio::spawn(async {
        pausa().await;
        println!("tarea: {nombre}");
    });
    tarea.await.unwrap();
    println!("main: {nombre}");
}
```

```salida
error[E0373]: async block may outlive the current function,
              but it borrows `nombre`, which is owned by the
              current function
7 |     let tarea = tokio::spawn(async {
  |                              ^^^^^ may outlive borrowed
  |                                    value `nombre`
8 |         pausa().await;
9 |         println!("tarea: {nombre}");
  |                           ------ `nombre` is borrowed here
```

El `help` que sigue propone la palabra `move`. `async move` mueve `nombre`
al futuro, igual que `move` en una closure. Con eso la tarea compila, y
ahora falla la última línea de `main` con *E0382: borrow of moved value:
`nombre`*. Cuando los dos lados necesitan el valor, se reparte con `Arc`
y cada uno es dueño de su copia del puntero:

```rust,ignore
// src/main.rs (cambia `main`; arriba, `use std::sync::Arc;`)
#[tokio::main]
async fn main() {
    let nombre = Arc::new(String::from("Ferris"));
    let copia = Arc::clone(&nombre);
    let tarea = tokio::spawn(async move {
        pausa().await;
        println!("tarea: {copia}");   // tarea: Ferris
    });
    tarea.await.unwrap();
    println!("main: {nombre}");       // main: Ferris
}
```

Una `async fn` que recibe `&str` choca con el mismo bound:
`tokio::spawn(saludar(&nombre))` falla con *E0597: `nombre` does not live
long enough*, y la nota *argument requires that `nombre` is borrowed for
`'static`*.

### Sin `spawn` no hace falta `Send`

`Send` lo exige `spawn`, no `async`. Un futuro que no se lanza como tarea
corre dentro de la tarea que lo espera y nunca cambia de hilo por su
cuenta: `.await` y `tokio::join!` no piden nada. Si hacen falta tareas de
verdad con valores que no son `Send`, `tokio` tiene `spawn_local`. Lanza
la tarea dentro de un `LocalSet`, un grupo de tareas que se queda en el
hilo que lo ejecuta. Las dos salidas, en un programa:

```rust,ignore
// src/main.rs
use std::rc::Rc;
use tokio::task::{LocalSet, spawn_local};

async fn pausa() { tokio::task::yield_now().await }

async fn tarea(id: u32) -> u32 {
    let n = Rc::new(id);
    pausa().await;          // un Rc cruza el .await
    *n * 10
}

#[tokio::main]
async fn main() {
    let (a, b) = tokio::join!(tarea(1), tarea(2));
    println!("{}", a + b);              // 30

    let local = LocalSet::new();
    let c = local.run_until(async {
        let t = spawn_local(tarea(3));  // tarea de verdad
        t.await.unwrap()
    });
    println!("{}", c.await);            // 30
}
```

Son salidas de emergencia: nada de esto aprovecha los demás hilos. Y el
runtime de un solo hilo, `flavor = "current_thread"`, no relaja la firma:
con él, `tokio::spawn(tarea(1))` falla con el error del inicio.

## Aplicación

Un contador de visitas por página, compartido entre tareas: el
`Arc<Mutex<...>>` de 8.3. Cada tarea suma su visita y avisa a otro
servicio, simulado con una espera de 10 ms. La primera versión de
`registrar` espera con el candado tomado:

```rust,ignore,compile_fail
// src/main.rs
use std::collections::BTreeMap;
use std::sync::{Arc, Mutex};
use std::time::Duration;

type Visitas = Arc<Mutex<BTreeMap<&'static str, u32>>>;

async fn avisar(_pagina: &str, _total: u32) {
    tokio::time::sleep(Duration::from_millis(10)).await;
}

async fn registrar(visitas: Visitas, pagina: &'static str) {
    let mut mapa = visitas.lock().unwrap();
    let total = mapa.entry(pagina).or_insert(0);
    *total += 1;
    avisar(pagina, *total).await;   // con el guard vivo
}
```

```salida
error: future cannot be sent between threads safely
note: future is not `Send` as this value is used across an
      await
13 |     let mut mapa = visitas.lock().unwrap();
   |         -------- has type `std::sync::MutexGuard<'_,
   |                  BTreeMap<&str, u32>>` which is not
   |                  `Send`
...
16 |     avisar(pagina, *total).await;   // con el guard vivo
   |                            ^^^^^ await occurs here, with
   |                                  `mut mapa` maybe used
   |                                  later
```

La `note` da las dos líneas: el guard nace en la 13 y cruza el `.await` de
la 16. La línea `error` apunta al `spawn` de `main`, que completa el
archivo:

```rust,ignore
// src/main.rs (continúa)
#[tokio::main]
async fn main() {
    let visitas = Visitas::default();
    let mut tareas = Vec::new();
    for pagina in ["inicio", "blog", "inicio", "ayuda"] {
        let tarea = registrar(Arc::clone(&visitas), pagina);
        tareas.push(tokio::spawn(tarea));
    }
    for t in tareas {
        t.await.unwrap();
    }
    for (pagina, total) in visitas.lock().unwrap().iter() {
        println!("{pagina}: {total}");
    }
}
```


El error protege además de algo que `Send` no nombra. Con el guard vivo,
las demás tareas esperarían el candado durante los 10 ms de cada aviso, y
las visitas se registrarían de una en una. Solo cambia `registrar`:

```rust,ignore
// src/main.rs (solo cambia `registrar`)
async fn registrar(visitas: Visitas, pagina: &'static str) {
    let total = {
        let mut mapa = visitas.lock().unwrap();
        let total = mapa.entry(pagina).or_insert(0);
        *total += 1;
        *total                      // copia el u32
    };                              // el candado se suelta
    avisar(pagina, total).await;    // espera sin guard
}
```

```salida
ayuda: 1
blog: 1
inicio: 2
```

Las cuatro tareas pueden terminar en cualquier orden y en cualquier hilo.
La salida no depende de eso: `main` espera a todas antes de leer, y un
`BTreeMap` recorre sus llaves en orden ([5.5 Otras colecciones]{.ref}). El
último `for` de `main` también tiene un guard vivo, el temporal de su
cabecera. No estorba, porque dentro de ese ciclo no hay ningún `.await`.

## A fondo

**Se puede comprobar que un futuro es `Send` sin lanzarlo.** Basta una
función que solo exista por su bound: `fn exige_send<T: Send>(_: &T) {}`.
`exige_send(&tarea())` compila si el futuro es `Send`. Si no, produce el
mismo mensaje con sus dos flechas, y la última `note` nombra a
`exige_send` en vez de a `tokio::spawn`. Sirve en un test, o para probar
una por una varias funciones `async` anidadas.

**Cuándo `drop` sí alcanza.** Con `rustc` 1.94, un valor movido antes del
`.await` deja de contar solo si nunca se prestó. `let g = m.lock().unwrap();
drop(g);` seguido de una espera compila. En cuanto hay un `*g += 1` de por
medio, ya no: usar un guard es prestarlo, porque `Deref` recibe `&self`
([4.5 Operadores y conversiones]{.ref}). Por eso `drop` casi nunca sirve
para este error. La otra mitad es la de 6.2: un valor con destructor vive
hasta que cierra su scope, se use o no. Un `Rc` que nadie toca después
del `.await` lo cruza de todos modos, porque su `Drop` corre después.

**El guard temporal también puede cruzar.** Vale la tabla de temporales de
6.2, ahora contra el `.await`. Aquí `m` es un `Mutex<Vec<usize>>` de `std`
dentro de una tarea lanzada con `spawn`, y `f` una `async fn`:

| Escrito | Resultado |
| :--- | :--- |
| `let n = m.lock().unwrap().len(); f(n).await;` | compila: el guard muere en el primer `;` |
| `f(m.lock().unwrap().len()).await;` | no compila: el `.await` está en el mismo enunciado |
| `if m.lock().unwrap().len() > 0 { f(0).await; }` | compila: el guard muere antes del bloque |
| `match m.lock().unwrap().len() { _ => f(0).await }` | no compila: vive hasta cerrar el `match` |
| `for x in m.lock().unwrap().iter() { f(*x).await; }` | no compila: vive todo el `for` |

En esos casos la flecha de guiones no señala una variable. Señala la
expresión `m.lock().unwrap()`, y el texto dice *with `m.lock().unwrap()`
maybe used later*. El arreglo es el de la primera fila.

**`Sync` casi no aparece en estos mensajes.** El futuro se mueve de un
hilo a otro, no se comparte: en cada momento lo ejecuta un solo hilo.
Por eso el bound es `Send`. `Sync` entra de forma indirecta, cuando lo
que cruza el `.await` es una referencia, porque `&T` es `Send` solo si
`T` es `Sync` (8.2). Un `RefCell<i32>` local puede cruzar un `.await`: es
`Send`. Una `&RefCell<i32>` no, y el `help` cambia a *the trait `Sync` is
not implemented for `RefCell<i32>`*.
