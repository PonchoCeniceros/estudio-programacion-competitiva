# 9.2 · async, await y Future

[9.1 El problema]{.ref} terminó con una condición. Para que una espera no
ocupe un hilo, la función que espera tiene que poder detenerse a la mitad y
continuar después. Una función normal no puede: corre de principio a fin
sobre la pila de su hilo.

`async` es la palabra que lo permite, y lo primero que cambia es lo que la
función devuelve. Con `async fn leer() -> u32`, la línea
`let n: u32 = leer();` no compila: E0308, *expected `u32`, found future*.
La llamada no entregó un número. Entregó un valor que describe el trabajo
por hacer, y que no avanza hasta que alguien lo empuja. Es la pereza de
[5.6 Iteradores]{.ref}, aplicada al tiempo.

## Definiciones y reglas

Futuro
:   *(future)*: un valor de un tipo que implementa el trait `Future`.
    Describe un cálculo que puede no haber terminado.

`async fn`
:   una función cuya llamada construye un futuro en vez de ejecutar su
    cuerpo.

`.await`
:   el operador que, dentro de código `async`, pide el resultado de un
    futuro. Cada `.await` es un punto donde la función puede detenerse.

`poll`
:   el único método de `Future`. Hace avanzar el futuro y responde si ya
    terminó.

Runtime
:   la pieza que ejecuta futuros llamando a `poll`. No es parte del
    lenguaje: viene de un crate ([9.3 El runtime]{.ref}).

::: {.reglas titulo="Las tres reglas de async"}
1. Una `async fn` no devuelve su resultado: devuelve un futuro. Llamarla no
   ejecuta su cuerpo.
2. `.await` solo se escribe dentro de código `async`. Entrega el resultado
   del futuro y, si todavía no está, cede el control sin bloquear el hilo.
3. Un futuro es una máquina de estados de tamaño conocido. Lo que sigue
   vivo al cruzar un `.await` queda guardado dentro de él.
:::

## De un vistazo

Un futuro repite el patrón de un iterador, pieza por pieza:

| | Iterador | Futuro |
| :--- | :--- | :--- |
| Trait | `Iterator` | `Future` |
| Tipo asociado | `Item` | `Output` |
| Método | `next` | `poll` |
| Respuesta | `Some(x)` o `None` | `Ready(x)` o `Pending` |
| Lo describe | `map`, `filter` | `async fn`, bloque `async` |
| Lo pone en marcha | un consumidor | `.await`, y al final el runtime |
| Entrega | muchos valores | uno solo |

De la tabla sale el criterio para leer código `async`: una llamada sin
`.await` no ha hecho nada todavía.

## Las reglas, una por una

### [Regla 1:]{.prefijo} una `async fn` devuelve un futuro

`async` delante de `fn` cambia el tipo de retorno sin que la firma lo
muestre. Las dos funciones de este programa son equivalentes:

```rust
async fn leer() -> u32 {
    42
}

fn leer_larga() -> impl Future<Output = u32> {
    async { 42 }
}

fn main() {
    let _a = leer();          // un futuro, no un u32
    let _b = leer_larga();    // lo mismo
}
```

La segunda forma dice lo que la primera esconde. El retorno es
`impl Future<Output = u32>`: algún tipo, sin nombre, que implementa
`Future` ([4.2 Generics]{.ref}). El `u32` de la firma `async` pasó a ser el
tipo asociado `Output`: lo que el futuro entregará al terminar. El cuerpo
de `leer_larga` es un bloque `async`, que tiene su propio apartado más
abajo. `Future` está en el preludio de la edición 2024 y no pide `use`.

### Llamar no ejecuta

El cuerpo de una `async fn` no corre con la llamada. En este programa,
`saludar` imprime una línea, y la línea nunca sale:

```rust
async fn saludar() {
    println!("hola desde saludar");
}

fn main() {
    println!("antes");
    saludar();              // construye un futuro y lo tira
    println!("después");
}
```

El programa imprime `antes` y `después`. La llamada construyó un futuro,
nadie lo empujó y el punto y coma lo destruyó. El compilador lo señala con
un aviso:

```salida
warning: unused implementer of `Future` that must be used
7 |     saludar();
  |     ^^^^^^^^^
  = note: futures do nothing unless you `.await` or poll them
```

Es el aviso de una cadena de iteradores sin consumidor, *iterators are lazy
and do nothing unless consumed*, con otro sujeto. Un adaptador describe un
recorrido y un consumidor lo ejecuta. Una `async fn` describe un cálculo, y
la nota nombra las dos formas de ejecutarlo: `.await` o `poll`.

### El trait `Future`

`Future` tiene un tipo asociado, `Output`, y un método, `poll`. `poll` es
una pregunta con dos respuestas. `Poll::Ready(valor)` dice que el futuro
terminó y entrega su `Output`. `Poll::Pending` dice que todavía no, y que
hay que volver a preguntar. La comparación con `next` es directa: un
iterador responde `Some` muchas veces y `None` al final; un futuro responde
`Pending` las veces que haga falta y `Ready` una sola. Así están
declarados el trait y el enum:

```rust
use std::pin::Pin;
use std::task::Context;

// std::future::Future
trait Future {
    type Output;
    fn poll(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
    ) -> Poll<Self::Output>;
}

// std::task::Poll
enum Poll<T> { Ready(T), Pending }

fn main() {}
```

En el código de todos los días nadie llama a `poll`: lo hacen `.await` y
el runtime. Los dos tipos de su firma, `Pin` y `Context`, se pueden leer
por encima; «A fondo» dice qué hace cada uno.

### [Regla 2:]{.prefijo} `.await` pide el resultado

Ejecutar un futuro pide una pieza que el lenguaje no trae: un runtime que
llame a `poll` hasta recibir `Ready`. Los ejemplos que corren usan el de
`tokio`, un crate externo ([7.2 Crates y Cargo]{.ref}). En `Cargo.toml`,
la dependencia pide tres *features*: el runtime, las macros y el reloj.

```toml
[dependencies.tokio]
version = "1"
features = ["rt-multi-thread", "macros", "time"]
```

El atributo `#[tokio::main]` sobre `async fn main` se usa aquí como
fórmula: arranca el runtime y le entrega el futuro de `main`.
[9.3 El runtime]{.ref} la abre. Con ella, `saludar` ya se puede esperar:

```rust,ignore
// src/main.rs
async fn saludar() {
    println!("hola desde saludar");
}

#[tokio::main]
async fn main() {
    let futuro = saludar();
    println!("el futuro ya existe");
    futuro.await;
    println!("después");
}
```

El programa imprime `el futuro ya existe`, después `hola desde saludar` y
al final `después`. Es la regla 1 vista desde dentro: `saludar()`
construyó el futuro sin imprimir nada, y el cuerpo corrió en
`futuro.await`. `.await` es postfijo, como `?` ([5.2 Result]{.ref}), y la
expresión completa vale el `Output` del futuro: `let n = leer().await;`
liga un `u32`.

`.await` solo existe dentro de código `async`. En una función normal no
compila:

```rust,compile_fail
async fn leer() -> u32 {
    42
}

fn main() {
    let n = leer().await;
    println!("{n}");
}
```

```salida
error[E0728]: `await` is only allowed inside `async`
              functions and blocks
5 | fn main() {
  | --------- this is not `async`
6 |     let n = leer().await;
  |                    ^^^^^ only allowed inside `async`
  |                          functions and blocks
```

La restricción sale de lo que `.await` hace. Si el futuro esperado responde
`Pending`, la función que espera tiene que detenerse y devolver el control,
y solo una función `async` sabe detenerse. Una función normal tendría que
quedarse bloqueada, que es lo que el capítulo anterior quería evitar. Por
eso `async` sube por la cadena de llamadas: quien espera a una función
`async` es `async` también, hasta llegar al runtime.

### [Regla 3:]{.prefijo} una máquina de estados

Una función que se detiene y continúa necesita recordar dónde quedó y qué
tenía en las manos. El compilador resuelve las dos cosas con un tipo
anónimo por cada `async fn`, igual que genera uno por cada closure
([4.3 Closures]{.ref}). Ese tipo es una máquina de estados: un enum
([2.3 Enums]{.ref}) con una variante por cada punto donde la función puede
quedar detenida. `total` tiene dos, y `FuturoTotal` es la forma aproximada
del tipo que el compilador genera para ella. `FuturoLeer` representa al
futuro de `leer`:

```rust
async fn leer(id: u32) -> u32 {
    id * 10
}

async fn total() -> u32 {
    let a = leer(1).await;
    let b = leer(2).await;
    a + b
}

struct FuturoLeer;

enum FuturoTotal {
    Inicio,
    Espera1 { pendiente: FuturoLeer },
    Espera2 { a: u32, pendiente: FuturoLeer },
    Terminado,
}

fn main() {
    let _futuro = total();
}
```

Cada variante guarda lo que la función necesita para continuar desde ahí.
En el primer `.await` solo existe el futuro de `leer(1)`. En el segundo ya
existe `a`, que se usará en la suma, y el futuro de `leer(2)`. El `poll`
generado es un `match` sobre el estado: corre el tramo de código que toca,
y si el futuro pendiente responde `Pending`, responde `Pending` también y
conserva el estado.

::: {.figura src="figuras/9.2-maquina.html"}
:::

De esa forma salen tres consecuencias. La primera: llamar una `async fn`
no reserva memoria en el heap. El futuro es un valor como cualquier enum, y
vive donde viva su variable.

La segunda es la base de [9.4 Send en las tareas]{.ref}. Todo valor que
cruza un `.await` es un campo del futuro, así que sus propiedades pasan al
futuro entero. Un valor que no se puede enviar a otro hilo, guardado a
través de un `.await`, produce un futuro que tampoco se puede enviar.

La tercera se puede medir: un futuro tiene tamaño conocido al compilar, el
de su variante más grande. `size_of_val` ([4.3 Closures]{.ref}) lo mide sin
ejecutarlo. `std::future::ready(valor)` construye un futuro que ya terminó,
y sirve para tener un `.await` sin runtime:

```rust
use std::future::ready;
use std::mem::size_of_val;

async fn con_arreglo() -> u8 {
    let datos = [0u8; 1024];
    ready(()).await;
    datos[0]              // datos sigue vivo tras el .await
}

async fn arreglo_antes() -> u8 {
    let primero = {
        let datos = [0u8; 1024];
        datos[0]
    };                    // datos murió antes del .await
    ready(()).await;
    primero
}

fn main() {
    println!("{}", size_of_val(&con_arreglo()));     // 1026
    println!("{}", size_of_val(&arreglo_antes()));   // 3
}
```

`con_arreglo` usa `datos` después del `.await`, así que el arreglo tiene
que sobrevivir a la pausa: sus 1,024 bytes están dentro del futuro. Los
otros dos son de la propia máquina de estados. `arreglo_antes` lo suelta antes de esperar, y el
futuro solo guarda el byte de `primero`. Los números son de `rustc` 1.94 y
pueden cambiar entre versiones; la diferencia de un kilobyte, no.

### Secuencial frente a concurrente

Dos `.await` seguidos corren uno después del otro. El segundo futuro no
empieza hasta que el primero entrega su resultado, porque nadie lo ha
empujado. Para que dos esperas avancen a la vez hace falta alguien que
empuje a los dos futuros por turnos. Eso hace `join!`: recibe varios
futuros, arma uno que los contiene y, en cada `poll`, empuja a todos. Al
terminar entrega una tupla con los resultados. `join!` no es del lenguaje:
es una macro ([7.6 Macros y atributos]{.ref}) de `tokio`, y otros crates,
como `futures`, traen la suya. El lenguaje solo pone `async`, `.await` y
`Future`.

El programa mide las dos formas. `tokio::time::sleep` devuelve un futuro
que termina cuando pasa el tiempo indicado, y simula una consulta de
100 ms. `Instant::now()` toma la hora, y `elapsed()` da el tiempo
transcurrido:

```rust,ignore
// src/main.rs
use std::time::{Duration, Instant};
use tokio::time::sleep;

async fn consultar(id: u32) -> u32 {
    sleep(Duration::from_millis(100)).await;
    id * 10
}

#[tokio::main]
async fn main() {
    let inicio = Instant::now();
    let a = consultar(1).await;
    let b = consultar(2).await;
    let ms = inicio.elapsed().as_millis();
    println!("en fila: {a} y {b}, {ms} ms");

    let inicio = Instant::now();
    let (a, b) = tokio::join!(consultar(1), consultar(2));
    let ms = inicio.elapsed().as_millis();
    println!("con join!: {a} y {b}, {ms} ms");
}
```

```salida
en fila: 10 y 20, 209 ms
con join!: 10 y 20, 103 ms
```

En fila, las esperas se suman: unos 200 ms. Con `join!` corren al mismo
tiempo y el total es el de la más larga: unos 100 ms. Los milisegundos
exactos cambian en cada ejecución. No hay un segundo hilo: `join!` avanza
los dos futuros dentro de la misma tarea.

Construir los dos futuros primero y esperarlos después no los vuelve
concurrentes. `let fa = consultar(1); let fb = consultar(2);` seguido de
`fa.await` y `fb.await` también tarda unos 200 ms: un futuro no avanza por
existir.

### Ceder no es bloquear

`.await` sobre un futuro pendiente devuelve el control a quien ejecuta la
función, que puede avanzar otro futuro en el mismo hilo. Por eso `join!`
intercala dos esperas. `thread::sleep` ([8.1 Hilos]{.ref}) hace lo
contrario: detiene el hilo entero, con todo lo que corre en él.

Basta cambiar una línea del programa anterior para verlo. Con
`std::thread::sleep(Duration::from_millis(100));` en lugar del
`sleep(...).await` de `consultar`, la segunda medición imprime
`con join!: 10 y 20, 205 ms`. `join!` dejó de ganar. `consultar` ya no
tiene ningún `.await`: su `poll` no regresa hasta que `thread::sleep`
termina. Mientras tanto nadie puede empujar al otro futuro, y las dos
esperas vuelven a sumarse.

::: {.advertencia titulo="Bloquear dentro de código async"}
Una función `async` solo cede en sus `.await`. Entre uno y otro ocupa el
hilo: un `thread::sleep`, una lectura bloqueante o un cálculo largo
detienen a todos los futuros que comparten ese hilo, y el compilador no
avisa.
:::

### Bloques `async` y `async move`

Un bloque `async { ... }` es a una `async fn` lo que una closure es a una
`fn`: una expresión que produce un futuro en el lugar, sin declarar una
función. Su cuerpo tampoco corre hasta que alguien lo espera. Como una
closure, usa las variables del scope donde nace ([4.3 Closures]{.ref}): por
default las toma prestadas, y con `move` se vuelve su dueño. La diferencia
es que un bloque no recibe argumentos y se ejecuta una sola vez.

```rust,ignore
// src/main.rs
fn saludo(nombre: String) -> impl Future<Output = usize> {
    async move {
        println!("hola, {nombre}");
        nombre.len()
    }
}

#[tokio::main]
async fn main() {
    let nombre = String::from("Ana");
    let prestado = async { nombre.len() };   // toma &nombre

    println!("el bloque todavía no corre");
    println!("{} letras", prestado.await);
    println!("{} letras", saludo(nombre).await);
}
```

El programa imprime `el bloque todavía no corre`, `3 letras`, `hola, Ana`
y otra vez `3 letras`. `prestado` solo lee `nombre`, que sigue disponible
para la última línea.
El bloque de `saludo` no puede prestar: su futuro sale de la función, y
`nombre` muere con ella. Sin `move` da E0373, *async block may outlive the
current function, but it borrows `nombre`*, el mismo error de una closure
devuelta. Con `async move`, `nombre` queda guardado dentro del futuro. Es
también la forma de entregar un futuro al runtime como tarea aparte, tema
de [9.3 El runtime]{.ref}.

## Aplicación

El programa de [9.1 El problema]{.ref} atendía peticiones simuladas con un
hilo por petición. Este consulta tres fuentes simuladas, de 300, 200 y
100 ms, sin crear ninguno: primero con tres `.await` en fila y luego con
`join!`.

```rust,ignore
// src/main.rs
use std::time::{Duration, Instant};
use tokio::time::sleep;

async fn consultar(fuente: &str, ms: u64) -> String {
    sleep(Duration::from_millis(ms)).await;
    format!("{fuente} ok")
}

#[tokio::main]
async fn main() {
    let inicio = Instant::now();
    let a = consultar("usuarios", 300).await;
    let b = consultar("pedidos", 200).await;
    let c = consultar("precios", 100).await;
    let ms = inicio.elapsed().as_millis();
    println!("en fila:  {ms} ms: {a}, {b}, {c}");

    let inicio = Instant::now();
    let (a, b, c) = tokio::join!(
        consultar("usuarios", 300),
        consultar("pedidos", 200),
        consultar("precios", 100),
    );
    let ms = inicio.elapsed().as_millis();
    println!("a la vez: {ms} ms: {a}, {b}, {c}");
}
```

```salida
en fila:  611 ms: usuarios ok, pedidos ok, precios ok
a la vez: 301 ms: usuarios ok, pedidos ok, precios ok
```

En fila, el total es la suma: unos 600 ms. Con `join!` es la espera más
larga: unos 300 ms. Las respuestas salen en el orden en que se pidieron,
aunque `precios` termine primero: `join!` entrega la tupla en el orden de
sus argumentos, no en el de llegada. Las tres
reglas están en juego: cada llamada a `consultar` solo construye un futuro,
cada `sleep(...).await` cede, y el futuro de `main` guarda `a` y `b`
mientras espera a `c`.

## A fondo

**`Pin` y `Context` son los dos tipos que `poll` pide.** `Pin` garantiza
que el futuro no se mueve de lugar en memoria mientras se ejecuta: la
máquina de estados puede guardar referencias a sus propios campos.
`Context` trae la forma de avisar que vale la pena volver a preguntar. Un
futuro que responde `Pending` guarda ese aviso y lo dispara cuando tiene
algo nuevo; el runtime no pregunta a ciegas.

**Una `async fn` recursiva necesita `Box::pin`.** Si `cuenta` se espera a
sí misma con `cuenta(n - 1).await`, su futuro tendría que contener otro del
mismo tipo: el tamaño infinito de [6.1 Box y listas enlazadas]{.ref}. El
compilador lo rechaza con E0733, *recursion in an async fn requires
boxing*. Con `Box::pin(cuenta(n - 1)).await`, el futuro interno va al heap
y el externo solo guarda un puntero.

**Un trait puede declarar métodos `async`.** Cada `impl` aporta su propio
futuro. El precio: ese trait deja de ser *dyn compatible*
([6.3 Despacho dinámico]{.ref}), y `&dyn Fuente` da E0038.

**Los futuros de Rust son perezosos; los de otros lenguajes, no siempre.**
Una promesa de JavaScript empieza a ejecutarse al crearse. En Rust, crear
un futuro no ejecuta nada.
