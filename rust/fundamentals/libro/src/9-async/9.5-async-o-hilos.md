# 9.5 · async o hilos

La sección 8 y esta dejaron dos formas de hacer varias cosas a la vez: hilos
y tareas. Se parecen en la superficie. Las dos se lanzan con un `spawn`, las
dos devuelven un handle, y las dos piden `Send` a lo que reciben. Elegir entre
ellas por costumbre produce un error que el compilador no ve: el programa
compila, pasa sus pruebas y se detiene cuando llega la carga.

La pregunta «¿async o hilos?» no se contesta mirando la herramienta. Se
contesta mirando el trabajo: ¿espera o calcula? [9.1 El problema]{.ref}
enunció esa distinción. Este capítulo la convierte en criterio, mide lo que
pasa al contestarla mal y muestra cómo se combinan los dos mundos.

## Definiciones y reglas

Trabajo que espera
:   el que pasa casi todo su tiempo detenido hasta que algo externo responde:
    la red, el disco, una base de datos, un temporizador.

Trabajo que calcula
:   el que ocupa un núcleo de principio a fin. No tiene ningún momento en que
    le falte algo de afuera.

Bloquear
:   dentro de una tarea, ocupar el hilo del runtime sin llegar a un `.await`.

`spawn_blocking`
:   la función de `tokio` que ejecuta una closure en un hilo aparte del
    runtime y devuelve un handle que se espera con `.await`.

Paralelismo de datos
:   aplicar la misma operación a muchos elementos independientes,
    repartidos entre los núcleos.

`rayon`
:   el crate que reparte así una cadena de iteradores.

::: {.reglas titulo="Qué pide cada trabajo"}
1. El trabajo que espera va en tareas async. El que calcula va en hilos.
2. Una tarea no retiene el hilo del runtime: lo que bloquea sale de él con
   `spawn_blocking`.
3. La misma operación sobre muchos datos independientes se reparte entre
   núcleos con `rayon`.
:::

## De un vistazo

| El trabajo | Herramienta | Por qué |
| :--- | :--- | :--- |
| espera red, disco o base de datos | tareas async | mientras espera no ocupa un hilo: miles de esperas caben en pocos hilos |
| calcula sin parar | un hilo: `thread::spawn`, `thread::scope` | no hay nada que ceder mientras se calcula |
| calcula lo mismo sobre muchos datos | `rayon`: `par_iter()` | el reparto entre núcleos es mecánico |
| calcula o bloquea en medio de un programa async | `spawn_blocking` | el cálculo sale del runtime y la tarea espera su resultado |

Criterio: una API web es la primera fila, porque casi todo su tiempo se va en
esperar a la base de datos. Un procesamiento de datos con Polars es la
tercera. Un programa real suele tener de las dos, y la cuarta fila las une.

## Las reglas, una por una

### [Regla 1:]{.prefijo} la pregunta es si espera o calcula

Una tarea que espera no necesita un hilo mientras espera. En el `.await`
devuelve el control, el runtime atiende otra tarea, y la primera continúa
cuando llega su dato ([9.2 async, await y Future]{.ref}). De ahí sale la
ventaja de async: muchas esperas simultáneas sobre pocos hilos.

Un cálculo no tiene esa pausa. Sumar, ordenar o comprimir ocupan el núcleo
hasta terminar, y ponerlos en una tarea no les quita trabajo. Lo que un
cálculo necesita es un núcleo para él solo, y eso lo da un hilo
([8.1 Hilos]{.ref}).

La diferencia de fondo es quién decide el cambio de turno. A un hilo lo
interrumpe el sistema operativo, esté donde esté. A una tarea no la
interrumpe nadie: cede solo cuando llega a un `.await` que tiene que
esperar. El resto del capítulo sale de ese hecho.

### Tres tareas que ceden

El programa de referencia lanza tres tareas que esperan 100, 300 y 100 ms.
`Instant::now()` guarda el momento de arranque, y `elapsed()` devuelve el
tiempo transcurrido desde entonces. El atributo lleva
`flavor = "current_thread"`: el runtime usa un solo hilo, el de `main`, en
lugar de uno por núcleo ([9.3 El runtime]{.ref}). Con un solo hilo, el
efecto de cada decisión se lee directo en los tiempos.

```rust,ignore
// src/main.rs
use std::time::{Duration, Instant};
use tokio::time::sleep;

async fn espera(nombre: &str, ms: u64, inicio: Instant) {
    sleep(Duration::from_millis(ms)).await;
    let t = inicio.elapsed().as_millis();
    println!("{nombre} terminó a los {t} ms");
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let inicio = Instant::now();
    let a = tokio::spawn(espera("a", 100, inicio));
    let b = tokio::spawn(espera("b", 300, inicio));
    let c = tokio::spawn(espera("c", 100, inicio));
    a.await.unwrap();
    b.await.unwrap();
    c.await.unwrap();
    println!("total: {} ms", inicio.elapsed().as_millis());
}
```

```salida
a terminó a los 100 ms
c terminó a los 100 ms
b terminó a los 300 ms
total: 300 ms
```

Las tres esperas suman 500 ms y el programa tarda 300, lo que dura la más
larga. Un solo hilo atendió las tres, porque ninguna lo ocupó mientras
esperaba. Los tiempos de este capítulo son mediciones redondeadas a decenas
de milisegundos; cada corrida varía en unos pocos.

### El error: una tarea que no cede

La tarea `b` cambia una línea. En vez del `sleep` de `tokio`, llama al de la
biblioteca estándar, que duerme al hilo entero:

```rust,ignore
// src/main.rs
async fn bloquea(nombre: &str, ms: u64, inicio: Instant) {
    std::thread::sleep(Duration::from_millis(ms));
    let t = inicio.elapsed().as_millis();
    println!("{nombre} terminó a los {t} ms");
}

// en main:
//  let b = tokio::spawn(bloquea("b", 300, inicio));
```

```salida
b terminó a los 300 ms
a terminó a los 300 ms
c terminó a los 400 ms
total: 400 ms
```

`cargo build` no imprime ningún error y ningún aviso. `bloquea` es una
`async fn` válida que no contiene ningún `.await`, y eso está permitido.

El orden de los hechos explica cada número. `a` arranca, llega a su `.await`
y cede. `b` arranca y duerme al hilo 300 ms: no hay `.await`, así que el
runtime no recupera el control. El temporizador de `a` vence a los 100 ms,
pero no hay hilo que la reanude. `c` ni siquiera empezó: su espera de 100 ms
comienza a los 300.

`b` tardó lo mismo en las dos versiones. El costo lo pagaron las otras dos
tareas, que no tienen nada que ver con ella. En un servidor, `b` es una
petición y las otras son todas las demás.

### Qué cuenta como bloquear

`std::thread::sleep` es el caso de laboratorio. Los que aparecen en un
programa real son estos:

| Dentro de una tarea | Por qué bloquea | En su lugar |
| :--- | :--- | :--- |
| `std::thread::sleep` | duerme al hilo entero | `tokio::time::sleep` |
| `std::fs`, `std::net` | no regresa sin el dato | `tokio::fs`, `tokio::net` |
| `lock()` muy disputado | detiene al hilo | secciones cortas |
| un cálculo largo | no tiene `.await` | `spawn_blocking`, `rayon` |
| una biblioteca síncrona | hace algo de lo anterior | `spawn_blocking` |

El criterio práctico no es un número. Entre un `.await` y el siguiente, una
tarea debe hacer poco: preparar una consulta, armar una respuesta, convertir
un dato. Si un tramo puede tardar lo que tarda una operación de red, ya
compite con las esperas que el runtime atiende, y debe salir de la tarea.

### [Regla 2:]{.prefijo} `spawn_blocking` saca el trabajo del runtime

Para `sleep` hay una versión async y el arreglo es usarla. Para un cálculo no
la hay. El cálculo de este capítulo cuenta primos por división, un trabajo
que ocupa el núcleo y cuyo resultado no depende de la corrida:

```rust,ignore
// src/main.rs
fn es_primo(n: u64) -> bool {
    let mut d = 2;
    while d * d <= n {
        if n % d == 0 { return false; }
        d += 1;
    }
    n >= 2
}

fn contar_primos(limite: u64) -> usize {
    (1..=limite).filter(|&n| es_primo(n)).count()
}
```

La tarea `b` ahora llama a `contar_primos(2_000_000)` directo en su cuerpo.
Compilado con `--release`, ese cálculo tarda unos 240 ms, y el resultado
repite el del apartado anterior: `a` termina a los 240 ms en lugar de 100,
y `c` a los 340.

`tokio::task::spawn_blocking` recibe una closure y la entrega a un pozo de
hilos que el runtime reserva para esto, distinto del hilo que atiende las
tareas. Devuelve un `JoinHandle`, como `tokio::spawn`. La tarea lo espera con
`.await`, y en ese `.await` cede.

```rust,ignore
// src/main.rs
use tokio::task::spawn_blocking;

async fn calcula(nombre: &str, limite: u64, inicio: Instant) {
    let handle =
        spawn_blocking(move || contar_primos(limite));
    let primos = handle.await.unwrap();
    let t = inicio.elapsed().as_millis();
    println!("{nombre}: {primos} primos a los {t} ms");
}

// en main:
//  let b = tokio::spawn(calcula("b", 2_000_000, inicio));
```

```salida
a terminó a los 100 ms
c terminó a los 100 ms
b: 148933 primos a los 240 ms
total: 240 ms
```

El cálculo tarda lo mismo: `spawn_blocking` no lo acelera. Lo que cambia es
dónde corre. Para el runtime, `calcula` volvió a ser una tarea que espera,
y `a` y `c` recuperaron sus 100 ms.

La closure lleva `move` por la razón de `thread::spawn`: corre en otro hilo
y puede vivir más que quien la lanzó, así que debe ser dueña de lo que usa
y ser `Send` ([8.2 Send y Sync]{.ref}). El `unwrap` atiende el `Result` del
handle, que es `Err` si la closure hizo panic.

### [Regla 3:]{.prefijo} `rayon` reparte los datos

El caso contrario no tiene esperas: es un cálculo grande, y la meta es que
termine antes. Si consiste en aplicar la misma operación a muchos elementos
que no dependen entre sí, se puede repartir entre los núcleos. A mano, eso
es partir el vector, lanzar un hilo por parte con `thread::scope`, y juntar
los parciales.

`rayon` hace ese reparto. Se declara con `cargo add rayon`
([7.2 Crates y Cargo]{.ref}), y su `prelude` agrega a las colecciones el
método `par_iter()`. Devuelve un iterador paralelo con los adaptadores y
consumidores de [5.7 Iteradores a fondo]{.ref}: `map`, `filter`, `sum`,
`count`. La cadena queda igual y cambia una palabra.

```rust,ignore
// src/main.rs
use rayon::prelude::*;
use std::thread::available_parallelism;
use std::time::Instant;

// es_primo: la misma función

fn main() {
    let numeros: Vec<u64> = (1..=5_000_000).collect();
    println!("núcleos: {}", available_parallelism().unwrap());

    let inicio = Instant::now();
    let primos =
        numeros.iter().filter(|&&n| es_primo(n)).count();
    let t = inicio.elapsed().as_millis();
    println!("iter:     {primos} primos en {t} ms");

    let inicio = Instant::now();
    let primos =
        numeros.par_iter().filter(|&&n| es_primo(n)).count();
    let t = inicio.elapsed().as_millis();
    println!("par_iter: {primos} primos en {t} ms");
}
```

```salida
$ cargo run --release
núcleos: 8
iter:     348513 primos en 860 ms
par_iter: 348513 primos en 120 ms
```

`available_parallelism` devuelve cuántos hilos puede ejecutar la máquina a
la vez. Los dos conteos coinciden, y eso es lo que el programa garantiza. Los
tiempos son una medición en una máquina: una Apple M1 Pro de ocho núcleos,
dos de ellos de bajo consumo, con otros procesos corriendo. En corridas
repetidas, `par_iter` quedó entre 120 y 130 ms. El factor depende de los
núcleos, de la carga y del trabajo; no es una propiedad de `rayon`. Sin
`--release`, los mismos conteos tardan 1,700 y 270 ms.

### Cuándo no vale la pena

Repartir tiene un costo fijo: partir los datos, despertar hilos y juntar
resultados. Si el trabajo por elemento es trivial o los datos son pocos, ese
costo pesa más que lo que ahorra. La suma de cuadrados
`numeros.iter().map(|n| n * n).sum::<u64>()`, medida en la misma máquina
con `--release`:

| Elementos | `iter()` | `par_iter()` |
| :--- | :--- | :--- |
| 1,000 | menos de 1 µs | entre 15 y 45 µs |
| 100,000 | 40 µs | entre 55 y 185 µs |
| 1,000,000 | entre 0.4 y 0.5 ms | entre 0.25 y 0.55 ms |

Con mil elementos, la versión paralela es más lenta por más de un orden
de magnitud. Con un millón, las dos quedan parejas: un cuadrado y una suma
cuestan tan poco que ocho núcleos no compensan el reparto. El conteo de
primos sí gana, porque cada elemento cuesta cientos de divisiones.

La otra condición no es de costo: los elementos deben ser independientes.
Si el resultado de uno alimenta al siguiente, no hay nada que repartir.

### Prestar sin `Arc`, y lo que no compila

En el programa de los primos, los hilos de `rayon` leen `numeros` sin `Arc`
y sin `move`. Es el principio de `thread::scope` ([8.1 Hilos]{.ref}): la
llamada no regresa hasta que todos los hilos terminaron, así que el préstamo
no puede sobrevivir al vector.

A cambio, `for_each` pide `OP: Fn(Self::Item) + Sync + Send`. La closure se
llama desde varios hilos a la vez, y por eso debe ser `Fn` y no `FnMut`
([4.3 Closures]{.ref}). Acumular en una variable de afuera no pasa de ahí:

```rust,ignore,compile_fail
// src/main.rs
use rayon::prelude::*;

fn main() {
    let numeros: Vec<u64> = (1..=1_000).collect();

    let mut total = 0;
    numeros.par_iter().for_each(|n| total += n);
    println!("{total}");
}
```

```salida
error[E0596]: cannot borrow `total` as mutable, as it is a
              captured variable in a `Fn` closure
7 |     let mut total = 0;
  |         --------- `total` declared here, outside the
  |                   closure
8 |     numeros.par_iter().for_each(|n| total += n);
  |                                 --- ^^^^^ cannot borrow
  |                                 |         as mutable
  |                                 in this closure
```

Con `iter()` ese programa compila e imprime `500500`. Con `par_iter()`, ocho
hilos escribirían `total` a la vez sin coordinarse: una carrera de datos. El
borrow checker la rechaza con la regla de siempre, una `&mut` o varias `&`.
Cambiar `total` por un `Cell<u64>` para mutar a través de `&` tampoco pasa:
*E0277: `Cell<u64>` cannot be shared between threads safely*, porque `Cell`
no es `Sync`.

La salida es no compartir el acumulador. Los consumidores de `rayon` juntan
los parciales de cada hilo: `numeros.par_iter().sum::<u64>()` da `500500`.
Cuando sí hace falta un estado compartido, va en un `Mutex`
([8.3 Estado compartido]{.ref}).

### Combinar los dos mundos

Un servidor async espera casi todo el tiempo, y de vez en cuando una petición
pide un cálculo pesado. El manejador no elige un mundo. Manda el cálculo
afuera con `spawn_blocking` y espera el handle con `.await`, como esperaría
a la red: mientras el pozo calcula, el hilo del runtime sigue atendiendo
peticiones. La función `peticion` de la Aplicación tiene esa forma.

Si el cálculo además se reparte entre núcleos, la closure usa `rayon` por
dentro. Con `(1..=limite).into_par_iter()` en lugar del rango, un manejador
que cuenta los primos hasta cinco millones baja de 860 a unos 140 ms.
`into_par_iter()` es a `par_iter()` lo que `into_iter()` es a `iter()`.

### Lo que hay que llevarse

async no acelera nada. No hace que un cálculo termine antes: hace que un hilo
que iba a estar esperando pueda atender otra cosa. Su ganancia es de escala,
no de velocidad.

Para que un cálculo termine antes hacen falta más núcleos trabajando, y eso
son hilos: a mano, o repartidos por `rayon`.

Dentro de una tarea, todo lo que no sea esperar debe ser breve. Lo que no lo
es sale con `spawn_blocking`. El compilador no vigila esa regla: se sostiene
leyendo el código y midiendo.

## Aplicación

El programa combina los dos mundos. Cuatro peticiones llegan a la vez a un
runtime de un hilo. Cada una espera 100 ms, que simulan la red, y después
cuenta los primos hasta dos millones con la `contar_primos` de antes.

```rust,ignore
// src/main.rs
use std::time::{Duration, Instant};
use tokio::task::spawn_blocking;
use tokio::time::sleep;

async fn peticion(limite: u64) -> usize {
    sleep(Duration::from_millis(100)).await; // la red
    let handle =
        spawn_blocking(move || contar_primos(limite));
    handle.await.unwrap()
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let inicio = Instant::now();
    let mut handles = Vec::new();
    for _ in 0..4 {
        handles.push(tokio::spawn(peticion(2_000_000)));
    }
    let mut primos = 0;
    for handle in handles {
        primos += handle.await.unwrap();
    }
    let t = inicio.elapsed().as_millis();
    println!("{primos} primos en {t} ms");
}
```

La versión de comparación calcula dentro de la tarea: `peticion` termina en
`contar_primos(limite)`, sin `spawn_blocking`. Estas son las salidas de
las dos, compiladas con `--release`:

| El cálculo corre | Salida |
| :--- | :--- |
| dentro de la tarea | `595732 primos en 1050 ms` |
| con `spawn_blocking` | `595732 primos en 340 ms` |

Las esperas se traslapan en las dos versiones: las cuatro terminan a los
100 ms. La diferencia está en los cálculos. Dentro de la tarea corren uno
tras otro en el único hilo del runtime, cuatro veces 240 ms, y durante ese
segundo el runtime no atiende nada más. Con `spawn_blocking`, cada uno
recibe un hilo del pozo y los cuatro corren en paralelo en núcleos
distintos: el total es la espera más un solo cálculo.

## A fondo

**Concurrencia no es paralelismo.** Hay concurrencia cuando varias tareas
están en progreso a la vez, y basta una forma de intercalarlas. Hay
paralelismo cuando varias se ejecutan en el mismo instante, y hacen falta
varios núcleos. El programa de las tres tareas es concurrente sin ser
paralelo: tres esperas en progreso sobre un solo hilo. El conteo con
`par_iter()` es paralelo. Los hilos sirven para las dos cosas; async, solo
para la primera.

**El runtime de varios hilos disimula el error.** Con `#[tokio::main]` a
secas, el runtime tiene un hilo trabajador por núcleo. El programa de
`bloquea` corrido así imprime 100 ms para `a` y `c`: `b` retiene un
trabajador y los otros siete siguen atendiendo. El defecto sigue ahí. Con
ocho tareas que calculan a la vez, una por trabajador, `a` y `c` volvieron a
retrasarse: terminaron entre los 280 y los 450 ms, según la corrida. Un
servidor con el error se ve sano con poca carga y se detiene con mucha, que
es cuando menos conviene.

**El pozo de `spawn_blocking` no es el de los trabajadores.** En el runtime
de un solo hilo, la closure imprime un `ThreadId` distinto al de `main`. El
pozo crea hilos conforme los necesita y, en `tokio` 1.54, admite hasta 512.
Ese límite sirve a llamadas que esperan, no a cálculos: cien cálculos a la
vez serían cien hilos disputando ocho núcleos. Para muchos cálculos conviene
`rayon`, cuyo pozo tiene un hilo por núcleo.

**Una tarea puede ceder a mano.** Con `tokio::task::yield_now().await` cada
10,000 números dentro del bucle que cuenta primos, `a` y `c` terminan a los
100 ms aunque el cálculo siga en el hilo del runtime. Sirve para un bucle
largo que no se puede sacar de la tarea; no reemplaza a `spawn_blocking`.
