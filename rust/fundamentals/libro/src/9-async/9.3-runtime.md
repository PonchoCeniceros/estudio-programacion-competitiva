# 9.3 · El runtime

[9.2 async, await y Future]{.ref} dejó un hecho incómodo: un futuro no hace nada
solo. Llamar a una `async fn` devuelve un valor que describe el trabajo, y ese
valor avanza cuando alguien le llama `poll`. Si devuelve `Pending`, alguien tiene
que volver a llamarlo cuando su espera terminó. Hasta ahora ese alguien fue una
línea copiada como fórmula: `#[tokio::main]`.

Ese alguien es el *runtime*, y Rust no lo trae en la biblioteca estándar: es un
crate. El capítulo responde tres preguntas. Qué hace un runtime, por qué no viene
con el lenguaje y qué escribe `#[tokio::main]` en lugar de quien programa.

## Definiciones y reglas

Runtime
:   la librería que ejecuta futuros. Reúne un ejecutor, un reactor y los
    temporizadores.

Ejecutor
:   *(executor)*: la pieza que guarda la cola de tareas listas y les llama
    `poll`.

Reactor
:   la pieza que pregunta al sistema operativo qué esperas terminaron y
    despierta a las tareas que dependían de ellas.

Tarea
:   *(task)*: un futuro entregado al runtime, que lo ejecuta por su cuenta. Es
    la unidad de concurrencia de async, como el hilo lo es en la sección 8.

`JoinHandle`
:   el valor que devuelve `tokio::spawn`. Es un futuro: con `.await` entrega el
    resultado de la tarea.

::: {.reglas titulo="Las tres reglas del runtime"}
1. Un futuro avanza solo cuando un ejecutor le llama `poll`. El lenguaje fija la
   interfaz, el trait `Future`; el ejecutor lo pone un crate.
2. `block_on` es la entrada desde el código síncrono: bloquea el hilo hasta que
   un futuro termina. `#[tokio::main]` la escribe alrededor de `main`.
3. `tokio::spawn` entrega un futuro al runtime como tarea independiente. La
   concurrencia viene de ceder en cada `.await`, no del número de hilos.
:::

## De un vistazo

| Llamada | Qué hace | Dónde se usa |
| :--- | :--- | :--- |
| `rt.block_on(fut)` | bloquea este hilo hasta que `fut` termina | código síncrono: `main` |
| `tokio::spawn(fut)` | crea una tarea y sigue de inmediato; devuelve un `JoinHandle` | dentro del runtime |
| `handle.await` | espera el resultado de una tarea | código async |
| `join!(a, b)` | avanza varios futuros dentro de la misma tarea | código async |

`block_on` aparece una vez por programa, y casi siempre la escribe el atributo.
Lo demás del programa usa `.await`, `join!` y `spawn`.

## Las reglas, una por una

### El problema de arranque

Para usar `.await` hace falta estar dentro de una `async fn`. El primer intento es
volver asíncrona la función `main`:

```rust,compile_fail
async fn trabajo() -> u32 {
    42
}

async fn main() {
    println!("{}", trabajo().await);
}
```

```salida
error[E0752]: `main` function is not allowed to be `async`
5 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be
  |                 `async`
```

El sistema operativo arranca el programa llamando a `main` como función normal.
Un `main` asíncrono devolvería un futuro, y nadie le llamaría `poll`. El compilador
prefiere rechazarlo a generar un programa que no hace nada. Alguna función
síncrona tiene que crear el runtime y entregarle el primer futuro.

### [Regla 1:]{.prefijo} alguien tiene que llamar `poll`

Un runtime hace tres trabajos, y cada uno tiene nombre:

- El ejecutor tiene una cola de tareas listas. Toma una, le llama `poll` y,
  según la respuesta, la da por terminada o la deja estacionada.
- El reactor conoce las esperas pendientes: un socket sin datos, una conexión
  a medio abrir. Pregunta al sistema operativo cuáles terminaron y regresa esas
  tareas a la cola.
- Los temporizadores hacen lo mismo con el tiempo. `tokio::time::sleep`
  devuelve un futuro que queda `Pending` hasta que pasa su plazo, sin ocupar un
  hilo mientras tanto.

::: {.figura src="figuras/9.3-runtime.html"}
:::

Una tarea estacionada no consume procesador. El ejecutor no le pregunta de nuevo
hasta que el reactor avisa, y por eso un programa con miles de esperas abiertas
puede estar casi en reposo.

Nada de esto viene en `std`, y la razón es de diseño. Un servidor web quiere un
ejecutor con varios hilos y un reactor conectado a la red. Un microcontrolador no
tiene sistema operativo, ni hilos, ni memoria para una cola que crece. Un runtime
único sería demasiado para uno y estorbaría al otro. El lenguaje y `std` fijan
la interfaz: `async`, `.await` y el trait `Future`. El motor queda en manos de
los crates.

`tokio` es el runtime más usado, y el de todos los ejemplos de esta sección.
Existen otros, como `smol` o `embassy`, este último para microcontroladores. Un
futuro escrito solo con `async` y `.await` corre en cualquiera.

### `tokio` en `Cargo.toml`

`tokio` se agrega como cualquier dependencia ([7.2 Crates y Cargo]{.ref}), pero
`tokio = "1"` a secas no alcanza. El crate está partido en *features* y por default
no activa ninguna: quien solo necesita una pieza no compila las demás. Los
ejemplos del capítulo usan tres.

```toml
[dependencies]
tokio = { version = "1", features = [
    "rt-multi-thread", "macros", "time",
] }
```

| Feature | Qué agrega |
| :--- | :--- |
| `rt` | el runtime de un solo hilo y `tokio::spawn` |
| `rt-multi-thread` | el runtime de varios hilos; incluye `rt` |
| `macros` | `#[tokio::main]` y `join!` |
| `time` | `tokio::time::sleep` y los temporizadores |

`features = ["full"]` las activa todas, y es lo usual al empezar. Cada feature
que falta da su propio error:

- Con `tokio = "1"` a secas, `#[tokio::main]` da E0433, *could not find `main` in
  `tokio`*. Lo acompaña el E0752 del apartado anterior: sin macro que la
  reescriba, `main` sigue siendo una `async fn`.
- Con `macros` y sin runtime, el mensaje lo da la propia macro: *The
  #[tokio::main] macro requires rt or rt-multi-thread*.
- Sin `time`, `use tokio::time::sleep` da E0432, con la nota *the item is gated
  behind the `time` feature*.

### [Regla 2:]{.prefijo} `#[tokio::main]` escribe un `block_on`

Con las features puestas, el programa del arranque compila si lleva el atributo:

```rust,ignore
// src/main.rs
async fn trabajo() -> u32 { 42 }

#[tokio::main]
async fn main() {
    println!("{}", trabajo().await);   // 42
}
```

[7.6 Macros y atributos]{.ref} explicó que un atributo de este tipo es una macro
que recibe la función y devuelve otro código. Lo que `#[tokio::main]` devuelve es
un `fn main` normal. La documentación de `tokio` da el equivalente escrito a mano:

```rust,ignore
// src/main.rs
async fn trabajo() -> u32 { 42 }

fn main() {
    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .unwrap()
        .block_on(async {
            println!("{}", trabajo().await);
        })
}
```

Esta versión también imprime `42`. No es la expansión literal, que lleva más
detalles, pero hace lo mismo en tres pasos:

- `Builder::new_multi_thread()` configura un runtime con varios hilos
  trabajadores, y `build()` lo crea.
- `enable_all()` enciende el reactor y los temporizadores. Sin esa línea, el
  primer `sleep` hace panic con *timers are disabled*.
- `block_on` recibe el cuerpo original de `main` como bloque `async` y bloquea el
  hilo principal hasta que termina.

`block_on` es la respuesta al problema de arranque: una función síncrona que
recibe un futuro, le llama `poll` hasta que da `Ready` y devuelve su valor.

### [Regla 3:]{.prefijo} `spawn` lanza una tarea

`block_on` ejecuta un futuro y espera. `tokio::spawn` lo entrega al runtime como
tarea, en la cola del ejecutor, y regresa de inmediato.

```rust,ignore
// src/main.rs
use std::time::Duration;
use tokio::time::sleep;

async fn consultar(id: u32) -> u32 {
    sleep(Duration::from_millis(100)).await;
    id * 10
}

#[tokio::main]
async fn main() {
    let h1 = tokio::spawn(consultar(1));
    let h2 = tokio::spawn(consultar(2));
    let a = h1.await.unwrap();
    let b = h2.await.unwrap();
    println!("{a} {b}");   // 10 20
}
```

Es el dibujo de `thread::spawn` y `join` de [8.1 Hilos]{.ref}, pieza por pieza.
`spawn` devuelve un handle; el handle entrega un `Result`, que es `Err` si la
tarea hizo panic. Cambia la forma de esperar: `join()` bloquea el hilo, y
`handle.await` cede el control. A diferencia de una `async fn` llamada a secas,
la tarea empieza a correr sin que nadie espere su handle.

La otra diferencia es el costo. Un hilo reserva su propio stack y lo administra
el sistema operativo. Una tarea es un valor en el heap, del tamaño de su máquina
de estados, y la administra el ejecutor. El programa siguiente lanza diez mil.

```rust,ignore
// src/main.rs
use std::time::{Duration, Instant};
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    let inicio = Instant::now();
    let mut handles = Vec::new();
    for _ in 0..10_000 {
        handles.push(tokio::spawn(async {
            sleep(Duration::from_millis(100)).await;
        }));
    }
    for h in handles {
        h.await.unwrap();
    }
    println!("{} ms", inicio.elapsed().as_millis());
}
```

En la máquina del autor el total queda cerca de 130 ms, y cerca de 110 con
`--release`: diez mil esperas de 100 ms que transcurren a la vez. La versión con
`thread::spawn` y `thread::sleep` no termina en esa misma máquina. El sistema
operativo se niega a crear tantos hilos y `spawn` hace panic con *failed to spawn
thread*.

`tokio::spawn` pide que el futuro sea `Send` y `'static`, como `thread::spawn`
pide lo mismo de su closure ([8.2 Send y Sync]{.ref}). Las tareas de este
capítulo lo cumplen sin esfuerzo. Cuándo no se cumple, y cómo se lee ese error,
es tema de [9.4 Send en las tareas]{.ref}.

### `spawn` frente a `join!`

`join!`, de [9.2 async, await y Future]{.ref}, también avanza varios futuros a la
vez. La diferencia está en quién los ejecuta.

| | `join!(a, b)` | `tokio::spawn(a)` |
| :--- | :--- | :--- |
| Dónde corre | dentro de la tarea actual | en una tarea nueva |
| Hilos | uno: el de esa tarea | el runtime la reparte |
| Si nadie espera | no corre | corre igual |
| Exige `Send` | no | sí |

Con `join!` los futuros se turnan dentro de una sola tarea: hay concurrencia y no
paralelismo. Con `spawn`, dos tareas pueden correr al mismo tiempo en dos hilos
del runtime. La tercera fila se comprueba con una tarea que nadie espera:

```rust,ignore
// src/main.rs
use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    tokio::spawn(async {
        for n in 1..=10 {
            println!("latido {n}");
            sleep(Duration::from_millis(40)).await;
        }
        println!("la tarea termina");
    });

    sleep(Duration::from_millis(100)).await;
    println!("main termina");
}
```

```salida
latido 1
latido 2
latido 3
main termina
```

El handle se descartó y la tarea corrió de todos modos: soltar un `JoinHandle` no
la cancela. Pero faltan siete latidos y la última línea. Cuando el futuro de
`block_on` termina, `main` regresa, el runtime se destruye y las tareas que
quedaban se cancelan en su siguiente `.await`. Una tarea cuyo resultado importa
se espera con su handle.

Con hilos pasa lo mismo ([8.1 Hilos]{.ref}): el programa termina cuando termina
`main`. En async el descuido es más fácil, porque `spawn` no avisa si su handle
se descarta.

### Un hilo también alcanza

`tokio` tiene dos sabores de runtime. `new_multi_thread` crea un grupo de hilos
trabajadores, uno por núcleo si no se indica otra cosa. `new_current_thread` no
crea ninguno: ejecuta todas las tareas en el hilo que llamó a `block_on`. El
atributo elige con un argumento, `flavor`:

```rust,ignore
// src/main.rs
use std::thread;
use std::time::{Duration, Instant};
use tokio::time::sleep;

async fn esperar(nombre: &'static str, ms: u64) {
    sleep(Duration::from_millis(ms)).await;
    let hilo = thread::current().id();
    println!("{nombre}: {ms} ms, en {hilo:?}");
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let inicio = Instant::now();
    let a = tokio::spawn(esperar("a", 300));
    let b = tokio::spawn(esperar("b", 100));
    let c = tokio::spawn(esperar("c", 200));

    for handle in [a, b, c] {
        handle.await.unwrap();
    }
    println!("total: {} ms", inicio.elapsed().as_millis());
}
```

```salida
b: 100 ms, en ThreadId(1)
c: 200 ms, en ThreadId(1)
a: 300 ms, en ThreadId(1)
total: 304 ms
```

Las tres tareas corren en el hilo 1, el principal, y el total es el de la espera
más larga, no la suma de 600 ms. Cada tarea llega a su `sleep`, devuelve
`Pending` y deja el hilo libre para la siguiente. La concurrencia sale de ceder
en los `.await`. Los hilos adicionales agregan paralelismo, que es otra cosa: con
el sabor de varios hilos el total es el mismo, y cada tarea reporta un
`ThreadId` distinto que cambia de una ejecución a otra.

Lo que un solo hilo no perdona es una tarea que no cede. Un cálculo largo sin
`.await` detiene a todas las demás, y ese caso se trata en
[9.5 async o hilos]{.ref}.

## Aplicación

Un programa lee tres sensores. Cada lectura es una tarea con su propia espera
simulada, y una de ellas falla con un panic. El programa lanza las tres y recoge
los resultados con sus handles.

```rust,ignore
// src/main.rs
use std::time::Duration;
use tokio::time::sleep;

async fn medir(sensor: &'static str, ms: u64) -> u64 {
    sleep(Duration::from_millis(ms)).await;
    if sensor == "gas" {
        panic!("sensor desconectado");
    }
    ms / 2
}

#[tokio::main]
async fn main() {
    let mut tareas = Vec::new();
    for (s, ms) in [("temp", 30), ("gas", 10), ("luz", 20)] {
        tareas.push((s, tokio::spawn(medir(s, ms))));
    }
    for (sensor, handle) in tareas {
        match handle.await {
            Ok(valor) => println!("{sensor}: {valor}"),
            Err(_) => println!("{sensor}: la tarea falló"),
        }
    }
}
```

```salida
thread 'tokio-rt-worker' panicked at src/main.rs:8:9:
sensor desconectado
temp: 15
gas: la tarea falló
luz: 10
```

Tres cosas que leer en la salida:

- El panic aparece primero, porque `gas` es la tarea de espera más corta. Lo
  reporta un hilo trabajador del runtime, `tokio-rt-worker`, no `main`.
- El panic no tumba el programa ni a las otras tareas. El runtime lo atrapa y lo
  entrega como `Err` en el handle de esa tarea, igual que `join()` con un hilo
  ([8.1 Hilos]{.ref}).
- El orden de las líneas es el del `for` que recorre los handles, no el orden en
  que las tareas terminaron. Las tres ya corrían desde el `spawn`; esperar
  primero a la más lenta no retrasa a las otras.

## A fondo

**`block_on` no se llama dentro de una tarea.** Bloquear un hilo trabajador
detendría a las demás tareas de ese hilo, y `tokio` lo impide con un panic. Dentro
de un `main` con `#[tokio::main]`, la línea
`Handle::current().block_on(async { 42 })` compila y falla al ejecutarse:

```salida
thread 'main' panicked at src/main.rs:5:31:
Cannot start a runtime from within a runtime. This happens
because a function (like `block_on`) attempted to block the
current thread while the thread is being used to drive
asynchronous tasks. If you are in an async function, use
`.await` on the future instead of blocking on it.
```

El mensaje trae el arreglo: dentro de código async se usa `.await`.

**Los hilos trabajadores se roban tareas.** En el runtime de varios hilos cada
trabajador tiene su propia cola. Cuando la suya se vacía, toma tareas de la cola
de otro: se llama *work stealing*. Por eso una tarea puede empezar en un hilo y
continuar en otro después de un `.await`, y de ahí sale el `Send` que exige
`spawn`.

**Un ejecutor mínimo es un bucle que llama `poll`.** Cabe en `std`, sin crates.
`ejecutar` hace lo que `block_on`, de la peor manera posible: pregunta sin
descanso hasta que el futuro responde `Ready`.

```rust
use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn ejecutar<F: Future>(futuro: F) -> F::Output {
    let mut fut = pin!(futuro);
    let mut cx = Context::from_waker(Waker::noop());
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

async fn doble(x: u32) -> u32 {
    x * 2
}

fn main() {
    let n = ejecutar(async { doble(4).await + 1 });
    println!("{n}");   // 9
}
```

`pin!` fija el futuro en su lugar, que es lo que `poll` exige de su receptor.
`Waker::noop()` es un despertador que no hace nada, y ahí está lo que le falta al
bucle. Con un futuro que espera de verdad, daría vueltas sin parar y ocuparía un
núcleo completo. Un ejecutor real entrega un `Waker` que regresa la tarea a la
cola, y duerme al hilo mientras la cola está vacía. El reactor es quien usa ese
`Waker`.
