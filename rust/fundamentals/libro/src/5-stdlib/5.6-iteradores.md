# 5.6 · Iteradores

Duplicar los números de un `Vec` con un `for` pide tres piezas que no son la
tarea: un `Vec` vacío y mutable, un `push` por vuelta y la devolución al
final. Filtrar antes de duplicar agrega un `if`, y sumar al final, un
acumulador. El código dice cómo recorrer y esconde qué se calcula.

Cada `for` del libro ya usaba un iterador sin nombrarlo. Un iterador entrega
valores uno por uno, y sobre él se encadenan métodos que transforman,
filtran y resumen sin índices ni variables auxiliares. El capítulo presenta
el modelo y lo mínimo para encadenar; el catálogo completo está en
[5.7 Iteradores a fondo]{.ref}.

## Definiciones y reglas

Iterador
:   un valor de un tipo que implementa el trait `Iterator`. Cada llamada a
    su método `next` entrega el siguiente elemento.

`IntoIterator`
:   el trait de los tipos que saben producir un iterador. Es lo que pide un
    `for`.

Adaptador
:   un método que recibe un iterador y devuelve otro: `map`, `filter`.

Consumidor
:   un método que recorre el iterador y devuelve un valor final: `sum`,
    `count`, `collect`.

Perezoso
:   *(lazy)*: que no hace trabajo hasta que alguien lo pide. Los adaptadores
    lo son.

::: {.reglas titulo="Las tres reglas de los iteradores"}
1. Un iterador es cualquier tipo que implementa `Iterator`: entrega
   `Some(elemento)` con cada `next` y `None` al agotarse.
2. La forma de pedir el iterador decide qué entrega: `&T`, `&mut T` o `T`.
   Solo la última consume la colección.
3. Los adaptadores no recorren nada. La cadena corre cuando un consumidor la
   pide, y cada elemento la atraviesa entera antes del siguiente.
:::

## De un vistazo

Las tres formas de recorrer un `Vec<T>`. Es la tabla de [3.3
Borrowing]{.ref} aplicada a colecciones:

| Método | Entrega | Efecto sobre la colección | En un `for` |
| :--- | :--- | :--- | :--- |
| `v.iter()` | `&T` | intacta; solo lectura | `for x in &v` |
| `v.iter_mut()` | `&mut T` | intacta; elementos modificables | `for x in &mut v` |
| `v.into_iter()` | `T` | consumida; deja de existir | `for x in v` |

El criterio es el de las firmas: `.iter()` por default, `.iter_mut()` para
modificar en su lugar y `.into_iter()` solo si los elementos cambian de
dueño.

## Las reglas, una por una

### [Regla 1:]{.prefijo} un trait con un solo método obligatorio

Un iterador no es un tipo del lenguaje. Es cualquier tipo que implemente
`Iterator`, y el trait solo obliga a esto:

```rust
// std::iter::Iterator, reducido a lo obligatorio
trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}

fn main() {}
```

`Item` es un tipo asociado ([4.2 Generics]{.ref}): cada iterador fija qué
entrega. `next` devuelve `Some` mientras queden elementos y `None` al
agotarse ([5.1 Option]{.ref}). Los demás métodos del trait, entre ellos
`map`, `filter` y `sum`, tienen cuerpo: son métodos por default
([4.1 Traits]{.ref}) escritos sobre `next`. Un tipo que implementa `next`
recibe todos los demás sin escribirlos.

Llamar a `next` a mano muestra lo único que hace un iterador: entregar el
siguiente elemento y avanzar.

```rust
fn main() {
    let v = vec![10, 20];
    let mut it = v.iter();     // Item = &i32

    println!("{:?}", it.next());   // Some(10)
    println!("{:?}", it.next());   // Some(20)
    println!("{:?}", it.next());   // None
}
```

`{:?}` imprime `Some(10)` aunque el valor sea `Some(&10)`: el formato de
depuración sigue las referencias. El binding lleva `mut` porque `next` pide
`&mut self`: avanzar cambia la posición que el iterador guarda. Sin `mut`,
la llamada da E0596, *cannot borrow `it` as mutable, as it is not declared
as mutable*, el mismo error de [3.3 Borrowing]{.ref}.

### `for` es azúcar sobre `IntoIterator`

Un `for` no recorre colecciones: pide un iterador y lo agota. Lo pide con
`IntoIterator::into_iter`, y después llama a `next` hasta recibir `None`. La
expansión aproximada usa el `while let` de [1.6 Control de flujo]{.ref}:

```rust
fn main() {
    let v = vec![1, 2, 3];

    for x in &v {                              // x: &i32
        println!("{x}");
    }

    // expansión aproximada
    let mut it = IntoIterator::into_iter(&v);  // = v.iter()
    while let Some(x) = it.next() {
        println!("{x}");
    }
}
```

`Vec` implementa `IntoIterator` tres veces: para `&Vec<T>`, para
`&mut Vec<T>` y para `Vec<T>`. Cada implementación es una fila de la tabla.
El `&` de la expresión del `for` decide cuál se usa, y con ella si el vector
sobrevive al recorrido. Los rangos de [1.6 Control de flujo]{.ref} son el
caso directo: `0..5` ya es un iterador, y `for i in 0..5` lo agota.

### [Regla 2:]{.prefijo} la forma decide qué entrega

`.iter()` presta cada elemento para leerlo. `.iter_mut()` lo presta para
modificarlo, y el valor se alcanza con `*`, como cualquier `&mut`:

```rust
fn main() {
    let mut precios = vec![100, 250, 80];

    for p in precios.iter_mut() {   // p: &mut i32
        *p += 10;
    }
    for p in precios.iter() {       // p: &i32
        print!("{p} ");             // 110 260 90
    }
    println!();
}
```

`.into_iter()` entrega cada elemento por valor. Para entregar un `String`
tiene que ser su dueño, así que mueve el vector entero, igual que pasarlo a
una función ([3.2 Ownership]{.ref}). El `for` sin `&` hace esa llamada:

```rust,compile_fail
fn main() {
    let nombres = vec![String::from("Ana")];
    for n in nombres {
        println!("{n}");
    }
    println!("{}", nombres.len());
}
```

```salida
error[E0382]: borrow of moved value: `nombres`
2 |     let nombres = vec![String::from("Ana")];
  |         ------- move occurs because `nombres` has type
  |                 `Vec<String>`, which does not implement
  |                 the `Copy` trait
3 |     for n in nombres {
  |              ------- `nombres` moved due to this
  |                      implicit call to `.into_iter()`
...
6 |     println!("{}", nombres.len());
  |                    ^^^^^^^ value borrowed here after move
```

El mensaje nombra la llamada que el `for` esconde: *implicit call to
`.into_iter()`*. Su sugerencia, `for n in &nombres`, es la primera fila de
la tabla.

### De una función propia a `map`

Antes de los adaptadores, una función que los necesita. `aplicar_a_todos`,
ejercicio del curso *Aprende Rust*, recibe un slice y una closure
([4.3 Closures]{.ref}), y devuelve un `Vec` con la closure aplicada a cada
número:

```rust
fn aplicar_a_todos(
    numeros: &[i32],
    f: impl Fn(i32) -> i32,
) -> Vec<i32> {
    let mut resultado: Vec<i32> = vec![];
    for numero in numeros {
        resultado.push(f(*numero));
    }
    resultado
}

fn main() {
    let numeros = [1, 2, 3, 4];
    let extra = 10;
    let dobles = aplicar_a_todos(&numeros, |x| x * 2);
    let con_extra = aplicar_a_todos(&numeros, |x| x + extra);

    println!("{dobles:?}");      // [2, 4, 6, 8]
    println!("{con_extra:?}");   // [11, 12, 13, 14]
}
```

La función es correcta, y es `map` escrito a mano. `map` es un adaptador
que aplica una closure a cada elemento. Con él y con `collect`, que reúne
los resultados en un `Vec`, el cuerpo queda en una línea:

```rust
fn aplicar_a_todos(
    numeros: &[i32],
    f: impl Fn(i32) -> i32,
) -> Vec<i32> {
    numeros.iter().map(|n| f(*n)).collect()
}

fn main() {
    let dobles = aplicar_a_todos(&[1, 2, 3, 4], |x| x * 2);
    println!("{dobles:?}");      // [2, 4, 6, 8]
}
```

Desaparecen el `Vec` mutable, el `push` y la devolución. `.iter()` entrega
`&i32`, y la closure lo desreferencia con `*n` antes de pasarlo a `f`, que
pide un `i32`.

### `filter` y el doble `&`

`filter` conserva los elementos para los que su closure, el predicado,
devuelve `true`. Escrito como si recibiera números, no compila:

```rust,compile_fail
fn main() {
    let v = vec![1, 2, 3, 4];
    let pares: Vec<&i32> =
        v.iter().filter(|n| n % 2 == 0).collect();
}
```

```salida
error[E0369]: cannot calculate the remainder of
              `&&{integer}` divided by `{integer}`
4 |         v.iter().filter(|n| n % 2 == 0).collect();
  |                             - ^ - {integer}
  |                             |
  |                             &&{integer}
```

El predicado recibe `&&i32`, dos capas de referencia, y cada una tiene un
origen distinto:

1. `v.iter()` sobre un `Vec<i32>` entrega `&i32`. Es la primera capa.
2. `filter` tiene que devolver el elemento si pasa, así que no se lo da al
   predicado: se lo presta. Prestar un `&i32` produce un `&&i32`.

`map` no tiene la segunda capa porque consume el elemento para producir otro:
su closure lo recibe tal como sale del iterador. Para llegar al `i32` se
puede desreferenciar dos veces en el cuerpo, con `**n`, o quitar las capas
en el parámetro con un patrón. En un patrón, `&` hace lo
contrario que en una expresión: en vez de crear una referencia, encaja con
una y liga lo que hay detrás. `|&&n|` quita las dos capas y deja `n: i32`:

```rust
fn main() {
    let v = vec![1, 2, 3, 4];
    let pares: Vec<&i32> =
        v.iter().filter(|&&n| n % 2 == 0).collect();
    println!("{pares:?}");   // [2, 4]
}
```

`filter` no cambia el tipo de los elementos: entran `&i32` y salen `&i32`,
por eso `pares` es un `Vec<&i32>`. El doble `&` solo estorba con operadores
y patrones. Un predicado como `|p| p.precio > 50` compila tal cual: el
acceso a un campo o a un método lo resuelve el punto, que sigue las
referencias por su cuenta ([3.5 impl y métodos]{.ref}).

### [Regla 3:]{.prefijo} los adaptadores son perezosos

Un adaptador no recorre nada: describe una operación y la deja pendiente.
Un `println!` dentro de cada closure lo hace visible. El programa arma la
cadena, imprime una línea, y solo después la consume con `sum`:

```rust
fn main() {
    let v = vec![1, 2, 3, 4];
    let cadena = v
        .iter()
        .filter(|&&n| {
            println!("filter {n}");
            n % 2 == 0
        })
        .map(|n| {
            println!("  map {n}");
            n * 10
        });

    println!("antes de consumir");
    let total: i32 = cadena.sum();
    println!("total {total}");
}
```

```salida
antes de consumir
filter 1
filter 2
  map 2
filter 3
filter 4
  map 4
total 60
```

La salida muestra las dos mitades de la regla. Armar la cadena no imprimió
nada: `cadena` es un iterador en espera, y las closures corrieron cuando
`sum` pidió los elementos. Y las líneas salen intercaladas. Si `filter`
terminara antes de que empezara `map`, sus cuatro líneas saldrían
seguidas; entre etapas no hay un `Vec` intermedio, solo un elemento en
tránsito.

Una cadena sin consumidor es trabajo descrito y nunca hecho. Escrita como
enunciado suelto, `v.iter().map(|n| n * 2);`, el compilador la señala con
un aviso:

```salida
warning: unused `Map` that must be used
3 |     v.iter().map(|n| n * 2);
  |     ^^^^^^^^^^^^^^^^^^^^^^^
  = note: iterators are lazy and do nothing unless consumed
```

Los métodos de un iterador son entonces de dos clases:

| Clase | Devuelve | ¿Recorre? | Ejemplos |
| :--- | :--- | :--- | :--- |
| Adaptador | otro iterador | no | `map`, `filter` |
| Consumidor | un valor final | sí, y pone la cadena en marcha | `sum`, `count`, `collect` |

Una cadena son varios adaptadores y un consumidor al final. El consumidor
pide un elemento al último adaptador, este lo pide al anterior, y así hasta
el origen. Cada elemento atraviesa la cadena completa antes de que el origen
entregue el siguiente:

### Consumidores: `sum`, `count` y `collect`

`count` devuelve un `usize` con el número de elementos. `sum` los suma, y
`collect` los reúne en una colección:

```rust
fn main() {
    let v = vec![1, 2, 3, 4];

    let total: i32 = v.iter().sum();           // 10
    let cuantos = v.iter().count();            // 4
    let dobles: Vec<i32> =
        v.iter().map(|n| n * 2).collect();     // [2, 4, 6, 8]

    println!("{total} {cuantos} {dobles:?}");
}
```

`map(|n| n * 2)` recibe `&i32` y aun así compila: la multiplicación está
implementada también para referencias a enteros ([4.5 Operadores]{.ref}), y
el resultado es un `i32`.

`sum` y `collect` llevan anotación y `count` no. Los dos primeros son
genéricos en lo que devuelven: `sum` produce cualquier tipo que implemente
el trait `Sum`, y `collect`, cualquier colección que implemente
`FromIterator` ([5.7 Iteradores a fondo]{.ref}). Sin anotación, el compilador no tiene de dónde deducirlo:

```rust,compile_fail
fn main() {
    let v = vec![1, 2, 3, 4];
    let copia = v.iter().collect();
    println!("{copia:?}");
}
```

```salida
error[E0283]: type annotations needed
3 |     let copia = v.iter().collect();
  |         ^^^^^            ------- type must be known
  |                                  at this point
  = note: cannot satisfy `_: FromIterator<&i32>`
help: consider giving `copia` an explicit type
3 |     let copia: Vec<_> = v.iter().collect();
  |              ++++++++
```

La nota lo dice en términos del trait: el destino tiene que implementar
`FromIterator<&i32>`, y muchos tipos lo hacen.

El destino se dice de dos formas equivalentes. Una es la anotación de la
variable: `let copia: Vec<&i32>`. La otra es el *turbofish*, que pone el
tipo en el método: `.collect::<Vec<&i32>>()`. Sirve cuando el resultado no
va a una variable, por ejemplo al final de una expresión más larga. En los
dos casos basta `Vec<_>`: el tipo de los elementos sale del iterador.

### Costo cero

Una cadena es una abstracción de costo cero, como los generics de
[4.2 Generics]{.ref}. Cada adaptador es un struct genérico que guarda el
iterador anterior y la closure. Al compilar, la monomorfización genera un
`next` concreto para cada uno, y el optimizador los integra en el bucle del
consumidor. Queda un bucle comparable al escrito a mano, sin llamadas a
`filter` ni a `map` y sin colecciones intermedias.

## Aplicación

Una tienda, a partir del ejemplo del curso *Aprende Rust*: de una lista de
productos, los textos de los que cuestan menos de 50 pesos. La misma tarea
se resuelve con un `for` y con una cadena:

```rust
struct Producto {
    nombre: &'static str,
    precio: f64,
}

fn baratos_con_for(productos: &[Producto]) -> Vec<String> {
    let mut textos = Vec::new();
    for p in productos {
        if p.precio < 50.0 {
            let t = format!("{}: ${:.2}", p.nombre, p.precio);
            textos.push(t);
        }
    }
    textos
}

fn baratos_con_cadena(productos: &[Producto]) -> Vec<String> {
    productos
        .iter()
        .filter(|p| p.precio < 50.0)
        .map(|p| format!("{}: ${:.2}", p.nombre, p.precio))
        .collect()
}

fn main() {
    let productos = vec![
        Producto { nombre: "teclado", precio: 45.0 },
        Producto { nombre: "monitor", precio: 180.0 },
        Producto { nombre: "ratón", precio: 15.5 },
    ];

    let a = baratos_con_for(&productos);
    let b = baratos_con_cadena(&productos);
    println!("{}", a == b);   // true
    println!("{a:?}");
    // ["teclado: $45.00", "ratón: $15.50"]
}
```

Las dos funciones dan el mismo resultado, y la cadena lee como la tarea:
filtrar por precio, armar el texto, reunir. El `for` reparte la misma
lógica entre un `Vec` mutable, un `if` y un `push`. El predicado recibe
`&&Producto` y no lo desempaca: el punto de `p.precio` sigue las dos
referencias. Las tres reglas están en juego. `.iter()` presta los productos,
así que `productos` sigue disponible para la segunda función. `filter` y
`map` no hacen nada hasta que `collect` pide los elementos.

## A fondo

**El tipo de una cadena crece con cada adaptador.** El compilador lo escribe
completo en un error de tipos. Para `v.iter().filter(...).map(...)` es
`Map<Filter<std::slice::Iter<'_, i32>, {closure}>, {closure}>`: cada
adaptador envuelve al anterior. Los tipos de las closures no se pueden
escribir ([4.3 Closures]{.ref}), y por eso una función que devuelve una
cadena declara `-> impl Iterator<Item = i32>` ([4.2 Generics]{.ref}).

**Lo comprobado sobre el costo cero.** Con `rustc -O` en aarch64, una suma
de pares por diez escrita con `for` y la misma suma con
`filter`/`map`/`sum` compilan a bucles de la misma forma: vectorizados, de
16 elementos por vuelta, sin ninguna llamada a función. No son idénticos
instrucción por instrucción (106 y 100 líneas de ensamblador). No se midió
el tiempo de ejecución.

**Un iterador agotado no se reinicia.** Después del primer `None`, el
iterador de un `Vec` sigue devolviendo `None`. Para recorrer otra vez se
pide un iterador nuevo con otro `.iter()`. El trait no lo garantiza para
todo tipo: un iterador propio podría volver a dar `Some`. Los que prometen
quedarse en `None` implementan el trait `FusedIterator`.
