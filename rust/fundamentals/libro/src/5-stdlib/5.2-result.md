# 5.2 · Result

Convertir el texto `"42"` en un número puede salir bien. Convertir `"hola"` no
puede. Leer un archivo falla si el archivo no existe, y una conexión falla si la
red está caída. En estos casos el resultado no solo puede faltar, como en
[5.1 Option]{.ref}: falta por un motivo, y quien llama necesita conocerlo.

Muchos lenguajes resuelven esto con excepciones: la función lanza el error y
alguien, más arriba, tal vez lo atrapa. Nada en la firma avisa que la función
puede fallar. Rust no tiene excepciones. El error viaja en el tipo de retorno, y
como es parte del tipo, el compilador no permite usar el valor sin decidir antes
qué hacer con el error.

## Definiciones y reglas

Panic
:   la detención del programa con un mensaje, el archivo y la línea. Es la
    respuesta a un error irrecuperable: un bug.

Error recuperable
:   una falla esperable, como un texto que no es número, que el programa puede
    manejar y seguir.

`Result<T, E>`
:   el enum de la biblioteca estándar para una operación que puede fallar:
    `Ok(T)` lleva el valor y `Err(E)` lleva el error.

Propagar
:   devolver el error a la función que llamó, en lugar de manejarlo en el
    lugar.

::: {.reglas titulo="Las tres reglas de Result"}
1. Un bug detiene el programa con `panic!`; un error esperable se devuelve en un
   `Result`.
2. El valor de un `Result` no se usa sin abrir antes el caso `Err`.
3. `?` propaga el `Err` a quien llama: solo cabe en una función que devuelve
   `Result` u `Option`, y convierte el error con `From`.
:::

## De un vistazo

| Situación | Herramienta |
| :--- | :--- |
| un bug que nunca debería ocurrir | `panic!` |
| prototipo o test | `unwrap`, `expect` |
| error esperable que se maneja aquí | `match`, `if let` |
| hay un valor default razonable | `unwrap_or` |
| no se sabe manejar aquí, quien llama sí | `?` |

Las dos primeras filas detienen el programa ante un `Err`; las otras tres lo
manejan sin detenerlo. Un `unwrap` que sobrevive al prototipo suele ser un `?` o
un `match` pendiente.

## Las reglas, una por una

### [Regla 1:]{.prefijo} dos clases de error

Algunas fallas son bugs: un estado que el programa nunca debió alcanzar. Para esas,
seguir adelante solo produciría resultados falsos. La macro `panic!` detiene el
programa e informa dónde:

```rust,should_panic
fn trimestre(mes: u32) -> u32 {
    if mes < 1 || mes > 12 {
        panic!("mes fuera de rango: {mes}");
    }
    (mes - 1) / 3 + 1
}

fn main() {
    println!("{}", trimestre(5));
    println!("{}", trimestre(13));
}
```

```salida
2
thread 'main' panicked at src/main.rs:3:9:
mes fuera de rango: 13
```

La primera llamada imprime `2`; la segunda detiene el programa. Algunas
operaciones hacen panic por sí solas: el desbordamiento de
[1.2 Tipos escalares]{.ref} y el índice fuera de rango de
[2.1 Tuplas y arreglos]{.ref}.

Otras fallas son parte del funcionamiento normal. Un usuario que escribe
`"cuarenta"` donde se pedía un número no es un bug del programa. Detenerlo sería
desproporcionado: lo razonable es avisar y pedir otra vez. Para esas fallas, la
función devuelve un `Result`.

### `Result`, otro enum de dos variantes

La biblioteca estándar lo declara así, con un parámetro de tipo para el valor y
otro para el error ([4.2 Generics]{.ref}):

```rust
enum Resultado<T, E> {
    Ok(T),
    Err(E),
}

fn main() {
    let r: Resultado<i32, &str> = Resultado::Ok(42);
}
```

El ejemplo usa otro nombre para no chocar con el original. `Result`, `Ok` y `Err`
están siempre disponibles, sin prefijo: se escriben `Ok(42)`, no
`Result::Ok(42)`.

El primer `Result` del libro es `parse`, el método de `&str` que convierte un texto
en otro tipo. El turbofish dice a qué tipo convertir: `"42".parse::<i32>()` da
`Ok(42)`, y `"hola".parse::<i32>()` da un `Err` con un valor de tipo
`ParseIntError`. Un `match` abre el resultado como cualquier otro enum:

```rust
fn main() {
    for texto in ["42", "hola", "-7"] {
        match texto.parse::<i32>() {
            Ok(n) => println!("número: {n}"),
            Err(e) => println!("{texto}: {e}"),
        }
    }
}
```

```salida
número: 42
hola: invalid digit found in string
número: -7
```

El `match` obliga a cubrir los dos casos ([2.3 Enums]{.ref}). El error se imprime
con `{}` porque `ParseIntError` implementa `Display`.

La diferencia con `Option` está en el segundo parámetro. `None` dice que no hay
valor y nada más. `Err(e)` dice que la operación falló, y `e` explica por qué.
Criterio: si la ausencia es normal y esperada, como un elemento que no está en un
arreglo, corresponde `Option`. Si es una falla que amerita explicación, corresponde
`Result`.

### [Regla 2:]{.prefijo} el valor no se usa sin abrir el `Result`

`parse` no devuelve un `i32`. Devuelve un `Result<i32, ParseIntError>`, y tratarlo
como número no compila:

```rust,compile_fail
fn main() {
    let n: i32 = "42".parse::<i32>();
    println!("{}", n + 1);
}
```

```salida
error[E0308]: mismatched types
2 |     let n: i32 = "42".parse::<i32>();
  |            ---   ^^^^^^^^^^^^^^^^^^^ expected `i32`,
  |            |     found `Result<i32, ParseIntError>`
  |            expected due to this
help: consider using `Result::expect` to unwrap the
      `Result<i32, ParseIntError>` value, panicking if
      the value is a `Result::Err`
```

Es lo que una excepción no garantiza. Con el texto `"42"` el programa funcionaría,
pero el compilador no lo sabe, y exige decidir qué pasa con el `Err`. Además de
`match` e `if let`, hay tres métodos que lo deciden en una línea:

```rust
fn main() {
    let a: i32 = "42".parse().unwrap();
    let b: i32 = "7".parse().expect("el texto es fijo");
    let c: i32 = "x".parse().unwrap_or(0);
    println!("{a} {b} {c}");   // 42 7 0
}
```

Aquí `parse` va sin turbofish: la anotación de cada variable dice a qué tipo
convertir. `unwrap` saca el valor de `Ok` y hace panic con un `Err`. `expect` hace
lo mismo con un mensaje propio. `unwrap_or` cambia el `Err` por un valor default y
nunca hace panic; funciona igual que en `Option`.

El mensaje de `expect` documenta por qué el autor cree que el `Err` no puede
ocurrir. Si ocurre, el panic muestra esa explicación junto al error original:

```rust,should_panic
fn main() {
    let n: u8 = "cuarenta".parse().expect("el texto es fijo");
    println!("{n}");
}
```

```salida
thread 'main' panicked at src/main.rs:2:36:
el texto es fijo: ParseIntError { kind: InvalidDigit }
```

### Propagar a mano

A veces la función que encuentra el error no sabe qué hacer con él. Una función que
suma dos textos no sabe si quien la llama quiere avisar al usuario, usar un cero o
abortar. Lo honesto es devolver el error tal cual. Con `match`, cada operación
lleva su rama `Err` con `return`:

```rust
use std::num::ParseIntError;

fn sumar(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x = match a.parse::<i32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    let y = match b.parse::<i32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    Ok(x + y)
}

fn main() {
    println!("{:?}", sumar("2", "40"));
    println!("{:?}", sumar("2", "xl"));
}
```

```salida
Ok(42)
Err(ParseIntError { kind: InvalidDigit })
```

`{:?}` imprime el `Result` completo, con su variante. La línea `use` permite escribir `ParseIntError` sin su ruta completa,
`std::num::ParseIntError` ([7.1 Módulos]{.ref}). El éxito se envuelve en `Ok`,
porque la función devuelve un `Result`. Cada operación que puede fallar suma cuatro
líneas idénticas.

### [Regla 3:]{.prefijo} `?`, el mismo patrón en un carácter

El operador `?`, escrito después de una expresión de tipo `Result`, hace lo mismo
que cada `match` del ejemplo anterior. Si el resultado es `Ok(v)`, la expresión vale
`v`. Si es `Err(e)`, la función termina ahí y devuelve el error:

```rust
use std::num::ParseIntError;

fn sumar(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", sumar("2", "40"));   // Ok(42)
}
```

::: {.figura src="figuras/5.2-interrogacion.html"}
:::

**Primera condición: necesita a dónde propagar.** `?` puede terminar la función con
un `Err`, así que la función debe devolver `Result` (u `Option`, con `?` sobre
`Option`: [5.1 Option]{.ref}). En un `main` que no devuelve nada, no compila:

```rust,compile_fail
fn main() {
    let n: i32 = "42".parse()?;
    println!("{n}");
}
```

```salida
error[E0277]: the `?` operator can only be used in a
              function that returns `Result` or `Option`
              (or another type that implements
              `FromResidual`)
1 | fn main() {
  | --------- this function should return `Result` or
  |           `Option` to accept `?`
2 |     let n: i32 = "42".parse()?;
  |                              ^ cannot use the `?`
  |                                operator in a function
  |                                that returns `()`
```

`main` también puede devolver un `Result`. En su forma mínima, el éxito es `Ok(())`
y un `Err` termina el programa con el error impreso:

```rust
use std::num::ParseIntError;

fn main() -> Result<(), ParseIntError> {
    let n: i32 = "42".parse()?;
    println!("{n}");   // 42
    Ok(())
}
```

La ayuda del compilador propone otro tipo de error, `Box<dyn std::error::Error>`,
que acepta errores de cualquier clase ([7.4 Manejo de errores idiomático]{.ref}).

**Segunda condición: convierte el error con `From`.** Antes de devolver `e`, `?`
llama a `From::from(e)` ([4.4 Traits de la stdlib]{.ref}). Por eso el `E` de la
función no tiene que coincidir con el de la operación: basta con que exista la
conversión. Si no existe, el error lo dice:

```rust,compile_fail
fn doble(t: &str) -> Result<i32, String> {
    let n: i32 = t.parse()?;
    Ok(n * 2)
}

fn main() {}
```

```salida
error[E0277]: `?` couldn't convert the error to `String`
1 | fn doble(t: &str) -> Result<i32, String> {
  |                      ------------------- expected
  |                      `String` because of this
2 |     let n: i32 = t.parse()?;
  |                    -------^ the trait
  |                    |        `From<ParseIntError>` is
  |                    |        not implemented for
  |                    |        `String`
  |                    this can't be annotated with `?`
  |                    because it has type
  |                    `Result<_, ParseIntError>`
  = note: the question mark operation (`?`) implicitly
          performs a conversion on the error value using
          the `From` trait
```

`String` sí implementa `From<&str>`. Un `Err("...")` de tipo `&str` pasa por `?`
hacia una función que devuelve `Result<_, String>`, y llega convertido. Para el
`ParseIntError`, el método `map_err` transforma el error antes de que `?` lo vea.
Recibe una closure ([4.3 Closures]{.ref}) que toma el error y devuelve el nuevo:

```rust
fn doble(t: &str) -> Result<i32, String> {
    let n: i32 = t
        .parse()
        .map_err(|_| format!("no es número: {t}"))?;
    Ok(n * 2)
}

fn main() {
    println!("{:?}", doble("21")); // Ok(42)
    println!("{:?}", doble("xx")); // Err("no es número: xx")
}
```

La closure descarta el error original con `_` y describe el dato que falló. Los
errores propios se definen en [7.4 Manejo de errores idiomático]{.ref}.

## Aplicación

Un ejercicio del curso *Aprende Rust*: sumar los enteros de una línea e ignorar
lo que no convierte. El método `split_whitespace` de `&str` entrega los trozos
separados por espacios; un `for` los recorre, y `if let Ok` salta los inválidos:

```rust
fn sumar_linea(linea: &str) -> i32 {
    let mut suma = 0;
    for trozo in linea.split_whitespace() {
        if let Ok(n) = trozo.parse::<i32>() {
            suma += n;
        }
    }
    suma
}

fn main() {
    println!("{}", sumar_linea("3 10 abc 7"));   // 20
}
```

Esta versión toma la decisión de la fila «hay un valor default razonable»: un trozo
inválido cuenta como nada. Si un trozo inválido significa que la línea entera está
mal, la decisión correcta es otra: devolver el error y dejar que decida quien
llama. El cambio es el tipo de retorno, un `?` y un `Ok` final:

```rust
use std::num::ParseIntError;

fn sumar_linea(linea: &str) -> Result<i32, ParseIntError> {
    let mut suma = 0;
    for trozo in linea.split_whitespace() {
        suma += trozo.parse::<i32>()?;
    }
    Ok(suma)
}

fn main() {
    for linea in ["3 10 7", "3 10 abc 7"] {
        match sumar_linea(linea) {
            Ok(s) => println!("{linea}: {s}"),
            Err(e) => println!("{linea}: {e}"),
        }
    }
}
```

```salida
3 10 7: 20
3 10 abc 7: invalid digit found in string
```

En la segunda línea, el `?` sale de la función al llegar a `abc`: el `7` ya no se
suma. La firma de la segunda versión avisa que la suma puede fallar; la de la
primera promete que siempre da un número.

## A fondo

**Ignorar un `Result` produce un aviso.** `Result` lleva el atributo `must_use`.
Llamar a `sumar("2", "x");` como enunciado, sin usar el valor, compila con el aviso
*unused `Result` that must be used*. Si se quiere descartar a propósito, se escribe
`let _ = sumar("2", "x");`.

**Un `main` que devuelve `Err` sale con código 1.** Antes imprime el error con el
formato de `{:?}`: con `"x".parse()?`, la salida es
`Error: ParseIntError { kind: InvalidDigit }`. El código de salida distinto de cero
permite que un script detecte la falla. El uso con archivos está en
[7.5 Entrada y salida]{.ref}.

**`fmt::Result` es un `Result`.** El tipo que devuelve `fmt` en
[4.4 Traits de la stdlib]{.ref} es un alias de `Result<(), fmt::Error>`. El `()`
dice que una escritura exitosa no produce valor: solo importa si falló.

**`Result` y `Option` se convierten entre sí.** `.ok()` cambia un `Result` en un
`Option` y descarta el error. En sentido contrario, `.ok_or(e)` cambia `None` por
`Err(e)`. Hacen falta porque `?` no mezcla los dos tipos: en una función que
devuelve `Result`, un `?` sobre un `Option` no compila.

**`unwrap_or` evalúa su argumento siempre.** Si el default es caro de calcular,
`unwrap_or_else` recibe una closure y solo la llama ante un `Err`.
`unwrap_or_default` usa el valor de `Default` del tipo: `0` para los números.

**Juntar muchos `Result` en uno.** Recorrer una lista de textos y obtener todos los
números o el primer error se hace con `collect` ([5.7 Iteradores a fondo]{.ref}).
