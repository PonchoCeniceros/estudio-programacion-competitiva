# 5.5 · Otras colecciones

`Vec` y `HashMap` resuelven la mayoría de los programas. Cada una tiene, sin
embargo, operaciones que le salen caras. Atender una fila con un `Vec` parece
natural: se agrega al final con `push` y se atiende al primero con `remove(0)`.
Pero `remove(0)` desplaza un lugar cada elemento restante, y con una fila larga
cada turno cuesta más.

Algo parecido pasa con el orden. Un `HashMap` no recorre sus llaves en ningún
orden fijo, y encontrar el mayor de un `Vec` exige revisarlo entero. Para esas
operaciones concretas la biblioteca estándar trae otras colecciones, todas bajo
`std::collections`.

## Definiciones y reglas

Costo
:   cuánto trabajo hace una operación según el número de elementos, *n*. Se
    escribe con la notación *O* (*big O*), que describe cómo crece.

`O(1)`
:   costo constante: no depende de cuántos elementos haya.

`O(n)`
:   costo lineal: crece en proporción a *n*. Con el doble de elementos, el doble
    de trabajo.

`O(log n)`
:   costo logarítmico: duplicar *n* agrega un paso. Con un millón de elementos
    son unos 20 pasos.

Cola
:   *(queue)*: una secuencia donde se mete por un extremo y se saca por el otro.
    El primero en entrar es el primero en salir.

Montículo binario
:   *(binary heap)*: una estructura que siempre tiene el elemento mayor a la
    mano. No tiene relación con el heap de memoria de [3.1 Stack y heap]{.ref}.

Árbol B
:   *(B-tree)*: un árbol que guarda sus llaves ordenadas. Es la estructura
    detrás de `BTreeMap` y `BTreeSet`.

::: {.reglas titulo="Tres reglas para elegir colección"}
1. Se empieza por `Vec` o `HashMap`. Se cambia cuando una operación concreta
   sale cara.
2. `BinaryHeap` entrega siempre el mayor. Para el menor, cada elemento se
   envuelve en `Reverse`.
3. Las colecciones ordenadas piden `Ord` a sus llaves; las de hash piden
   `Hash + Eq`.
:::

## De un vistazo

| Colección | Para qué sirve | Costo típico |
| :--- | :--- | :--- |
| `Vec<T>` | secuencia con acceso por índice | índice y `push` al final `O(1)` |
| `VecDeque<T>` | cola: mete y saca por los dos extremos | `O(1)` en ambos extremos |
| `HashMap<K, V>` | llave → valor, sin orden | `O(1)` promedio |
| `BTreeMap<K, V>` | llave → valor, ordenado por llave | `O(log n)` |
| `BinaryHeap<T>` | sacar siempre el mayor | ver el mayor `O(1)`, meter y sacar `O(log n)` |
| `HashSet<T>` | valores únicos, sin orden | `O(1)` promedio |
| `BTreeSet<T>` | valores únicos, ordenados | `O(log n)` |

Los dos conjuntos son sus mapas sin valor: solo guardan llaves. La columna de
costo es la que decide el cambio, y solo cuando la operación cara se repite
mucho.

## Las reglas, una por una

### [Regla 1:]{.prefijo} `Vec` o `HashMap` primero

Sobre `vec!["Ana", "Beto", "Caro"]`, `remove(0)` devuelve `"Ana"` y deja
`["Beto", "Caro"]`. El resultado es correcto; el problema es su costo. Los elementos de un `Vec` van seguidos en memoria y el
índice 0 está siempre al inicio del bloque ([5.3 Vec]{.ref}). Para cerrar el
hueco, `remove(0)` copia cada elemento restante un lugar a la izquierda: es
`O(n)`. Con tres nombres no se nota. Con cien mil turnos, atender a cada
persona recorre a todas las demás.

El criterio va en ese orden. `Vec` y `HashMap` son la elección inicial, y casi
siempre la final. Otra colección se justifica cuando el programa repite una
operación que en ellas sale cara: sacar por el frente, recorrer en orden o
pedir el mayor una y otra vez.

### `VecDeque`: una cola por los dos extremos

`VecDeque` (*double-ended queue*, cola de dos extremos) mete y saca por el frente
y por el final, siempre en `O(1)`:

```rust
use std::collections::VecDeque;

fn main() {
    let mut cola = VecDeque::new();
    cola.push_back("Ana");
    cola.push_back("Beto");
    cola.push_front("Urgente");

    println!("{:?}", cola.pop_front());   // Some("Urgente")
    println!("{:?}", cola.pop_back());    // Some("Beto")
    println!("{cola:?}");                 // ["Ana"]
    println!("{:?}", cola.front());       // Some("Ana")
}
```

`pop_front` y `pop_back` devuelven `Option`: una cola vacía da `None`
([5.1 Option]{.ref}). `front` y `back` prestan el elemento de cada extremo sin
sacarlo. El truco está en cómo guarda los datos. El bloque es el mismo de un
`Vec`, pero el `VecDeque` lleva además el índice de su frente. Sacar el primero
no mueve nada: el índice avanza.

:::

Es la colección indicada para una cola de tareas, un búfer de los últimos *k*
eventos o un recorrido en anchura (*breadth-first search*), que visita los
nodos en el orden en que los descubre.

### [Regla 2:]{.prefijo} `BinaryHeap` entrega el mayor

Un `BinaryHeap` no guarda sus elementos en orden. Garantiza una sola cosa: el
mayor está siempre arriba. `peek` lo presta en `O(1)` y `pop` lo saca en
`O(log n)`:

```rust
use std::collections::BinaryHeap;

fn main() {
    let mut montones = BinaryHeap::from([3, 1, 4, 1, 5]);
    println!("{:?}", montones.peek());   // Some(5)
    println!("{:?}", montones.pop());    // Some(5)
    println!("{:?}", montones.pop());    // Some(4)
    println!("{}", montones.len());      // 3
}
```

Es un *max-heap*: sale el mayor. El descuido más común es usarlo esperando el
menor, por ejemplo para atender primero la tarea de prioridad 1. El programa
compila y entrega todo al revés.

Para el menor no hay otra colección. Se envuelve cada elemento en
`std::cmp::Reverse`, un tuple struct cuyo `Ord` es el del valor envuelto,
invertido ([4.4 Traits de la stdlib]{.ref}). Para el heap, el menor de los
valores es ahora el mayor de los `Reverse`:

```rust
use std::cmp::Reverse;
use std::collections::BinaryHeap;

fn main() {
    let mut menores = BinaryHeap::new();
    for n in [3, 1, 4] {
        menores.push(Reverse(n));
    }
    println!("{:?}", menores.peek());   // Some(Reverse(1))

    let Reverse(minimo) = menores.pop().unwrap();
    println!("{minimo}");               // 1
}
```

Lo que sale es un `Reverse`, no el número. El patrón `Reverse(minimo)` lo
desarma en el mismo `let` ([2.4 Patrones]{.ref}).

### `BTreeMap`: las llaves en orden

`BTreeMap` tiene la misma interfaz que `HashMap`: `insert`, `get`, `remove` y
`entry`. La diferencia está en el recorrido, que sale siempre en orden de llave,
sin importar el orden de inserción:

```rust
use std::collections::BTreeMap;

fn main() {
    let mut ventas = BTreeMap::new();
    ventas.insert(3, 30);
    ventas.insert(1, 10);
    ventas.insert(12, 5);
    ventas.insert(2, 20);

    for (mes, monto) in &ventas {
        println!("{mes}: {monto}");   // 1, 2, 3, 12
    }
    // imprimen Some((1, 10)) y Some((12, 5))
    println!("{:?}", ventas.first_key_value());
    println!("{:?}", ventas.last_key_value());

    for (mes, monto) in ventas.range(2..=3) {
        println!("{mes}: {monto}");   // 2: 20 y 3: 30
    }
}
```

El orden habilita tres operaciones que un `HashMap` no tiene.
`first_key_value` y `last_key_value` devuelven los extremos, en un `Option`.
`range` recorre solo las llaves dentro de un rango, con la sintaxis de rangos
de [1.6 Control de flujo]{.ref}. Con llaves de texto el orden es el de
`String`: alfabético por bytes, así que `"abril"` queda antes que `"enero"`.

A cambio, cada acceso es `O(log n)` en lugar del `O(1)` promedio del hash. Se
elige `BTreeMap` cuando el orden importa. `BTreeSet` es lo mismo sin valores:
un conjunto que se recorre ordenado y responde `first` y `last`.

### [Regla 3:]{.prefijo} lo que cada colección pide a sus llaves

Cada colección pide un trait distinto, según cómo ubica a sus elementos. Las de
hash calculan un número a partir de la llave y comparan con `==`: piden
`Hash + Eq`. `BTreeMap`, `BTreeSet` y `BinaryHeap` comparan con `<` para
decidir dónde va cada elemento: piden `Ord`. Los dos juegos se presentaron en
[4.4 Traits de la stdlib]{.ref}.

`f64` no implementa ninguno de los dos, por culpa de `NaN`. Un montón de precios
no compila:

```rust,compile_fail
use std::collections::BinaryHeap;

fn main() {
    let mut precios: BinaryHeap<f64> = BinaryHeap::new();
    precios.push(19.5);
    println!("{}", precios.len());
}
```

```salida
error[E0599]: the method `push` exists for struct
              `BinaryHeap<f64>`, but its trait bounds
              were not satisfied
5 |     precios.push(19.5);
  |             ^^^^ method cannot be called on
  |                  `BinaryHeap<f64>` due to unsatisfied
  |                  trait bounds
  = note: the following trait bounds were not satisfied:
          `f64: Ord`
```

Crear el montón vacío sí compila: `new` y `len` no comparan. El error aparece en
`push`, el primer método que necesita ordenar. Si un `NaN` entrara, `NaN < x` y
`x < NaN` serían falsos los dos, y el heap no podría decidir quién va arriba.
Con un `BTreeMap<f64, &str>`, `insert` falla con *E0277: the trait bound `f64:
Ord` is not satisfied*. Un `HashMap<f64, &str>` da el mismo E0599 de arriba y
pide `f64: Eq` y `f64: Hash`.

## Aplicación

Una ronda de tiros con turnos. Los jugadores esperan en un `VecDeque`; uno con
cita entra por el frente. Un `BinaryHeap` de `Reverse` guarda el podio: los tres
mejores puntajes, con el menor de ellos arriba para sacarlo cuando llega uno
mejor.

```rust
use std::cmp::Reverse;
use std::collections::{BinaryHeap, VecDeque};

fn main() {
    let mut turnos = VecDeque::from([("Ana", 72)]);
    turnos.push_back(("Beto", 91));
    turnos.push_back(("Caro", 64));
    turnos.push_back(("Dani", 88));
    turnos.push_front(("Eva", 95)); // llegó con cita
    turnos.push_back(("Fede", 79));

    let mut podio = BinaryHeap::new();
    while let Some((nombre, puntos)) = turnos.pop_front() {
        print!("{nombre} ");
        podio.push(Reverse((puntos, nombre)));
        if podio.len() > 3 {
            podio.pop(); // sale el menor de los cuatro
        }
    }
    println!();

    for Reverse((puntos, nombre)) in podio.into_sorted_vec() {
        println!("{nombre} {puntos}");
    }
}
```

```salida
Eva Ana Beto Caro Dani Fede
Eva 95
Beto 91
Dani 88
```

La tupla va con el puntaje primero porque las tuplas se comparan campo por
campo, en orden. El heap nunca pasa de cuatro elementos, así que cada `pop`
es barato. `into_sorted_vec` consume el heap y devuelve un `Vec` en orden
ascendente de `Reverse`, que es descendente de puntaje.

## A fondo

**El costo por operación, estructura por estructura.** Las cuatro
operaciones, por separado:

| Estructura | Acceso | Búsqueda | Inserción | Borrado |
| :--- | :--- | :--- | :--- | :--- |
| `Vec` | `O(1)` | `O(n)` | `O(1)`\* al final | `O(1)` al final, `O(n)` en medio |
| `VecDeque` | `O(1)` | `O(n)` | `O(1)`\* en los extremos | `O(1)` en los extremos |
| `HashMap`, `HashSet` | `O(1)`† | `O(1)`† | `O(1)`† | `O(1)`† |
| `BTreeMap`, `BTreeSet` | `O(log n)` | `O(log n)` | `O(log n)` | `O(log n)` |
| `BinaryHeap` | `O(1)` el mayor | `O(n)` | `O(log n)` | `O(log n)` el mayor |

\* Amortizado: de vez en cuando un `push` copia todo a un bloque más grande
([5.3 Vec]{.ref}); repartido entre todos, el costo sigue siendo constante. † Caso promedio: si muchas llaves caen en la misma
posición de la tabla, el peor caso es `O(n)`.

**`VecDeque` es un búfer circular.** Cuando el final llega al borde del bloque,
sigue desde el inicio si hay lugar. Sus elementos pueden quedar en dos tramos:
`as_slices` devuelve los dos slices y `make_contiguous` los junta. El acceso por índice, `cola[2]`, sigue siendo
`O(1)`.

**Un `BinaryHeap` es un `Vec` por dentro.** Guarda un árbol binario en un
arreglo: los hijos del índice *i* están en *2i + 1* y *2i + 2*, y cada padre es
mayor o igual que sus hijos. `push` agrega al final y sube el elemento mientras
supere a su padre; `pop` hace el camino inverso. Cada uno recorre una rama: de
ahí el `O(log n)`.

**La prioridad se define con el `Ord` del elemento.** Un struct que deriva
`Ord` compara sus campos en orden de declaración
([4.4 Traits de la stdlib]{.ref}): el campo de prioridad va primero, como en
una tupla.

**Un `f64` entra si se cambia la representación.** Lo habitual es guardar un
entero de centavos, como `Dinero` en [4.4 Traits de la stdlib]{.ref}, que deriva
el juego completo. La otra salida es un newtype con `Ord` escrito a mano que
llame a `total_cmp`.

**Ordenar una vez puede bastar.** Si el orden solo se necesita al final, un
`Vec` que se ordena antes de imprimir cuesta menos que un `BTreeMap` mantenido
en cada inserción ([5.3 Vec]{.ref}). `BTreeMap` conviene cuando se inserta y se
consulta en orden de forma intercalada.

**`LinkedList` existe y casi nunca conviene.** Inserta en `O(1)` en sus extremos,
igual que `VecDeque`, pero cada nodo es un bloque aparte del heap y recorrerla
es lento. La lista enlazada se construye a mano en
[6.1 Box y listas enlazadas]{.ref}.
