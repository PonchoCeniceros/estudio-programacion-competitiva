# 4.1 · Traits

Un `Punto` y un `Usuario` pueden tener cada uno su método `describir`,
escrito en su bloque `impl` de [3.5 impl y métodos]{.ref}. Para el
compilador esa coincidencia de nombres no significa nada: son dos métodos
sin relación. Una función que reciba "algo que se pueda describir" no se
puede escribir, porque su parámetro lleva un solo tipo.

Un trait le pone nombre a lo que esos tipos tienen en común. Declara un
comportamiento, cada tipo lo implementa a su manera y una función puede
pedir cualquier tipo que lo cumpla. Con él abre la sección 4, cuyas tres
herramientas se resuelven al compilar y no cuestan nada al ejecutar.

## Definiciones y reglas

Trait
:   un contrato de comportamiento: un conjunto de métodos con nombre. No
    dice qué es un tipo, sino qué sabe hacer.

Implementar un trait
:   escribir, para un tipo, los métodos que el trait declara. Se hace en un
    bloque `impl Trait for Tipo { ... }`.

Método por default
:   método que el trait declara ya con cuerpo. El tipo que implementa el
    trait lo recibe sin escribirlo.

`derive`
:   atributo que pide al compilador generar la implementación de un trait:
    `#[derive(Debug)]`.

::: {.reglas titulo="Las tres reglas de los traits"}
1. Un tipo cumple un trait solo si lo declara con `impl Trait for Tipo`, y
   ese bloque debe escribir todos los métodos que el trait deja sin cuerpo.
2. Un método con cuerpo en el trait es un default: el tipo lo usa tal cual
   o lo sobrescribe.
3. Un parámetro `&impl Trait` acepta cualquier tipo que implemente el
   trait, y ningún otro.
:::

## De un vistazo

| Escrito | Dónde va | Qué hace |
| :--- | :--- | :--- |
| `fn f(&self);` | en el `trait` | declara un método obligatorio |
| `fn g(&self) { ... }` | en el `trait` | da un método por default |
| `impl Trait for Tipo { ... }` | junto al tipo | el tipo cumple el contrato |
| `fn h(x: &impl Trait)` | en una firma | pide cualquier tipo que lo cumpla |
| `#[derive(Trait)]` | sobre el tipo | el compilador escribe el `impl` |

Criterio para diseñar un trait: dejar sin cuerpo lo mínimo que cada tipo
debe decir de sí mismo, y dar como default lo que se calcula a partir de
eso.

## Las reglas, una por una

Antes de las reglas, el problema completo, con el error que produce.

### Dos métodos iguales no hacen un tipo común

```rust,compile_fail
struct Punto { x: f64, y: f64 }
struct Usuario { nombre: String }

impl Punto {
    fn describir(&self) -> String {
        format!("({}, {})", self.x, self.y)
    }
}

impl Usuario {
    fn describir(&self) -> String {
        format!("usuario {}", self.nombre)
    }
}

fn mostrar(item: &Punto) {
    println!("{}", item.describir());
}

fn main() {
    let u = Usuario { nombre: String::from("Ana") };
    mostrar(&u);   // E0308: mismatched types
}
```

Los dos tipos tienen un método con el mismo nombre y la misma firma, y
`mostrar` solo usa ese método. Aun así la firma de `mostrar` nombra un tipo,
y `Usuario` es otro: *expected `&Punto`, found `&Usuario`*. La salida sin traits es escribir `mostrar_punto` y
`mostrar_usuario`, con el mismo cuerpo, y una más por cada tipo nuevo.

### [Regla 1:]{.prefijo} el trait declara, el tipo implementa

El trait lleva las firmas, terminadas en punto y coma, sin cuerpo. Cada
tipo las completa en un bloque `impl Trait for Tipo`.

```rust
trait Descriptible {
    fn describir(&self) -> String;
}

struct Punto { x: f64, y: f64 }
struct Usuario { nombre: String }

impl Descriptible for Punto {
    fn describir(&self) -> String {
        format!("({}, {})", self.x, self.y)
    }
}

impl Descriptible for Usuario {
    fn describir(&self) -> String {
        format!("usuario {}", self.nombre)
    }
}

fn main() {
    let p = Punto { x: 1.0, y: 2.0 };
    let u = Usuario { nombre: String::from("Ana") };
    println!("{}", p.describir());   // (1, 2)
    println!("{}", u.describir());   // usuario Ana
}
```

Los cuerpos son los de antes y las llamadas con punto no cambian. Lo nuevo
es la cabecera del bloque: `impl Descriptible for Punto` afirma que `Punto`
cumple el contrato. Esa afirmación es explícita. Un tipo con un método
`describir` en su `impl` propio no implementa `Descriptible` por tener el
nombre correcto.

El compilador revisa que el bloque esté completo. Un `impl` que omite un
método obligatorio no compila:

```rust,compile_fail
trait Descriptible {
    fn describir(&self) -> String;
}

struct Punto { x: f64, y: f64 }

impl Descriptible for Punto {}

fn main() {
    let p = Punto { x: 1.0, y: 2.0 };
    println!("{}", p.describir());
}
```

```salida
error[E0046]: not all trait items implemented,
              missing: `describir`
2 |     fn describir(&self) -> String;
  |     ------------------------------ `describir` from trait
...
7 | impl Descriptible for Punto {}
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^ missing `describir`
  |                             in implementation
```

El bloque tampoco admite métodos de más: uno que el trait no declara da
E0407. Los métodos propios del tipo siguen en su `impl Punto { ... }`, y
cada trait lleva su bloque aparte.

### [Regla 2:]{.prefijo} un método con cuerpo es un default

Un trait puede traer métodos ya escritos. Aquí `presentarse` tiene cuerpo y
se apoya en `describir`, que no lo tiene:

```rust
trait Descriptible {
    fn describir(&self) -> String;

    fn presentarse(&self) -> String {
        format!("Soy {}", self.describir())
    }
}

struct Punto { x: f64, y: f64 }
struct Usuario { nombre: String }

impl Descriptible for Punto {
    fn describir(&self) -> String {
        format!("({}, {})", self.x, self.y)
    }
}

impl Descriptible for Usuario {
    fn describir(&self) -> String {
        format!("usuario {}", self.nombre)
    }

    fn presentarse(&self) -> String {
        format!("Hola, me llamo {}", self.nombre)
    }
}

fn main() {
    let p = Punto { x: 1.0, y: 2.0 };
    let u = Usuario { nombre: String::from("Ana") };
    println!("{}", p.presentarse());   // Soy (1, 2)
    println!("{}", u.presentarse());   // Hola, me llamo Ana
}
```

`Punto` solo escribe `describir` y recibe `presentarse` sin pedirlo.
`Usuario` escribe los dos: su versión sustituye al default. Para quien
llama no hay diferencia, porque `presentarse` existe en ambos tipos.

El default llama a `self.describir()` sin saber qué tipo es `self`. Le
basta saber que implementa el trait, así que el método existe. Al compilar,
la llamada desde un `Punto` usa el `describir` de `Punto`.

### [Regla 3:]{.prefijo} un trait como parámetro

La función que el arranque del capítulo no pudo escribir pide ahora el
contrato en vez de un tipo. `&impl Descriptible` se lee: un préstamo de
cualquier tipo que implemente `Descriptible`. Lo que decide si una llamada
compila es el `impl`, no la forma del tipo.

::: {.figura src="figuras/4.1-contrato.html"}
:::

`Factura` no tiene un `impl Descriptible`, y el compilador lo dice así:

```rust,compile_fail
trait Descriptible {
    fn describir(&self) -> String;
}

struct Punto { x: f64, y: f64 }
struct Factura { total: f64 }

impl Descriptible for Punto {
    fn describir(&self) -> String {
        format!("({}, {})", self.x, self.y)
    }
}

fn mostrar(item: &impl Descriptible) {
    println!("{}", item.describir());
}

fn main() {
    let p = Punto { x: 1.0, y: 2.0 };
    let f = Factura { total: 99.5 };
    mostrar(&p);
    mostrar(&f);
}
```

```salida
error[E0277]: the trait bound `Factura: Descriptible`
              is not satisfied
22 |     mostrar(&f);
   |     ------- ^^ unsatisfied trait bound
   |     |
   |     required by a bound introduced by this call
help: the trait `Descriptible` is not implemented
      for `Factura`
 6 | struct Factura { total: f64 }
   | ^^^^^^^^^^^^^^
```

La llamada con `Punto` compila, y con un `Usuario` que implemente el trait
compilaría igual: una sola función sirve a todos los tipos que cumplen el
contrato. La llamada con `Factura` se rechaza en el punto de la llamada, no
dentro de `mostrar`. El mensaje llama *trait bound* a la exigencia de la
firma, el nombre que usa [4.2 Generics]{.ref}.

Dentro de `mostrar`, `item` solo ofrece lo que el trait declara. La función
no sabe si recibió un `Punto`, así que `item.x` da E0609: *no field `x` on
type `&impl Descriptible`*. Ese límite es lo que permite compilar el cuerpo
una vez y aceptar tipos que todavía no existen.

`&impl Trait` es la forma corta de un parámetro genérico. La forma larga,
`<T: Trait>`, y el caso de dos parámetros que deben ser del mismo tipo
están en [4.2 Generics]{.ref}.

### Quién puede implementar qué

Un `impl Trait for Tipo` no tiene que estar junto a la definición del
tipo. Un trait propio se puede implementar sobre un tipo ajeno, incluso
sobre un primitivo:

```rust
trait Descriptible {
    fn describir(&self) -> String;
}

impl Descriptible for i32 {
    fn describir(&self) -> String {
        format!("el entero {self}")
    }
}

fn main() {
    println!("{}", 7.describir());   // el entero 7
}
```

El límite es la regla de coherencia: para implementar un trait sobre un
tipo, el trait o el tipo tienen que ser propios. Propio significa definido
en el mismo crate, que es el programa o la biblioteca que se compila
([7.2 Crates y Cargo]{.ref}). `Debug` y `bool` son los dos de la biblioteca
estándar, así que `impl std::fmt::Debug for bool` da E0117: *only traits
defined in the current crate can be implemented for primitive types*.

La regla garantiza que cada par de trait y tipo tenga una sola
implementación en todo el programa. El motivo completo y la salida usual,
envolver el tipo ajeno en uno propio, están en
[4.4 Traits de la stdlib]{.ref}.

### `derive`: el compilador escribe el `impl`

Los traits ya habían aparecido sin explicarse. El `#[derive(Debug)]` de
[2.2 Structs]{.ref} pide al compilador que genere `impl Debug for Tipo`, y
esa implementación es la que usa `{:?}`. Lo mismo vale para otros traits de
la biblioteca estándar cuya implementación se deduce de los campos.

```rust
#[derive(Debug, Clone, PartialEq)]
struct Punto {
    x: i32,
    y: i32,
}

fn main() {
    let a = Punto { x: 1, y: 2 };
    let b = a.clone();         // Clone
    println!("{:?}", a);       // Debug: Punto { x: 1, y: 2 }
    println!("{}", a == b);    // PartialEq: true
}
```

Sin el `derive`, `a == b` da E0369: *binary operation `==` cannot be
applied to type `Punto`*. El operador `==` no está fijo en el lenguaje para
cada tipo: es una llamada a un método del trait `PartialEq`.

| Derive | Qué habilita |
| :--- | :--- |
| `Debug` | imprimir con `{:?}` |
| `Clone` | el método `.clone()` |
| `PartialEq`, `Eq` | comparar con `==` y `!=` |
| `PartialOrd`, `Ord` | comparar con `<` y `>`, y ordenar |
| `Hash` | ser llave de un `HashMap` ([5.4 HashMap y HashSet]{.ref}) |

Un `derive` exige que todos los campos implementen ya ese trait, porque el
código generado trabaja campo por campo. Un struct con un campo de un tipo
sin `Debug` no puede derivar `Debug`: da E0277 sobre ese campo. El detalle
de cada trait de la tabla está en [4.4 Traits de la stdlib]{.ref}.

### Dónde aparecen después

Buena parte de la sintaxis del lenguaje es un trait de la biblioteca
estándar visto desde fuera. La tabla dice cuál, y dónde se explica.

| Construcción | El trait detrás | Capítulo |
| :--- | :--- | :--- |
| `println!("{:?}", x)` | `Debug` | [2.2 Structs]{.ref} |
| `println!("{}", x)` | `Display` | [4.4 Traits de la stdlib]{.ref} |
| `String::from("x")` | `From` | [4.4 Traits de la stdlib]{.ref} |

## Aplicación

Un ejercicio del curso *Aprende Rust*. `Animal` obliga a decir el nombre y
da dos defaults: un sonido, y una presentación armada con los otros dos.

```rust
trait Animal {
    fn nombre(&self) -> String;
    fn sonido(&self) -> String {
        String::from("...")
    }
    fn presentarse(&self) -> String {
        format!("{} hace {}", self.nombre(), self.sonido())
    }
}

struct Perro;
struct Pez;

impl Animal for Perro {
    fn nombre(&self) -> String {
        String::from("Perro")
    }
    fn sonido(&self) -> String {
        String::from("guau")
    }
}

impl Animal for Pez {
    fn nombre(&self) -> String {
        String::from("Pez")
    }
}

fn main() {
    println!("{}", Perro.presentarse());   // Perro hace guau
    println!("{}", Pez.presentarse());     // Pez hace ...
}
```

Ninguno de los dos tipos escribe `presentarse`. `Perro` sobrescribe
`sonido`, y el `presentarse` heredado usa esa versión: el default llama al
método del tipo, no al del trait. `Pez` solo cumple lo obligatorio y se
queda con los dos defaults. Un tercer animal entra al programa con un
`impl` de un solo método.

## A fondo

**Un default no puede leer campos.** El cuerpo de un método por default se
compila sin saber qué tipo será `self`, así que solo dispone de los otros
métodos del trait. Escribir `self.nombre` en un default da E0609: *no field
`nombre` on type `&Self`*. Por eso `Animal` pide el nombre con un método
obligatorio.

**La llamada se decide al compilar.** Con `&impl Trait` el compilador
conoce el tipo concreto en cada llamada y enlaza el método que corresponde,
igual que con una función suelta. No queda ninguna búsqueda para el momento
de ejecutar ([4.2 Generics]{.ref}): de ahí el nombre de la sección. La
alternativa que decide al ejecutar es de [6.3 Despacho dinámico]{.ref}.

**Un método propio le gana al del trait.** Si `Punto` tiene `describir` en
su `impl Punto` y además implementa `Descriptible`, `p.describir()` llama
al método propio. El del trait se alcanza con la forma desplegada de
[3.5 impl y métodos]{.ref}: `Descriptible::describir(&p)`.

**Un trait se parece a una interfaz, con una diferencia.** Las interfaces
de Java, TypeScript o Go cumplen el mismo papel de contrato. En Rust la
implementación va separada de la definición del tipo, y por eso un trait
nuevo se puede implementar sobre tipos que ya existían, como `i32`.
