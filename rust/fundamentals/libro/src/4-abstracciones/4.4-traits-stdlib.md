# 4.4 · Traits de la stdlib

Un struct recién definido no hace casi nada. No se imprime con `{}`, no se compara
con `==`, no se ordena con `<` y se mueve en cada asignación. El compilador no
supone ninguna de esas capacidades: cada una se declara.

Se declaran con traits de la biblioteca estándar. Cada sintaxis del lenguaje está
ligada a uno: `{}` busca `Display`, `==` busca `PartialEq`, `.into()` busca `From`.
Implementar el trait conecta el tipo propio con esa sintaxis. Algunos se obtienen
con `derive` ([4.1 Traits]{.ref}); otros hay que escribirlos, y unos pocos traen
restricciones que no se ven hasta que el compilador las reclama.

## Definiciones y reglas

Trait derivable
:   el que `#[derive(...)]` puede implementar a partir de los campos del tipo.

Destructor
:   el método `drop` del trait `Drop`. El compilador lo invoca cuando el valor se
    destruye.

Crate
:   la unidad que `rustc` compila de una vez. Por ahora, el programa propio; la
    biblioteca estándar es otro crate ([7.2 Crates y Cargo]{.ref}).

Regla del huérfano
:   *(orphan rule)*: la que decide en qué crate se puede escribir un `impl`.

::: {.reglas titulo="Cuatro restricciones que sorprenden"}
1. `Display` no se deriva: se escribe a mano.
2. `Copy` exige que todos los campos sean `Copy` y que el tipo no implemente
   `Drop`.
3. Se implementa `From`, nunca `Into`: el segundo sale del primero.
4. Un `impl` solo se permite si el trait o el tipo son del crate propio.
:::

## De un vistazo

| Trait | Da acceso a | Se obtiene con |
| :--- | :--- | :--- |
| `Debug` | `{:?}` y `dbg!` | `derive` |
| `Display` | `{}` y `.to_string()` | a mano |
| `Clone` | `.clone()` | `derive` |
| `Copy` | copia implícita en vez de move | `derive`, junto con `Clone` |
| `Default` | `T::default()` | `derive` |
| `PartialEq`, `Eq` | `==` y `!=` | `derive` |
| `PartialOrd`, `Ord` | `<`, `>`, `.max()`, ordenar | `derive` |
| `Hash` | ser llave de un `HashMap` | `derive` |
| `From`, `Into` | `.into()` y el `?` | a mano |
| `Drop` | código al destruirse el valor | a mano |

Se deriva lo que se deduce de los campos. Se escribe a mano lo que es una decisión
del autor del tipo: cómo se muestra, de qué se convierte y qué hace al destruirse.

## Las reglas, una por una

### Un tipo nuevo no trae nada

Dos puntos con los mismos campos no se pueden comparar todavía:

```rust,compile_fail
struct Punto {
    x: i32,
    y: i32,
}

fn main() {
    let a = Punto { x: 1, y: 2 };
    let b = Punto { x: 1, y: 2 };
    println!("{}", a == b);
}
```

```salida
error[E0369]: binary operation `==` cannot be applied to
              type `Punto`
9 |     println!("{}", a == b);
  |                    - ^^ - Punto
  |                    |
  |                    Punto
help: consider annotating `Punto` with
      `#[derive(PartialEq)]`
```

El mensaje nombra el trait que falta y propone derivarlo. El mismo patrón se repite
con las demás sintaxis: `a < b` pide `PartialOrd` con otro E0369, y `a.clone()`
falla con E0599 porque el método no existe. Con
un `derive` de `Debug`, `Clone`, `PartialEq` y `PartialOrd` encima de `Punto`,
las tres compilan y el struct además se imprime con `{:?}`.

### Comparar, ordenar y servir de llave

La igualdad y el orden vienen cada uno en dos traits. El primero habilita los
operadores. El segundo agrega una promesa sobre todos los valores del tipo.

| Trait | Habilita | Promete |
| :--- | :--- | :--- |
| `PartialEq` | `==` y `!=` | nada más |
| `Eq` | nada nuevo | todo valor es igual a sí mismo |
| `PartialOrd` | `<`, `<=`, `>`, `>=` | nada más |
| `Ord` | `.max()`, `.min()`, `.cmp()` | dos valores siempre se pueden ordenar |

El tipo que separa las dos mitades es `f64`. Tiene un valor, `NaN` (*not a
number*, el resultado de `0.0 / 0.0`), que no es igual a nada ni se ordena con
nada:

```rust
fn main() {
    let nan = f64::NAN;
    println!("{}", nan == nan);   // false
    println!("{}", nan < 1.0);    // false
    println!("{}", nan >= 1.0);   // false
}
```

Por eso `f64` implementa `PartialEq` y `PartialOrd`, pero no `Eq` ni `Ord`. La
restricción se hereda: un struct con un campo `f64` tampoco puede derivarlos.
`#[derive(PartialEq, Eq)]` sobre `struct Medida(f64);` falla con *E0277: the trait
bound `f64: Eq` is not satisfied*. Los enteros, `bool`, `char` y `String`
implementan los cuatro.

La distinción importa por las estructuras que la exigen. Ordenar una colección y
usar un `BinaryHeap` o un `BTreeMap` piden `Ord` ([5.3 Vec]{.ref},
[5.5 Otras colecciones]{.ref}). Ser llave de un `HashMap` pide `Eq` y además
`Hash`, el trait que reduce un valor a un número para ubicarlo en la tabla
([5.4 HashMap y HashSet]{.ref}). Con un `NaN` de llave o en medio de un
ordenamiento, esas estructuras no podrían cumplir lo que prometen. Un tipo que va
a usarse como llave o a ordenarse deriva el juego completo: `PartialEq`, `Eq`,
`PartialOrd`, `Ord` y `Hash`.

### [Regla 1:]{.prefijo} `Display` se escribe a mano

`Debug` se deriva porque su salida es mecánica: el nombre del tipo y sus campos.
`Display` es el formato de cara al usuario, y ese formato es una decisión. Un punto
puede mostrarse como `(1, 2)`, como `x=1 y=2` o como `1;2`, y nada en los campos
dice cuál. No existe `#[derive(Display)]`.

Se implementa el único método del trait, `fmt`. Recibe un `Formatter`, que es el
destino del texto, y escribe en él con `write!`. Esa macro usa la sintaxis de
`println!` con el destino como primer argumento.

```rust
use std::fmt;

struct Punto { x: i32, y: i32 }

impl fmt::Display for Punto {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

fn main() {
    let p = Punto { x: 1, y: 2 };
    println!("{p}");                  // (1, 2)
    let texto = p.to_string();        // gratis con Display
    println!("{}", texto.len());      // 6
}
```

La firma se copia tal cual. `fmt::Result` es el tipo con que `write!` avisa si la
escritura falló, y `fmt` lo devuelve sin tocarlo ([5.2 Result]{.ref}). Todo tipo
con `Display` gana además el método `.to_string()`, que produce el mismo texto en
un `String`.

Sin el `impl`, `println!("{p}")` da *E0277: `Punto` doesn't implement
`std::fmt::Display`*. `Display` es también lo que permite imprimir un error
propio ([7.4 Manejo de errores idiomático]{.ref}).

### [Regla 2:]{.prefijo} `Copy` no se elige libremente

`Copy` cambia el significado de la asignación: `let b = a;` copia los bits y deja
válida a `a`. Se deriva junto con `Clone`, y solo funciona cuando copiar los bits
produce dos valores independientes. `Punto`, con sus dos `i32`, cumple: basta
agregar `Copy` a su `derive`. Con un campo que guarda datos en el heap, el
compilador lo rechaza:

```rust,compile_fail
#[derive(Clone, Copy)]
struct Persona {
    nombre: String,
    edad: u8,
}

fn main() {
    let p = Persona { nombre: String::from("Ana"), edad: 30 };
    let q = p;
    println!("{} {}", q.nombre, q.edad);
}
```

```salida
error[E0204]: the trait `Copy` cannot be implemented for
              this type
1 | #[derive(Clone, Copy)]
  |                 ^^^^
2 | struct Persona {
3 |     nombre: String,
  |     -------------- this field does not implement `Copy`
```

Es la regla de [3.2 Ownership]{.ref}, vista desde quien define el tipo. Copiar los
bits de `Persona` duplicaría el puntero de `nombre` sin duplicar el texto, y habría
dos dueñas del mismo buffer. `Persona` puede derivar `Clone`, que duplica el heap
cuando se le pide con `.clone()`. No puede ser `Copy`.

### `Default` y la sintaxis de actualización

`Default` da un valor inicial sin argumentos. Derivado, usa el default de cada
campo: `0` para los números, `false` para `bool` y el texto vacío para `String`.

Se combina con la sintaxis de actualización de [2.2 Structs]{.ref}.
`..Default::default()` usa un valor default como base: se escriben los campos que
cambian y el resto se rellena. Es el patrón habitual en structs de configuración
con muchos campos opcionales.

```rust
#[derive(Debug, Default)]
struct Config {
    reintentos: u32,
    verboso: bool,
    nombre: String,
}

fn main() {
    let c = Config { reintentos: 3, ..Default::default() };
    println!("{c:?}");
}
```

Imprime `Config { reintentos: 3, verboso: false, nombre: "" }`.

### [Regla 3:]{.prefijo} se implementa `From`, nunca `Into`

`From<T>` declara que un tipo se puede construir a partir de un `T`. Tiene una sola
función asociada, `from`, que consume el valor de origen:

```rust
struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self {
        Fahrenheit(c.0 * 9.0 / 5.0 + 32.0)
    }
}

fn main() {
    let a = Fahrenheit::from(Celsius(100.0));
    let b: Fahrenheit = Celsius(0.0).into();  // sale del From
    println!("{} {}", a.0, b.0);              // 212 32
}
```

El programa nunca implementa `Into`, y aun así `.into()` funciona. La biblioteca
estándar trae un `impl` genérico: todo tipo `T` con `From<T> for U` recibe
`Into<U>`. Al revés no ocurre, y de ahí la regla: escribir `From` da las dos
direcciones, escribir `Into` da una.

`.into()` necesita saber a qué tipo convertir. En el ejemplo lo dice la anotación
`let b: Fahrenheit`; sin ella, el compilador no puede elegir. La biblioteca
estándar usa el mismo trait para sus conversiones sin pérdida:
`String::from("hola")` y `i64::from(5_i32)`. `From` es además lo que permite al
operador `?` convertir un error en otro ([5.2 Result]{.ref}).

### `Drop`: código al destruirse el valor

La regla 3 de [3.2 Ownership]{.ref} dice que el valor se libera cuando su dueño
sale de scope. `Drop` permite correr código propio en ese punto: cerrar un archivo,
soltar un candado, avisar. Un tipo que solo imprime al destruirse deja ver el
orden:

```rust
struct Recurso(&'static str);

impl Drop for Recurso {
    fn drop(&mut self) {
        println!("suelto {}", self.0);
    }
}

fn main() {
    let _a = Recurso("a");
    let _b = Recurso("b");
    let _c = Recurso("c");
    println!("fin de main");
}   // aquí: suelto c, suelto b, suelto a
```

El programa imprime `fin de main` y después tres líneas: `suelto c`, `suelto b`,
`suelto a`. Nadie llama a `drop`: lo invoca el compilador al cerrar la llave de
`main`. El orden es inverso al de declaración.

::: {.figura src="figuras/4.4-drop-orden.html"}
:::

El orden tiene una razón: un valor declarado después puede guardar una referencia
a uno declarado antes, así que debe destruirse primero. Llamar al destructor a
mano no compila:

```rust,compile_fail
struct Recurso(&'static str);

impl Drop for Recurso {
    fn drop(&mut self) { println!("suelto {}", self.0); }
}

fn main() {
    let c = Recurso("c");
    c.drop();
}
```

```salida
error[E0040]: explicit use of destructor method
9 |     c.drop();
  |       ^^^^ explicit destructor calls not allowed
help: consider using `drop` function
```

Si `c.drop()` se permitiera, el compilador volvería a destruir `c` al final del
scope y el destructor correría dos veces. Para adelantar la destrucción se usa la
función `drop(c)`, como propone la ayuda. Recibe el valor por move: el valor
termina su vida dentro de esa función, en esa línea, y `c` queda invalidada como
en cualquier otro move.

Aquí se cierra la regla 2. Un tipo con `Drop` no puede ser `Copy`: cada copia
correría el destructor sobre el mismo recurso. Derivar `Copy` sobre `Recurso` da
*E0184: the trait `Copy` cannot be implemented for this type; the type has a
destructor*.

### [Regla 4:]{.prefijo} la regla del huérfano

Un arreglo no implementa `Display`. El primer impulso es dárselo:

```rust,compile_fail
use std::fmt;

impl fmt::Display for [i32; 3] {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "<{}, {}, {}>", self[0], self[1], self[2])
    }
}

fn main() {
    println!("{}", [1, 2, 3]);
}
```

```salida
error[E0117]: only traits defined in the current crate can
              be implemented for arbitrary types
3 | impl fmt::Display for [i32; 3] {
  | ^^^^^^^^^^^^^^^^^^^^^^--------
  |                       |
  |                       this is not defined in the
  |                       current crate because arrays
  |                       are always foreign
  = note: define and implement a trait or new type instead
```

Ni `Display` ni el arreglo se definieron en este programa: los dos son de la
biblioteca estándar. La regla del huérfano pide que al menos uno sea propio. Un
trait propio para un tipo ajeno se permite, y un trait ajeno para un tipo propio
también: es lo que hicieron todos los `impl` de este capítulo.

La última nota del mensaje da la salida. Es el patrón *newtype* de
[2.2 Structs]{.ref}: un tuple struct de un campo que envuelve al tipo ajeno.

```rust
use std::fmt;

struct Terna([i32; 3]);

impl fmt::Display for Terna {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        let t = self.0;
        write!(f, "<{}, {}, {}>", t[0], t[1], t[2])
    }
}

fn main() {
    println!("{}", Terna([1, 2, 3]));   // <1, 2, 3>
}
```

`Terna` es un tipo propio, así que el `impl` se permite. El envoltorio no ocupa
memoria adicional. Su costo es de escritura: los métodos del arreglo quedan detrás
de `.0`. El trait `Deref` se los devuelve
([4.5 Operadores y conversiones]{.ref}).

## Aplicación

Una cantidad de dinero, guardada en centavos para no hacer cuentas con decimales.
Su único campo es un entero, así que puede derivar el juego completo. `Display` y
`From` se escriben a mano: el formato `$12.50` y la conversión desde pesos enteros
son decisiones.

```rust
use std::fmt;

#[derive(Debug, Clone, Copy, Default)]
#[derive(PartialEq, Eq, PartialOrd, Ord, Hash)]
struct Dinero {
    centavos: i64,
}

impl fmt::Display for Dinero {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        let c = self.centavos;
        write!(f, "${}.{:02}", c / 100, c % 100)
    }
}

impl From<i64> for Dinero {
    fn from(pesos: i64) -> Self {
        Dinero { centavos: pesos * 100 }
    }
}

fn main() {
    let precio = Dinero { centavos: 1250 };
    let pago: Dinero = 20.into();        // From<i64>
    let copia = precio;                  // Copy

    println!("{precio} de {pago}");      // Display
    println!("{copia:?}");               // Debug
    println!("{}", precio == copia);     // PartialEq
    println!("{}", precio < pago);       // PartialOrd
    println!("{}", precio.max(pago));    // Ord
    println!("{}", Dinero::default());   // Default
}
```

```salida
$12.50 de $20.00
Dinero { centavos: 1250 }
true
true
$20.00
$0.00
```

`{:02}` escribe el número con dos dígitos y rellena con ceros. Después de
`let copia = precio;` la variable `precio` sigue en uso: sin `Copy`, la línea
siguiente sería un E0382. Cada línea de `main` depende de un trait distinto.

## A fondo

**El `derive` compara campo por campo, en el orden de declaración.** `PartialEq`
derivado exige que todos los campos sean iguales. `PartialOrd` y `Ord` derivados
comparan el primer campo y solo pasan al siguiente si hay empate: en
un struct `Version` con los campos `mayor` y `menor`, en ese orden, la versión
1.9 es menor que la 2.0 porque decide `mayor`. El orden en que se escriben los campos decide el orden del
tipo. En un enum, una variante declarada
antes es menor que una declarada después.

**`Eq` y `Copy` no tienen métodos.** Son traits marcadores: no agregan código,
solo afirman una propiedad del tipo que el compilador y otras bibliotecas pueden
exigir. Por eso se derivan junto a su par, `PartialEq` y `Clone`, que es quien
trae el método.

**`Hash` debe coincidir con `Eq`.** Dos valores iguales según `==` tienen que
producir el mismo hash, o un `HashMap` buscaría la llave en el lugar equivocado.
Derivar los dos sobre los mismos campos lo garantiza. Escribir uno a mano y
derivar el otro es la forma usual de romperlo.

**Un `f64` sí se puede ordenar, con otro método.** `a.total_cmp(&b)` define un
orden total sobre los flotantes, con `NaN` positivo después de todos los demás
valores. Devuelve el mismo tipo que `.cmp()`, y es lo que se usa para ordenar
flotantes ([5.3 Vec]{.ref}).

**`Into` se usa en las firmas.** La regla prohíbe implementarlo, no pedirlo. Una
función `fn mostrar(t: impl Into<Fahrenheit>)` acepta cualquier tipo convertible
y llama a `t.into()` adentro. Acepta también un `Fahrenheit`: todo tipo implementa
`From` de sí mismo.

**El orden de `Drop` tiene tres casos más.** Los campos de un struct se destruyen
en orden de declaración, no inverso, y después del `drop` del propio struct.
`let _ = valor;` no liga el valor a nada, así que se destruye en esa misma línea;
`let _a = valor;` sí lo conserva hasta el final del scope. Y un valor movido no se
destruye en su scope original: lo hace su nueva dueña. De ese orden fijo dependen
los *guards* que sueltan un préstamo o un candado al salir de scope
([6.2 Rc, RefCell y árboles]{.ref}).

**La regla del huérfano protege la coherencia.** Si dos crates pudieran
implementar `Display` para `[i32; 3]`, un programa que usara los dos tendría dos
implementaciones y ninguna forma de elegir. Al exigir que el trait o el tipo sean
propios, solo el crate del trait y el del tipo pueden escribir ese `impl`. El
mensaje cambia con el tipo: con `String` en lugar del arreglo, el mismo E0117
anota *`String` is not defined in the current crate*.
