# 4.2 · Generics

Una función que devuelve el mayor de dos enteros y otra que devuelve el mayor
de dos caracteres tienen el mismo cuerpo. Solo cambia el tipo de la firma:

```rust
fn mayor_i32(a: i32, b: i32) -> i32 {
    if a > b { a } else { b }
}

fn mayor_char(a: char, b: char) -> char {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", mayor_i32(3, 7));       // 7
    println!("{}", mayor_char('a', 'z'));  // z
}
```

Cada tipo nuevo pide otra copia, y un error en la comparación hay que
corregirlo en todas. La copia que se olvida conserva el error. Los *generics*
permiten escribir el cuerpo una vez y dejar el tipo como un parámetro. El
`<'a>` de [3.6 Lifetimes]{.ref} ya era un parámetro genérico, de lifetime.
Aquí el parámetro es un tipo.

## Definiciones y reglas

Parámetro de tipo
:   `T`: el nombre de un tipo que todavía no se conoce. Se declara entre `<`
    y `>`, igual que un lifetime. Por convención es una letra mayúscula: `T`,
    y `U` si hace falta un segundo.

Trait bound
:   `T: Trait`: la condición que debe cumplir el tipo que ocupe el lugar de
    `T`. Se lee «cualquier tipo, siempre que implemente `Trait`».

Monomorfización
:   el paso en que el compilador genera una versión concreta del código
    genérico por cada tipo con el que se usa.

Tipo asociado
:   un tipo que un trait declara sin valor (`type Elemento;`) y que cada
    `impl` fija.

::: {.reglas titulo="Las tres reglas de los genéricos"}
1. El código genérico solo usa de `T` lo que sus bounds declaran.
2. Cada uso fija cada parámetro a un solo tipo concreto.
3. El compilador genera una versión por cada tipo usado. El costo se paga al
   compilar, no al ejecutar.
:::

## De un vistazo

Todas las formas del capítulo dejan un tipo sin escribir. Cambia quién lo
elige.

| Forma | Qué declara | Quién elige el tipo |
| :--- | :--- | :--- |
| `fn f<T>(x: T)` | cualquier tipo | quien llama |
| `<T: Trait>`, `where` | solo tipos con `Trait` | quien llama |
| `x: &impl Trait` | lo mismo, sin nombre | quien llama |
| `struct S<T>` | campos por fijar | quien crea el valor |
| `impl<T> S<T>` | métodos para todo `T` | ya lo fijó el valor |
| `impl S<f64>` | métodos de un solo tipo | quien escribe el `impl` |
| `type X;` en un trait | tipo del contrato | cada `impl` |
| `-> impl Trait` | retorno sin nombrar | la función |

Criterio: se empieza por `<T>` sin bounds y se agrega cada bound cuando el
cuerpo lo necesita. El compilador dice cuál falta.

## Las reglas, una por una

### [Regla 1:]{.prefijo} el código solo usa lo que el bound declara

El primer intento reemplaza el tipo por `T` y no toca el cuerpo:

```rust,compile_fail
fn mayor<T>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", mayor(3, 7));
}
```

```salida
error[E0369]: binary operation `>` cannot be applied to
              type `T`
2 |     if a > b { a } else { b }
  |        - ^ - T
help: consider restricting type parameter `T` with trait
      `PartialOrd`
```

El error está en la definición, no en la llamada. `<T>` promete que la función
sirve para cualquier tipo, y no todos los tipos se comparan con `>`: una
struct sin `derive` no lo hace. El compilador revisa el cuerpo una sola vez,
contra lo que la firma declara, sin mirar con qué tipos se llama después.

El operador `>` lo aporta el trait `PartialOrd` ([4.1 Traits]{.ref}). El bound
lo exige en la firma:

```rust
fn mayor<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", mayor(3, 7));             // 7
    println!("{}", mayor('a', 'z'));         // z
    println!("{}", mayor(1.5, 0.2));         // 1.5
    println!("{}", mayor::<u8>(200, 100));   // 200
}
```

`T: PartialOrd` se lee: `T` es cualquier tipo, siempre que se pueda comparar.
El bound obliga en los dos sentidos. Dentro de la función permite usar `>`.
En la llamada rechaza los tipos que no lo implementan.

El tipo casi nunca se escribe al llamar: el compilador lo infiere de los
argumentos. Cuando no hay de dónde inferirlo, o se quiere uno distinto, va
entre `::<` y `>` después del nombre. Esa forma se conoce como *turbofish*,
y es la de `size_of::<i32>()` en [3.1 Stack y heap]{.ref}: esa función no
recibe argumentos.

### Varios bounds: `+` y `where`

Un parámetro puede necesitar más de un trait. Se suman con `+`:
`<T: PartialOrd + Clone>`. Con dos parámetros o bounds largos la firma deja
de leerse, y la cláusula `where` dice lo mismo después de la lista de
parámetros, un tipo por renglón. Aquí el segundo trait es `Debug`, que
permite imprimir con `{:?}` y cuyo nombre completo es `std::fmt::Debug`:

```rust
fn anunciar<T, U>(a: T, b: T, etiqueta: U)
where
    T: PartialOrd + std::fmt::Debug,
    U: std::fmt::Debug,
{
    let m = if a > b { a } else { b };
    println!("{etiqueta:?}: {m:?}");
}

fn main() {
    anunciar(2.5, 1.0, 'm');         // 'm': 2.5
    anunciar("sol", "luna", 7);      // 7: "sol"
}
```

`T` y `U` son parámetros independientes: en la primera llamada, `T` es `f64`
y `U` es `char`.

### `&impl Trait` es un genérico sin nombre

[4.1 Traits]{.ref} escribió parámetros como `f: &impl Figura`. Esa es la forma
corta de un parámetro de tipo con bound: `fn describir(f: &impl Figura)`
declara lo mismo que `fn describir<T: Figura>(f: &T)`. La diferencia aparece
con dos parámetros:

```rust
trait Figura {
    fn area(&self) -> f64;
}

struct Cuadrado { lado: f64 }
struct Circulo { radio: f64 }

impl Figura for Cuadrado {
    fn area(&self) -> f64 { self.lado * self.lado }
}

impl Figura for Circulo {
    fn area(&self) -> f64 { 3.1416 * self.radio * self.radio }
}

fn cubre(a: &impl Figura, b: &impl Figura) -> bool {
    a.area() >= b.area()
}

fn cubre_igual<T: Figura>(a: &T, b: &T) -> bool {
    a.area() >= b.area()
}

fn main() {
    let c = Cuadrado { lado: 2.0 };
    let r = Circulo { radio: 1.0 };
    println!("{}", cubre(&c, &r));         // true
    println!("{}", cubre_igual(&c, &c));   // true
}
```

Cada `impl Figura` es un parámetro de tipo propio, así que `cubre` acepta un
cuadrado y un círculo. En `cubre_igual` los dos argumentos comparten `T`, y
`cubre_igual(&c, &r)` no compila: `E0308`, *expected `&Cuadrado`, found
`&Circulo`*. La forma larga hace falta cuando el mismo tipo debe aparecer en
dos lugares de la firma, o cuando se quiere nombrarlo con turbofish.

### [Regla 2:]{.prefijo} cada uso fija el parámetro a un solo tipo

Una struct también puede dejar un tipo como parámetro. Se declara después del
nombre:

```rust,compile_fail
struct Punto<T> {
    x: T,
    y: T,
}

fn main() {
    let p = Punto { x: 5, y: 4.0 };
}
```

```salida
error[E0308]: mismatched types
7 |     let p = Punto { x: 5, y: 4.0 };
  |                              ^^^ expected integer, found
  |                                  floating-point number
```

`T` no significa «cualquier tipo en cada campo». Significa un tipo por
elegir, el mismo en todos los lugares donde aparece. Al leer `x: 5` el
compilador fija `T` a un entero, y `y: 4.0` ya no encaja. Es lo que pasó con
`cubre_igual`.

Si las coordenadas pueden ser de tipos distintos, hacen falta dos
parámetros: `struct Punto<T, U> { x: T, y: U }`. Con esa definición,
`Punto { x: 5, y: 4.0 }` compila y es un `Punto<i32, f64>`. Dos parámetros
permiten tipos distintos, no los exigen: `Punto { x: 1, y: 2 }` es un
`Punto<i32, i32>`. Son tipos diferentes, y una variable de uno no acepta un
valor del otro. El programa de «Aplicación» usa esta struct.

### Métodos: para todo `T` o para un solo tipo

Un bloque `impl` de un tipo genérico declara sus propios parámetros.
`impl<T> Punto<T>` se lee: para todo `T`, estos son los métodos de
`Punto<T>`. Un `impl` sin parámetros, sobre un tipo concreto, agrega métodos
solo a ese tipo:

```rust
struct Punto<T> {
    x: T,
    y: T,
}

impl<T> Punto<T> {
    fn x(&self) -> &T { &self.x }
}

impl Punto<f64> {
    fn distancia_al_origen(&self) -> f64 {
        (self.x * self.x + self.y * self.y).sqrt()
    }
}

fn main() {
    let p = Punto { x: 3.0, y: 4.0 };
    println!("{}", p.x());                    // 3
    println!("{}", p.distancia_al_origen());  // 5

    let q = Punto { x: 3, y: 4 };
    println!("{}", q.x());                    // 3
}
```

`x()` no necesita saber nada de `T` y existe para cualquier `Punto`. La
distancia usa multiplicación, suma y `sqrt`, que el bloque genérico no tiene
permitidas. `q.distancia_al_origen()` no compila: `E0599`, con la nota *the
method was found for `Punto<f64>`*.

Sin el `<T>` después de `impl`, el compilador buscaría un tipo concreto
llamado `T` y fallaría con `E0425`, *cannot find type `T` in this
scope*.

### El bound que vive solo en el `impl`

Entre «todo `T`» y «un solo tipo» hay un punto medio: los `T` que cumplen un
bound. `Par<T>` no pide nada en su definición, y su método `mayor` solo
existe si `T` se puede comparar:

```rust
struct Par<T> {
    primero: T,
    segundo: T,
}

impl<T: PartialOrd> Par<T> {
    fn mayor(&self) -> &T {
        if self.primero > self.segundo {
            &self.primero
        } else {
            &self.segundo
        }
    }
}

fn main() {
    let n = Par { primero: 3, segundo: 8 };
    println!("{}", n.mayor());   // 8
}
```

Un `Par` de una struct sin `PartialOrd`, como `Par<Sensor>`, se construye y
sus campos se leen. Lo único que no tiene es el método: llamarlo falla con
`E0599`, *the method `mayor` exists for struct `Par<Sensor>`, but its trait
bounds were not satisfied*. Con el bound en la struct
(`struct Par<T: PartialOrd>`), ni siquiera se podría crear ese par. Por eso
el bound se pone en el `impl` que lo usa y no en la definición del tipo.

### [Regla 3:]{.prefijo} una versión por cada tipo usado

El código genérico no existe en el ejecutable. Al compilar, cada llamada con
un tipo nuevo produce una copia de la función con `T` sustituido. Ese paso
es la monomorfización. Las tres primeras llamadas de `mayor` generan lo mismo
que `mayor_i32`, `mayor_char` y una `mayor_f64` escritas a mano.

::: {.figura src="figuras/4.2-monomorfizacion.html"}
:::

De ahí sale el nombre de la sección, abstracciones de costo cero. Cuando el
programa corre, cada llamada va directo a una función concreta: no hay tabla
que consultar ni tipo que averiguar. La abstracción no cuesta nada en
ejecución frente a la versión escrita a mano.

El costo está en otro lado. Cada versión es código real: más tipos usados son
más copias que compilar y un ejecutable más grande. La alternativa es `dyn`,
que mantiene una sola copia y decide en ejecución a qué método llamar. Es la
única de estas herramientas que cuesta algo al correr, y se explica en
[6.3 Despacho dinámico]{.ref}.

### Tipos asociados: el tipo lo fija el `impl`

Un parámetro `<T>` lo elige quien llama. Hay contratos donde el tipo no es
una opción, sino una consecuencia de la implementación. Un contenedor de
enteros entrega enteros. El trait declara ese tipo sin valor, con `type`, y
cada `impl` lo resuelve:

```rust
trait Contenedor {
    type Elemento;   // parte del contrato, aún sin valor
    fn primero(&self) -> &Self::Elemento;
}

struct Terna { datos: [u32; 3] }
struct Letras { datos: [char; 2] }

impl Contenedor for Terna {
    type Elemento = u32;   // el impl lo fija
    fn primero(&self) -> &u32 { &self.datos[0] }
}

impl Contenedor for Letras {
    type Elemento = char;
    fn primero(&self) -> &char { &self.datos[0] }
}

fn main() {
    let t = Terna { datos: [7, 8, 9] };
    let l = Letras { datos: ['a', 'b'] };
    println!("{} {}", t.primero(), l.primero());   // 7 a
}
```

Dentro del trait el tipo se nombra `Self::Elemento`: el `Elemento` del tipo
que implemente el trait. En un bound se fija con `=`. Una función con
`C: Contenedor<Elemento = u32>` acepta `&t` y rechaza `&l` con `E0271`.

El criterio para elegir entre las dos formas:

| | Parámetro: `trait Tr<T>` | Tipo asociado: `type X;` |
| :--- | :--- | :--- |
| Implementaciones por tipo | varias: `Tr<u32>` y `Tr<String>` a la vez | una sola |
| Quién elige | quien llama | el `impl` |
| Se usa cuando | el mismo tipo debe servir con varios `T` | el tipo se deduce de quién implementa |

Los dos tipos asociados más frecuentes de la biblioteca estándar son `Item`,
del trait `Iterator` ([5.6 Iteradores]{.ref}), y `Output`, del trait `Future`
([9.2 async, await y Future]{.ref}).

### `impl Trait` en el retorno: el tipo lo elige la función

Como parámetro, `impl Trait` es un genérico y lo elige quien llama. Como tipo
de retorno significa lo contrario. La función devuelve un tipo concreto,
elegido en su cuerpo, y la firma solo promete que implementa el trait:

```rust,compile_fail
trait Figura {
    fn area(&self) -> f64;
}

struct Cuadrado { lado: f64 }

impl Figura for Cuadrado {
    fn area(&self) -> f64 { self.lado * self.lado }
}

fn unidad() -> impl Figura {
    Cuadrado { lado: 1.0 }
}

fn main() {
    let f = unidad();
    println!("{}", f.area());   // se puede: está en el trait
    println!("{}", f.lado);
    // E0609: no field `lado` on type `impl Figura`
}
```

El compilador sabe que `unidad` devuelve un `Cuadrado` y genera una llamada
directa a su `area`: sigue sin haber costo en ejecución. Quien llama no lo
sabe. Solo puede usar lo que `Figura` declara. Si mañana `unidad` devuelve
otra figura, ningún código que la use deja de compilar.

Esta forma sirve sobre todo cuando el tipo real es largo o no se puede
escribir. Es el caso de los iteradores, cuyo tipo crece con cada operación
encadenada: una función los devuelve como `impl Iterator`
([5.6 Iteradores]{.ref}).

### Dónde aparecen después

Casi todos los tipos de las secciones 5 y 6 son genéricos. Se leen con lo de
este capítulo:

| Tipo | Parámetros | Bound | Capítulo |
| :--- | :--- | :--- | :--- |
| `Option<T>` | el valor | ninguno | 5.1 |
| `Result<T, E>` | valor y error | ninguno | 5.2 |
| `Vec<T>` | los elementos | ninguno | 5.3 |
| `HashMap<K, V>` | llave y valor | `K: Hash + Eq` | 5.4 |
| `BinaryHeap<T>` | los elementos | `T: Ord` | 5.5 |
| `Box<T>`, `Rc<T>` | el dato apuntado | ninguno | 6.1, 6.2 |

`HashMap` y `BinaryHeap` siguen el patrón de `Par<T>`: el tipo acepta
cualquier parámetro y el bound está en los `impl` de sus métodos.

## Aplicación

Ejercicio del curso *Aprende Rust*. Un `Punto<T>` obliga a que `x` y `y`
sean del mismo tipo. El ejercicio pide dos cosas: que cada coordenada tenga
su tipo, y un método `intercambiar` que consuma el punto y devuelva otro con
las coordenadas cruzadas.

```rust
struct Punto<T, U> {
    x: T,
    y: U,
}

impl<T, U> Punto<T, U> {
    // Devuelve un punto nuevo con x e y intercambiados
    fn intercambiar(self) -> Punto<U, T> {
        Punto {
            x: self.y,
            y: self.x,
        }
    }
}

fn main() {
    let p = Punto { x: 5, y: 'a' };   // Punto<i32, char>
    let q = p.intercambiar();         // Punto<char, i32>
    println!("x = {}, y = {}", q.x, q.y);   // x = a, y = 5
}
```

El tipo de retorno es `Punto<U, T>`, con los parámetros en el otro orden. El
compilador lo comprueba: con `x: self.x` en el cuerpo, el resultado sería un
`Punto<T, U>` y la función no compilaría. El método recibe `self` y no
`&self` ([3.5 impl y métodos]{.ref}) porque mueve los dos campos al punto
nuevo. Con `&self` tendría que copiarlos, y eso exigiría un bound que el
ejercicio no necesita. Después de la llamada, `p` queda movida.

El bloque no pide ningún bound porque no hace nada con los valores: solo los
cambia de lugar. Sirve igual con un `Punto<String, f64>`.

## A fondo

**Un trait con parámetro se implementa varias veces para el mismo tipo.**
Es la primera fila de la tabla de criterio. Con
`trait En<T> { fn convertir(&self) -> T; }`, una struct `Metros` puede tener
a la vez `impl En<f64> for Metros` e `impl En<String> for Metros`. Quien
llama elige con el tipo que espera: `let n: f64 = m.convertir();` usa la
primera y `let s: String = m.convertir();` la segunda. Sin la anotación, el
compilador no sabe cuál elegir y emite `E0283`. Con un tipo asociado esa duda
no existe: un segundo `impl Contenedor for Terna` se rechaza con `E0119`,
*conflicting implementations*.

**`-> impl Trait` es un solo tipo, aunque no se nombre.** Una función que
devuelve un `Circulo` en una rama del `if` y un `Cuadrado` en la otra no
compila: `E0308`, *`if` and `else` have incompatible types*. Las dos figuras
implementan el trait, pero el retorno debe ser un único tipo concreto, fijo
al compilar. Devolver uno u otro según un dato de
ejecución es trabajo de `dyn` ([6.3 Despacho dinámico]{.ref}).

**Lifetimes y tipos comparten los mismos `<` y `>`.** Los lifetimes van
primero: `struct Vista<'a, T> { dato: &'a T }`. Los dos son parámetros
genéricos. La diferencia es que un lifetime no produce copias: la
monomorfización solo ocurre por tipos.

**La monomorfización ocurre por tipo, no por llamada.** Cien llamadas a
`mayor` con `i32` comparten una sola versión. El tamaño del ejecutable crece
con la cantidad de tipos distintos, y el efecto se nota en funciones
genéricas largas que se usan con muchos tipos. Las structs siguen la misma
regla: `Punto<u8>` y `Punto<f64>` son tipos aparte, de 2 y 16 bytes.
