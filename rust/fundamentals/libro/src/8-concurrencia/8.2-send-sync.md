# 8.2 · Send y Sync

[6.2 Rc, RefCell y árboles]{.ref} dejó un error sin explicar: un
`Rc<RefCell<i32>>` enviado a un hilo no compila. [8.1 Hilos]{.ref} movió un
`String` y un `Vec` a otro hilo con `move`, y el compilador los aceptó. Algo
separa a unos tipos de otros, y se decide antes de ejecutar.

No lo decide una regla especial para hilos: el lenguaje no tiene ninguna.
Lo deciden dos traits de la biblioteca estándar, `Send` y `Sync`, y los
bounds que `thread::spawn` escribe en su firma. Un valor que no puede cruzar
a otro hilo es un tipo que no cumple un bound. El error es un E0277, y se
lee como los de [4.1 Traits]{.ref}.

## Definiciones y reglas

Carrera de datos
:   *(data race)*: dos hilos acceden al mismo dato al mismo tiempo, al menos
    uno escribe, y nada ordena los accesos. El resultado no está definido.

`Send`
:   trait marcador, sin métodos, como `Copy`
    ([4.4 Traits de la stdlib]{.ref}). Un valor de un tipo `Send` se puede
    mover a otro hilo.

`Sync`
:   trait marcador. Un valor de un tipo `Sync` se puede compartir entre
    hilos por referencia `&`.

`Arc<T>`
:   *(atomically reference counted)*: un `Rc<T>` de `std::sync` cuyo
    contador se modifica con operaciones atómicas. Una operación atómica se
    completa en un solo paso: ningún hilo observa un estado intermedio.

::: {.reglas titulo="Las tres reglas de Send y Sync"}
1. `thread::spawn` exige que la closure y su resultado sean `Send`. Un valor
   cruza a otro hilo solo si su tipo lo es.
2. `T` es `Sync` exactamente cuando `&T` es `Send`: compartir un valor es
   mandar una referencia.
3. Los dos son *auto traits*: el compilador los implementa solo. Un tipo
   los cumple si todos sus campos los cumplen.
:::

## De un vistazo

| Tipo | `Send` | `Sync` |
| :--- | :--- | :--- |
| `i32`, `bool`, `char`, `String` | sí | sí |
| `Vec<T>`, `Box<T>` | si `T: Send` | si `T: Sync` |
| `&T` | si `T: Sync` | si `T: Sync` |
| `&mut T` | si `T: Send` | si `T: Sync` |
| `Rc<T>` | no | no |
| `Arc<T>` | si `T: Send + Sync` | si `T: Send + Sync` |
| `Cell<T>`, `RefCell<T>` | si `T: Send` | no |
| `Mutex<T>` | si `T: Send` | si `T: Send` |
| `*const T`, `*mut T` | no | no |

Criterio: ante un E0277 que menciona hilos, se busca en el tipo una pieza de
las filas con «no». `Rc` se cambia por `Arc`. `Cell` y `RefCell` se cambian
por `Mutex`, que es tema de [8.3 Estado compartido]{.ref}.

## Las reglas, una por una

### El punto donde el compilador revisa

La función `lanzar` copia la firma de `thread::spawn`, con sus mismos bounds,
y le pasa la closure tal cual. Compila, así que esos bounds son todo lo que
`spawn` pide:

```rust
use std::thread::{self, JoinHandle};

fn lanzar<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
{
    thread::spawn(f)
}

fn main() {
    let texto = String::from("hola");
    let hilo = lanzar(move || texto.len());
    println!("{}", hilo.join().unwrap());   // 4
}
```

Cada pieza del `where` responde a algo que ocurre al lanzar el hilo.
`F: FnOnce() -> T` pide una closure sin parámetros, que el hilo llama una
sola vez ([4.3 Closures]{.ref}). `F: Send` pide que la closure pueda cruzar:
se crea en un hilo y corre en otro. `F: 'static` pide que no guarde
préstamos que caduquen, porque el hilo puede vivir más que quien lo lanzó.
`T: Send + 'static` pide lo mismo para el resultado, que `join` entrega en
el hilo que espera.

Una closure guarda lo que captura. Por la regla 3, es `Send` si todas sus
capturas lo son. El bound `F: Send` es entonces una pregunta sobre cada valor
que entra al hilo, y `T: Send` es la misma pregunta sobre lo que sale. Una
closure que devuelve un `Rc`, como `thread::spawn(|| Rc::new(5))`, falla
con el mismo E0277, y la nota señala el bound `T: Send + 'static`.

### [Regla 1:]{.prefijo} un valor cruza solo si su tipo es `Send`

Dos `Rc` apuntan al mismo `Vec`. Uno se queda en `main` y el otro se mueve
al hilo nuevo:

```rust,compile_fail
use std::rc::Rc;
use std::thread;

fn main() {
    let tabla = Rc::new(vec![10, 20, 30]);
    let copia = Rc::clone(&tabla);

    let h = thread::spawn(move || copia.len());
    println!("{} {}", h.join().unwrap(), tabla.len());
}
```

```salida
error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads
              safely
 8 |     let h = thread::spawn(move || copia.len());
   |             ------------- -------^^^^^^^^^^^^
   |             |             |
   |             |             `Rc<Vec<i32>>` cannot be sent
   |             |             between threads safely
   |             required by a bound introduced by this call
   = help: within `{closure@src/main.rs:8:27: 8:34}`, the
           trait `Send` is not implemented for
           `Rc<Vec<i32>>`
note: required by a bound in `spawn`
   |     F: Send + 'static,
   |        ^^^^ required by this bound in `spawn`
```

El mensaje trae las tres partes de todo E0277. El `help` dice qué trait
falta y a qué tipo: `Send`, a `Rc<Vec<i32>>`. El `within` dice dónde está
ese tipo: dentro de la closure, como captura. La nota final dice quién lo
pidió: el bound `F: Send` de `spawn`.

`Rc` no es `Send` por su contador. `Rc::clone` lo lee, le suma 1 y lo
escribe, en tres pasos y sin sincronizar. En este programa, `tabla` y
`copia` comparten un contador desde dos hilos. Si los dos clonan a la vez,
los dos leen el mismo número y escriben el mismo resultado: una suma se
pierde. Es una carrera de datos. Con el contador de menos, el `Vec` se
libera cuando todavía queda un dueño, y ese dueño lee memoria liberada.

::: {.figura src="figuras/8.2-contador.html"}
:::

`Arc<T>` es el mismo tipo con el contador atómico. Tiene la misma interfaz
que `Rc`: `Arc::new`, `Arc::clone`, `Arc::strong_count` y lectura por
`Deref`. El programa anterior compila con cambiar el tipo:

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let tabla = Arc::new(vec![10, 20, 30]);
    let copia = Arc::clone(&tabla);

    let h = thread::spawn(move || copia.len());
    println!("{} {}", h.join().unwrap(), tabla.len());  // 3 3
}
```

La diferencia tiene un costo. Una suma atómica cuesta más que una suma
ordinaria: la documentación de `Arc` lo da como el motivo para conservar
`Rc`. Se paga en cada `Arc::clone` y en cada destrucción de un `Arc`. Leer a
través del puntero cuesta lo mismo, y los dos miden 8 bytes en una máquina
de 64 bits. Dentro de un solo hilo, `Rc` no paga esa coordinación, y el
compilador impide usarlo donde sí haría falta.

### [Regla 2:]{.prefijo} compartir es mandar una referencia

`thread::scope` ([8.1 Hilos]{.ref}) permite que un hilo tome prestada una
variable local. Aquí dos hilos leen el mismo `Vec` sin moverlo:

```rust
use std::thread;

fn main() {
    let precios = vec![120, 80, 45];

    let (suma, mayor) = thread::scope(|s| {
        let a = s.spawn(|| precios.iter().sum::<i32>());
        let b = s.spawn(|| precios.iter().max().copied());
        (a.join().unwrap(), b.join().unwrap())
    });
    println!("{suma} {mayor:?}");   // 245 Some(120)
}
```

Ninguna closure lleva `move`: cada una captura un `&Vec<i32>`. El `spawn` de
un scope también pide `F: Send`, así que esa referencia tiene que ser
`Send`. Esa es la definición de `Sync`: `Vec<i32>` es `Sync` porque
`&Vec<i32>` es `Send`. No hay un segundo mecanismo. Compartir entre hilos es
mover una referencia, y la regla 1 se aplica a la referencia.

Para la mayoría de los tipos la respuesta es sí. Una `&` solo deja leer, y
dos lecturas simultáneas no forman una carrera de datos. La respuesta cambia
en los tipos con mutabilidad interior, que escriben a través de `&`
([6.2 Rc, RefCell y árboles]{.ref}). Con `let celda = RefCell::new(0);` en
lugar del `Vec`, y un hilo que ejecuta `*celda.borrow_mut() += 1`, el
programa no compila: *E0277: `RefCell<i32>` cannot be shared between threads
safely*. La nota dice *required for `&RefCell<i32>` to implement `Send`*.
El mensaje cambia de «sent» a «shared», y el trait que falta es `Sync`.

### Las tres excepciones

Casi todo tipo es `Send` y `Sync`. Los que no lo son caben en tres grupos,
que son las filas con «no» de la tabla inicial.

`Rc<T>` no es ninguna de las dos cosas. Mover un `Rc` a otro hilo deja al
contador con dueños en dos hilos, que es el caso de la figura. Compartir un
`&Rc<T>` permite llamar a `Rc::clone` desde el otro hilo, con el mismo
efecto.

`RefCell<T>` sí es `Send`. Una celda que se muda entera a otro hilo sigue
teniendo un solo dueño, y su bandera la toca un hilo a la vez. No es
`Sync`: `borrow_mut` recibe `&self`, y dos hilos con una `&RefCell` leerían
la bandera a la vez y obtendrían dos préstamos exclusivos. `Cell<T>` es la
celda de `std::cell` para valores `Copy`: cambia su contenido con `set`, a
través de `&` y sin bandera. Tiene la misma respuesta por el mismo motivo.

Un puntero crudo, `*const T` o `*mut T`, es una dirección de memoria sin
dueño ni lifetime. Leer a través de él exige un bloque `unsafe`, que se presenta en
[10.1 El ecosistema]{.ref}. El compilador no sabe quién más usa esa dirección, y
responde «no» en las dos columnas.

### `Arc<RefCell<T>>` no cruza

En un solo hilo, compartir y mutar se resolvía con `Rc<RefCell<T>>`. Cambiar
`Rc` por `Arc` parece la traducción directa:

```rust,compile_fail
use std::cell::RefCell;
use std::sync::Arc;
use std::thread;

fn main() {
    let celda = Arc::new(RefCell::new(0));
    let c2 = Arc::clone(&celda);

    let h = thread::spawn(move || *c2.borrow_mut() += 1);
    h.join().unwrap();
    println!("{}", celda.borrow());
}
```

```salida
error[E0277]: `RefCell<i32>` cannot be shared between threads
              safely
 9 |     let h = thread::spawn(move || *c2.borrow_mut() += 1);
   |             ------------- ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |             |
   |             required by a bound introduced by this call
   = help: the trait `Sync` is not implemented for
           `RefCell<i32>`
   = note: if you want to do aliasing and mutation between
           multiple threads, use `std::sync::RwLock` instead
   = note: required for `Arc<RefCell<i32>>` to implement
           `Send`
```

El programa mueve un `Arc`, y el error habla de compartir. La última nota
une las dos cosas: `Arc<RefCell<i32>>` sería `Send` solo si `RefCell<i32>`
fuera `Sync`. Un `Arc` movido a otro hilo deja otro `Arc` en el hilo de
origen, y los dos entregan `&T` al mismo valor. Mover un `Arc<T>` es
compartir un `T`. Por eso la fila de `Arc<T>` pide `T: Send + Sync`.

`Arc` resuelve el contador, no la mutación. Falta una celda cuya
comprobación de préstamos sea segura entre hilos. El compilador sugiere
`RwLock`. La más usada es `Mutex<T>`, y `Arc<Mutex<T>>` es el punto de
partida de [8.3 Estado compartido]{.ref}.

### Preguntarle al compilador

Para saber si un tipo cumple un trait no hace falta lanzar un hilo. Basta
una función genérica vacía con ese bound. Este programa comprueba la tabla
de «De un vistazo»: las líneas activas compilan, y cada línea comentada da
E0277 al activarla.

```rust
use std::cell::{Cell, RefCell};
use std::sync::{Arc, Mutex};

fn es_send<T: Send>() {}
fn es_sync<T: Sync>() {}

fn main() {
    es_send::<Arc<Vec<i32>>>();
    es_sync::<Arc<Vec<i32>>>();
    es_sync::<Mutex<Cell<i32>>>();    // Sync con T: Send
    es_send::<RefCell<i32>>();
    es_send::<&mut Cell<i32>>();      // &mut T pide T: Send
    // es_sync::<RefCell<i32>>();     E0277
    // es_send::<std::rc::Rc<i32>>(); E0277, y es_sync igual
    // es_send::<&Cell<i32>>();       E0277: Cell no es Sync
    // es_send::<Arc<Cell<i32>>>();   E0277: Cell no es Sync
    // es_send::<*const i32>();       E0277, y es_sync igual
}
```

### [Regla 3:]{.prefijo} se propagan solos

Ningún programa de este capítulo escribe `impl Send`. El compilador
implementa los dos traits para cada tipo, a partir de sus campos. Un struct
con un `String` es `Send` y `Sync` sin declarar nada. Con un campo `Rc`
deja de serlo, también sin declarar nada:

```rust,compile_fail
use std::rc::Rc;
use std::thread;

struct Config {
    nombre: String,
    etiquetas: Rc<Vec<String>>,
}

fn largo(c: &Config) -> usize { c.nombre.len() }

fn main() {
    let config = Config {
        nombre: String::from("api"),
        etiquetas: Rc::new(Vec::new()),
    };
    let h = thread::spawn(move || largo(&config));
    println!("{}", h.join().unwrap());
}
```

```salida
error[E0277]: `Rc<Vec<String>>` cannot be sent between
              threads safely
16 |     let h = thread::spawn(move || largo(&config));
   |             ------------- -------^^^^^^^^^^^^^^^
   = help: within `{closure@src/main.rs:16:27: 16:34}`, the
           trait `Send` is not implemented for
           `Rc<Vec<String>>`
note: required because it appears within the type `Config`
 4 | struct Config {
   |        ^^^^^^
note: required because it's used within this closure
```

El error no nombra a `Config` en su primera línea. Nombra el tipo del campo
que rompe la cadena, `Rc<Vec<String>>`, y las notas reconstruyen el camino
hacia afuera: ese tipo está dentro de `Config`, y `Config` está dentro de la
closure. Se lee de abajo hacia arriba, desde lo que cruza hasta la pieza que
no puede. El nombre del campo no aparece: se localiza por su tipo.

Con `etiquetas: Arc<Vec<String>>` y `Arc::new` en `main`, el programa compila
e imprime `3`. La propagación también atraviesa los tipos genéricos de la
biblioteca: `Vec<Rc<i32>>` y `Option<Rc<i32>>` no son `Send`. El compilador
no avisa al declarar el campo `Rc`, sino en la llamada que pide el bound.

## Aplicación

Una tabla de tarifas se calcula una vez y la consultan varios hilos. Nadie
la modifica, así que basta `Arc<Vec<u32>>`: varios dueños que solo leen.
Cada `Envio` lleva sus datos y un `Arc` a la tabla, con la tarifa por kilo
de cada zona, y se mueve completo a su hilo.

```rust
use std::sync::Arc;
use std::thread;

struct Envio {
    zona: usize,
    kilos: u32,
    tarifas: Arc<Vec<u32>>,
}

fn costo(e: &Envio) -> u32 { e.kilos * e.tarifas[e.zona] }

fn main() {
    let tarifas = Arc::new(vec![12, 18, 25]);
    let pedidos = [(0, 10), (2, 4), (1, 5)];
    let mut hilos = Vec::new();
    for (zona, kilos) in pedidos {
        let tarifas = Arc::clone(&tarifas);
        let envio = Envio { zona, kilos, tarifas };
        hilos.push(thread::spawn(move || costo(&envio)));
    }
    for (n, h) in hilos.into_iter().enumerate() {
        println!("envío {}: ${}", n + 1, h.join().unwrap());
    }
    println!("dueños: {}", Arc::strong_count(&tarifas));
}
```

El programa imprime `envío 1: $120`, `envío 2: $100`, `envío 3: $90` y
`dueños: 1`, una línea cada uno. Los hilos pueden terminar en cualquier
orden. La salida es fija porque `main` hace `join` en el orden de
lanzamiento, y cada hilo devuelve su resultado en lugar de imprimirlo.

`Envio` es `Send` por sus tres campos: dos enteros y un `Arc<Vec<u32>>`.
Con `tarifas: Rc<Vec<u32>>` y `Rc::clone`, el programa falla en
`thread::spawn` con *E0277: `Rc<Vec<u32>>` cannot be sent between threads
safely*, y la nota *required because it appears within the type `Envio`*.
El arreglo está en la declaración del campo, no en la línea señalada.

## A fondo

**Implementar `Send` a mano exige `unsafe impl`.** Para un struct con un
puntero crudo, `impl Send for Direccion {}` no compila: *E0200: the trait
`Send` requires an `unsafe impl` declaration*. Con `unsafe impl` compila, y
la garantía pasa a ser responsabilidad de quien lo escribe. Así lo hace la
biblioteca estándar: `Arc` guarda un puntero crudo, y su código declara
`unsafe impl Send` con el bound `T: Sync + Send`.

**`MutexGuard` es `Sync` y no es `Send`.** Es el guard que entrega un
`Mutex` ([8.3 Estado compartido]{.ref}), y libera el candado en su `Drop`.
Algunos sistemas operativos exigen que lo libere el mismo hilo que lo tomó.
La restricción reaparece con las tareas asíncronas
([9.4 Send en las tareas]{.ref}).

**`'static` en un bound no significa «vive todo el programa».** `T: 'static`
pide que el tipo no contenga préstamos que puedan caducar
([3.6 Lifetimes]{.ref}). Un `String` o un `Envio` lo cumplen, aunque se
destruyan un instante después: son dueños de sus datos.

**`thread::scope` quita `'static` y conserva `Send`.** Su `spawn` declara
`F: FnOnce() -> T + Send + 'scope`. El scope espera a sus hilos antes de
regresar, y eso permite capturar préstamos de variables locales. Un `Rc`
prestado a uno de esos hilos falla igual, con *E0277: `Rc<Vec<i32>>` cannot
be shared between threads safely*.

**Una closure captura campos, no structs completos.** Con el `Config` de la
regla 3, `thread::spawn(move || config.nombre.len())` compila, aunque
`Config` no sea `Send`. La closure solo usa `config.nombre`, y solo ese
`String` se mueve al hilo. En el ejemplo de la regla 3 la closure pasa
`&config` a una función, y eso captura el struct entero.
