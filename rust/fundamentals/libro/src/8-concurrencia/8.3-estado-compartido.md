# 8.3 · Estado compartido

[8.2 Send y Sync]{.ref} cerró con un programa a medias. `Arc<T>` resolvió
que varios hilos fueran dueños del mismo valor. Al envolver ese valor en un
`RefCell` para modificarlo, el compilador lo rechazó con *E0277:
`RefCell<i32>` cannot be shared between threads safely*. La bandera de
préstamos no está protegida contra dos hilos que la toquen a la vez.

Son los dos problemas de [6.2 Rc, RefCell y árboles]{.ref}, ahora entre
hilos: varios dueños, y mutar después de compartir. El primero ya tiene su
tipo. Este capítulo trae el del segundo, `Mutex<T>`, y con él una falla que
en un solo hilo no existía.

## Definiciones y reglas

`Mutex<T>`
:   *(mutual exclusion)*: un valor guardado junto a un candado. El único
    camino al valor es `lock()`, que toma el candado.

`MutexGuard<T>`
:   el guard que devuelve `lock()`. Da acceso al valor, como un `&mut T`,
    y suelta el candado en su `Drop`.

Sección crítica
:   el tramo de código que corre con el candado tomado.

Envenenamiento
:   *(poisoning)*: marca que queda en un mutex cuando un hilo hace panic
    con el candado tomado.

Interbloqueo
:   *(deadlock)*: dos o más hilos detenidos, cada uno en espera de un
    candado que tiene otro.

::: {.reglas titulo="Qué cambia entre hilos"}
1. `Arc<T>` reparte la propiedad entre hilos y `Mutex<T>` entrega el dato
   a un solo hilo a la vez. Es `Rc<RefCell<T>>`, pieza por pieza.
2. `lock()` espera. Donde `borrow_mut()` hacía panic, el hilo se detiene
   hasta que el candado queda libre.
3. El candado dura lo que vive el guard. Mientras vive, los demás hilos
   esperan.
:::

## De un vistazo

| Un solo hilo (6.2) | Varios hilos | Qué cambia |
| :--- | :--- | :--- |
| `Rc<T>` | `Arc<T>` | el contador es atómico |
| `RefCell<T>` | `Mutex<T>` | la bandera pasa a ser un candado |
| `borrow_mut()` | `lock()` | devuelve un `Result` |
| `RefMut<T>` | `MutexGuard<T>` | nada: un guard con `Drop` |
| dato ocupado: panic | dato ocupado: espera | aparece el interbloqueo |
| `borrow()` y `borrow_mut()` | `read()` y `write()` de `RwLock<T>` | lo mismo, con espera |
| `Rc<RefCell<T>>` | `Arc<Mutex<T>>` | la combinación se traduce entera |

Criterio: el de 6.2, sin cambios. Se cuentan los dueños y se pregunta si
hay que mutar después de compartir. Varios hilos que solo leen piden
`Arc<T>`. Varios hilos que además modifican piden `Arc<Mutex<T>>`.

## Las reglas, una por una

### `Mutex<T>`, primero sin hilos

Un `Mutex` no necesita hilos para funcionar, y sin ellos se ve mejor qué
hace. `Mutex::new(5)` guarda el 5 dentro del mutex. `lock()` toma el candado
y devuelve un guard dentro de un `Result`: el `.unwrap()` se explica en la
regla 2. El dato se lee y se escribe a través del guard.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);     // sin `mut`
    {
        let mut guard = m.lock().unwrap();
        *guard += 1;           // se usa como un &mut i32
        println!("{m:?}");     // data: "<locked>"
    }                          // muere el guard
    println!("{m:?}");         // data: 6
}
```

```salida
Mutex { data: "<locked>", poisoned: false, .. }
Mutex { data: 6, poisoned: false, .. }
```

Es el `RefCell` de 6.2 con otros nombres. `lock()` recibe `&self`, así que
el binding no lleva `mut`: es mutabilidad interior. El guard se usa como
referencia gracias a `Deref`. No existe un `unlock()`: el candado se suelta
en el `Drop` del guard ([4.4 Traits de la stdlib]{.ref}), al cerrar la llave.

En C o en Java, el candado y el dato son dos variables, y nada obliga a
tomar el primero antes de tocar el segundo. Aquí el dato vive dentro del
mutex: un programa que lo toca sin pasar por `lock()` no se puede escribir.

### [Regla 1:]{.prefijo} `Arc<Mutex<T>>`, el dibujo de 6.2 entre hilos

Con `Arc` por fuera y `Mutex` por dentro compila el programa que 8.2 dejó
pendiente. Ocho hilos suman mil veces cada uno sobre el mismo contador.
Cada hilo recibe su propio clon del `Arc`, movido a su closure.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let contador = Arc::new(Mutex::new(0));
    let mut hilos = Vec::new();

    for _ in 0..8 {
        let c = Arc::clone(&contador);    // un dueño por hilo
        hilos.push(thread::spawn(move || {
            for _ in 0..1000 {
                *c.lock().unwrap() += 1;
            }
        }));
    }
    for h in hilos {
        h.join().unwrap();
    }

    println!("{}", contador.lock().unwrap());   // 8000
}
```

El resultado es 8000 en todas las corridas. Sumar 1 son tres pasos: leer,
sumar y escribir. Sin exclusión, dos hilos podrían leer el mismo valor y una
de las dos sumas se perdería. El candado vuelve indivisibles los tres pasos.
El orden en que los hilos se turnan cambia de una corrida a otra, y el total
no depende de él.

Cada tipo atiende a un problema. `Arc` responde quién es el dueño cuando
los dueños están en hilos distintos. `Mutex` responde cómo se modifica algo
que varios alcanzan.

::: {.figura src="figuras/8.3-traduccion.html"}
:::

El compilador acepta el programa por lo que dice 8.2. `Mutex<T>` es `Sync`
cuando `T` es `Send`, porque garantiza que solo un hilo a la vez toca el
dato. Con eso `Arc<Mutex<i32>>` es `Send` y puede moverse a cada closure.

### [Regla 2:]{.prefijo} `lock()` espera

Si el candado está libre, `lock()` lo toma y regresa de inmediato. Si lo
tiene otro hilo, `lock()` no regresa: el sistema operativo detiene al hilo
que llamó y lo despierta cuando el candado se libera. `RefCell` no podía
hacer eso. Con un solo hilo, nadie más iba a soltar el préstamo, y esperar
era esperar para siempre. Por eso hacía panic.

::: {.figura src="figuras/8.3-candado.html"}
:::

`lock()` devuelve un `Result` por un caso que tampoco existía en 6.2. Un
hilo puede hacer panic con el candado tomado. El guard se destruye durante
el panic y el candado queda libre, pero el dato pudo quedar a medio
modificar. El mutex se marca como envenenado, y desde entonces todo `lock()`
devuelve `Err`.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let saldo = Arc::new(Mutex::new(100));

    let s = Arc::clone(&saldo);
    let hilo = thread::spawn(move || {
        let mut guard = s.lock().unwrap();
        *guard -= 30;
        panic!("falla a media operación");
    });
    hilo.join().unwrap_err();     // el hilo terminó en panic

    if let Err(veneno) = saldo.lock() {
        println!("{veneno}");
        println!("dato: {}", veneno.into_inner());
    }
}
```

```salida
thread '<unnamed>' panicked at src/main.rs:11:9:
falla a media operación
poisoned lock: another task failed inside
dato: 70
```

El `Err` no pierde el dato: `into_inner()` entrega el guard de todos modos,
para el programa que sepa reparar el estado. El `.unwrap()` habitual toma la
otra decisión. Si un hilo falló a media operación, los demás fallan también
en vez de seguir con un dato dudoso.

### [Regla 3:]{.prefijo} el candado dura lo que vive el guard

Es la regla 3 de 6.2 y pesa más. Allá, un guard que vivía de más provocaba
un panic visible. Aquí no falla nada: los demás hilos esperan, y el programa
se vuelve lento sin dar aviso. Las tres formas de terminar antes son las
mismas, y las tres destruyen el guard. `try_lock()` hace la consulta sin
esperar y sirve para ver el estado del candado.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(vec![1, 2, 3]);

    let guard = m.lock().unwrap();
    println!("{}", m.try_lock().is_ok());   // false: tomado
    drop(guard);                            // muere aquí
    println!("{}", m.try_lock().is_ok());   // true

    m.lock().unwrap().push(4);              // temporal: `;`
    {
        let mut guard = m.lock().unwrap();
        guard.push(5);
    }                                       // con el bloque
    println!("{:?}", m.lock().unwrap());    // [1, 2, 3, 4, 5]
}
```

En el contador, `*c.lock().unwrap() += 1;` usa un guard temporal: el candado
se toma y se suelta en cada vuelta. Con `let mut n = c.lock().unwrap();`
antes del `for`, el primer hilo conservaría el candado durante sus mil
sumas. El total sería el mismo, y los ocho hilos correrían uno tras otro.

La disciplina es acortar la sección crítica. El cálculo largo, la lectura de
un archivo o un `println!` se hacen fuera, y con el candado tomado solo se
copia o se actualiza el dato.

### El interbloqueo

Esperar trae un problema que el panic no tenía. El caso mínimo cabe en un
hilo: dos `m.lock().unwrap()` seguidos, con el primer guard todavía vivo.
Con `RefCell`, el segundo `borrow_mut()` hacía panic. Aquí el programa
compila y no termina: el hilo espera un candado que solo él puede soltar.
La documentación dice que esa llamada puede colgarse o hacer panic. En la
máquina donde se probó, se cuelga.

La forma común usa dos hilos y dos mutex tomados en orden inverso: cada
hilo toma el suyo y espera el del otro. La pausa con `thread::sleep` da
tiempo a que los dos tomen su primer candado.

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let a = Arc::new(Mutex::new(0));
    let b = Arc::new(Mutex::new(0));

    let (a2, b2) = (Arc::clone(&a), Arc::clone(&b));
    let hilo = thread::spawn(move || {
        let _ga = a2.lock().unwrap();     // toma a
        thread::sleep(Duration::from_millis(50));
        let _gb = b2.lock().unwrap();     // espera b
    });

    let _gb = b.lock().unwrap();          // toma b
    thread::sleep(Duration::from_millis(50));
    let _ga = a.lock().unwrap();          // espera a
    hilo.join().unwrap();
    println!("fin");                      // no se alcanza
}
```

::: {.advertencia titulo="El compilador no detecta un interbloqueo"}
Los dos casos compilan sin avisos y ninguno termina: hay que
interrumpirlos con Ctrl+C. Un interbloqueo no es una carrera de datos ni un
acceso inválido, y las garantías de `Send` y `Sync` no lo cubren.
:::

Dos hábitos lo evitan. El primero es tomar los candados siempre en el mismo
orden: si los dos hilos piden `a` y después `b`, uno espera y el otro
termina. El segundo es no pedir un candado con otro tomado, que es la regla
3 llevada al extremo.

### `RwLock<T>`: varios lectores o un escritor

`Mutex` no distingue leer de escribir: todo acceso es exclusivo, y dos
hilos que solo leen se estorban. `RwLock<T>` separa los dos permisos.
`read()` admite varios guards de lectura a la vez, y `write()` entrega uno
solo, sin lectores vivos.

```rust
use std::sync::RwLock;

fn main() {
    let config = RwLock::new(String::from("v1"));
    {
        let uno = config.read().unwrap();
        let dos = config.read().unwrap();      // dos lectores
        println!("{uno} {dos}");               // v1 v1
        println!("{}", config.try_write().is_ok());  // false
    }                                          // mueren
    config.write().unwrap().push_str(".1");    // un escritor
    println!("{}", config.read().unwrap());    // v1.1
}
```

Es la regla 1 de [3.3 Borrowing]{.ref}, una `&mut` o varias `&`, comprobada
al ejecutar y entre hilos. Un `write()` con lectores vivos espera, por la
regla 2. `RwLock` conviene cuando las lecturas son mucho más frecuentes que
las escrituras y duran lo suficiente para estorbarse, como una
configuración que se consulta siempre y cambia rara vez. Lleva más
contabilidad que un `Mutex`, que sigue siendo la opción por default.

### Canales: comunicar en vez de compartir

Hay otra manera de coordinar hilos, y no usa candados. En lugar de que
todos alcancen el mismo dato, un hilo le envía valores a otro.
`mpsc::channel()` devuelve las dos puntas de un canal: un emisor, `tx`, y
un receptor, `rx`.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let aviso = String::from("listo");
        tx.send(aviso).unwrap();     // mueve `aviso` al canal
    });

    let recibido = rx.recv().unwrap();   // espera un valor
    println!("{recibido}");              // listo
}
```

`send` recibe el valor por move. Un `println!("{aviso}")` después del
`send` no compila: *E0382: borrow of moved value: `aviso`*. Es el ownership
de [3.2 Ownership]{.ref} haciendo el trabajo del candado. El valor tiene un
dueño a la vez, y el hilo que lo envió ya no puede tocarlo. `recv` detiene
al hilo hasta que llega un valor. Devuelve `Err` cuando el canal está vacío
y ya no queda ningún emisor.

`mpsc` abrevia *multiple producer, single consumer*: el emisor se clona y
el receptor no. Tres hilos envían cada uno un valor con su propio clon de
`tx` (ejercicio del curso *Aprende Rust*). El receptor es además un
iterador, que entrega valores hasta que todos los emisores se destruyen.
El orden de llegada cambia entre corridas, y por eso se ordenan.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for id in 1..=3 {
        let tx = tx.clone();             // un emisor por hilo
        thread::spawn(move || tx.send(id * 10).unwrap());
    }
    drop(tx);                            // suelta el original

    let mut recibidos: Vec<i32> = rx.iter().collect();
    recibidos.sort();

    println!("Recibidos: {recibidos:?}");   // [10, 20, 30]
    println!("Total: {}", recibidos.iter().sum::<i32>());
}
```

::: {.advertencia titulo="El drop(tx) olvidado"}
Sin `drop(tx)`, el programa compila y no termina. Los tres clones mueren
con sus hilos, pero el `tx` original sigue vivo en `main`, y el iterador
espera a un emisor que nunca va a enviar.
:::

Criterio: canal cuando el trabajo fluye en una dirección y cada valor
tiene un destinatario, como en una cadena de etapas. `Arc<Mutex<T>>` cuando
hay un estado central que varios hilos deben ver y actualizar: un contador,
una caché, un registro. Un canal tampoco es inmune a la espera, como mostró
el `drop(tx)`.

## Aplicación

Cuatro hilos suman cada uno la cantidad de un pedido a un total compartido
(ejercicio del curso *Aprende Rust*). El enunciado parte de un
`Rc::new(RefCell::new(0))` que no compila entre hilos, y se resuelve
cambiando dos tipos y una llamada.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let pedidos = [3, 5, 2, 7];
    let total = Arc::new(Mutex::new(0));
    let mut hilos = Vec::new();

    for cantidad in pedidos {
        let total = Arc::clone(&total);
        hilos.push(thread::spawn(move || {
            let mut suma = total.lock().unwrap();
            *suma += cantidad;
        }));
    }
    for hilo in hilos {
        hilo.join().unwrap();
    }

    println!("Total: {}", total.lock().unwrap());   // 17
}
```

Aquí el guard sí se liga a una variable, `suma`. Muere al terminar la
closure, que tiene dos líneas: la sección crítica sigue siendo corta.

La misma traducción se aplica a la lista de tareas de 6.2, que Ana y Luis
llenaban en un solo hilo. Cambian seis líneas:

| En 6.2 | Aquí |
| :--- | :--- |
| `use std::cell::RefCell;` y `use std::rc::Rc;` | `use std::sync::{Arc, Mutex};` |
| `type Tareas = Rc<RefCell<Vec<String>>>;` | `type Tareas = Arc<Mutex<Vec<String>>>;` |
| `Rc::new(RefCell::new(Vec::new()))` | `Arc::new(Mutex::new(Vec::new()))` |
| `tareas.borrow_mut().push(...)` | `tareas.lock().unwrap().push(...)` |
| `tareas.borrow().len()` | `tareas.lock().unwrap().len()` |
| `Rc::clone(&lista)` | `Arc::clone(&lista)` |

Las firmas de `anotar` y `cuantas` no cambian, gracias al alias. En `main`,
cada clon se mueve a su hilo: `thread::spawn(move || anotar(&ana, ...))`.
La disciplina es la de 6.2: cada función toma el candado y lo suelta en el
mismo enunciado, con un guard temporal, así que ningún hilo espera más de
lo que dura un `push`. El conteo es 3 en todas las corridas. El orden de
las tareas en el vector depende de qué hilo llega primero al candado.

## A fondo

**Dentro de `thread::scope`, el `Arc` sobra.** `Arc` existe porque un hilo
de `thread::spawn` puede vivir más que la función que lo lanzó. Los hilos
de `thread::scope` ([8.1 Hilos]{.ref}) terminan antes de que el scope
regrese, y pueden tomar prestado. Como `Mutex<T>` es `Sync`, un `&Mutex<T>`
cruza a cada hilo. El contador de la regla 1 funciona con
`let contador = Mutex::new(0);`, sin `Arc` y sin clones: cada closure de
`s.spawn` captura `&contador`, y el total vuelve a ser 8000. Hay un solo
dueño, `main`, y varios hilos que mutan.

**Un contador simple no necesita candado.** Los tipos de
`std::sync::atomic`, como `AtomicUsize`, hacen en una sola instrucción del
procesador lo que el contador hacía en tres pasos. Con
`AtomicUsize::new(0)` en lugar del mutex, cada suma se escribe
`contador.fetch_add(1, Ordering::Relaxed)`, y el resultado es el mismo
8000 sin guard ni espera. Sirven para un número o una bandera sueltos: un
dato con varias partes que cambian juntas pide un `Mutex`. Elegir el
argumento `Ordering` es tema de un texto de concurrencia avanzada.

**`MutexGuard` no es `Send`.** Un candado debe soltarlo el mismo hilo que
lo tomó, así que el guard no puede moverse a otro hilo. Una closure `move`
que captura un guard y se pasa a `spawn` recibe *E0277:
`MutexGuard<'_, i32>` cannot be sent between threads safely*. La regla
reaparece en [9.4 Send en las tareas]{.ref}: un guard vivo al cruzar un
`.await` vuelve a la tarea entera no `Send`.

**El guard de un temporal puede vivir más que una línea.** La tabla de
«A fondo» de 6.2 aplica igual, con peor resultado. En
`if let Some(x) = m.lock().unwrap().first() { ... }`, el guard vive hasta
cerrar el bloque. Un segundo `m.lock()` dentro de ese bloque hacía panic
con `RefCell`; con `Mutex` es el interbloqueo de un solo hilo. El arreglo
es el mismo: sacar el dato a una variable en un enunciado propio.

**La sección 6, traducida, y lo que nada cambia.** `Box<T>` cruza entre
hilos tal cual si `T` es `Send`. `Rc<T>` es `Arc<T>`, y su `Weak<T>` tiene
un gemelo en `std::sync`. `RefCell<T>` es `Mutex<T>` o `RwLock<T>`. La
lista de 6.2 sobre lo que ninguna herramienta cambia vale completa: un
`Arc` no quita el dueño, lo reparte, y un guard no sobrevive a su mutex.
La sección 8 devuelve una comprobación al compilador: `Send` y `Sync`
deciden qué cruza a otro hilo. Al ejecutar queda la exclusividad, con una
diferencia. El panic de `RefCell` se anunciaba solo, y un interbloqueo es
un programa que no avanza.
