# 10.1 · El ecosistema

El servidor de [9.6 Un servidor mínimo]{.ref} usa `tokio`, `axum` y
`serde_json`. Ninguno es parte de Rust. La biblioteca estándar no trae un
runtime de async, ni JSON, ni un cliente HTTP. Tampoco trae un generador de
números aleatorios. Todo eso vive en crates que escriben y versionan otras
personas.

El lenguaje es pequeño al lado de lo que se construye con él. Saber Rust
incluye saber moverse alrededor del compilador: qué crate se usa en cada
área, qué herramientas acompañan a `rustc`, dónde termina el Rust seguro y
cómo cambia el lenguaje sin romper lo ya escrito. Este capítulo sigue el hilo
de la lección «El ecosistema de Rust» del curso *Aprende Rust*.

## Definiciones y reglas

*Feature*
:   una parte opcional de un crate, que el manifiesto activa por nombre. Un
    crate trae algunas activadas por default.

Toolchain
:   `rustc`, `cargo`, `std` y herramientas de una misma versión.

`unsafe`
:   la palabra clave que marca un bloque o una función donde se permiten
    operaciones que el compilador no puede comprobar.

Edición
:   un conjunto de reglas del lenguaje que cada crate elige en su
    `Cargo.toml`: 2015, 2018, 2021 o 2024.

::: {.reglas titulo="Las tres reglas del ecosistema"}
1. La biblioteca estándar trae lo que casi todo programa necesita y nunca rompe compatibilidad. Lo demás vive en crates, que versionan por su cuenta.
2. `unsafe` no apaga ninguna comprobación. Permite unas pocas operaciones más y deja su corrección a cargo del programador.
3. Un compilador nuevo compila todas las ediciones. Cada crate elige la suya, y solo un cambio de edición puede romper código que compilaba.
:::

## El ecosistema, parte por parte

### [Regla 1:]{.prefijo} la biblioteca estándar es corta a propósito

Lo que entra a `std` queda para siempre: un `rustc` nuevo compila lo que
compilaba el anterior, así que una función estándar no cambia de firma. Un crate sí puede: sube su versión
mayor y quien lo usa decide cuándo migrar ([7.2 Crates y Cargo]{.ref}).

Ese margen se usa. En noviembre de 2026, `cargo search` reporta `rand` en
0.10 y `reqwest` en 0.13. Antes de 1.0, cada versión menor puede romper la
API, y estos crates han cambiado de diseño varias veces. En `std`, cada uno
de esos cambios habría sido imposible.

Async es el caso más visible. El curso presenta `async` y Tokio en esta
lección; el libro les dedicó la sección 9. El lenguaje define `Future` y
`.await`, y el ejecutor lo pone un crate ([9.3 El runtime]{.ref}).

### crates.io y docs.rs

*crates.io* es el registro donde se publican los crates; los criterios para
elegir uno están en [7.2 Crates y Cargo]{.ref}. *docs.rs* es donde se leen.
Cada vez que alguien publica una versión, docs.rs la compila con `rustdoc` y
guarda las páginas, las mismas que `cargo doc` genera en local. Tres partes
responden la mayoría de las dudas:

- **Las *features*.** El menú del crate enlaza a su lista. Lo que depende
  de una lleva una marca: *Available on crate feature `thread_rng` only*.
- **Los `impl` de un tipo.** Tras los métodos vienen *Trait
  Implementations* y los traits automáticos: ahí se ve si un tipo es
  `Clone`, `Display` o `Send` ([8.2 Send y Sync]{.ref}).
- **Los ejemplos.** Son *doctests*: `cargo test` los compila
  ([7.3 Tests]{.ref}), así que no se quedan atrás de la API.

### Las herramientas

`cargo check`, `clippy`, `fmt`, `doc` y `test` están en
[7.2 Crates y Cargo]{.ref} y [7.3 Tests]{.ref}. Las demás resuelven otros
problemas.

`rustup` instala y actualiza toolchains: `rustup update` baja la versión
estable más reciente con sus componentes. `rustup doc` abre una copia local
de la documentación de `std` y de los libros oficiales, que sirve sin
conexión. `cargo tree`, que viene con Cargo, muestra qué crates trajo cada
dependencia; la Aplicación lo usa.

`rust-analyzer` es un servidor de lenguaje: el editor le pregunta tipos,
definiciones y métodos. Analiza el código mientras se escribe, y al guardar
corre `cargo check` para mostrar los errores del propio compilador.

Tres subcomandos más resuelven problemas puntuales. `cargo expand`, de
[7.6 Macros y atributos]{.ref}, muestra el código que generan las macros.
`cargo audit` avisa de dependencias con fallas de seguridad: compara `Cargo.lock` con la base pública de avisos de RustSec. `cargo watch`
repite un comando, como `cargo test`, cada vez que cambia un archivo. Las
tres se instalan aparte con `cargo install`.

### [Regla 2:]{.prefijo} `unsafe` no apaga las comprobaciones

Algunas operaciones son correctas, pero el compilador no tiene cómo
demostrarlo. Leer un puntero crudo ([8.2 Send y Sync]{.ref}) es una: la
dirección puede ser válida o no, y el tipo no lo dice. Fuera de un bloque
`unsafe`, el compilador la rechaza:

```rust,compile_fail
fn main() {
    let x = 42;
    let p: *const i32 = &x;
    let valor = *p;
    println!("{valor}");
}
```

```salida
error[E0133]: dereference of raw pointer is unsafe and
              requires unsafe block
4 |     let valor = *p;
  |                 ^^ dereference of raw pointer
```

Dentro de un bloque `unsafe`, la misma lectura compila. La convención es
explicar arriba, en un comentario `// SAFETY:`, por qué la operación es
correcta:

```rust
fn main() {
    let x = 42;
    let p: *const i32 = &x;

    // SAFETY: p apunta a x, que sigue viva en este scope.
    let valor = unsafe { *p };
    println!("{valor}"); // 42
}
```

El curso enumera tres operaciones que el bloque permite: desreferenciar
punteros crudos, llamar funciones marcadas `unsafe`, entre ellas las de C, y
modificar variables `static mut`. *The Rust Reference* agrega dos más:
implementar un trait `unsafe`, como el `unsafe impl Send` de
[8.2 Send y Sync]{.ref}, y leer campos de una `union`.

Lo demás sigue igual. El borrow checker revisa un bloque `unsafe` como
cualquier otro, y el préstamo de [3.3 Borrowing]{.ref} falla igual dentro
de él. `rustc` avisa además que el bloque sobra: nada en él pide `unsafe`.

```rust,compile_fail
fn main() {
    let mut v = vec![1, 2, 3];
    unsafe {
        let primero = &v[0];
        v.push(4); // E0502: cannot borrow `v` as mutable
        println!("{primero}");
    }
}
```

Importa aunque no se escriba. `Vec`, `Rc`, `Arc` y `Mutex` están hechos con
punteros crudos y bloques `unsafe` por dentro, y ofrecen por fuera una
interfaz segura. El curso recomienda evitarlo en aplicaciones y mantener los
bloques pequeños.

### [Regla 3:]{.prefijo} versiones y ediciones

Rust publica una versión estable cada seis semanas. Cada noche sale una
*nightly*; cada seis semanas, nightly pasa a *beta* y la beta a estable.

La promesa de estabilidad dice que lo que compila en una versión estable
sigue compilando en las siguientes. Reservar una palabra nueva la rompería
para quien ya la usaba como nombre, así que esos cambios esperan a una
edición. La 2018 reservó `async`, `await` y `dyn`; la 2024, `gen`. En 2024,
`let gen = 3;` da *expected identifier, found reserved keyword `gen`*; con
`--edition 2021`, el mismo archivo compila. Por eso las ediciones conviven
([7.2 Crates y Cargo]{.ref}): cada crate se lee con las reglas de su
edición, y entre crates viajan tipos y funciones ya compilados. Para
migrar, `cargo fix --edition` reescribe lo que puede antes de cambiar la
línea `edition` del manifiesto.

### Dónde se usa Rust

El lenguaje no impone recolector de basura ni runtime: la memoria se libera
en el `drop` de cada dueño ([3.2 Ownership]{.ref}) y async no trae motor
propio. Por eso las mismas reglas sirven en un servidor con miles de
conexiones y en un chip sin sistema operativo.

**Línea de comandos.** Un programa Rust compila a un ejecutable que no pide
intérprete ni máquina virtual, y arranca de inmediato. `clap` lee los
argumentos a partir de un struct ([7.5 Entrada y salida]{.ref}); lo demás es
`std`. El curso cita `ripgrep`, `bat` y `fd` como ejemplos.

**Servicios web.** El libro ya construyó uno, de
[9.6 Un servidor mínimo]{.ref} a [9.8 Un servidor MCP]{.ref}. Encaja por
dos razones vistas: miles de esperas sin un hilo por conexión
([9.1 El problema]{.ref}), y un estado compartido que no compila si le falta
el candado ([9.4 Send en las tareas]{.ref}). El curso menciona a Cloudflare,
Discord y AWS, con `axum` y `actix-web` como frameworks.

La tabla reúne todos los terrenos, con el crate o la herramienta de entrada:

| Terreno | Qué se construye | Por dónde empezar |
| :--- | :--- | :--- |
| Línea de comandos | herramientas | `clap` |
| Servicios web | APIs y servidores | `tokio`, `axum` |
| Embebidos | firmware de microcontroladores | `embedded-hal`, Embassy |
| WebAssembly | módulos para navegador y WASI | `wasm-bindgen`, `wasm-pack` |
| Extensiones de Python | módulos nativos | `pyo3`, `maturin` |
| Datos y cómputo | *DataFrames*, cálculo en paralelo | `polars`, `rayon` |
| Escritorio | aplicaciones | `tauri` |
| Videojuegos | juegos y motores | `bevy` |
| Sistemas operativos | kernels y controladores | Rust en Linux |

**WebAssembly.** Es un formato de código para una máquina virtual portátil:
la del navegador o un runtime fuera de él. Rust compila a ese formato sin
cargar un recolector de basura. `wasm-bindgen` genera el puente con
JavaScript: una función marcada con `#[wasm_bindgen]` se llama desde
JavaScript como cualquier otra. `wasm-pack` empaqueta el resultado como
paquete de npm. Fuera del navegador, el destino `wasm32-wasip1` da acceso a
la salida estándar y a archivos por medio de WASI. En la máquina de este
libro, `rustc --target wasm32-wasip1` convirtió un hola mundo en un archivo
`.wasm`, y Node lo ejecutó con su módulo `node:wasi`.

**Extensiones de Python.** Un cálculo lento en Python puro se escribe en
Rust y se importa como un módulo más. `pyo3` expone funciones y tipos de
Rust a Python; `maturin` compila el crate como paquete de Python, y
`maturin develop` lo instala en el entorno virtual activo. Polars está hecho
así: su repositorio lo describe como un motor de consultas escrito en Rust,
y el paquete de Python sale, con `maturin`, del crate `py-polars`, que
envuelve al crate `polars`. El curso agrega `uv` y `ruff`, herramientas de
Python escritas en Rust, y en JavaScript SWC, Turbopack, Rolldown, Biome y
Oxc.

**Datos y cómputo.** `polars` también se usa directo desde Rust, como un
crate más. Para un cálculo propio, `rayon` reparte una cadena de iteradores
entre núcleos ([9.5 async o hilos]{.ref}). Lo que impide una carrera de
datos es lo de [8.2 Send y Sync]{.ref}, revisado al compilar.

**Escritorio y videojuegos.** `tauri` arma aplicaciones de escritorio y
móviles: la interfaz es HTML que dibuja el webview del sistema, y la lógica
corre en Rust. `bevy` es un motor de videojuegos orientado a datos: el juego
son entidades con componentes, y funciones llamadas sistemas los recorren.

**Sistemas operativos.** El kernel de Linux admite código en Rust y tiene
una sección de documentación propia (<https://docs.kernel.org/rust/>). El
curso agrega que Windows y Android ya incluyen código en Rust. Ahí pesa la
regla 2 de este capítulo: el acceso directo al hardware necesita `unsafe`, y
se encierra en interfaces seguras para que el resto del código no lo use.

### Microcontroladores con Embassy

Un microcontrolador es un chip con procesador, memoria y pines, con decenas o
cientos de kilobytes de RAM. No tiene sistema operativo: no hay archivos, ni
hilos, ni un asignador de memoria dispuesto de antemano. `std` supone todo
eso, así que un programa para un chip empieza con `#![no_std]`, un atributo
del crate entero ([7.6 Macros y atributos]{.ref}).

Con `#![no_std]`, el crate usa `core` en lugar de `std`. El lenguaje queda
completo: ownership, préstamos, traits, genéricos, closures, `Option`,
`Result`, slices e iteradores. Falta lo que depende del sistema operativo o
del heap: `Vec`, `String` y `Box` piden un asignador, y archivos, hilos y
`println!` piden un sistema que los dé. El crate `alloc` devuelve las
colecciones si el programa configura un asignador.

`embedded-hal` es un conjunto de traits para el hardware: un pin de salida
con `set_high` y `set_low`, un bus I2C, un bus SPI. Cada fabricante de chips
tiene un HAL que los implementa. Un controlador para un sensor se escribe
genérico sobre esos traits ([4.1 Traits]{.ref}, [4.2 Generics]{.ref}) y
sirve en cualquier chip que los implemente.

Embassy es un runtime de async para microcontroladores, el que
[9.3 El runtime]{.ref} menciona. La idea que lo hace posible es de
[9.2 async, await y Future]{.ref}: un futuro es una máquina de estados de
tamaño conocido al compilar. Según su documentación, cada tarea vive en su
propio `static`, sin heap, y todas comparten un solo stack. Cuando no hay
trabajo, el ejecutor duerme el núcleo, y una interrupción del hardware
despierta a la tarea que esperaba. El mismo `async` y `.await` de la
sección 9 corre en un chip con kilobytes de memoria.

El programa que sigue enciende y apaga un LED cada medio segundo. Está
tomado del ejemplo `blinky` del repositorio de Embassy para el chip
nRF52840, sin las líneas de bitácora. Es ilustrativo: no se compiló ni se
ejecutó, porque pide la placa y el destino del chip.

```rust,ignore
// src/main.rs (ilustrativo, no ejecutado)
#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_nrf::gpio::{Level, Output, OutputDrive};
use embassy_time::Timer;
use panic_probe as _;

#[embassy_executor::main]
async fn main(_spawner: Spawner) {
    let p = embassy_nrf::init(Default::default());
    let mut led = Output::new(
        p.P0_13,
        Level::Low,
        OutputDrive::Standard,
    );

    loop {
        led.set_high();
        Timer::after_millis(500).await;
        led.set_low();
        Timer::after_millis(500).await;
    }
}
```

`#![no_main]` avisa que ningún sistema operativo llama a `main`:
`#[embassy_executor::main]` define el punto de entrada y entrega el cuerpo
al ejecutor como tarea. Un programa `no_std` define qué pasa ante un panic,
y `panic_probe` aporta esa función. Cada `.await` sobre `Timer` cede el
núcleo medio segundo. Embassy mantiene HALs para STM32, los nRF de Nordic y
el RP2040 de Raspberry Pi; los ESP32 tienen el suyo en `esp-rs`.

Los cuatro primeros los recomienda el curso:

  (<https://doc.rust-lang.org/book/>): la explicación de referencia.
- ***Rust by Example*** (<https://doc.rust-lang.org/rust-by-example/>):
  cada concepto como un programa corto que se puede ejecutar.

  pequeños en la terminal, guiados por el compilador.

  libro. `rustc --explain E0382` imprime sin red la página de un error.

## Aplicación

La lección del curso no tiene ejercicio. La aplicación es agregar un crate
de principio a fin, en un paquete nuevo (`cargo new dado`): tirar cinco
dados y una moneda con `rand`.

**Buscar, leer y agregar.** `cargo search rand` da `rand = "0.10.4"`. En
docs.rs, las dos funciones del programa llevan la marca de `thread_rng`.
`cargo add` lista las *features*: `+` las activadas, `-` las demás:

```salida
$ cargo add rand
      Adding rand v0.10.4 to dependencies
             Features:
             + alloc
             + std
             + std_rng
             + sys_rng
             + thread_rng
             - chacha
             ...
```

**Ver qué más llegó.** El manifiesto declara un crate, pero `cargo tree`
muestra más:

```salida
$ cargo tree
dado v0.1.0 (/proyectos/dado)
└── rand v0.10.4
    ├── chacha20 v0.10.2
    │   ├── cfg-if v1.0.5
    │   └── rand_core v0.10.1
    ├── getrandom v0.4.3
    │   ├── cfg-if v1.0.5
    │   ├── libc v0.2.191
    │   └── rand_core v0.10.1
    └── rand_core v0.10.1
```

`getrandom` pide la semilla al sistema operativo y `chacha20` es el
algoritmo del generador.

**Usar.** Cinco líneas útiles:

```rust,ignore
// src/main.rs
fn main() {
    let tiradas: Vec<u8> = (0..5)
        .map(|_| rand::random_range(1..=6))
        .collect();
    println!("{tiradas:?}");
    println!("¿águila? {}", rand::random_bool(0.5));
}
```

Una corrida de `cargo run -q` imprimió `[3, 6, 4, 2, 6]` y
`¿águila? true`.

**Probar sin las *features* default.** Con `default-features = false`, el
programa da E0425, *cannot find function `random_range` in crate `rand`*, y
una nota: *the item is gated behind the `thread_rng` feature*: la marca de
docs.rs, dicha por el compilador.

## A fondo

**Miri revisa el `unsafe` en ejecución.** Es un intérprete de MIR, la
representación intermedia del compilador. `cargo miri test` corre los tests
con él y detecta comportamiento indefinido. Es un componente de nightly.

## Cierre

El libro recorrió el lenguaje en nueve secciones. Las dos primeras dan la
sintaxis y los tipos. La 3 da la idea central: cada valor tiene un dueño y
cada préstamo un alcance que el compilador revisa. De la 4 a la 6 vienen
traits, generics, closures, las colecciones de `std` y los punteros que
admiten más de un dueño. Las tres últimas llevan lo mismo a
proyectos, a hilos y a tareas que esperan sin ocupar uno.

Lo que sigue ya no es lenguaje. Una API con base de datos, un análisis con
Polars o un programa para un chip usan las mismas reglas de ownership,
`Result`, traits y `Send`, sobre los crates de este capítulo. Lo nuevo es
la documentación de cada crate y la práctica de leerla.
