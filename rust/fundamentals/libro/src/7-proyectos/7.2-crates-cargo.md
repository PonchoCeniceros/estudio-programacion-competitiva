# 7.2 · Crates y Cargo

Hasta aquí cada programa del libro cabe en un archivo, y `rustc` lo convierte en
un ejecutable. Un proyecto real no es así. Tiene varios archivos, organizados en
módulos ([7.1 Módulos]{.ref}). Usa código que escribieron otros: colores para la
terminal, lectura de JSON, un servidor web. Y se compila de dos maneras: rápido
mientras se escribe, optimizado para entregarlo.

Llamar a `rustc` a mano obliga a decidir qué archivo compilar, dónde está cada
librería, qué versión usar y con qué opciones. Cargo es la herramienta que lleva
esas cuentas. Para hacerlo, piensa en *crates*: la unidad con la que trabaja el
compilador.

## Definiciones y reglas

Crate
:   lo que el compilador procesa de una vez, a partir de un archivo raíz. Es
    binario si produce un ejecutable y librería si otros crates lo usan.

Raíz del crate
:   *(crate root)*: el archivo donde el compilador empieza a leer. `src/main.rs`
    para el binario y `src/lib.rs` para la librería.

Paquete
:   *(package)*: una carpeta con un `Cargo.toml`. Reúne uno o más crates.

Dependencia
:   un crate de otro paquete que el código usa. Casi siempre viene de
    *crates.io*, el registro público de crates.

::: {.reglas titulo="Las tres reglas del paquete"}
1. Un crate se compila de una vez, a partir de su raíz.
2. Un paquete tiene a lo más una librería y cualquier número de binarios.
3. Un crate solo ve los crates que su `Cargo.toml` declara, y `Cargo.lock` fija sus versiones exactas.
:::

## De un vistazo

| Pieza | Qué es | Cómo se reconoce |
| :--- | :--- | :--- |
| Paquete | lo que Cargo administra | un `Cargo.toml` |
| Crate | lo que `rustc` compila de una vez | una raíz: `main.rs` o `lib.rs` |
| Módulo | una división dentro de un crate | `mod` ([7.1 Módulos]{.ref}) |

Criterio: el módulo ordena el código de un crate; el crate separa lo que se
compila aparte; el paquete agrupa lo que se versiona y se publica junto.

## Las reglas, una por una

Antes de las reglas, qué crea Cargo y qué dice el manifiesto.

### `cargo new`: un paquete desde cero

`cargo new saludo` crea una carpeta con un paquete binario listo para
ejecutarse:

```salida
saludo/
├── .gitignore
├── Cargo.toml
└── src
    └── main.rs
```

`src/main.rs` trae el hola mundo. `.gitignore` excluye la carpeta `target`, donde
Cargo deja lo que compila. Si la carpeta no está dentro de un repositorio, Cargo
además inicia uno con `git init`. El manifiesto es corto:

```toml
[package]
name = "saludo"
version = "0.1.0"
edition = "2024"

[dependencies]
```

`[package]` describe el paquete y `[dependencies]`, todavía vacía, listará
los crates de otros paquetes. Los tres campos:

- **`name`** es el nombre del paquete, y también el del crate y el del
  ejecutable. Un guion en el nombre pasa a guion bajo en el código: el paquete
  `mi-api` se usa como `mi_api`.
- **`version`** sigue el esquema *semver*, mayor.menor.parche, que se explica
  más abajo.
- **`edition`** dice qué reglas del lenguaje aplican a este crate. La edición
  2024 reservó `gen` como palabra clave, por ejemplo ([1.1 Tokens]{.ref}).

`cargo run` compila y ejecuta. La primera línea dice qué compila; la última, qué
corre:

```salida
$ cargo run
   Compiling saludo v0.1.0 (/proyectos/saludo)
    Finished `dev` profile [unoptimized + debuginfo]
             target(s) in 0.18s
     Running `target/debug/saludo`
Hello, world!
```

### [Regla 1:]{.prefijo} el crate se compila a partir de su raíz

`rustc` no recibe una lista de archivos. Recibe una raíz y desde ahí sigue cada
`mod` hasta tener el crate completo ([7.1 Módulos]{.ref}). Todo lo que cuelga de
esa raíz se compila de una vez y produce una sola cosa: un ejecutable o una
librería.

`cargo new --lib temperatura` crea un paquete de librería, con `src/lib.rs` en
lugar de `src/main.rs`. Con una función pública en la librería y un `main.rs`
junto a ella, el paquete tiene dos crates:

```rust,ignore
// src/lib.rs
pub fn a_fahrenheit(c: f64) -> f64 {
    c * 9.0 / 5.0 + 32.0
}
```

```rust,ignore
// src/main.rs
use temperatura::a_fahrenheit;

fn main() {
    let c = 37.0;
    println!("{c} °C = {} °F", a_fahrenheit(c));
}
```

`cargo run` imprime `37 °C = 98.6 °F`. El binario no declara `mod lib;`. Usa la librería por el nombre del paquete,
como usaría cualquier dependencia. `cargo build -v` muestra las llamadas que
Cargo hace a `rustc`, una por crate. Recortada, la salida es esta:

```salida
$ cargo build -v
   Compiling temperatura v0.1.0 (/proyectos/temperatura)
     Running `rustc --crate-name temperatura
              --edition=2024 src/lib.rs --crate-type lib ...`
     Running `rustc --crate-name temperatura
              --edition=2024 src/main.rs --crate-type bin ...
              --extern temperatura=.../libtemperatura.rlib`
```

Primero compila la librería, que queda en un archivo `.rlib`. Luego compila el
binario y le pasa ese archivo con `--extern`. Así llega el nombre `temperatura`
al código del binario.

### [Regla 2:]{.prefijo} una librería y cualquier número de binarios

Un paquete admite una sola librería, la de `src/lib.rs`. Binarios admite
cuantos haga falta: `src/main.rs`, si existe, y cada archivo de `src/bin/`. Cada
uno es un crate aparte, con su propio `main`, y cada uno puede usar la
librería:

```rust,ignore
// src/bin/tabla.rs
use temperatura::a_fahrenheit;

fn main() {
    for c in [0.0, 25.0, 100.0] {
        println!("{c} °C = {} °F", a_fahrenheit(c));
    }
}
```

:::

Con dos binarios, `cargo run` ya no sabe cuál ejecutar. `--bin` elige uno por
su nombre, que es el del archivo sin `.rs`:

```salida
$ cargo run
error: `cargo run` could not determine which binary to run.
Use the `--bin` option to specify a binary, or the
`default-run` manifest key.
available binaries: tabla, temperatura
$ cargo run --bin tabla
     Running `target/debug/tabla`
0 °C = 32 °F
25 °C = 77 °F
100 °C = 212 °F
```

Esta forma conviene cuando varias herramientas comparten la misma lógica: la
lógica va en la librería y cada herramienta es un binario delgado.

### [Regla 3:]{.prefijo} solo se ve lo que se declara

El paquete `saludo` quiere imprimir en colores. El crate `colored` agrega
métodos como `.green()` a los textos, por medio de un trait, `Colorize`
([4.1 Traits]{.ref}). Sin declararlo en el manifiesto, el `use` falla:

```rust,ignore,compile_fail
// src/main.rs
use colored::Colorize;

fn main() {
    println!("{}", "listo".green().bold());
    println!("{}", "falló".red());
}
```

```salida
error[E0432]: unresolved import `colored`
1 | use colored::Colorize;
  |     ^^^^^^^ use of unresolved module or unlinked crate
  |             `colored`
  = help: if you wanted to use a crate named `colored`,
          use `cargo add colored` to add it to your
          `Cargo.toml`
```

Le siguen dos E0599, *no method named `green` found*: sin el trait, los
métodos no existen. `cargo add` escribe la línea en el manifiesto, consulta el
registro y resuelve la versión:

```salida
$ cargo add colored@3
    Updating crates.io index
      Adding colored v3 to dependencies
     Locking 3 packages to latest Rust 1.94.0 compatible
             versions
      Adding colored v3.1.1
      Adding windows-link v0.2.1
      Adding windows-sys v0.61.2
```

`[dependencies]` queda con `colored = "3"`. Con eso el mismo `main.rs`
compila, y en la terminal «listo» sale en verde y negritas. La primera
compilación descarga `colored` y lo compila como un crate más. Las siguientes
lo reutilizan desde `target`.

Los otros dos paquetes llegan con `colored`, para la consola de Windows.
Cargo resuelve el árbol completo, aunque en otro sistema esa rama no
se compile.

### Versiones: el rango y el lockfile

Una versión semver tiene tres números. El parche corrige errores; el menor
agrega funciones sin romper nada; el mayor rompe compatibilidad. Por eso
`Cargo.toml` no declara una versión exacta sino un rango de versiones
compatibles:

| En `Cargo.toml` | Acepta | Cuándo |
| :--- | :--- | :--- |
| `"3"` | de `3.0.0` a antes de `4.0.0` | lo usual |
| `"3.1"` | de `3.1.0` a antes de `4.0.0` | se usa algo agregado en 3.1 |
| `"0.8"` | de `0.8.0` a antes de `0.9.0` | crates antes de 1.0 |
| `"=3.1.1"` | solo `3.1.1` | casi nunca: bloquea las correcciones |

Antes de 1.0, semver deja que cada versión menor rompa compatibilidad. Por eso
`"0.8"` no acepta `0.9`. `cargo add colored`, sin `@3`, escribe
`colored = "3.1.1"`: el rango que empieza en la versión más reciente.

El rango dice qué se acepta, pero una compilación usa una versión concreta. La
primera vez, Cargo elige la más reciente dentro del rango y la anota en
`Cargo.lock`: una entrada `[[package]]` por crate, con `name = "colored"`,
`version = "3.1.1"`, su origen y una suma de verificación.

Las compilaciones siguientes leen el lockfile y no vuelven a elegir. Si sale
`colored` 3.2, el proyecto sigue con 3.1.1 hasta que alguien corra
`cargo update`. Así dos máquinas, o la misma máquina un año después, compilan
exactamente lo mismo. Por eso el `.gitignore` de `cargo new` excluye `target`
pero no `Cargo.lock`: el lockfile se sube al repositorio. Esto vale también
para una librería, aunque su lockfile no viaja con ella: quien la usa como
dependencia resuelve las versiones con su propio `Cargo.lock`.

### Los comandos

Seis comandos cubren el ciclo de escribir y compilar. El primer criterio es la
velocidad: `check` mientras se escribe, `build` o `run` cuando hace falta el
ejecutable.

| Comando | Qué hace |
| :--- | :--- |
| `cargo new nombre` | crea un paquete binario; `--lib`, de librería |
| `cargo add crate` | agrega una dependencia al manifiesto |
| `cargo check` | revisa tipos y préstamos, sin generar ejecutable |
| `cargo build` | compila en `target/debug` |
| `cargo build --release` | compila optimizado en `target/release` |
| `cargo run` | compila y ejecuta; `--bin nombre` si hay varios |

`cargo check` hace todo el análisis: tipos, ownership, préstamos. Se salta la
generación de código máquina, que es la parte más lenta. Sus líneas dicen
`Checking` en lugar de `Compiling`.

`build` y `build --release` compilan con dos *perfiles* distintos. El perfil
`dev` no optimiza y guarda información de depuración: compila rápido y el
ejecutable es más lento. Además revisa los desbordamientos de enteros y hace
panic en ellos ([1.2 Tipos escalares]{.ref}). El perfil `release` optimiza:
compila más lento, el ejecutable corre más rápido, y la revisión de
desbordamiento se apaga. La última línea de cada compilación dice cuál se
usó: ``Finished `dev` profile [unoptimized + debuginfo]`` o
``Finished `release` profile [optimized]``.

Los otros cuatro comandos no compilan para ejecutar: revisan, prueban,
formatean o documentan.

| Comando | Qué hace |
| :--- | :--- |
| `cargo test` | compila y corre los tests ([7.3 Tests]{.ref}) |
| `cargo clippy` | señala código que funciona pero tiene una forma mejor |
| `cargo fmt` | reescribe el código con el formato estándar |
| `cargo doc --open` | genera la documentación del paquete y sus dependencias |

`cargo fmt` aplica el estilo de `rustfmt`, el mismo de todos los ejemplos de
este libro. `cargo doc` genera páginas HTML en `target/doc`, con los
comentarios `///` del código y los de cada dependencia.

Clippy va más lejos que los avisos de `rustc`: conoce cientos de patrones que
compilan bien pero tienen una forma más clara. Este `main.rs` es correcto:
declara `let tareas: Vec<&str> = Vec::new();` y pregunta si está vacío
comparando su largo con cero. `rustc` no dice nada; Clippy sí:

```salida
$ cargo clippy
warning: length comparison to zero
 --> src/main.rs:3:8
  |
3 |     if tareas.len() == 0 {
  |        ^^^^^^^^^^^^^^^^^ help: using `is_empty` is clearer
  |                          and more explicit:
  |                          `tareas.is_empty()`
  |
  = note: `#[warn(clippy::len_zero)]` on by default
```

Cada aviso trae su nombre, aquí `len_zero`, y casi siempre la corrección.

### Elegir un crate

*crates.io* publica más crates de los que se pueden revisar, y varios
resuelven lo mismo. Antes de agregar uno conviene mirar cinco cosas:

- **Uso:** las descargas recientes y cuántos crates dependen de él.
- **Mantenimiento:** la fecha de la última versión.
- **Documentación:** su página en *docs.rs*, y si trae ejemplos.
- **Versión:** desde 1.0, el autor promete no romper la API sin subir el mayor.
- **Dependencias y licencia:** cada dependencia suya también se compila.

Algunos nombres aparecen en casi cualquier proyecto. El libro toca varios más
adelante:

| Crate | Para qué | En el libro |
| :--- | :--- | :--- |
| `serde` | pasar structs a JSON y de regreso | [9.6 Un servidor mínimo]{.ref} |
| `anyhow`, `thiserror` | errores en aplicaciones y en librerías | [7.4 Manejo de errores idiomático]{.ref} |
| `clap` | leer los argumentos del programa | — |
| `rayon` | repartir un cálculo en núcleos | [9.5 async o hilos]{.ref} |
| `tokio` | el runtime de async | [9.3 El runtime]{.ref} |
| `reqwest` | cliente HTTP | — |
| `axum` | servidor web | [9.6 Un servidor mínimo]{.ref} |

### Workspaces

Cuando un proyecto crece a varios paquetes, cada uno con su `Cargo.toml`,
compilarlos por separado duplica trabajo: cada paquete tendría su `target` y
compilaría sus dependencias por su cuenta. Un *workspace* los junta. El
`Cargo.toml` de la raíz no describe un paquete. Tiene una sección
`[workspace]` con dos líneas: `members = ["nucleo", "cli"]`, la lista de
miembros, y `resolver = "3"`. Queda así:

```salida
taller/
├── Cargo.toml   el del workspace
├── Cargo.lock   uno para todos los miembros
├── target/      una sola carpeta de compilación
├── nucleo/      Cargo.toml y src/lib.rs
└── cli/         Cargo.toml y src/main.rs
```

`cli` depende de `nucleo` por ruta, no por versión del registro: su
manifiesto dice `nucleo = { path = "../nucleo" }`. Desde la raíz,
`cargo build` compila todos los miembros, y `cargo run -p cli` elige uno.
`resolver = "3"` elige cómo Cargo resuelve versiones, el default de la edición
2024. La raíz no tiene edición, así que sin la línea Cargo avisa y usa el
algoritmo más viejo.

## Aplicación

El paquete `katas`, con los problemas de LeetCode resueltos en Rust de este
cuaderno, es un caso real de la regla 2. Su manifiesto entero:

```toml
[package]
name = "katas"
version = "0.1.0"
edition = "2024"

[dependencies]
regex = "1"
colored = "3"
```

No tiene `src/main.rs`. Tiene `src/lib.rs`, la raíz de la librería, con un
módulo `macros.rs`, y 38 archivos en `src/bin/`, uno por problema:
`1_two_sum.rs`, `20_valid_parentheses.rs`, etc. Son 39 crates en un paquete.

La librería exporta una sola cosa, una macro `s!` que abrevia `String::from`
([7.6 Macros y atributos]{.ref}). Cada binario la importa con el nombre del
paquete, igual que importa `colored`, que viene de crates.io. Así empieza
`src/bin/20_valid_parentheses.rs`: `use colored::*;` y, en la línea
siguiente, `use katas::s;`.

Para el binario, las dos líneas son iguales: dos crates externos que Cargo le
pasa con `--extern`, uno de la misma carpeta y otro del registro. Como no hay
`main.rs`, `cargo run` siempre necesita `--bin`:
`cargo run --bin 20_valid_parentheses` compila la librería y ese binario, y lo
ejecuta. Y aunque tenga muchos programas, `katas` no es un workspace: tiene un
solo `Cargo.toml`.

## A fondo

**El perfil se configura en el manifiesto.** Con `overflow-checks = true` en
una sección `[profile.release]`, el perfil release también hace panic al
desbordar: `x + 1` con `x = 255` en un `u8` da *attempt to add with overflow*
([1.2 Tipos escalares]{.ref}).

**«Propio» en la regla del huérfano quiere decir «del mismo crate».** La
coherencia de [4.1 Traits]{.ref} se cuenta por crate, no por paquete. Un
binario de `src/bin/` no puede implementar `Display` para un tipo de la
librería de su mismo paquete. Da E0117, *only traits defined in the current
crate can be implemented for types defined outside of the crate*: el tipo es de
otro crate, y el trait es de `std`, la biblioteca estándar, que también es un
crate. Todo programa la recibe sin declararla.

**Las ediciones conviven.** Una edición nueva sale cada tres años: 2015, 2018,
2021, 2024. Un `rustc` nuevo sale cada seis semanas y compila todas. La edición
se fija por crate: `colored` 3.1.1 declara `edition = "2021"` y `saludo` lo usa
desde 2024. Cambiar de edición puede romper código, y por eso nunca cambia sola.

**Una dependencia puede pedir solo una parte del crate.** Con
`features = ["derive"]`, `serde` agrega la pieza que deriva sus traits. Sin la
lista, solo se compila lo básico.
