# 7.4 · Manejo de errores idiomático

En [5.2 Result]{.ref} cada función fallaba de una sola manera: un texto que no
convertía daba un `ParseIntError`, y ese era el `E` de la firma. Una función real
hace varias cosas, y cada una falla con su propio tipo. Leer un archivo falla con
`io::Error`; convertir su contenido en número, con `ParseIntError`.

La firma admite un solo tipo de error, y `?` solo propaga lo que se puede
convertir a ese tipo. Este capítulo presenta tres maneras de darle a una función
un tipo de error único, de la más floja a la más precisa, y el criterio para
elegir entre ellas.

## Definiciones y reglas

`Error`
:   el trait de la biblioteca estándar, `std::error::Error`, que implementan los
    tipos de error. Exige `Debug` y `Display`; sus métodos traen implementación
    default.

`Box<dyn Error>`
:   un *trait object* de `Error` ([6.3 Despacho dinámico]{.ref}): un puntero a
    un error de cualquier tipo.

Enum de error
:   un enum propio cuyas variantes son las causas por las que falla una
    operación.

Causa
:   *(source)*: el error de más abajo que provocó un error de más arriba.

Contexto
:   un mensaje que se agrega a un error para decir qué se intentaba cuando
    ocurrió.

::: {.reglas titulo="Las tres reglas de los errores propios"}
1. `Box<dyn Error>` acepta cualquier error que implemente `Error`. Quien lo
   recibe solo puede mostrarlo.
2. Un enum de error tiene una variante por causa. Quien lo recibe distingue la
   causa con `match`.
3. `?` convierte el error con `From`. Un `impl From` por cada error de origen
   deja que `?` convierta solo.
:::

## De un vistazo

| | `Box<dyn Error>` | enum a mano | `thiserror` | `anyhow` |
| :--- | :--- | :--- | :--- | :--- |
| Acepta | cualquier error | sus variantes | sus variantes | cualquier error |
| Se distingue la causa | no | sí | sí | no |
| Se escribe | nada | enum, `Display`, `Error`, `From` | enum y atributos | nada |
| Dependencia | ninguna | ninguna | `thiserror` | `anyhow` |
| Pensado para | prototipos | librerías | librerías | binarios |

Criterio: una librería define su tipo de error, porque quien la usa decide qué
hacer con cada causa. Un binario casi siempre reporta el error y termina, y le
basta un tipo único con contexto.

## Las reglas, una por una

### Dos operaciones, dos tipos de error

Un pedido llega como dos textos: la cantidad, un entero, y el precio, un número
con decimales. La función que calcula el total convierte los dos. El primer
`parse` falla con `ParseIntError`, el segundo con `ParseFloatError`, y la firma
solo puede nombrar uno:

```rust,compile_fail
use std::num::ParseIntError;

fn total(c: &str, p: &str) -> Result<f64, ParseIntError> {
    let n = c.parse::<u32>()?;
    let p = p.parse::<f64>()?;
    Ok(n as f64 * p)
}

fn main() {}
```

```salida
error[E0277]: `?` couldn't convert the error to
              `ParseIntError`
3 | fn total(c: &str, p: &str) -> Result<f64, ParseIntError> {
  |                               --------------------------
  |                               expected `ParseIntError`
  |                               because of this
4 |     let n = c.parse::<u32>()?;
5 |     let p = p.parse::<f64>()?;
  |               --------------^ the trait
  |               |               `From<ParseFloatError>`
  |               |               is not implemented for
  |               |               `ParseIntError`
  |               this can't be annotated with `?` because
  |               it has type `Result<_, ParseFloatError>`
```

El primer `?` pasa: el error ya es del tipo declarado. El segundo no, porque no
existe una conversión de `ParseFloatError` a `ParseIntError`. Cambiar la firma a
`ParseFloatError` solo mueve el problema a la otra línea. Hace falta un tipo que
pueda recibir los dos.

### [Regla 1:]{.prefijo} `Box<dyn Error>` acepta cualquier error

Los dos errores implementan el trait `Error`. Un `Box<dyn Error>` guarda
cualquier valor que lo implemente, así que sirve de tipo común sin escribir nada
más:

```rust
use std::error::Error;

fn total(c: &str, p: &str) -> Result<f64, Box<dyn Error>> {
    let n = c.parse::<u32>()?;
    let p = p.parse::<f64>()?;
    Ok(n as f64 * p)
}

fn main() {
    let pedidos = [("3", "12.5"), ("x", "1"), ("3", "doce")];
    for (c, p) in pedidos {
        match total(c, p) {
            Ok(t) => println!("total: {t}"),
            Err(e) => println!("error: {e}"),
        }
    }
}
```

```salida
total: 37.5
error: invalid digit found in string
error: invalid float literal
```

Es despacho dinámico: el `Box` lleva el error y la tabla de métodos de su tipo
concreto ([6.3 Despacho dinámico]{.ref}). Con eso, `{e}` llama al `Display` que
corresponde. Eso es casi todo lo que quien llama puede hacer. El tipo del error
es `Box<dyn Error>` en los tres casos, y no hay variantes que poner en un `match`.
Para saber si falló la cantidad o el precio, solo queda leer el texto.

Por eso `Box<dyn Error>` encaja donde el error solo se muestra: un prototipo, un
script, un `main`. `main` puede devolverlo, y cada `?` dentro de él propaga
cualquier error:

```rust
use std::error::Error;

fn total(c: &str, p: &str) -> Result<f64, Box<dyn Error>> {
    Ok(c.parse::<u32>()? as f64 * p.parse::<f64>()?)
}

fn main() -> Result<(), Box<dyn Error>> {
    println!("{}", total("3", "12.5")?);
    println!("{}", total("3", "doce")?);
    Ok(())
}
```

```salida
37.5
Error: ParseFloatError { kind: Invalid }
```

El programa termina con código de salida 1 ([5.2 Result]{.ref}). El error se
imprime con `Debug`, no con `Display`: sirve a quien depura, no a un usuario.

### [Regla 2:]{.prefijo} un enum, una variante por causa

La alternativa precisa es nombrar las causas. Cada variante lleva el error
original, si lo hay. La regla de negocio «la cantidad no puede ser cero» es una
causa más, sin error que la acompañe:

```rust
use std::error::Error;
use std::fmt;
use std::num::{ParseFloatError, ParseIntError};

#[derive(Debug)]
enum ErrorPedido {
    Cantidad(ParseIntError),
    Precio(ParseFloatError),
    CantidadCero,
}

impl fmt::Display for ErrorPedido {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ErrorPedido::Cantidad(e) => {
                write!(f, "cantidad inválida: {e}")
            }
            ErrorPedido::Precio(e) => {
                write!(f, "precio inválido: {e}")
            }
            ErrorPedido::CantidadCero => {
                write!(f, "la cantidad es cero")
            }
        }
    }
}

impl Error for ErrorPedido {}

fn total(c: &str, p: &str) -> Result<f64, ErrorPedido> {
    let n = c.parse::<u32>().map_err(ErrorPedido::Cantidad)?;
    let p = p.parse::<f64>().map_err(ErrorPedido::Precio)?;
    if n == 0 {
        return Err(ErrorPedido::CantidadCero);
    }
    Ok(n as f64 * p)
}

fn main() {
    let pedidos = [("3", "12.5"), ("0", "1"), ("3", "doce")];
    for (c, p) in pedidos {
        match total(c, p) {
            Ok(t) => println!("total: {t}"),
            Err(ErrorPedido::CantidadCero) => {
                println!("pedido vacío")
            }
            Err(e) => println!("error: {e}"),
        }
    }
}
```

```salida
total: 37.5
pedido vacío
error: precio inválido: invalid float literal
```

Tres piezas convierten el enum en un error: `Debug` derivado, `Display` escrito
a mano con un mensaje por variante ([4.4 Traits de la stdlib]{.ref}) e
`impl Error` vacío, porque los métodos del trait tienen implementación default.
`map_err` recibe una variante en lugar de una closure: una variante con datos se
comporta como una función que recibe el dato y devuelve el enum.

La diferencia con `Box<dyn Error>` está en el `main`. La segunda rama encaja con
una causa concreta y responde distinto, y el compilador revisa que el `match`
cubra todas las variantes ([2.3 Enums]{.ref}).

### [Regla 3:]{.prefijo} `From` es lo que hace funcionar al `?`

Los `map_err` de `total` repiten una conversión que siempre es la misma. `?`
llama a `From::from` antes de devolver el error ([5.2 Result]{.ref}).
Desazucarado, un `?` es este `match`:

```rust
use std::error::Error;

fn cantidad(c: &str) -> Result<u32, Box<dyn Error>> {
    // let n = c.parse::<u32>()?;  equivale a:
    let n = match c.parse::<u32>() {
        Ok(v) => v,
        Err(e) => return Err(From::from(e)),
    };
    Ok(n)
}

fn main() {
    println!("{:?}", cantidad("x"));
}
```

`From::from(e)` no nombra el tipo de destino. Lo fija el `return`: el `Err`
tiene que ser del tipo de error de la función. Aquí la conversión va de
`ParseIntError` a `Box<dyn Error>`, y existe porque la biblioteca estándar
declara un `impl` genérico que, simplificado, dice
`impl<E: Error> From<E> for Box<dyn Error>`. Todo tipo que implementa `Error`
se convierte en un `Box<dyn Error>`, y por eso la regla 1 funciona. Hay además
conversiones desde `&str` y `String`: `Err("la cantidad es cero".into())` es un
error válido en esa firma.

Para un enum propio, la conversión la escribe su autor. Era lo que faltaba en el
primer ejemplo del capítulo: no había `From<ParseFloatError>` para
`ParseIntError`. Con un `impl From` por cada error de origen, `?` convierte solo
y los `map_err` sobran:

```rust
use std::num::{ParseFloatError, ParseIntError};

#[derive(Debug)]
enum ErrorPedido {
    Cantidad(ParseIntError),
    Precio(ParseFloatError),
    CantidadCero,
}

impl From<ParseIntError> for ErrorPedido {
    fn from(e: ParseIntError) -> Self {
        ErrorPedido::Cantidad(e)
    }
}

impl From<ParseFloatError> for ErrorPedido {
    fn from(e: ParseFloatError) -> Self {
        ErrorPedido::Precio(e)
    }
}

fn total(c: &str, p: &str) -> Result<f64, ErrorPedido> {
    let n = c.parse::<u32>()?;
    let p = p.parse::<f64>()?;
    if n == 0 {
        return Err(ErrorPedido::CantidadCero);
    }
    Ok(n as f64 * p)
}

fn main() {
    println!("{:?}", total("3", "doce"));
}
```

```salida
Err(Precio(ParseFloatError { kind: Invalid }))
```

El `?` de la cantidad elige `From<ParseIntError>`; el del precio,
`From<ParseFloatError>`. Lo decide el compilador con los tipos, sin nada escrito
en la línea. El error que la función construye ya es un `ErrorPedido` y no pasa
por conversión:

### Las dos librerías

El enum a mano ocupa cerca de cuarenta líneas, y casi todas son ceremonia: un mensaje por
variante y un `From` por error de origen. El crate `thiserror` las genera a
partir de atributos. Se agrega con `thiserror = "2"` en la sección
`[dependencies]` del `Cargo.toml` ([7.2 Crates y Cargo]{.ref}). El mismo
`ErrorPedido`, con `Display`, `Error` y los dos `From`:

```rust,ignore
// src/main.rs
use std::num::{ParseFloatError, ParseIntError};
use thiserror::Error;

#[derive(Debug, Error)]
enum ErrorPedido {
    #[error("cantidad inválida: {0}")]
    Cantidad(#[from] ParseIntError),
    #[error("precio inválido: {0}")]
    Precio(#[from] ParseFloatError),
    #[error("la cantidad es cero")]
    CantidadCero,
}
```

`#[derive(Error)]` genera el `impl Error`. Cada `#[error("...")]` es la rama de
`Display` de su variante, y `{0}` es el primer campo. El atributo `#[from]`
genera un `impl From` como los de la regla 3. Con este enum, la función `total` de la regla 3
y el `main` de la regla 2 compilan sin cambios y dan la misma salida. El resultado es
un tipo normal: quien lo usa no necesita saber que existe `thiserror`. Los
atributos son entrada para la macro `derive` del crate ([7.6 Macros y
atributos]{.ref}).

El crate `anyhow` resuelve el otro caso. Su tipo `anyhow::Error` acepta cualquier
error, como `Box<dyn Error>`, y le agrega contexto. `anyhow::Result<T>` es un
alias de `Result<T, anyhow::Error>`. Se agrega con `anyhow = "1"` en
`[dependencies]`. El programa lee además un archivo con `fs::read_to_string`, que
devuelve el contenido como `String` o falla con `io::Error`
([7.5 Entrada y salida]{.ref}). El archivo no existe:

```rust,ignore
// src/main.rs
use anyhow::{Context, Result, bail};
use std::fs;

fn total(c: &str, p: &str) -> Result<f64> {
    let n = c.parse::<u32>().context("cantidad inválida")?;
    let p = p.parse::<f64>().context("precio inválido")?;
    if n == 0 {
        bail!("la cantidad es cero");
    }
    Ok(n as f64 * p)
}

fn main() -> Result<()> {
    println!("{}", total("3", "12.5")?);
    let texto = fs::read_to_string("pedido.txt")
        .context("no se pudo leer pedido.txt")?;
    println!("{texto}");
    Ok(())
}
```

```salida
$ cargo run
37.5
Error: no se pudo leer pedido.txt

Caused by:
    No such file or directory (os error 2)
```

`context` envuelve el error con un mensaje y conserva el original como causa.
`with_context` hace lo mismo con una closure, que solo se evalúa si hay error.
`bail!` devuelve un error hecho de un texto. Al salir de `main`, `anyhow`
imprime el contexto y debajo la cadena de causas, en lugar del `Debug` crudo
de la regla 1. Con `total("3", "doce")` la salida sería `precio inválido` y,
como causa, `invalid float literal`.

Lo que `anyhow` no da es la distinción: un pedido vacío y un precio mal escrito
son el mismo tipo. En un binario basta, porque el error se muestra y el programa
termina. En una librería, quien la usa no podría responder a cada causa.

## Aplicación

El ejercicio `32_error_password` del curso *Aprende Rust*: un enum de error para
validar contraseñas, con `Display` y una función `validar`. Una contraseña es
corta si tiene menos de ocho caracteres, y le faltan números si no tiene ningún
dígito.

La versión original medía con `len()`, que cuenta bytes y no caracteres
([3.4 Strings]{.ref}). `"ñandú12"` tiene siete caracteres pero nueve bytes, y
pasaba como válida. Aquí se mide con `chars().count()`. El bucle con bandera
que buscaba un dígito es un `any` ([5.7 Iteradores a fondo]{.ref}). El enum gana
`Debug` e `impl Error`, y en los patrones de su `Display`, `Self` es
`ErrorPassword` ([3.5 impl y métodos]{.ref}).

El `main` combina las dos maneras. `validar` devuelve un error preciso, que
`println!` muestra con su `Display`; `unwrap_err` es el reverso de `unwrap`:
saca el error y hace panic con un `Ok`. Después, el mismo `main` propaga con
`?` un `ErrorPassword` y un `ParseIntError`, porque los dos caben en su
`Box<dyn Error>`. `"ferris2024"` pasa la validación, `"treinta"` no convierte,
y el programa termina con código 1:

```rust
use std::error::Error;
use std::fmt;

#[derive(Debug)]
enum ErrorPassword {
    Corta,
    SinNumeros,
}

impl fmt::Display for ErrorPassword {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{}", match self {
            Self::Corta => "demasiado corta",
            Self::SinNumeros => "le falta un número",
        })
    }
}

impl Error for ErrorPassword {}

fn validar(password: &str) -> Result<(), ErrorPassword> {
    if password.chars().count() < 8 {
        Err(ErrorPassword::Corta)
    } else if !password.chars().any(|c| c.is_ascii_digit()) {
        Err(ErrorPassword::SinNumeros)
    } else {
        Ok(())
    }
}

fn main() -> Result<(), Box<dyn Error>> {
    for p in ["abc", "rustaceo", "ñandú12"] {
        println!("{p}: {}", validar(p).unwrap_err());
    }
    validar("ferris2024")?;
    "treinta".parse::<u8>()?;
    Ok(())
}
```

```salida
abc: demasiado corta
rustaceo: le falta un número
ñandú12: demasiado corta
Error: ParseIntError { kind: InvalidDigit }
```

## A fondo

**`source` encadena las causas.** El método `source` del trait `Error` devuelve
la causa de un error, o `None` por default. `#[from]` de `thiserror` lo
implementa para su variante, y el «Caused by» de `anyhow` sale de recorrer
`source` hasta el final. Si el mensaje ya incluye la causa, como `{0}` en
`ErrorPedido`, la cadena la imprime dos veces. El texto de la causa va en el
mensaje o en `source`, no en los dos.

**`#[from]` es un `impl From` generado.** Por eso tiene las restricciones de un
`impl` escrito a mano. Dos variantes con `#[from] ParseIntError` dan
*E0119: conflicting implementations of trait `From<ParseIntError>`*: el `?` no
tendría cómo elegir. Si dos causas comparten el tipo de error, al menos una se
construye con `map_err`.

**Una librería no devuelve `Box<dyn Error>` ni `anyhow::Error`.** Quien la usa
no puede distinguir la causa con `match`. Solo le queda
`downcast_ref::<ParseIntError>()`, que devuelve un `Option` y obliga a adivinar
los tipos internos de la librería.

**`panic!` sigue siendo para los bugs.** El criterio de [5.2 Result]{.ref} no
cambia: un tipo de error describe fallas esperables, no estados imposibles.
