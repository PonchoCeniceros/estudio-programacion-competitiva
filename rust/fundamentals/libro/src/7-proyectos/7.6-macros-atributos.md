# 7.6 · Macros y atributos

Desde la primera página el libro escribe `println!`, `vec!` y `#[derive(Debug)]`,
y en [7.3 Tests]{.ref} aparecieron `#[cfg(test)]` y `#[test]`. Ninguna se explicó.
Se usaron como fórmulas: funcionan si se copian tal cual. Cuando algo falla, el
error a veces señala una línea que no está en el archivo.

Las cinco son código que escribe código. El compilador las reemplaza por código
normal antes de revisar tipos y préstamos. El capítulo no enseña a escribir macros
complejas: enseña a leerlas, a saber qué generan y a entender sus errores.

## Definiciones y reglas

Macro
:   código que recibe tokens y produce código al compilar ([1.1 Tokens]{.ref}).
    Se invoca con `!`: `println!(...)`, `vec![...]`.

Expansión
:   el paso en que el compilador reemplaza cada macro por el código que genera.

`macro_rules!`
:   la forma de definir una macro *declarativa*: una lista de patrones de
    sintaxis, cada uno con el código que lo sustituye.

Atributo
:   una anotación `#[...]` sobre un elemento: un struct, una función, un
    módulo. Algunos solo informan al compilador; otros son macros.

::: {.reglas titulo="Las tres reglas de las macros"}
1. Una macro se expande antes de la revisión de tipos: recibe sintaxis, no
   valores, y devuelve código.
2. `derive` agrega un `impl` y no modifica el tipo. Exige que cada campo
   implemente el trait.
3. Un atributo anota o reescribe el elemento que lo sigue. Con `#!`, aplica
   al elemento que lo contiene.
:::

## De un vistazo

| Forma | Qué es | Qué produce | Ejemplos |
| :--- | :--- | :--- | :--- |
| `nombre!(...)` | macro invocada | el código que la sustituye | `println!`, `vec!` |
| `#[derive(X)]` | macro de derivación | un `impl X for Tipo` nuevo | `Debug`, `Clone` |
| `#[atributo]` | anotación o macro | una marca, o el elemento reescrito | `#[test]`, `#[allow]` |

Las tres se resuelven al compilar. Ninguna cuesta nada en ejecución que no costara
el código equivalente escrito a mano.

## Las reglas, una por una

### Una macro no es una función

`println!("listo")` recibe un argumento; `println!("{} {} {} {}", a, b, c, d)`
recibe cinco. Una función de Rust tiene un número fijo de parámetros, y llamarla
con otro número da E0061. La macro no tiene firma: tiene patrones, y cada
invocación encaja en alguno.

`vec![0; 5]`, de [5.3 Vec]{.ref}, no sería una llamada válida: `f(0; 5)` ni siquiera se lee como
expresión. La macro recibe los tokens `0`, `;` y `5` sin evaluar, y decide qué
hacer con ellos. Lo mismo pasa con la cadena de formato de `println!`: la macro la
lee al compilar, cuenta los huecos y los compara con los argumentos.

```rust,compile_fail
fn main() {
    let x = 5;
    println!("{} y {}", x);
}
```

```salida
error: 2 positional arguments in format string, but there
       is 1 argument
3 |     println!("{} y {}", x);
  |               ^^   ^^   -
```

El programa no llega a ejecutarse. En un lenguaje donde la función de imprimir
recibe un texto y una lista de valores, ese error aparece en ejecución, o no
aparece. Por eso `println!` tiene que ser macro: ninguna función de Rust acepta
un número variable de argumentos ni revisa un texto al compilar. La tabla resume
la diferencia.

| | Función | Macro |
| :--- | :--- | :--- |
| Argumentos | fijos por la firma | los que acepten sus patrones |
| Recibe | valores ya evaluados | tokens sin evaluar |
| Actúa | en ejecución, al llamarla | al compilar, antes de revisar tipos |

Una macro se invoca con `()`, `[]` o `{}` después del `!`, y los tres son
equivalentes. La costumbre es `vec![...]` para lo que parece un arreglo y `(...)`
para lo demás.

### `macro_rules!`: un `match` sobre sintaxis

Una macro declarativa se lee como un `match` ([2.4 Patrones]{.ref}). Cada rama es
un patrón, `=>` y la expansión. El compilador prueba las ramas en orden y usa la
primera que encaja con los tokens de la invocación. `mi_vec!` es una versión
reducida de `vec!`:

```rust
macro_rules! mi_vec {
    () => {
        Vec::new()
    };
    ($($x:expr),*) => {{
        let mut v = Vec::new();
        $(v.push($x);)*
        v
    }};
}

fn main() {
    let vacio: Vec<i32> = mi_vec![];
    let v = mi_vec![1, 2, 3 + 4];
    println!("{vacio:?} {v:?}");   // [] [1, 2, 7]
}
```

Tres piezas bastan para leerla:

- `$x:expr` captura una expresión completa, como `3 + 4`, y la nombra `$x`.
  Otras capturas son `ident` (un nombre) y `ty` (un tipo).
- `$( ... ),*` es una repetición: lo de adentro, cero o más veces, separado por
  comas. En la expansión, `$( ... )*` repite el código una vez por cada `$x`
  capturado.
- Las llaves exteriores delimitan la expansión; las interiores forman un bloque,
  una sola expresión que vale `v` ([1.4 Todo es una expresión]{.ref}).

Si ninguna rama encaja, el error llega antes que cualquier revisión de tipos.
`mi_vec![1; 3]` da *no rules expected `;`*, con la nota *while trying to match
`,`*: la macro solo conoce la coma.

### [Regla 1:]{.prefijo} la expansión ocurre antes de revisar

El compilador corta el texto en tokens, expande las macros y solo entonces revisa
tipos y préstamos. Un error de tipos en código generado se reporta sobre el código
expandido.

::: {.figura src="figuras/7.6-etapas.html"}
:::

Con `mi_vec![1, "dos"]`, la expansión es correcta como sintaxis: dos llamadas a
`push`. El error aparece en la revisión de tipos, y `rustc` lo reporta así:

```salida
error[E0308]: mismatched types
 4 |         $(v.push($x);)*
   |           - ---- arguments to this method are incorrect
   |           |
   |           ... which causes `v` to have type
   |               `Vec<{integer}>`
...
10 |     let v = mi_vec![1, "dos"];
   |                     -  ^^^^^ expected integer,
   |                     |        found `&str`
   |                     |
   |                     this argument has type `{integer}`...
```

La línea 4 es parte de la definición de la macro, no de `main`. El compilador la
muestra porque ahí está el `push` que recibió el texto. Con una macro de un crate
ajeno, esa línea está en el código de otra persona.

### [Regla 2:]{.prefijo} `derive` agrega, no modifica

[4.1 Traits]{.ref} presentó `derive` como el atributo que escribe el `impl`. Es una
macro, y su salida se puede ver. El compilador nocturno (*nightly*) imprime el
programa expandido con `rustc +nightly -Zunpretty=expanded`. Para
`#[derive(Clone, PartialEq)]` sobre `struct Punto { x: i32, y: i32 }`, la
expansión deja el struct igual y agrega dos bloques debajo. El de `Clone`,
recortado:

```salida
#[automatically_derived]
impl ::core::clone::Clone for Punto {
    #[inline]
    fn clone(&self) -> Self {
        Punto {
            x: ::core::clone::Clone::clone(&self.x),
            y: ::core::clone::Clone::clone(&self.y),
        }
    }
}
```

El de `PartialEq` compara `self.x == other.x && self.y == other.y`. Con nombres
cortos, el `Clone` es lo mismo que se escribiría a mano:

```rust
struct Punto { x: i32, y: i32 }

impl Clone for Punto {
    fn clone(&self) -> Self {
        Punto { x: self.x.clone(), y: self.y.clone() }
    }
}

fn main() {
    let a = Punto { x: 1, y: 2 };
    let b = a.clone();
    println!("{} {}", b.x, b.y);   // 1 2
}
```

Las rutas completas (`::core::clone::Clone`) evitan depender de lo que el archivo
haya importado. El código generado trabaja campo por campo: `clone` llama a `clone` de cada campo,
`eq` compara cada par. De ahí sale la condición de la regla. Si un campo no
implementa el trait, el `impl` generado no compila:

```rust,compile_fail
struct Celda(i32);

#[derive(Debug)]
struct Tablero {
    celda: Celda,
}

fn main() {
    println!("{:?}", Tablero { celda: Celda(0) });
}
```

```salida
error[E0277]: `Celda` doesn't implement `Debug`
3 | #[derive(Debug)]
  |          ----- in this derive macro expansion
4 | struct Tablero {
5 |     celda: Celda,
  |     ^^^^^^^^^^^^ the trait `Debug` is not implemented
  |                  for `Celda`
help: consider annotating `Celda` with `#[derive(Debug)]`
```

El error no está en `Tablero` sino en `Celda`, y la ayuda lo dice. *in this derive
macro expansion* marca que el código que falla salió de la macro. Con `Clone` el
mensaje es *the trait bound `Celda: Clone` is not satisfied*, con el mismo E0277.

### [Regla 3:]{.prefijo} atributos que anotan y atributos que reescriben

Un atributo se escribe en la línea anterior al elemento. Hay dos clases. Los que
anotan dejan el elemento como está y le dan una instrucción al compilador. Los que
son macros reciben el elemento como tokens y devuelven otro código.

| Atributo | Clase y efecto |
| :--- | :--- |
| `#[derive(...)]` | macro: agrega implementaciones |
| `#[test]` | macro: registra la función como test |
| `#[tokio::main]` | macro de un crate: envuelve `main` en un runtime |
| `#[cfg(test)]` | anota: el elemento existe solo en los tests |
| `#[allow(...)]`, `#[deny(...)]` | anota: apaga un aviso o lo vuelve error |
| `#[inline]` | anota: sugiere copiar el cuerpo en cada llamada |
| `#[must_use]` | anota: avisa si se descarta el valor |

`#[tokio::main]` es de un crate externo y se explica en
[9.3 El runtime]{.ref}. `#[must_use]` marca una función cuyo resultado no debe
ignorarse. Si `fn doble(x: i32) -> i32` lo lleva, la línea `doble(4);` da el
aviso *unused return value of `doble` that must be used*. `Result` lleva ese atributo en la biblioteca estándar, y por
eso descartar un `Result` da un aviso parecido.

Con `#!` el atributo aplica al elemento que lo contiene, no al siguiente. Al inicio
de `main.rs` o `lib.rs`, ese elemento es el crate entero
([7.2 Crates y Cargo]{.ref}); en otro archivo, su módulo. `#![deny(unused_variables)]` en la primera línea
vuelve error toda variable sin usar del programa:

```rust,compile_fail
#![deny(unused_variables)]

fn main() {
    let x = 5;
}
```

```salida
error: unused variable: `x`
4 |     let x = 5;
  |         ^ help: if this is intentional, prefix it with an
  |                 underscore: `_x`
```

`#[cfg(test)]` anota, pero su efecto es quitar código: fuera de los tests, el elemento
se elimina antes de revisar tipos. El módulo de tests de [7.3 Tests]{.ref} cabe en
un archivo con `main`:

```rust
fn doble(x: i32) -> i32 {
    x * 2
}

fn main() {
    println!("{}", doble(4));   // 8
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn duplica() {
        assert_eq!(doble(4), 8);
    }
}
```

Compilado normal, el programa expandido no tiene módulo `tests`: solo `doble` y
`main`. Compilado como test, `#[test]` reescribe `duplica`. La deja como está y
agrega a su lado un registro con el nombre, el archivo y la línea, que es lo que
el ejecutor de tests recorre.

### Cómo ver lo que generan

`cargo expand` es un subcomando externo que imprime un proyecto con todas sus
macros expandidas. Se instala con `cargo install cargo-expand`, y por debajo pide
al compilador la misma salida que `-Zunpretty=expanded`. Es la forma directa de entender un error que señala código ajeno, o de
ver qué hace `#[tokio::main]` con `main`.

Aplicado a `println!("{} elementos", v.len())`, el resultado es:

```salida
{ ::std::io::_print(format_args!("{0} elementos\n",
        v.len())); };
```

`println!` se volvió una llamada a una función interna, con el salto de línea
agregado al formato. `format_args!` es otra macro, que el compilador resuelve él
mismo y que no se expande más.

Sin instalar nada, la documentación sirve para la regla 2. `cargo doc --open`
genera la página de cada tipo del proyecto, y su sección *Trait Implementations*
lista los `impl`, derivados o escritos a mano. La documentación de la biblioteca
estándar tiene la misma sección: la de `String` muestra `Clone`, `Debug`,
`Display`, `PartialEq` y el resto.

## Aplicación

El paquete `katas` del autor, donde viven sus soluciones de LeetCode en Rust,
define una macro en `src/macros.rs`:

```rust,ignore
// src/macros.rs
#[macro_export]
macro_rules! s {
    ($x:expr) => {
        String::from($x)
    };
}
```

Línea por línea:

- `#[macro_export]` publica la macro en la raíz del crate. Aunque `macros.rs` sea
  un módulo privado (`mod macros;` en `lib.rs`), la macro se importa como
  `katas::s` ([7.1 Módulos]{.ref}).
- `macro_rules! s` la nombra `s`; se invoca `s!(...)`.
- Tiene una rama, con un patrón: una expresión, `$x`.
- La expansión es `String::from($x)`.

Los binarios del paquete la importan con `use katas::s;` y la usan para armar
los `Vec<String>` de entrada. En `src/bin/14_longest_common_prefix.rs`:
`vec![s!("flower"), s!("flow"), s!("flight")]`.

`s!("flow")` se expande a `String::from("flow")`. La macro ahorra escritura y nada
más: una función `fn s(x: &str) -> String` daría lo mismo. Una macro se justifica
cuando hace algo que una función no puede, como aceptar un número variable de
argumentos. Es el caso de un constructor de `HashMap` con dos ramas, que conecta
con [5.4 HashMap y HashSet]{.ref}:

```rust
use std::collections::HashMap;

macro_rules! mapa {
    () => {
        HashMap::new()
    };
    ($($k:expr => $v:expr),*) => {{
        let mut m = HashMap::new();
        $(m.insert($k, $v);)*
        m
    }};
}

fn main() {
    let vacio: HashMap<&str, u32> = mapa!();
    let edades = mapa! {
        "Ana" => 30,
        "Luis" => 25
    };
    println!("{} {}", vacio.len(), edades["Ana"]);
    println!("{:?}", edades.get("Luis"));
}
```

```salida
0 30
Some(25)
```

El `=>` dentro del patrón no tiene significado propio: es un token que la
invocación debe repetir, igual que la coma. La macro lo exige entre cada clave y
su valor. La rama vacía necesita la anotación de tipo en `vacio`, como
`HashMap::new()` escrito a mano.

## A fondo

**Las macros son higiénicas.** Una variable creada dentro de la expansión no choca
con las del código que invoca. Con `let v = 10;`, `mi_vec![v, v + 1]` vale
`[10, 11]`, aunque la expansión contiene `v.push(v)`. El compilador recuerda de
dónde salió cada nombre: la `v` del `let mut` es de la macro y la del argumento
es de `main`.

**La coma final no se acepta sola.** `mapa!` con una coma después del último par
falla con *unexpected end of macro invocation*: la repetición espera otra clave
después de cada coma. Las macros de la biblioteca estándar agregan `$(,)?` al
final del patrón, una coma opcional, y por eso `vec![1, 2,]` compila.

**Hay macros que viven en otro crate.** `macro_rules!` transforma tokens con
patrones. Las macros *procedurales* son funciones de Rust que reciben tokens y
devuelven tokens, compiladas en un crate aparte antes que el programa que las
usa. Son de tres tipos: de derivación (`#[derive(Serialize)]`), de atributo
(`#[tokio::main]`) y con forma de función (`sqlx::query!(...)`). `derive` no es
magia reservada a la biblioteca estándar: el crate `serde` define el suyo, que
genera `impl Serialize for Tipo`. Si se olvida el `derive`, el error dice que el
tipo no implementa `Serialize`, el mismo E0277 de la regla 2.

**`todo!()` y `unimplemented!()` son macros.** Expanden a un `panic!` con mensaje
fijo, que encaja con cualquier tipo de retorno: una función a medio escribir
compila.
