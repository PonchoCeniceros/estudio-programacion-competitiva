# 7.3 · Tests

El compilador garantiza que un programa no rompe la memoria ni los tipos. No
sabe qué debe hacer el programa. Una función que convierte 100 °C en 87 °F
compila igual que una que da 212: los tipos encajan y ningún préstamo sobrevive a
su dueño. La fórmula equivocada pasa todas las revisiones.

Comprobarla a mano es correr el programa y mirar lo que imprime, después de cada
cambio. Un `assert!` dentro de `main` lo automatiza a medias: se detiene en la
primera falla y viaja en el ejecutable final. Un test es una función que hace esa
comprobación y que Cargo sabe encontrar, correr y reportar.

## Definiciones y reglas

Test
:   función sin parámetros, marcada con `#[test]`, que comprueba un
    comportamiento del código.

Aserción
:   macro que hace panic si una condición no se cumple: `assert!`,
    `assert_eq!` y `assert_ne!`.

Test unitario
:   test que vive en el mismo archivo que el código que prueba, dentro de un
    módulo `tests`.

Test de integración
:   test en un archivo de la carpeta `tests/`, que usa la librería desde fuera,
    como lo haría otro crate.

Doc-test
:   ejemplo de código dentro de un comentario de documentación `///`, que
    `cargo test` compila y ejecuta.

::: {.reglas titulo="Las tres reglas de los tests"}
1. Un test pasa si termina y falla si hace panic.
2. Los tests unitarios viven en un módulo hijo del que prueban: ven lo privado.
3. Los tests de integración y los doc-tests son crates aparte: solo ven lo
   público.
:::

## De un vistazo

| Se escribe | El test falla si |
| :--- | :--- |
| `assert!(c)` | `c` es `false` |
| `assert_eq!(a, b)` | `a != b`; imprime los dos valores |
| `assert_ne!(a, b)` | `a == b`; imprime los dos valores |
| `#[should_panic(expected = "t")]` | no hace panic, o el mensaje no contiene `t` |
| `fn t() -> Result<(), E>` | devuelve `Err` |
| `#[ignore]` | no corre, salvo con `cargo test -- --ignored` |

Criterio: `assert_eq!(a, b)` antes que `assert!(a == b)`. Los dos fallan en el
mismo caso, pero solo el primero dice qué valores encontró.

## Las reglas, una por una

### [Regla 1:]{.prefijo} un test falla cuando hace panic

Los tests de un archivo se agrupan en un módulo `tests`, al final del mismo
archivo. Tres líneas lo arman. `#[cfg(test)]` compila el módulo solo cuando se
corren los tests; `#[test]` registra una función como test. Los dos son
atributos ([7.6 Macros y atributos]{.ref}). `use super::*` trae al módulo los
nombres del archivo, que es su módulo padre ([7.1 Módulos]{.ref}).

```rust
fn celsius_a_fahrenheit(c: i32) -> i32 {
    c * 9 / 5 + 32
}

fn main() {
    println!("{}", celsius_a_fahrenheit(100));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn congelacion() {
        assert_eq!(celsius_a_fahrenheit(0), 32);
    }

    #[test]
    fn ebullicion() {
        assert_eq!(celsius_a_fahrenheit(100), 212);
    }
}
```

`cargo run` ignora el módulo. `cargo test` compila el proyecto con los tests,
corre cada función marcada y reporta:

```salida
$ cargo test
     Running unittests src/main.rs

running 2 tests
test tests::congelacion ... ok
test tests::ebullicion ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured;
             0 filtered out; finished in 0.00s
```

Cada test aparece con su ruta, módulo y función. Si la fórmula se escribe al
revés, `c * 5 / 9 + 32`, el primer test sigue pasando: 0 °C da 32 con las dos
fórmulas. El segundo falla, y la salida dice dónde y con qué valores:

```salida
running 2 tests
test tests::congelacion ... ok
test tests::ebullicion ... FAILED

failures:

---- tests::ebullicion stdout ----

thread 'tests::ebullicion' panicked at src/main.rs:20:9:
assertion `left == right` failed
  left: 87
 right: 212

failures:
    tests::ebullicion

test result: FAILED. 1 passed; 1 failed; 0 ignored;
             0 measured; 0 filtered out; finished in 0.00s

error: test failed, to rerun pass `--bin temperatura`
```

`left` es el primer argumento de `assert_eq!` y `right` el segundo. Rust no los
llama «obtenido» y «esperado»: el orden es una convención de quien escribe. En
este libro va primero lo que se calcula y después lo que se espera.

`assert_eq!` hace panic, y el panic es lo que marca el test como fallido. Por eso
cualquier panic cuenta: un `unwrap` sobre `None`, o el índice fuera de rango de
[2.1 Tuplas y arreglos]{.ref}, que reporta
`index out of bounds: the len is 0 but the index is 0`. Un test que falla no
detiene a los demás. Al final, `cargo test` sale con un código distinto de cero,
y un script lo puede detectar.

### Las aserciones

`assert!` recibe una condición. `assert_ne!` es el contrario de `assert_eq!`:
falla si los dos valores son iguales. Las tres aceptan, después de sus
argumentos, un mensaje con el formato de `println!`:

```rust
fn celsius_a_fahrenheit(c: i32) -> i32 { c * 9 / 5 + 32 }
fn main() { println!("{}", celsius_a_fahrenheit(-40)); }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn escalas_no_coinciden() {
        let f = celsius_a_fahrenheit(-40);
        assert_ne!(f, -40, "coinciden en {f}");
    }
}
```

El test falla, porque −40 es el punto donde las dos escalas coinciden. El test estaba mal, no la función, y la salida
basta para notarlo:

```salida
---- tests::escalas_no_coinciden stdout ----

thread 'tests::escalas_no_coinciden' panicked at
src/main.rs:11:9:
assertion `left != right` failed: coinciden en -40
  left: -40
 right: -40
```

Sin mensaje, `assert!` imprime el texto de la condición:
`assertion failed: celsius_a_fahrenheit(37) > 100`. Con mensaje, imprime solo el
mensaje, así que conviene que incluya el valor encontrado.

Para imprimir los dos valores, `assert_eq!` y `assert_ne!` piden que el tipo
implemente `Debug`, además de `PartialEq` para compararlos
([4.4 Traits de la stdlib]{.ref}). Sin `Debug`, el error aparece en la línea de
la aserción:

```rust,compile_fail
#[derive(PartialEq)]
struct Punto { x: i32, y: i32 }

fn main() {
    let a = Punto { x: 1, y: 2 };
    assert_eq!(a, Punto { x: 1, y: 2 });
}
```

```salida
error[E0277]: `Punto` doesn't implement `Debug`
9 |     assert_eq!(a, Punto { x: 1, y: 2 });
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ the trait `Debug`
  |                          is not implemented for `Punto`
  = note: add `#[derive(Debug)]` to `Punto` or manually
          `impl Debug for Punto`
```

Sin `PartialEq`, el error es E0369: *binary operation `==` cannot be applied to
type `Punto`*. Lo usual es derivar los dos.

### Un test que espera un panic

Algunas funciones deben hacer panic ante ciertos datos. El atributo
`#[should_panic]` invierte el criterio: el test pasa si hace panic. Con
`expected`, además, el mensaje del panic debe contener ese texto. Un ejercicio
del curso *Aprende Rust* lo usa con una puntuación que solo admite valores de 1
a 10:

```rust
struct Puntuacion(u8);

impl Puntuacion {
    fn new(valor: u8) -> Puntuacion {
        if !(1..=10).contains(&valor) {
            panic!("debe estar entre 1 y 10; llegó {valor}");
        }
        Puntuacion(valor)
    }
}

fn main() { println!("{}", Puntuacion::new(8).0); }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "entre 1 y 10")]
    fn rechaza_cero() {
        Puntuacion::new(0);
    }
}
```

El reporte marca el atributo: `test tests::rechaza_cero - should panic ... ok`.
Sin `expected`, cualquier panic daría el test por bueno, incluso uno que no
tiene que ver con el rango. Si el mensaje no contiene el texto, el test falla y
muestra los dos. Con `expected = "entre 0 y 10"` y `Puntuacion::new(11)`:

```salida
note: panic did not contain expected string
      panic message: "debe estar entre 1 y 10; llegó 11"
 expected substring: "entre 0 y 10"
```

Si la función no hace panic, por ejemplo con `Puntuacion::new(10)`, la nota es
*test did not panic as expected*.

### Tests que devuelven `Result`

Un test puede devolver `Result<(), E>`. Pasa con `Ok(())` y falla con `Err`.
Así el cuerpo usa `?` en lugar de `unwrap`
([5.2 Result]{.ref}):

```rust
use std::num::ParseIntError;

fn sumar(a: &str, b: &str) -> Result<i32, ParseIntError> {
    Ok(a.parse::<i32>()? + b.parse::<i32>()?)
}

fn main() { println!("{:?}", sumar("2", "40")); }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn suma_con_espacio() -> Result<(), ParseIntError> {
        assert_eq!(sumar("2", " 40")?, 42);
        Ok(())
    }
}
```

`parse` no acepta espacios, así que el `?` devuelve el `Err` y el test falla.
La salida imprime el error con el formato de `{:?}`, igual que un `main` que
devuelve `Err`: `Error: ParseIntError { kind: InvalidDigit }`. No dice en qué
línea ocurrió. Un `unwrap` sí la diría, porque hace
panic en el lugar. Un test que devuelve `Result` tampoco admite
`#[should_panic]`: el compilador responde
*functions using `#[should_panic]` must return `()`*.

### Ignorar y filtrar

Un test lento se marca con `#[ignore]` debajo de `#[test]`, opcionalmente con el
motivo: `#[ignore = "un millón de casos"]`. `cargo test` lo lista como
`ignored, un millón de casos`, pero no lo corre.

Mientras un test pasa, `cargo test` captura lo que imprime con `println!` y lo
descarta; si falla, lo muestra en su sección `stdout`. Lo mismo vale para
`dbg!` ([4.4 Traits de la stdlib]{.ref}). Lo ignorado y lo
capturado se piden con opciones:

| Comando | Qué corre |
| :--- | :--- |
| `cargo test` | todos, menos los ignorados |
| `cargo test congelacion` | los tests cuya ruta contiene `congelacion` |
| `cargo test -- --ignored` | solo los ignorados |
| `cargo test -- --include-ignored` | todos, con los ignorados |
| `cargo test -- --nocapture` | todos, y muestra lo que imprimen |
| `cargo test -- --test-threads=1` | todos, uno por uno |

El `--` separa las opciones de Cargo de las del ejecutable de tests. El filtro
por nombre va antes y se combina con las demás. Sobre el primer ejemplo del
capítulo:

```salida
$ cargo test congelacion

running 1 test
test tests::congelacion ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured;
             1 filtered out; finished in 0.00s
```

### [Regla 2:]{.prefijo} los tests unitarios ven lo privado

Ninguna función de este capítulo lleva `pub`, y aun así los tests las llaman.
`celsius_a_fahrenheit` es privada del módulo raíz del crate, y `tests` es un
módulo hijo de ese módulo. Un módulo ve los elementos privados de sus ancestros
([7.1 Módulos]{.ref}). Así, un test unitario prueba también las funciones
auxiliares que nadie fuera del crate puede llamar.

### [Regla 3:]{.prefijo} integración y doc-tests ven solo lo público

Un test de integración prueba el crate como lo usaría otro programa: desde fuera
y solo por su API pública. Cada archivo de la carpeta `tests/` se compila como un
crate aparte que depende del proyecto. Para poder importar algo, el proyecto
necesita una librería, un `src/lib.rs` ([7.2 Crates y Cargo]{.ref}). El
proyecto del ejemplo se llama `calendario` y tiene dos archivos: `src/lib.rs` y
`tests/fechas.rs`.

La librería expone `es_bisiesto` y guarda `divisible` como auxiliar privada. El
comentario `///` encima de `es_bisiesto` documenta la función, y su bloque de
código es un doc-test:

```rust,ignore
// src/lib.rs
/// Dice si un año es bisiesto en el calendario gregoriano.
///
/// ```
/// assert!(calendario::es_bisiesto(2024));
/// ```
pub fn es_bisiesto(anio: u32) -> bool {
    divisible(anio, 4) && !divisible(anio, 100)
        || divisible(anio, 400)
}

fn divisible(n: u32, d: u32) -> bool {
    n % d == 0
}
```

El test de integración importa la librería por el nombre del crate, como
cualquier dependencia. No necesita `#[cfg(test)]`: la carpeta `tests/` solo se
compila con `cargo test`.

```rust,ignore
// tests/fechas.rs
use calendario::es_bisiesto;

#[test]
fn febrero_de_2024_tiene_29_dias() {
    assert!(es_bisiesto(2024));
}
```

Desde ese archivo, `calendario::divisible(8, 4)` no compila:

```salida
error[E0603]: function `divisible` is private
  --> tests/fechas.rs:11:25
   |
11 |     assert!(calendario::divisible(8, 4));
   |                         ^^^^^^^^^ private function
```

Sin `lib.rs`, el `use` falla antes, con E0432: *unresolved import
`calendario`*. Un proyecto que solo tiene `src/main.rs` admite tests unitarios,
pero no de integración ni doc-tests.

`cargo test` corre los tres niveles en orden; `--lib`, `--test fechas` y
`--doc` corren uno solo. La librería no tiene módulo `tests`, así que el primero
queda vacío:

```salida
     Running unittests src/lib.rs
running 0 tests

     Running tests/fechas.rs
test febrero_de_2024_tiene_29_dias ... ok

   Doc-tests calendario
test src/lib.rs - es_bisiesto (line 4) ... ok
```

El doc-test se compila como un programa aparte que depende del crate: por eso el
ejemplo nombra la función con la ruta completa, `calendario::es_bisiesto`. Si el
ejemplo deja de ser cierto, `cargo test` falla y lo señala por archivo, función
y línea.

| | Unitario | Integración | Doc-test |
| :--- | :--- | :--- | :--- |
| Dónde | `mod tests` | `tests/*.rs` | `///` |
| Qué ve | privado y público | solo público | solo público |
| Prueba | una función aislada | el crate desde fuera | que el ejemplo siga siendo cierto |

Los unitarios son los más numerosos y los más baratos: uno por caso límite. Los
de integración, menos y más amplios. Los doc-tests, uno o dos por función
pública.

## Aplicación

Un ejercicio del curso *Aprende Rust*: un año es bisiesto si es divisible entre
4, salvo los divisibles entre 100, que solo lo son si además son divisibles entre
400. El ejercicio comprobaba la regla con cuatro `assert!` en `main`. Como tests,
cada caso límite lleva su función, y el nombre dice qué regla prueba:
divisible entre 4, entre 100 y entre 400. La primera
versión olvida las excepciones:

```rust
fn es_bisiesto(anio: u32) -> bool {
    anio % 4 == 0
}

fn main() { println!("{}", es_bisiesto(1900)); }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn divisible_entre_4_es_bisiesto() {
        assert!(es_bisiesto(2024));
    }

    #[test]
    fn divisible_entre_100_no_es_bisiesto() {
        assert!(!es_bisiesto(1900), "1900 no es bisiesto");
    }

    #[test]
    fn divisible_entre_400_es_bisiesto() {
        assert!(es_bisiesto(2000));
    }
}
```

```salida
test tests::divisible_entre_400_es_bisiesto ... ok
test tests::divisible_entre_4_es_bisiesto ... ok
test tests::divisible_entre_100_no_es_bisiesto ... FAILED

---- tests::divisible_entre_100_no_es_bisiesto stdout ----

thread 'tests::divisible_entre_100_no_es_bisiesto' panicked
at src/main.rs:18:9:
1900 no es bisiesto
```

El nombre del test que falla dice qué regla falta, y los demás corren igual. La versión corregida suma las dos excepciones,
`(anio % 4 == 0 && anio % 100 != 0) || anio % 400 == 0`, y los tres tests
pasan. El caso de 2000 cubre la excepción de la excepción. Sin él, la versión
`anio % 4 == 0 && anio % 100 != 0` pasaría los otros dos tests y seguiría mal.

## A fondo

**`cargo test` compila un ejecutable aparte.** Con los tests activados, el
compilador define `cfg(test)`, incluye los módulos marcados y genera su propio
`main`, que corre los tests y escribe el reporte. El `main` del programa no se
llama. En la compilación normal, `#[cfg(test)]` deja fuera el módulo entero: los
tests no llegan al ejecutable final. Con `rustc` directo, la opción `--test` hace
lo mismo que `cargo test`.

**Los tests corren en paralelo.** Cada test corre en su propio hilo, y el hilo
lleva el nombre del test: de ahí el `thread 'tests::ebullicion'` de la salida.
Un panic termina ese hilo y no los demás. Dos tests que escriben en el mismo
archivo pueden pisarse; `-- --test-threads=1` los corre uno por uno. Los hilos
se explican en [8.1 Hilos]{.ref}.
